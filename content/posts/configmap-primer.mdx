한 웹 애플리케이션이 화면 색상을 환경 변수 `APP_COLOR`에서 읽는다고 해봅시다. 도커에서는 컨테이너를 띄울 때 `-e` 옵션으로 이 값을 넘깁니다.

```bash
docker run -e APP_COLOR=pink simple-webapp-color
```

쿠버네티스에서 같은 이미지를 `Pod`로 띄울 때는 매니페스트 파일의 `env` 속성에 같은 값을 적습니다.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: simple-webapp-color
spec:
  containers:
    - name: simple-webapp-color
      image: simple-webapp-color
      ports:
        - containerPort: 8080
      env:
        - name: APP_COLOR
          value: pink
```

`env`의 각 항목은 `name`과 `value` 두 필드를 가집니다. `name`은 환경 변수의 이름, `value`는 그 값입니다. 이렇게 이름과 값을 매니페스트 안에 그대로 적는 방식을 평문 Key-Value 방식이라고 부릅니다.

이 글은 평문 방식의 한계에서 출발해, 설정을 `Pod` 밖으로 빼내는 `ConfigMap`이 무엇인지, `ConfigMap`을 어떻게 만들고, 만든 `ConfigMap`을 `Pod`에 어떤 방식으로 주입하는지를 한 자리에 정리합니다.

## 평문 Key-Value 방식의 한계

`Pod` 하나라면 매니페스트 안에 `env`를 직접 적는 것으로 충분합니다. 문제는 `Pod` 정의 파일이 늘어날 때입니다.

`APP_COLOR`, `APP_MODE` 같은 설정을 여러 애플리케이션이 공유한다고 해봅시다. `Pod` 정의 파일이 스무 개라면 같은 설정 값이 스무 개의 파일에 흩어져 들어갑니다. 운영 환경의 색상을 `pink`에서 `blue`로 바꾸려면 스무 개의 파일을 모두 찾아 열고, 같은 자리를 똑같이 고쳐야 합니다. 한 파일이라도 빠뜨리면 그 `Pod`만 다른 색을 띄웁니다.

설정 값이 `Pod` 정의 파일 안에 박혀 있다는 점이 원인입니다. 설정과 `Pod` 정의가 한 덩어리로 묶여 있으니, 설정을 한 번 바꾸려면 `Pod` 정의를 전부 건드려야 합니다.

해결은 설정을 `Pod` 정의 파일 밖으로 빼내는 것입니다. 설정 값을 한곳에 모아 두고, 각 `Pod` 정의는 값을 직접 갖는 대신 그 <E>한곳</E>을 가리키게 합니다. 이 <E>한곳</E>이 `ConfigMap`입니다.

## ConfigMap

`ConfigMap`은 쿠버네티스에서 구성 데이터를 키-값 쌍 형태로 담아 두는 오브젝트입니다. 다음처럼 설정 항목을 모아 둔 표 하나라고 보면 됩니다.

```text
APP_COLOR: blue
APP_MODE:  prod
```

`ConfigMap`은 `Pod`와 분리된 별개의 오브젝트입니다. 한 번 만들어 두면 여러 `Pod`이 같은 `ConfigMap`을 가리킬 수 있습니다. `Pod`이 생성될 때 쿠버네티스는 이 `ConfigMap`의 키-값을 컨테이너 안 애플리케이션이 읽을 수 있는 형태로 주입합니다.

평문 방식과 `ConfigMap` 방식의 차이는 `env` 항목 한 줄에서 드러납니다. 평문 방식은 값을 직접 적고, `ConfigMap` 방식은 값 대신 그 값이 어디 있는지, 즉 출처를 적습니다.

```yaml
# 평문 Key-Value — 값을 직접 적는다
env:
  - name: APP_COLOR
    value: blue
```

```yaml
# ConfigMap 참조 — 값의 출처를 적는다
env:
  - name: APP_COLOR
    valueFrom:
      configMapKeyRef:
        name: app-config
        key: APP_COLOR
```

`ConfigMap`을 쓰는 작업은 두 단계로 나뉩니다. 먼저 `ConfigMap`을 만들고, 그다음 다른 쿠버네티스 오브젝트와 마찬가지로 그것을 `Pod`에 주입합니다.

## ConfigMap 만들기

`ConfigMap`을 만드는 방식은 두 가지입니다. 명령으로 바로 만드는 명령형 방식과, 정의 파일을 작성해 적용하는 선언형 방식입니다.

### 명령형 방식

명령형 방식에서는 키와 값을 명령줄에 직접 적어 넘깁니다. `--from-literal` 옵션이 키-값 쌍 하나를 받습니다.

```bash
kubectl create configmap app-config \
  --from-literal=APP_COLOR=blue \
  --from-literal=APP_MODE=prod
```

이 방식은 항목이 두세 개일 때는 편하지만, 항목이 열 개를 넘어가면 `--from-literal`을 그만큼 반복해야 해서 명령이 길어집니다. 그럴 때는 설정을 파일에 적어 두고 그 파일을 통째로 넘기는 `--from-file` 옵션을 씁니다.

```bash
kubectl create configmap app-config \
  --from-file=app_config.properties
```

### 선언형 방식

선언형 방식에서는 `ConfigMap`을 정의 파일로 작성합니다. `kind`가 `ConfigMap`이고, 키-값 쌍은 `data` 아래에 적습니다.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  APP_COLOR: blue
  APP_MODE: prod
```

이 파일을 적용하면 `app-config`라는 이름의 `ConfigMap`이 만들어집니다.

```bash
kubectl apply -f config-map.yaml
```

같은 방식으로 목적에 따라 필요한 만큼 `ConfigMap`을 만들 수 있습니다. 만들어진 `ConfigMap`의 목록은 `kubectl get configmaps`로 보고, 한 `ConfigMap` 안에 어떤 키-값이 들어 있는지는 `kubectl describe configmap app-config`로 확인합니다. `describe`는 `Data` 항목 아래에 키-값을 그대로 나열합니다.

## Pod에 ConfigMap 주입하기

`ConfigMap`을 만들었다면 이제 그것을 `Pod`에 주입할 차례입니다. 주입 방식은 세 가지이며, 셋의 차이는 <E>몇 개의 키를, 어떤 형태로</E> 컨테이너 안에 넣느냐입니다.

<ConfigMapInjectionViz />

아래 예시는 모두 앞에서 만든 `app-config` `ConfigMap`을 주입합니다. `app-config`에는 `APP_COLOR`와 `APP_MODE` 두 키가 들어 있습니다.

### envFrom: 모든 키를 한 번에

`envFrom`은 `ConfigMap`에 든 모든 키-값을 한 번에 환경 변수로 주입합니다. 컨테이너 정의에 `envFrom` 아래 `configMapRef`로 `ConfigMap` 이름만 적으면 됩니다.

```yaml
spec:
  containers:
    - name: simple-webapp-color
      image: simple-webapp-color
      envFrom:
        - configMapRef:
            name: app-config
```

이렇게 하면 컨테이너 안 애플리케이션은 `APP_COLOR`와 `APP_MODE` 두 환경 변수를 모두 갖게 됩니다. 키를 하나씩 나열하지 않고 `ConfigMap`을 통째로 가져오는 방식이라, `ConfigMap`의 키 전체가 그대로 그 애플리케이션의 설정인 경우에 가장 간결합니다.

### 단일 env: 키 하나만 골라서

`envFrom`이 `ConfigMap` 전체를 가져온다면, 단일 `env`는 `ConfigMap`에서 키 하나만 골라 환경 변수 하나로 주입합니다. 앞에서 본 평문 `env`와 같은 자리이되, `value` 대신 `valueFrom`을 써서 값의 출처를 가리킵니다.

```yaml
spec:
  containers:
    - name: simple-webapp-color
      image: simple-webapp-color
      env:
        - name: APP_COLOR
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: APP_COLOR
```

`configMapKeyRef`는 `name`으로 `ConfigMap`을 고르고, `key`로 그 안의 키 하나를 고릅니다. 위 예시는 `app-config`의 `APP_COLOR` 하나만 가져오고 `APP_MODE`는 가져오지 않습니다. 또한 `env`의 `name`은 컨테이너가 보게 될 환경 변수 이름이므로, `ConfigMap`의 키 이름과 다르게 줄 수도 있습니다.

<Callout type="warning" title="핵심 포인트: configMapRef와 configMapKeyRef는 가리키는 단위가 다르다">
이름이 비슷해 헷갈리기 쉽지만, 두 키워드가 가리키는 단위가 다릅니다. `envFrom` 아래의 `configMapRef`는 `ConfigMap` **하나 전체**를 가리키고, `valueFrom` 아래의 `configMapKeyRef`는 `ConfigMap` 안의 **키 하나**를 가리킵니다. 그래서 `configMapKeyRef`에는 `key` 필드가 더 있고 `configMapRef`에는 없습니다. 단수 `Key`가 이름에 들어가는 쪽이 키 하나를 지목하는 쪽이라고 기억하면 구분이 쉽습니다.
</Callout>

### Volume: 파일로 마운트

앞의 두 방식은 `ConfigMap`을 환경 변수로 바꿔 줍니다. 세 번째 방식인 `Volume`은 `ConfigMap`을 파일로 바꿔 컨테이너 안 디렉터리에 올려놓습니다.

`ConfigMap`을 `Volume`으로 쓰려면 두 곳을 적습니다. `spec.volumes`에 `ConfigMap`을 가리키는 볼륨을 정의하고, 컨테이너의 `volumeMounts`에서 그 볼륨을 디렉터리 경로에 연결합니다.

```yaml
spec:
  containers:
    - name: simple-webapp-color
      image: simple-webapp-color
      volumeMounts:
        - name: app-config-volume
          mountPath: /etc/config
  volumes:
    - name: app-config-volume
      configMap:
        name: app-config
```

이렇게 하면 `mountPath`로 지정한 `/etc/config` 디렉터리 안에 `ConfigMap`의 키마다 파일이 하나씩 생깁니다. 파일 이름은 키 이름과 같고, 파일 내용은 그 키의 값입니다.

```text
/etc/config/APP_COLOR   → 내용: blue
/etc/config/APP_MODE    → 내용: prod
```

애플리케이션은 환경 변수가 아니라 이 파일들을 읽어 설정을 가져갑니다. 키-값 몇 개가 아니라 `nginx.conf`나 `application.yaml` 같은 설정 파일 전체를 컨테이너에 넣어 줘야 할 때, 그 파일을 `ConfigMap`의 값으로 담아 두고 `Volume`으로 마운트하면 컨테이너 안에 같은 파일이 그대로 나타납니다.

## 세 방식의 선택 기준

세 방식은 같은 `ConfigMap`을 서로 다른 형태로 컨테이너에 들여놓습니다. 정리하면 다음과 같습니다.

| 방식 | 가져오는 단위 | 컨테이너 안 형태 | 적합한 때 |
|---|---|---|---|
| `envFrom` | `ConfigMap` 전체 | 환경 변수 여러 개 | `ConfigMap`의 키 전체가 그 애플리케이션의 설정일 때 |
| 단일 `env` | 키 하나 | 환경 변수 한 개 | 일부 키만 필요하거나, 환경 변수 이름을 바꿔 줄 때 |
| `Volume` | `ConfigMap` 전체 | 디렉터리 안의 파일들 | 설정 파일 자체를 통째로 넣어 줘야 할 때 |

환경 변수 방식과 `Volume` 방식 사이에는 한 가지 더 중요한 차이가 있습니다. `envFrom`이나 `configMapKeyRef`로 주입한 환경 변수는 컨테이너가 시작되는 시점의 값으로 고정됩니다. 이미 떠 있는 `Pod`의 환경 변수는 `ConfigMap`을 나중에 고쳐도 바뀌지 않고, 그 `Pod`을 다시 만들어야 새 값이 들어갑니다. 반면 `Volume`으로 마운트한 파일은 `kubelet`이 주기적으로 `ConfigMap`과 맞춰 주므로, `ConfigMap`을 고치면 떠 있는 `Pod` 안의 파일 내용도 따라 갱신됩니다.

<Callout type="error" title="핵심 통찰: ConfigMap은 설정 값을 줄이지 않고 위치를 옮긴다">
`ConfigMap`을 도입해도 설정 값의 개수 자체가 줄지는 않습니다. `APP_COLOR`와 `APP_MODE`는 여전히 어딘가에 적혀 있어야 합니다. `ConfigMap`이 바꾸는 것은 그 값이 적히는 **위치**입니다. 설정 값이 스무 개의 `Pod` 정의 파일에 흩어져 있던 것을 `ConfigMap` 한 곳으로 모으고, `Pod` 정의는 값을 직접 갖는 대신 그 한 곳을 가리키게 됩니다. 그래서 운영 환경의 색상을 바꾸는 작업이 스무 개 파일 수정에서 `ConfigMap` 한 곳 수정으로 줄어듭니다. 설정과 `Pod` 정의를 분리하는 것, 이것이 `ConfigMap`의 핵심입니다.
</Callout>
