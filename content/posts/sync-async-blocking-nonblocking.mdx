동기와 비동기, 블로킹과 논블로킹. 네 단어가 한 줄에 등장하면 대부분의 개발자가 어느 쪽이 어느 쪽과 반대말인지 헷갈립니다. 실은 이들은 **서로 다른 두 개의 축**이며, 섞어 쓰는 순간부터 혼란이 시작됩니다. 이 글에서는 두 축을 분리해 4가지 I/O 모델이 어떻게 동작하고 언제 어떤 모델을 선택해야 하는지 정리합니다.

<Callout type="info" title="이 글의 학습 목표">
  1. Sync/Async와 Blocking/Non-Blocking이 서로 다른 축임을 이해한다
  2. 두 축이 만드는 4가지 I/O 모델의 내부 동작을 구분할 수 있다
  3. 시스템 요구사항에 맞는 I/O 모델을 선택하는 기준을 얻는다
</Callout>

## 핵심 프레임

많은 글에서 이 개념들을 같은 축의 반대말처럼 섞어서 설명합니다. 그 결과 "Non-Blocking = Async"라는 오해가 널리 퍼져 있고, 이 오해 위에서 Java NIO나 Node.js의 동작을 설명하면 앞뒤가 맞지 않는 지점이 반드시 등장합니다. 혼란의 뿌리는 간단합니다. **이 개념들은 2차원이고, 각 차원이 묻는 질문이 다릅니다.**

**축 1. Sync vs Async** 호출자가 결과를 어떻게 받는가를 묻습니다.

- Sync(동기) 호출자가 결과를 **직접** 확인합니다. "다 됐어?" "아직." "다 됐어?" 또는 "다 될 때까지 여기서 기다릴게" 방식.
- Async(비동기) 피호출자 또는 커널이 **완료 통보**를 보냅니다. 호출자는 다른 일을 하다가 콜백·이벤트·Future로 결과를 받습니다.

**축 2. Blocking vs Non-Blocking** 호출한 순간 제어권이 어디로 가는가를 묻습니다.

- Blocking 작업이 끝나야 함수가 리턴합니다. 그동안 호출 스레드는 sleeping 상태로 멈춥니다.
- Non-Blocking 즉시 리턴합니다. 결과가 없으면 "아직 없음"(`EAGAIN`)이라고 답하고 바로 돌려보냅니다.

두 축은 **직교(orthogonal)**이므로 4가지 조합이 실제로 존재합니다.

<IOModelMatrix />

여기서 주목할 부분은 `select`/`epoll`입니다. 흔히 "epoll은 async"라고 말하지만 엄밀히는 Async Blocking에 가깝습니다. 여러 fd 중 ready인 놈을 알려주는 감시는 async스럽지만, 실제 `read()`로 데이터를 퍼내는 건 여전히 sync + blocking입니다. 이게 왜 이렇게 분류되는지는 이어지는 동작 원리 섹션에서 커널 버퍼 2단계 복사 관점으로 풀어냅니다.

## 왜 필요한가

1만 명이 동시에 주문하는 식당을 상상해봅시다. 전통 방식은 손님 1명당 직원 1명을 붙여 주문부터 서빙까지 전담시키는 구조입니다. 작은 식당은 괜찮지만 1만 명이 몰리면 직원 1만 명이 필요하고, 각 직원이 서 있을 공간(스레드 스택)부터 부족해집니다. 이게 1999년 Dan Kegel이 제기한 **C10K 문제**(1만 동시 연결 문제)입니다.

전통 Java Tomcat이 정확히 이 구조입니다.

```java title="ThreadPerRequestServer.java"
ServerSocket server = new ServerSocket(8080);
while (true) {
    Socket client = server.accept();
    new Thread(() -> handleOrder(client)).start(); // [!code highlight]
}
// 스택 1MB × 1만 커넥션 = 10GB+ 메모리 + 컨텍스트 스위칭 비용
```

`client.getInputStream().read()`가 데이터를 기다리는 동안 OS는 그 스레드를 sleeping 상태로 만듭니다. CPU는 다른 스레드를 돌릴 수 있으니 낭비처럼 보이지 않지만, **스레드 자체의 메모리와 컨텍스트 스위칭 비용이 병목**입니다. "사용자 1명 = 스레드 1개"라는 가정 자체를 깨야 했습니다.

해결책이 **진동벨 시스템**입니다. 직원 1명이 모든 주문의 진동벨을 들고 있다가 울리는 벨만 확인합니다. 이게 Linux의 `epoll`이고, Nginx와 Node.js가 이 방식으로 1만 커넥션을 수백 MB로 처리합니다. Kotlin에서는 Coroutine + Ktor가, Java에서는 NIO `Selector` 또는 Project Loom의 virtual thread가 유사한 역할을 합니다.

<Callout type="warning" title="흔한 오해: epoll은 async가 아니다">
  epoll은 '어느 벨이 울렸는지' 감시만 해주는 도구입니다. 음식을 집는(`read()`)
  행위는 여전히 sync + blocking입니다. 이 구분을 놓치면 Node.js가 왜 single-thread인데
  빠른지, Java NIO의 non-blocking read가 왜 여전히 sync인지를 설명할 수 없게 됩니다.
</Callout>

## 동작 원리

<Callout type="warning" title="이 구조를 이해하는 핵심">
  모든 I/O 모델의 차이는 **"데이터 준비"** 와 **"커널 → 유저 복사"** 라는 두 단계를
  누가 기다리고 누가 복사하느냐에 있습니다. 이 두 단계를 분리해서 보면
  5가지 I/O 모델 전체가 한 장의 매트릭스로 수렴합니다.
</Callout>

<Callout type="error" title="핵심 통찰: 두 축은 직교한다">
  Sync/Async와 Blocking/Non-Blocking은 서로 다른 축이며, 많은 개발자가
  "Non-Blocking = Async"라고 여기지만 Java NIO처럼 **Non-Blocking이면서 Sync인
  조합**이 실제로 존재합니다. 두 축을 분리해서 보면 epoll이 왜 async가 아닌지,
  Node.js가 왜 single-thread인데 C10K를 풀었는지가 한번에 풀립니다.
</Callout>

### I/O의 두 단계

네트워크 `read()`는 겉보기엔 한 번의 호출이지만 내부는 두 단계로 나뉩니다.

1. **데이터 준비 단계** 네트워크 패킷이 도착해 커널 버퍼에 쌓임
2. **복사 단계** 커널 버퍼에서 유저 버퍼로 복사

각 I/O 모델의 차이는 **이 두 단계를 누가 기다리고 누가 복사하느냐**에 있습니다. 음식점 비유로는 (1) 주방에서 요리가 만들어지는 시간, (2) 홀 직원이 주방에서 음식을 받아 손님에게 가져가는 시간으로 나누는 것입니다.

### Sync Blocking

가장 단순한 모델. 손님이 카운터에서 음식이 나올 때까지 서서 기다리는 방식입니다. 두 단계 모두 호출 스레드가 멈춥니다.

```java title="BlockingRead.java"
InputStream in = socket.getInputStream();
int n = in.read(buf);  // 데이터 도착 + 복사 완료까지 block // [!code highlight]
```

OS 관점에서 스레드는 `TASK_INTERRUPTIBLE` sleeping 상태로 들어갑니다. CPU는 다른 스레드를 스케줄링할 수 있지만, 이 스레드 자체는 깨어나기 전까진 아무것도 못 합니다. Tomcat의 전통 servlet 구조, JDBC, 구식 HTTP 클라이언트가 모두 이 방식입니다.

### Non-Blocking Poll

`O_NONBLOCK` 플래그로 fd를 설정한 뒤 `read()`를 계속 호출하는 폴링 방식입니다. 데이터가 없으면 `EAGAIN` 에러로 즉시 리턴하므로 스레드는 block되지 않지만, 그 대가로 CPU를 계속 돌려야 합니다.

```c title="nonblocking_poll.c"
fcntl(fd, F_SETFL, O_NONBLOCK);
while (true) {
    ssize_t n = read(fd, buf, sizeof(buf));
    if (n >= 0) break;                    // 성공
    if (errno != EAGAIN) handle_error();  // 진짜 에러
    do_other_work();                      // EAGAIN → 다른 일 하다 재시도
}
```

폴링은 반응성이 좋지만 CPU 낭비가 심해서 실무에서 단독으로 쓰이는 경우는 드뭅니다. 대부분 I/O Multiplexing의 전처리 단계로만 사용됩니다.

### I/O Multiplexing

진동벨 여러 개를 직원 1명이 감시하다가 울리는 것만 처리하는 방식. `select`, `poll`, `epoll`, `kqueue`가 모두 이 모델에 해당합니다.

```java title="NioSelector.java"
Selector selector = Selector.open();
channel.configureBlocking(false);
channel.register(selector, SelectionKey.OP_READ);

selector.select();                                   // ready 대기 (block) // [!code highlight]
for (SelectionKey k : selector.selectedKeys()) {
    ((SocketChannel) k.channel()).read(buf);         // 여기는 여전히 sync
}
```

`select()`는 여러 fd 감시를 묶어주는 도구일 뿐, 실제 `read()`는 sync + blocking입니다. 차이는 **하나의 스레드가 수만 개의 fd를 감시**할 수 있다는 점이고, 이게 C10K를 푸는 열쇠입니다.

| 호출 | 복잡도 | 최대 fd | 비고 |
|---|---|---|---|
| `select` | $O(n)$ | 1024 (`FD_SETSIZE`) | 초기 POSIX, 매 호출마다 fd set 복사 |
| `poll` | $O(n)$ | 제한 없음 | select와 거의 동일한 성능 |
| `epoll` | $O(1)$ | 제한 없음 | Linux 2.6+, ready list만 리턴 |
| `kqueue` | $O(1)$ | 제한 없음 | BSD/macOS, epoll의 유사체 |

epoll은 커널이 내부에 ready list를 유지하므로 감시 대상 fd가 아무리 많아도 알림 비용이 $O(1)$입니다. Nginx, Redis, Node.js가 모두 epoll(또는 kqueue)을 기반으로 합니다.

### Signal-Driven I/O

커널이 데이터 도착을 `SIGIO` 시그널로 알려주면 핸들러에서 `read()`를 호출하는 방식입니다. 이론적으로는 async에 가장 가까워 보이지만, 시그널 처리가 까다롭습니다. 핸들러 안에서 사용 가능한 함수(async-signal-safe)가 제한적이고, 멀티 스레드 환경에서 시그널 전달 대상 스레드가 불확실합니다. 이런 이유로 실무에서는 거의 쓰이지 않으며, 현대 시스템은 이 자리를 I/O Multiplexing이나 True Async로 대체했습니다.

### True Async

두 단계 모두 커널이 처리하고 완료 시 알림을 주는 방식. Linux의 `io_uring`(5.1+), Windows의 IOCP(I/O Completion Port), POSIX AIO가 여기 속합니다.

```kotlin title="KotlinCoroutineAsync.kt"
suspend fun fetchOrder(id: Long): Order {
    val resp = httpClient.get("/orders/$id")  // suspension point, 스레드 해제 // [!code highlight]
    return resp.body()
}
```

JVM 관점에서 `suspend` 지점에서 스레드는 **해제되어 다른 coroutine으로 전환**되고, 결과가 도착하면 event loop가 continuation을 호출합니다. 커널 레벨에서 `io_uring`은 submission queue에 요청을 넣고 completion queue로 결과를 받는 구조이므로 단계 1과 2 모두 진짜 비동기화됩니다.

## 어디서 쓰는가

선택의 두 축은 **"동시 커넥션 수"** 와 **"요청당 I/O 대기 시간"** 입니다. 동시 커넥션이 적고 로직이 CPU-bound면 blocking이 오히려 빠릅니다(컨텍스트 스위칭 오버헤드 없음, 코드 단순성). 동시 커넥션이 많고 요청당 대기 시간이 길면 multiplexing이나 true async가 필요합니다.

### 음식점 매칭

| 시나리오 | 적합한 모델 | 실제 기술 |
|---|---|---|
| 작은 동네 식당 (손님 10명 동시) | Sync Blocking | Tomcat + Spring MVC |
| 푸드코트 (1만 명, 간단한 서빙) | I/O Multiplexing | Nginx, Redis, Node.js |
| 배달 플랫폼 (긴 호출 체인) | True Async | Kotlin Coroutines, io_uring |

### Java/Kotlin 실무 매핑

사내 관리자 API처럼 동시성이 낮고 로직이 단순하면 전통 Tomcat이 정답입니다.

```kotlin title="AdminApi.kt"
@RestController
class AdminController(private val orderRepository: OrderRepository) {
    @GetMapping("/orders")
    fun list(): List<Order> = orderRepository.findAll()  // blocking 그대로
}
```

고트래픽 공개 API는 coroutine 기반으로 전환합니다.

```kotlin title="ReactiveApi.kt"
@Bean
fun router() = coRouter {
    GET("/orders/{id}") { req ->
        val id = req.pathVariable("id").toLong()
        val order = orderService.find(id)  // suspend, 스레드 해제 // [!code highlight]
        ServerResponse.ok().bodyValueAndAwait(order)
    }
}
```

외부 API 호출 체인에서는 coroutine의 병렬 실행이 빛을 발합니다.

```kotlin title="OrderService.kt"
suspend fun placeOrder(req: OrderRequest): Order = coroutineScope {
    val payment = async { paymentClient.charge(req.amount) }  // [!code highlight]
    val stock   = async { stockClient.reserve(req.items) }    // [!code highlight]
    val result  = Order(payment.await(), stock.await())        // 병렬 대기
    launch { notifyClient.send(result) }                       // fire-and-forget
    result
}
```

### Virtual Thread — 제4의 선택지

JDK 21+의 Virtual Thread(Project Loom)는 blocking 코드 스타일을 그대로 두면서 C10K를 해결합니다. JVM이 내부에서 스레드를 un-mount/remount하는 방식이라, 수백만 개의 virtual thread를 만들어도 메모리가 폭발하지 않습니다.

```java title="VirtualThread.java"
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 1_000_000; i++) {
        executor.submit(() -> {
            var result = httpClient.send(request, BodyHandlers.ofString());  // blocking 코드 // [!code highlight]
            handle(result);
        });
    }
}
```

Reactive 스택의 러닝 커브와 디버깅 난이도 없이 동시성을 얻을 수 있으므로, 많은 JVM 팀이 coroutine이나 reactive 대신 virtual thread로 이동하고 있습니다. 단, JNI 경계나 `synchronized` 블록 안에서는 여전히 OS 스레드를 점유(pin)하므로 라이브러리 호환성을 확인해야 합니다.

## 트레이드오프

도입의 본질은 **"개발자 멘탈 모델의 단순성 vs 하드웨어 활용도"** 입니다. Blocking은 "한 스레드가 한 요청을 처음부터 끝까지 처리"하므로 스택 트레이스가 선형이고 디버깅이 직관적이지만, 스레드 메모리가 확장 한계를 만듭니다. Async로 갈수록 하드웨어 활용도는 올라가지만 "한 스레드가 수천 요청의 조각"을 다루게 되어 디버깅·예외 추적이 분절됩니다.

| 모델 | 스택 메모리 | 동시 커넥션 한도 | 개발 복잡도 |
|---|---|---|---|
| Tomcat Blocking | $\approx$ 1MB × 200 (default) | 200 | 낮음 |
| Netty + NIO | 코어 × 2 event loop | 수만–수십만 | 높음 |
| Kotlin Coroutines | KB 단위 × 수백만 | 수백만 | 중간 |
| Virtual Thread (JDK 21+) | KB 단위 × 수백만 | 수백만 | 낮음 |

### 숨은 복잡도

Async 모델의 진짜 비용은 코드 바깥에 있습니다.

**스택 트레이스 분절** `CompletableFuture.thenCompose()` 체인에서 예외가 터지면 실제 원인 지점이 스택에 드러나지 않습니다. Kotlin coroutines는 `CoroutineStackFrame`으로 일부 개선했지만 여전히 한계가 있습니다.

**ThreadLocal 단절** MDC 로그 컨텍스트, security context가 suspension 경계에서 사라집니다. `ThreadContextElement`, `MDCContext`로 명시적 전파가 필요합니다.

**백프레셔(backpressure)** 생산자가 소비자보다 빠르면 이벤트가 쌓여 OOM으로 이어집니다. Reactor는 `Flux.onBackpressureBuffer()`로 명시 관리해야 하지만, blocking 모델은 자연스러운 흐름 제어로 이 문제가 아예 없습니다.

**디버깅 환경** 브레이크포인트가 suspension point에서 이상하게 동작하고, IDE 스텝 디버깅이 예상 흐름과 다릅니다.

<Callout type="success" title="실무 교훈">
  "일단 async/reactive로 시작"은 안티패턴입니다. Blocking으로 단순하게
  시작해 실제 한계에 부딪혔을 때 NIO나 coroutine을 도입하거나, JDK 21+의
  Virtual Thread로 blocking 코드를 그대로 수평 확장하는 경로가 가장 낮은
  리스크입니다.
</Callout>

## 흔한 오해

이 개념들이 헷갈리는 가장 큰 이유는 **프로그래밍 언어의 추상화가 OS 레벨의 실체를 숨기기** 때문입니다. 코드에 `await`라고 쓰여 있어도 런타임이 실제로 어떤 시스템콜을 호출하는지는 언어마다 다릅니다. 코드 레벨과 OS 레벨을 분리해서 봐야 정리됩니다.

### 1. Non-Blocking이면 곧 Async다?

다른 축입니다. Java NIO의 `SocketChannel.read()`는 `configureBlocking(false)`면 non-blocking이지만 여전히 sync입니다. 호출자가 `read()`를 직접 호출하고 결과를 직접 받으니까요. True async는 커널이 완료를 통보하는 방식입니다.

### 2. epoll은 async다?

epoll은 "어느 fd가 ready되었는지" 감시만 해주는 도구입니다. 실제 데이터 복사(`read()`)는 여전히 sync + blocking입니다. Nginx, Redis, Node.js가 epoll을 쓰지만 내부의 `read()` 지점은 여전히 커널 → 유저 복사를 수행합니다.

### 3. Promise/Future를 쓰면 async다?

런타임이 실제 async I/O(io_uring, IOCP)를 쓰지 않으면 Promise는 **스레드 풀에 blocking 작업을 떠넘기는 것**에 불과합니다. JDBC를 Reactor로 감싸면 논리적으로는 non-blocking처럼 보이지만, 실제로는 별도 스레드에서 blocking `read()`가 일어나고 있습니다. Spring의 `@Async`도 동일합니다.

### 4. Node.js는 single-thread라 async다?

인과 관계가 반대입니다. Node.js는 **async I/O(libuv + epoll)를 쓰니까 single-thread로 C10K를 해결할 수 있는 것**이지, single-thread여서 async가 된 게 아닙니다. 실제로 libuv 내부에는 파일 I/O용 스레드 풀이 따로 돌고 있습니다.

## 마무리

네 가지 I/O 모델을 구분하는 핵심은 "축이 두 개"라는 사실 하나입니다. **Sync/Async는 호출자가 결과를 받는 방식**, **Blocking/Non-Blocking은 호출 순간 제어권의 방향**입니다. 두 축이 독립적이므로 4가지 조합이 실제로 존재하고, 각 조합은 "데이터 준비"와 "커널 → 유저 복사"라는 두 단계를 누가 기다리는지만 다릅니다.

실전에서는 무조건 async를 고르지 마세요. 동시 커넥션이 적고 로직이 단순하면 blocking이 가장 빠르고 싸게 먹힙니다. C10K 규모의 연결을 감당해야 하면 I/O Multiplexing 기반 서버(Nginx, Netty, Ktor)로 가거나, JDK 21+이라면 Virtual Thread로 blocking 코드 스타일 그대로 수평 확장하는 길을 먼저 고려하세요. Reactive·Coroutine은 외부 API 체이닝이나 고도의 I/O-bound 처리량이 필요할 때의 선택지입니다.
