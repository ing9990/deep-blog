이 글은 쿠버네티스 명령어와 YAML 템플릿의 누적 색인입니다. 깊은 동작·트레이드오프는 다루지 않고, 한 줄 명령과 최소 YAML로 빠르게 찾을 수 있는 자리에 둡니다. 새 쿠버네티스 개념 글이 추가될 때마다 해당 리소스 섹션이 한 묶음씩 늘어납니다.

## 사용법

- 좌측 목차에서 리소스명으로 점프합니다.
- 각 리소스 섹션은 (1) 핵심 명령 표, (2) 최소 YAML, (3) 깊은 설명 글 링크의 3 부분으로 구성됩니다.
- 깊은 동작·옵션 전체·트레이드오프는 이 글에서 다루지 않습니다. 각 섹션 끝의 `<RelatedPost>` 링크를 따라가면 개념 글에서 확인할 수 있습니다.
- 명령 표의 `<...>` 표기는 사용자가 채울 자리입니다.

## CKAD 도메인 색인

| 도메인 | 비중 | 다루는 리소스 |
|---|---|---|
| Application Design and Build | 20% | `Pod` |
| Application Deployment | 20% | `ReplicaSet`, `Deployment` |
| Observability and Maintenance | 15% | (추가 예정) |
| Environment, Configuration and Security | 25% | `ConfigMap`, `Namespace`, `ResourceQuota` |
| Services and Networking | 20% | `Service` |

리소스가 여러 도메인에 걸쳐 등장하면 가장 비중이 큰 도메인 한 곳에 표기합니다. 리소스 자체의 깊은 설명 글 링크는 본문 각 섹션에 둡니다.

## kubectl 기본

리소스 종류와 무관하게 자주 쓰는 명령입니다. 모든 리소스 섹션에서 공통으로 사용합니다.

| 명령 | 설명 | 비고 |
|---|---|---|
| `kubectl cluster-info` | 클러스터 엔드포인트 확인 | 첫 연결 점검 |
| `kubectl get <resource>` | 리소스 목록 조회 | `-A`로 모든 namespace |
| `kubectl get nodes` | 노드 목록 조회 | `-o wide`로 IP·OS 표시 |
| `kubectl get <resource> <name> -o yaml` | 한 객체의 YAML 덤프 | 디버깅 시작점 |
| `kubectl describe <resource> <name>` | 객체 상세와 이벤트 | 실패 원인 추적 |
| `kubectl run <name> --image=<image>` | `Pod` 즉석 생성 | demo·디버깅용. 실서비스는 `Deployment` |
| `kubectl apply -f <file>.yaml` | YAML로 리소스 생성·갱신 | 멱등 적용 |
| `kubectl delete <resource> <name>` | 객체 삭제 | `--grace-period=0 --force`로 강제 |
| `kubectl edit <resource> <name>` | 클러스터의 객체 즉시 편집 | `EDITOR` 환경변수 사용 |
| `kubectl logs <pod>` | 컨테이너 로그 | `-f` 추적, `-c <name>` 컨테이너 지정 |
| `kubectl exec -it <pod> -- <cmd>` | 컨테이너 안에서 명령 실행 | `-c`로 컨테이너 지정 |
| `kubectl port-forward <pod> <local>:<remote>` | 로컬 포트로 터널 | 로컬 디버깅 |
| `kubectl config use-context <name>` | 클러스터 컨텍스트 전환 | `kubectl config get-contexts`로 목록 |

### 출력 형식 옵션

| 옵션 | 효과 |
|---|---|
| `-o yaml` | 객체 전체 YAML |
| `-o json` | JSON. `jq`와 결합해 필터 |
| `-o wide` | 추가 칼럼 (노드, IP) |
| `-o jsonpath='{.spec.x}'` | 특정 필드 한 값 |
| `--watch` | 변경 스트림 |

### 명령형 워크플로 (`--dry-run=client -o yaml`)

| 플래그 | 효과 |
|---|---|
| `--dry-run=client` | kubectl이 객체만 만들고 API 서버 호출 안 함 |
| `--dry-run=server` | API 서버까지 가되 저장만 생략. admission·quota 검증 받음 |
| `-o yaml` | 만든 객체를 YAML로 출력 |
| `--dry-run=client -o yaml > <file>.yaml` | 매니페스트 뼈대 생성 후 손으로 보완 → `kubectl apply` |

### 리소스 스키마 탐색 (`api-resources` · `explain`)

| 명령 | 효과 |
|---|---|
| `kubectl api-resources` | 클러스터가 다루는 모든 리소스 카탈로그. `NAME`·`SHORTNAMES`·`APIVERSION`·`NAMESPACED`·`KIND` 컬럼 |
| `kubectl api-resources --api-group=<group>` | 특정 API 그룹(`apps`, `batch`, `networking.k8s.io` 등)만 필터 |
| `kubectl explain <resource>` | 리소스의 최상위 필드와 자료형. 한 단계까지만 펼침 |
| `kubectl explain <resource>.<field>` | 점 표기법으로 하위 필드 펼치기 (`pods.spec.containers.livenessProbe.httpGet`) |
| `kubectl explain <resource> --recursive` | 설명 문구 없이 필드 트리 전체를 들여쓰기로 출력 |

## ConfigMap

구성 데이터를 키-값 쌍으로 담아 `Pod`에 환경 변수나 파일로 주입하는 오브젝트.

### 명령

| 명령 | 설명 | 비고 |
|---|---|---|
| `kubectl create configmap <name> --from-literal=<k>=<v>` | 키-값을 명령줄에 적어 생성 | `--from-literal` 반복 가능 |
| `kubectl create configmap <name> --from-file=<path>` | 파일을 통째로 담아 생성 | 항목이 많을 때 |
| `kubectl apply -f <file>.yaml` | YAML로 생성·갱신 | 선언적 |
| `kubectl get configmaps` | `ConfigMap` 목록 조회 | `cm`로 단축 |
| `kubectl describe configmap <name>` | 키-값 확인 | `Data` 항목에 나열 |

### 최소 YAML

```yaml title="config-map.yaml"
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  APP_COLOR: blue
  APP_MODE: prod
```

#### envFrom 주입 (모든 키)

```yaml
spec:
  containers:
    - name: app
      image: myapp:1.0
      envFrom:
        - configMapRef:
            name: app-config
```

#### 단일 env 주입 (키 하나)

```yaml
spec:
  containers:
    - name: app
      image: myapp:1.0
      env:
        - name: APP_COLOR
          valueFrom:
            configMapKeyRef:
              name: app-config
              key: APP_COLOR
```

#### Volume 주입 (파일)

```yaml
spec:
  containers:
    - name: app
      image: myapp:1.0
      volumeMounts:
        - name: app-config-volume
          mountPath: /etc/config
  volumes:
    - name: app-config-volume
      configMap:
        name: app-config
```

## Deployment

`ReplicaSet` 위에 한 층을 더 둬 롤링 업데이트와 롤백을 자동으로 처리하는 컨트롤러.

### 명령

| 명령 | 설명 | 비고 |
|---|---|---|
| `kubectl apply -f deployment.yaml` | `Deployment` 생성·갱신 | 선언적, 멱등 |
| `kubectl create -f deployment.yaml` | `Deployment` 생성 | 이미 있으면 실패 |
| `kubectl create deployment <name> --image=<img>` | `Deployment` 즉석 생성 | `--replicas=N` 동시 지정 가능 |
| `kubectl create deployment <name> --image=<img> --dry-run=client -o yaml` | `Deployment` YAML 뼈대 생성 | `> <file>.yaml`로 저장 후 보완 |
| `kubectl get deployments` | `Deployment` 목록 조회 | `deploy`로 단축 |
| `kubectl describe deployment <name>` | 상세와 이벤트 | 디버깅 시작점 |
| `kubectl delete deployment <name>` | `Deployment`·`RS`·`Pod` 삭제 | 자식 리소스 함께 정리 |
| `kubectl scale --replicas=N deployment <name>` | 복제본 수 즉시 조정 | YAML은 변경 안 됨 |
| `kubectl get all` | 워크로드 + `Service` 일괄 조회 | `ConfigMap`·`Secret`·`Ingress` 등은 빠짐 |

### 최소 YAML

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-deployment
  labels:
    app: myapp
    type: front-end
spec:
  replicas: 3
  selector:
    matchLabels:
      type: front-end
  template:
    metadata:
      labels:
        type: front-end
    spec:
      containers:
        - name: nginx-container
          image: nginx
```

## Namespace

한 클러스터 안에서 리소스 이름·정책·한도를 격리하는 단위. 같은 이름의 리소스가 다른 `Namespace`에 공존할 수 있습니다.

### 명령

| 명령 | 설명 | 비고 |
|---|---|---|
| `kubectl create namespace <name>` | `Namespace` 생성 | 한 줄 명령 |
| `kubectl apply -f namespace.yaml` | YAML로 `Namespace` 생성·갱신 | 선언적 |
| `kubectl get namespaces` | `Namespace` 목록 조회 | `ns`로 단축 |
| `kubectl get pods --namespace=<name>` | 특정 `Namespace`의 파드 조회 | `-n` 단축 |
| `kubectl get pods --all-namespaces` | 모든 `Namespace` 한꺼번에 | `-A` 단축 |
| `kubectl config set-context --current --namespace=<name>` | 현재 컨텍스트의 기본 `Namespace` 전환 | 이후 `-n` 생략 가능 |
| `kubectl delete namespace <name>` | `Namespace`와 그 안의 모든 리소스 삭제 | 자식 리소스 함께 정리 |

### 최소 YAML

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: dev
```

리소스를 특정 `Namespace`에 만들려면 매니페스트의 `metadata.namespace`에 적습니다.

```yaml
metadata:
  name: myapp-pod
  namespace: dev
```

서비스 FQDN의 형식은 `<service-name>.<namespace>.svc.cluster.local`입니다. 같은 `Namespace` 안에서는 짧은 호스트명만으로 충분합니다.

## Pod

쿠버네티스가 컨테이너를 한 단위로 묶어 스케줄·재시작하는 가장 작은 오브젝트입니다.

### 명령

| 명령 | 설명 | 비고 |
|---|---|---|
| `kubectl create -f <file>.yaml` | YAML로 `Pod` 생성 | 이미 있으면 실패 |
| `kubectl get pods` | `Pod` 목록 조회 | `-A` 모든 namespace |
| `kubectl describe pod <name>` | `Pod` 상세와 이벤트 | 시작 실패 원인 추적 |
| `kubectl run <name> --image=<image>` | `Pod` 즉석 생성 | demo·디버깅용 |
| `kubectl run <name> --image=<img> --dry-run=client -o yaml` | `Pod` YAML 뼈대 생성 | `> <file>.yaml`로 저장 후 보완 |

### 최소 YAML

#### 단일 컨테이너 Pod

```yaml title="single-container-pod.yaml"
apiVersion: v1
kind: Pod
metadata:
  name: myapp-pod
  labels:
    app: front-end
spec:
  containers:
    - name: nginx-container
      image: nginx
```

#### 멀티 컨테이너 Pod (사이드카)

```yaml title="sidecar-pod.yaml"
apiVersion: v1
kind: Pod
metadata:
  name: myapp-pod
  labels:
    app: front-end
spec:
  containers:
    - name: app
      image: myapp:1.0
      ports:
        - containerPort: 8080
    - name: log-agent
      image: fluent-bit:latest
```

## ReplicaSet

선언된 수만큼 같은 파드가 항상 돌도록 유지하는 컨트롤러.

### 명령

| 명령 | 설명 | 비고 |
|---|---|---|
| `kubectl apply -f rs.yaml` | `RS` 생성·갱신 | 선언적, 멱등 |
| `kubectl get replicaset` | `RS` 목록 조회 | `rs`로 단축 |
| `kubectl describe replicaset <name>` | 상세와 이벤트 | 디버깅 시작점 |
| `kubectl delete replicaset <name>` | `RS`와 관리 `Pod` 삭제 | |
| `kubectl scale --replicas=N replicaset <name>` | 복제본 수 즉시 조정 | YAML은 변경 안 됨 |
| `kubectl replace -f rs.yaml` | `RS`를 파일로 통째 대체 | apply가 권장 |

### 최소 YAML

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: myapp-replicaset
spec:
  replicas: 3
  selector:
    matchLabels:
      tier: frontend
  template:
    metadata:
      labels:
        tier: frontend
    spec:
      containers:
        - name: nginx
          image: nginx
```

set-based selector 변형은 다음과 같이 `matchExpressions`를 추가합니다.

```yaml
spec:
  selector:
    matchLabels:
      tier: frontend
    matchExpressions:
      - key: env
        operator: In
        values: [staging, production]
```

## ResourceQuota

한 `Namespace`가 동시에 가질 수 있는 자원의 상한을 선언하는 객체. 한도를 넘기는 요청은 `kubectl apply` 단계에서 거절됩니다.

### 명령

| 명령 | 설명 | 비고 |
|---|---|---|
| `kubectl apply -f quota.yaml` | `ResourceQuota` 생성·갱신 | 선언적 |
| `kubectl get resourcequota --namespace=<name>` | 해당 `Namespace`의 quota 조회 | `quota`로 단축 |
| `kubectl describe resourcequota <name> --namespace=<ns>` | 사용량과 한도 동시 확인 | 디버깅 시작점 |
| `kubectl delete resourcequota <name> --namespace=<ns>` | quota 삭제 | 한도 해제 |

### 최소 YAML

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: compute-quota
  namespace: dev
spec:
  hard:
    pods: "10"
    requests.cpu: "4"
    requests.memory: 5Gi
    limits.cpu: "10"
    limits.memory: 10Gi
```

`hard`의 각 항목이 해당 `Namespace`의 동시 보유 상한선입니다. `pods`는 개수, `requests.*`는 스케줄링 시 요청 합, `limits.*`는 컨테이너 한도 합을 가리킵니다.

## Secret

비밀번호·토큰 같은 민감한 구성 데이터를 `base64`로 담아 `Pod`에 주입하는 오브젝트.

### 명령

| 명령 | 설명 | 비고 |
|---|---|---|
| `kubectl create secret generic <name> --from-literal=<k>=<v>` | 키-값을 명령줄에 적어 생성 | 평문 입력, 인코딩은 자동 |
| `kubectl create secret generic <name> --from-file=<path>` | 파일을 통째로 담아 생성 | 항목이 많을 때 |
| `kubectl apply -f <file>.yaml` | YAML로 생성·갱신 | 선언적 |
| `kubectl get secrets` | `Secret` 목록 조회 | |
| `kubectl describe secret <name>` | 키와 바이트 길이 확인 | 값은 표시 안 됨 |
| `echo -n '<value>' \| base64` | 평문을 `base64`로 인코딩 | `data` 필드에 적을 값 |
| `echo -n '<encoded>' \| base64 --decode` | `base64`를 평문으로 디코딩 | |

### 최소 YAML

#### data 필드 (base64 인코딩한 값)

```yaml title="secret.yaml"
apiVersion: v1
kind: Secret
metadata:
  name: app-secret
data:
  DB_PASSWORD: UEBzc3cwcmQh
```

#### stringData 필드 (평문 입력)

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: app-secret
stringData:
  DB_PASSWORD: P@ssw0rd!
```

#### secretKeyRef 주입 (키 하나)

```yaml
spec:
  containers:
    - name: app
      image: myapp:1.0
      env:
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: app-secret
              key: DB_PASSWORD
```

## Service

`Pod` 그룹에 안정적인 가상 IP와 입구 포트를 제공하는 객체. `type`에 따라 클러스터 안 전용(`ClusterIP`), 모든 노드의 한 포트로 노출(`NodePort`), 클라우드 LB로 노출(`LoadBalancer`)이 됩니다.

### 명령

| 명령 | 설명 | 비고 |
|---|---|---|
| `kubectl apply -f service.yaml` | `Service` 생성·갱신 | 선언적, 멱등 |
| `kubectl expose pod <pod> --port=<p> --name=<svc>` | 기존 `Pod` 라벨로 `Service` 생성 | `--type=NodePort` 가능. nodePort 번호 지정 불가 |
| `kubectl expose pod <pod> --port=<p> --name=<svc> --dry-run=client -o yaml` | `Service` YAML 뼈대 생성 | selector 자동, nodePort는 손으로 추가 |
| `kubectl create service clusterip <name> --tcp=<p>:<t>` | `ClusterIP` `Service` 생성 | selector를 `app=<name>`으로 가정 |
| `kubectl create service nodeport <name> --tcp=<p>:<t> --node-port=<np>` | `NodePort` 번호 지정 가능 | selector는 `app=<name>` 가정 |
| `kubectl get services` | `Service` 목록 조회 | `svc`로 단축 |
| `kubectl get endpoints <name>` | `Service`에 묶인 실제 `Pod` IP 목록 | 디버깅 시작점 |
| `kubectl describe service <name>` | selector·`Endpoints`·이벤트 확인 | 트래픽 안 가는 원인 추적 |
| `kubectl delete service <name>` | `Service` 삭제 | `Pod`는 그대로 유지 |

### 최소 YAML

```yaml
apiVersion: v1
kind: Service
metadata:
  name: myapp-service
spec:
  type: NodePort
  ports:
    - targetPort: 80
      port: 80
      nodePort: 30008
  selector:
    app: myapp
    type: front-end
```

`port`만 필수. `targetPort` 생략 시 `port`와 동일, `nodePort` 생략 시 `30000–32767`에서 자동 할당. `type`을 빼면 기본 `ClusterIP`.
