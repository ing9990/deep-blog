같은 클러스터 안의 프론트엔드 Pod가 백엔드 Pod에 요청을 보내려고 합니다. 백엔드 Pod의 IP를 그대로 코드에 박아 두면, 백엔드가 재시작될 때마다 IP가 바뀌어 호출이 끊깁니다. 스케일 아웃으로 백엔드 Pod가 세 개가 되면 어느 IP를 골라야 할지도 모릅니다. 이 두 문제를 한 자리에서 푸는 객체가 `ClusterIP` 타입 `Service`입니다.

## Pod IP만으로는 부족한 이유

Pod의 IP는 Pod 네트워크의 CIDR(예: `10.244.0.0/16`)에서 동적으로 받습니다. Pod가 죽고 새로 만들어지면 그 자리에 같은 IP가 다시 붙는다는 보장이 없습니다. `Deployment`가 롤링 업데이트를 돌리는 동안 Pod가 차례로 교체되면 IP 목록 전체가 새로 갈리기도 합니다. 호출자가 Pod IP를 직접 들고 있으면 이 모든 변화가 호출자의 실패로 돌아옵니다.

호출 대상이 여러 개일 때도 같은 문제가 따라옵니다. 백엔드를 `replicas: 3`으로 두면 같은 라벨을 가진 Pod가 셋입니다. 프론트엔드는 셋 중 어느 IP로 갈지 알 수 없고, 한 곳에 몰아 보내면 나머지 두 Pod가 놀게 됩니다. 호출자가 분산까지 스스로 한다면 호출자 코드가 인프라 변화에 매번 끌려 다닙니다.

## ClusterIP가 푸는 두 문제

`Service`는 selector로 매치한 Pod 그룹에 안정적인 입구 하나를 만들어 주는 객체입니다. `Service`의 타입 중 `ClusterIP`는 그 입구를 클러스터 안에서만 통하는 가상 IP로 노출합니다. 호출자 입장에서는 백엔드 Pod가 몇 개든, 어느 노드에 있든, 방금 재시작됐든 상관없이 같은 IP 하나만 들고 있으면 됩니다.

이 가상 IP는 어느 노드의 NIC에도 붙어 있지 않습니다. 노드 OS에 <E>이 IP가 내 인터페이스다</E>라고 선언된 자리가 없습니다. 대신 각 노드의 `kube-proxy`가 이 IP를 보고 미리 박아 둔 `iptables` 또는 `IPVS` 규칙이 있습니다. 호출자가 가상 IP로 패킷을 보내면 노드 OS의 패킷 필터가 그 규칙을 매치해 selector로 고른 Pod IP 중 하나로 DNAT을 수행합니다. 호출자는 응답을 받지만, 응답을 만든 자리가 가상 IP가 아니라 실제 Pod였다는 사실은 모릅니다.

분산은 별도 로드 밸런서 객체 없이 따라옵니다. `kube-proxy`의 기본 모드인 `iptables`는 패킷 필터에 <E>33%·33%·33%</E>(셋일 때) 같은 통계 규칙을 박아 두고 들어오는 패킷마다 한 자리를 무작위로 고릅니다. `IPVS` 모드를 쓰면 round-robin·least-connection 같은 정책 중에서 골라 쓸 수 있습니다. 어느 모드든 selector가 매치한 Pod 풀이 분산의 대상이 됩니다. 분산의 깊은 동작과 NodePort 트래픽의 세 단계는 NodePort 글에서 다뤘습니다.

## Service 매니페스트의 세 자리

가장 짧은 `ClusterIP` 매니페스트는 다음과 같습니다.

```yaml title="back-end-clusterip.yaml"
apiVersion: v1
kind: Service
metadata:
  name: back-end
spec:
  type: ClusterIP
  ports:
    - port: 80
      targetPort: 80
  selector:
    app: myapp
    type: back-end
```

`type`을 비우면 기본값이 `ClusterIP`이므로 한 줄을 생략해도 동작이 같습니다. 다른 타입(`NodePort`·`LoadBalancer`)도 내부적으로는 항상 `ClusterIP`를 포함한 상태로 동작하기 때문에, 가상 IP·selector·`Endpoints`의 기본기는 모든 `Service` 타입의 공통 토대입니다.

세 자리만 적으면 됩니다.

| 필드 | 역할 |
|---|---|
| `port` | `Service` 자신이 노출하는 포트. 호출자가 박는 자리 |
| `targetPort` | Pod 안 컨테이너가 듣는 포트. 비우면 `port`와 같은 값으로 추론 |
| `selector` | Pod의 `metadata.labels`와 모두 일치해야 트래픽 대상 |

`NodePort`와 달리 `nodePort` 필드는 없습니다. 외부에서 들어올 입구가 없으므로 노드 OS에 외부용 포트를 열지 않습니다.

```bash
kubectl apply -f back-end-clusterip.yaml
kubectl get services
# NAME       TYPE        CLUSTER-IP    EXTERNAL-IP   PORT(S)   AGE
# back-end   ClusterIP   10.96.0.42    <none>        80/TCP    5s
```

`EXTERNAL-IP`가 `<none>`인 것이 `ClusterIP` 타입의 특징입니다. 이 IP로의 접근은 같은 클러스터 안에서만 통합니다.

## DNS 이름으로 부르기

호출자 입장에서 가상 IP `10.96.0.42`를 코드에 박아 두면 또 IP 의존이 됩니다. 그래서 쿠버네티스는 `Service`가 만들어질 때 클러스터 내부 DNS(`CoreDNS`)에 같은 이름의 레코드를 함께 등록합니다. 호출자 Pod의 `/etc/resolv.conf`에는 `CoreDNS`의 IP가 nameserver로 박혀 있어서, Pod 안에서 `curl http://back-end`를 치면 그 이름이 ClusterIP로 자동 해석됩니다.

이름이 어디까지 짧아질 수 있는지는 호출자의 Namespace에 달려 있습니다. 같은 Namespace에 있는 호출자는 `back-end`만 적으면 충분합니다. 다른 Namespace에 있는 호출자는 `back-end.default`처럼 Namespace까지 적어 주거나, 아예 전체 풀네임 `back-end.default.svc.cluster.local`을 써야 합니다.

이 풀네임의 네 조각이 무엇을 가리키는지는 Namespace 글에서 자세히 다뤘습니다.

## selector와 Endpoints

`selector`가 매치한 Pod IP 목록은 `Endpoints`라는 별도 객체에 자동으로 모입니다. `Service`와 같은 이름으로 함께 만들어지고, Pod가 추가되거나 죽으면 즉시 갱신됩니다. 갱신된 IP 목록을 본 `kube-proxy`가 노드 OS의 라우팅 규칙을 다시 씁니다.

```bash
kubectl get endpoints back-end
# NAME       ENDPOINTS                                AGE
# back-end   10.244.0.5:80,10.244.0.6:80,10.244.0.7:80   2m
```

`selector`를 빠뜨리거나 라벨이 어느 Pod과도 일치하지 않으면 `Endpoints`가 빈 상태로 만들어지고, 호출자의 요청은 그대로 끊깁니다. <E>호출이 안 된다</E>는 증상의 첫 디버깅 자리는 거의 항상 `kubectl get endpoints`입니다. `Endpoints`의 구조와 selector의 매칭 규칙은 NodePort 글이 같은 자리를 다뤘습니다.

<Callout type="warning" title="핵심 포인트: ClusterIP는 가상 IP, 응답을 만드는 자리는 실제 Pod">
  `ClusterIP`로 표시되는 IP(`10.96.0.42` 같은 자리)는 어느 노드의 NIC에도 붙어 있지 않은 가상 IP입니다. 호출자가 그 IP로 패킷을 보내면 노드의 `kube-proxy`가 미리 박아 둔 `iptables` 또는 `IPVS` 규칙이 selector로 고른 Pod IP 중 하나로 DNAT을 수행합니다. <E>가상 IP에서 응답이 오는 것처럼 보인다</E>는 인상은 노드 OS의 패킷 필터가 만드는 착시이고, 실제 응답을 만든 자리는 항상 어느 한 Pod입니다. 이 사실이 잡혀 있으면 디버깅 시 가상 IP·`Endpoints`·`kube-proxy` 규칙 세 자리를 분리해서 볼 수 있습니다.
</Callout>

## NodePort·LoadBalancer로 가는 길

`ClusterIP`는 클러스터 내부 호출 전용이라서 클러스터 바깥의 클라이언트에서는 닿지 않습니다. 같은 와이파이의 노트북 브라우저로 백엔드를 직접 열어 보려면 `NodePort`나 `LoadBalancer`로 한 단계 더 노출해야 합니다.

| 타입 | 외부 노출 | 주된 용도 |
|---|---|---|
| `ClusterIP` | 없음 (클러스터 내부 전용) | Pod 그룹 사이의 내부 호출 |
| `NodePort` | 모든 노드의 한 포트 | 학습·내부망·데모 |
| `LoadBalancer` | 클라우드 LB의 외부 IP | 실서비스의 외부 노출 |

`NodePort`나 `LoadBalancer` 타입을 만들어도 그 안에는 항상 `ClusterIP`가 자동으로 함께 만들어집니다. 외부 트래픽이 거치는 마지막 두 단계(`ClusterIP:port → Pod:targetPort`)가 결국 `ClusterIP`의 동작 그대로이기 때문입니다. 그래서 `ClusterIP`의 기본기를 잡아 두면 나머지 두 타입은 <E>외부에 입구를 한 겹 더 얹은 것</E>으로 이해할 수 있습니다.

<Callout type="error" title="핵심 통찰: 이름이 IP의 휘발성을 가린다">
  Pod의 IP는 재시작·롤링 업데이트·스케일 아웃마다 바뀝니다. `Service`의 `ClusterIP`와 DNS 이름은 그 변화의 위에 한 겹 안정된 입구를 만들고, 호출자에게는 변화의 흔적을 보이지 않습니다. 호출자 Pod의 코드에는 `http://back-end`라는 이름 하나만 박혀 있으면 충분합니다. 그 안에서 가상 IP가 어디에 있고, Pod가 몇 개인지, 누가 방금 죽었는지를 호출자는 모릅니다. `Service`가 푸는 진짜 문제는 트래픽 분산이 아니라 <E>인프라의 변화를 호출자 코드로부터 분리하는 일</E>이고, 분산은 그 부산물입니다.
</Callout>

## 마무리

`ClusterIP`는 `Service`의 기본 타입이자 다른 모든 타입의 토대입니다. 매니페스트의 `port`·`targetPort`·`selector` 세 자리가 핵심이고, `type`을 비우면 자동으로 `ClusterIP`가 됩니다. 가상 IP와 DNS 이름은 클러스터 안에서만 통하며, 호출자는 `http://back-end` 같은 짧은 이름으로 selector가 고른 Pod 풀에 접근합니다. `kube-proxy`의 `iptables`나 `IPVS` 규칙이 분산을 만들고, `Endpoints` 객체가 실제 Pod IP 목록을 들고 있습니다.

자주 쓰는 `Service` 명령과 최소 YAML은 [Kubernetes Cheatsheet](/posts/kubernetes-cheatsheet)에 누적됩니다. 후속 글에서는 `LoadBalancer` 타입으로 옮겨 가, 클라우드의 외부 로드 밸런서를 자동 프로비저닝하는 자리와 그 위에 얹는 `Ingress`까지 다룹니다.
