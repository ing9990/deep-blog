직전 글에서 결제 실패 보상은 Choreography Saga로 정리했지만, 마지막 단락이 두 가지 문제를 다음 글로 미뤄 두었습니다.

- 주문 상태를 `CANCELED`로 commit한 직후 Kafka 발행 직전에 프로세스가 죽으면 보상 메시지가 사라집니다.
- Kafka가 재시도해서 같은 메시지를 두 번 보내면 상품 서비스가 재고를 두 번 복구합니다.

이 글은 그 두 문제를 <E>Outbox로 발행을 보장</E>하고 <E>Inbox로 멱등을 보장</E>하는 두 패턴으로 어떻게 처리했는지 정리합니다.

- 메시지 발행은 비즈니스 commit과 한 단위로 묶이거나 같이 무산되어야 합니다.
- 같은 메시지가 두 번 들어와도 결과 상태는 한 번 처리한 것과 같아야 합니다.
- 두 보장은 서로를 전제합니다. 발행 보장만 있으면 재시도가 늘어 중복이 더 잦아지고, 멱등만 있으면 메시지 자체가 사라집니다.

## 요구사항과 제약

기능 요구는 세 가지입니다.

1. 주문 상태 전이(`PAID`, `CANCELED`)와 Kafka 발행은 정확히 한 번 함께 끝납니다. 한쪽만 적용되는 결과는 없습니다.
2. 같은 `eventId`를 가진 메시지가 두 번 도착해도 재고 차감과 복구는 한 번만 적용됩니다.
3. 발행 책임은 사용자 응답 시간에 들어가지 않습니다. 사용자는 결제 결과를 즉시 받습니다.

제약은 두 가지입니다.

- Kafka 발행은 네트워크 호출입니다. 호출 시점에 브로커가 응답하지 않을 수 있고, ack 도착 전에 우리 프로세스가 죽을 수도 있습니다.
- 컨슈머는 at-least-once 모델로 동작합니다. Kafka의 retry 정책과 retry topic이 있는 한 같은 메시지의 재전송을 0으로 만들 수 없습니다.

## 시작점: AFTER_COMMIT과 그 한계

처음 미니쿠팡이 Kafka 발행을 붙일 때는 Outbox가 아니라 Spring의 `@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)`를 썼습니다. 코드 한 어노테이션으로 "비즈니스 트랜잭션이 commit된 뒤에만 발행"이 처리됩니다. 추가 테이블도 relay도 필요하지 않습니다.

```java title="OrderConfirmedEventHandler.java"
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void handle(OrderConfirmedEvent event) {
    String key = String.valueOf(event.getPayload().orderId());
    kafkaProducer.sendMessage(
        EventTopic.ORDER_CONFIRMED.getName(),
        key,
        jsonConverter.toJson(event),
        () -> log.error("publish failed. orderId={}", event.getPayload().orderId())  // [!code highlight]
    );
}
```

이 코드가 보장하는 것은 분명합니다. 비즈니스 트랜잭션이 롤백되면 발행이 일어나지 않습니다. 그래서 "주문이 `PAID`로 바뀌지 않았는데 `PAID` 메시지만 나가는" 경우는 만들어지지 않습니다.

문제는 그 반대 방향입니다. 비즈니스 commit이 끝나고 AFTER_COMMIT 핸들러가 `kafkaTemplate.send`를 호출하기까지의 짧은 시간 동안 프로세스가 죽으면 어떻게 될까요?

<Diagram caption="commit 직후 발행 직전 크래시: orders는 PAID인데 Kafka에는 메시지가 없는 상태로 멈춘다.">{`sequenceDiagram

`}</Diagram>

`orders` 테이블에는 `PAID` 행이 영구로 남았는데 Kafka에는 메시지가 없습니다. 상품 서비스는 MySQL 재고 영구 차감을 못 합니다. 재시작 후에도 이 핸들러는 호출되지 않습니다. 이미 commit된 트랜잭션의 후처리는 메모리에만 있던 이벤트이기 때문입니다.

이 상황은 평시에는 자주 일어나지 않지만, 결제 직후 핫딜 윈도에서 인스턴스가 OOM이나 배포 reload로 죽는 상황을 모사하면 재현됩니다. <E>commit 직후의 짧은 시간 동안 메시지가 사라질 수 있습니다.</E> 미니쿠팡은 이 시점에 Outbox로 옮겼습니다.

## Outbox로 발행 보장

Outbox 패턴은 메시지 발행을 두 단계로 나눕니다. 비즈니스 commit과 같은 트랜잭션에서 outbox 테이블에 메시지를 `INSERT`한 뒤, 별도 relay가 미발행 행을 폴링해 Kafka로 보냅니다.

`OutboxEvent`는 단일 메시지 행을 담는 엔티티입니다.

```java title="OutboxEvent.java"
@Entity
@Table(name = "outbox_events", indexes = {
    @Index(name = "idx_outbox_unpublished", columnList = "published, outbox_event_id")  // [!code highlight]
})
public class OutboxEvent implements Persistable<Long> {

    @Id
    @Column(name = "outbox_event_id")
    private Long id;

    @Column(nullable = false, length = 100)
    private String topic;

    @Column(name = "event_id", nullable = false)
    private Long eventId;

    @Column(name = "event_type", nullable = false, length = 50)
    private String eventType;

    @Lob
    @Column(nullable = false)
    private String payload;

    @Column(nullable = false)
    private boolean published;
    // ... createdAt, publishedAt 생략
}
```

`(published, outbox_event_id)` 복합 인덱스가 relay의 폴링 쿼리(`WHERE published = false ORDER BY outbox_event_id`)를 빠르게 처리합니다. PK는 TSID 기반 long이라 `INSERT` 시각 순서와 정렬 순서가 같고, relay가 발행 순서를 보존할 수 있습니다.

발행 측은 비즈니스 서비스 안에서 `OutboxEventStore.save`를 부릅니다.

```java title="OutboxEventStore.java"
@Component
@RequiredArgsConstructor
public class OutboxEventStore {

    private final OutboxEventRepository repository;
    private final TsidGenerator tsidGenerator;
    private final JsonConverter jsonConverter;

    public void save(String topic, String messageKey, BaseEvent<?> event) {
        OutboxEvent record = OutboxEvent.create(
            tsidGenerator.nextId(),
            topic,
            messageKey,
            event.getEventId(),
            event.getEventType(),
            jsonConverter.toJson(event)
        );
        repository.save(record);  // [!code highlight]
    }
}
```

이 컴포넌트는 자체 트랜잭션을 시작하지 않습니다. 호출자가 이미 `@Transactional` 안에 있어야 합니다. 그래야 비즈니스 쓰기와 outbox 행 `INSERT`가 같은 commit으로 묶입니다.

호출 지점은 주문 `confirm`/`cancel` 두 곳입니다.

```java title="OrderService.java"
@Transactional
public ConfirmOrderResult confirmOrder(Long orderId, Long memberId, String paymentId) {
    Order order = loadOwnedPending(orderId, memberId);
    order.markPaid();
    OrderConfirmedEvent event = toConfirmedEvent(order);
    outboxEventStore.save(                                          // [!code highlight]
        EventTopic.ORDER_CONFIRMED.getName(),
        String.valueOf(order.getId()),
        event
    );
    return ConfirmOrderResult.of(order, paymentId);
}
```

`order.markPaid()`로 상태를 `PAID`로 바꾸고, 같은 메서드 안에서 `outboxEventStore.save`로 발행 메시지를 `INSERT`합니다. 두 SQL은 같은 `@Transactional` 경계에 있어 commit이나 롤백이 함께 일어납니다. <E>비즈니스 commit과 메시지 `INSERT`가 같은 트랜잭션에 묶입니다.</E>

발행 자체는 별도 컴포넌트가 폴링으로 처리합니다.

```java title="OutboxEventRelay.java"
@Component
@RequiredArgsConstructor
public class OutboxEventRelay {

    private final OutboxEventRepository repository;
    private final KafkaTemplate<String, String> kafkaTemplate;

    @Scheduled(fixedDelayString = "${outbox.relay.fixed-delay-ms:200}")  // [!code highlight]
    @Transactional
    public void relay() {
        List<OutboxEvent> batch = repository.findTop100ByPublishedFalseOrderByIdAsc();
        if (batch.isEmpty()) {
            return;
        }
        for (OutboxEvent event : batch) {
            try {
                kafkaTemplate.send(event.getTopic(), event.getMessageKey(), event.getPayload())
                    .get(2, TimeUnit.SECONDS);                             // [!code highlight]
                event.markPublished();
            } catch (Exception e) {
                log.warn("Outbox publish failed; will retry next tick. id={}, err={}",
                    event.getId(), e.getMessage());
                break;                                                      // [!code highlight]
            }
        }
    }
}
```

세 가지 처리가 발행 신뢰성을 만듭니다.

- `findTop100ByPublishedFalseOrderByIdAsc`로 미발행 행을 PK 오름차순 100건씩 가져옵니다. PK가 TSID라 시각 순서와 같습니다. 같은 키를 쓰는 메시지의 발행 순서가 보존됩니다.
- `kafkaTemplate.send(...).get(2, TimeUnit.SECONDS)`로 ack를 동기 대기합니다. ack가 오면 `markPublished`로 `published = true`를 commit합니다. ack가 안 오면 예외가 나고 `published`는 그대로 남아 다음 tick에 다시 발행됩니다.
- 한 batch 안에서 한 건이라도 실패하면 `break`로 멈춥니다. 같은 키를 쓰는 후속 메시지의 발행 순서가 어긋나지 않습니다.

이 구조에서 commit 직후 크래시가 일어나도 `published = false`인 outbox 행이 데이터베이스에 남습니다. 프로세스가 다시 뜨면 relay 스케줄러도 다시 떠서 미발행 행을 처음부터 다시 보냅니다. <E>발행 책임이 메모리에서 영구 저장소로 옮겨졌습니다.</E>

Outbox만 적용한 시점의 미니쿠팡 아키텍처는 이렇게 변합니다.

이 시점의 아키텍처는 발행 신뢰성을 보장하지만 같은 메시지가 한 번 더 발행될 가능성이 오히려 늘었습니다. relay가 `kafkaTemplate.send` 호출은 성공했는데 ack 도착 전에 죽으면, 다음 tick에 같은 행을 다시 보냅니다. Kafka 자체 retry 정책도 같은 방향으로 작동해 `<topic>-retry-N` 토픽이 같은 메시지를 다시 흘립니다. Kafka 입장에서는 같은 `eventId`의 메시지를 두 번 받게 됩니다. 수신 측의 멱등 보장이 함께 필요한 이유입니다.

## Inbox로 멱등 보장

수신 측은 `processed_events` 테이블에 처리한 메시지의 식별자를 기록합니다. 미니쿠팡에서는 (`event_id`, `event_type`) 두 컬럼에 UNIQUE 제약을 둡니다.

```java title="ProcessedEvent.java"
@Entity
@Table(
    name = "processed_events",
    uniqueConstraints = @UniqueConstraint(
        name = "uk_processed_events_event",
        columnNames = {"event_id", "event_type"}                    // [!code highlight]
    )
)
public class ProcessedEvent {

    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "event_id", nullable = false)
    private Long eventId;

    @Column(name = "event_type", nullable = false, length = 50)
    private String eventType;

    @Column(name = "processed_at", nullable = false)
    private LocalDateTime processedAt;
    // ... 생략
}
```

`event_id`는 발행 측에서 TSID로 만들어 넣은 64비트 long이고, `event_type`은 `ORDER_CONFIRMED` 같은 이벤트 종류 이름입니다. 두 값을 합치면 한 메시지를 식별하는 키가 됩니다.

처리 메서드는 본 처리에 들어가기 전에 `processed_events` 행을 먼저 `INSERT`합니다.

```java title="OrderEventProcessor.java"
@Transactional
public void processOrderConfirmed(long eventId, OrderConfirmedPayload payload) {
    processedEventRepository.save(ProcessedEvent.of(eventId, "ORDER_CONFIRMED"));  // [!code highlight]
    int updated = optionStockRepository.decreaseQuantityIfEnough(
        payload.optionId(), payload.quantity());
    if (updated == 0) {
        log.error("MySQL 재고 영구 차감 실패. orderId={}", payload.orderId());
    }
}

@Transactional
public void processPaymentFailed(long eventId, OrderPaymentFailedPayload payload) {
    processedEventRepository.save(ProcessedEvent.of(eventId, "ORDER_PAYMENT_FAILED"));
    long remaining = productStockRedisRepository.releaseStock(
        payload.optionId(), payload.quantity());
    // ... 실패 로그 생략
}
```

같은 메시지가 두 번 도착하면 두 번째 호출의 첫 줄(`processedEventRepository.save`)에서 UNIQUE 제약 위반이 일어납니다. JPA가 `DataIntegrityViolationException`을 던지고, 트랜잭션이 즉시 롤백됩니다. 두 번째 호출은 재고 차감을 시작하지도 못합니다.

예외는 컨슈머에서 잡습니다.

```java title="OrderEventConsumer.java"
@KafkaListener(topics = {
    "#{T(...).ORDER_CONFIRMED.getName()}",
    "#{T(...).ORDER_PAYMENT_FAILED.getName()}"
})
public void consume(String message,
                    @Header(KafkaHeaders.RECEIVED_TOPIC) String topic) {
    long eventId = 0L;
    try {
        EventMessage eventMessage = jsonConverter.fromJson(message, EventMessage.class);
        eventId = eventMessage.eventId();

        switch (EventTopic.fromName(topic)) {
            case ORDER_CONFIRMED -> {
                OrderConfirmedPayload p = jsonConverter.treeToValue(
                    eventMessage.payload(), OrderConfirmedPayload.class);
                processor.processOrderConfirmed(eventId, p);
            }
            case ORDER_PAYMENT_FAILED -> {
                OrderPaymentFailedPayload p = jsonConverter.treeToValue(
                    eventMessage.payload(), OrderPaymentFailedPayload.class);
                processor.processPaymentFailed(eventId, p);
            }
            case null, default -> log.warn("Unknown topic: {}", topic);
        }
    } catch (DataIntegrityViolationException e) {
        log.info("Duplicate event skipped. eventId={}, topic={}", eventId, topic);  // [!code highlight]
    }
}
```

`DataIntegrityViolationException`을 catch한 컨슈머는 메시지 처리를 정상 종료합니다. Kafka는 이 메시지의 offset이 commit된 것으로 보고 다음 메시지로 넘어갑니다. <E>두 번째 호출은 UNIQUE 제약 위반으로 막히고, 재고 차감과 복구는 한 번만 일어납니다.</E>

순서가 중요한 이유가 한 가지 있습니다. `processed_events` `INSERT`가 본 처리보다 **먼저** 일어나야 합니다. 만약 본 처리(예: Redis 재고 복구)를 먼저 하고 그 뒤에 `processed_events`를 `INSERT`하면, 첫 호출이 본 처리는 끝냈는데 `INSERT` 직전에 죽는 경우 두 번째 호출이 본 처리를 또 한 번 실행합니다. `INSERT`를 먼저 두면 같은 트랜잭션 안에서 commit 시점이 같아져, 한쪽만 적용되는 결과가 나오지 않습니다.

Outbox와 Inbox가 모두 적용된 미니쿠팡의 최종 아키텍처는 이렇게 자랐습니다.

이 구조가 막아 주는 문제를 정리하면 다음과 같습니다.

| 위협 | 어떻게 막았나 |
|---|---|
| 비즈니스 commit 직후 발행 직전 크래시로 메시지 유실 | outbox 행이 같은 트랜잭션으로 commit되어 영구 저장. relay가 다시 떠서 재발행 |
| relay가 send 후 ack 도착 전 크래시로 같은 메시지 재발행 | 수신 측의 `processed_events` UNIQUE 제약이 두 번째 호출의 `INSERT`를 막음 |
| Kafka 자체 retry 정책으로 같은 메시지 재전송 | 위와 동일한 UNIQUE 제약이 흡수 |
| 비즈니스 트랜잭션 롤백 시 메시지만 발행되어 어긋난 상태 | outbox `INSERT`도 같은 트랜잭션이라 롤백되어 발행 자체가 없음 |
| 컨슈머가 본 처리 후 멱등 `INSERT` 직전 크래시로 재처리 시 본 처리 중복 | 본 처리 앞에 `processed_events` `INSERT`를 두어 같은 트랜잭션 commit으로 묶음 |

<Callout type="error" title="핵심 통찰: 한 번 도달은 발행 측과 수신 측이 함께 만든다">
분산 환경에서 메시지의 한 번 적용은 발행 측의 트랜잭셔널 Outbox와 수신 측의 멱등 처리가 함께 만듭니다. 발행 측만 보장하면 재시도 중복이 본 처리에 그대로 흘러들고, 수신 측만 보장하면 메시지 자체가 사라진 경우를 복구할 방법이 없습니다. 두 보장이 서로의 전제입니다.
</Callout>

## 통합 테스트 결과

`integration-test` 모듈에서 모든 서비스와 인프라(MySQL × 5, Redis, Kafka)를 띄워 시나리오를 돌렸습니다. 발행 측 Outbox와 수신 측 `processed_events`가 함께 켜진 상태에서 다음 정합성을 측정했습니다.

| 시나리오 | 가정 | 정합성 결과 |
|---|---|---|
| 재고 100, 동시 50 결제 성공 | 정상 흐름 | `PAID` 50, MySQL 재고 50, outbox 50건 모두 `published` |
| 재고 100, 동시 100 결제 성공 | 경계 조건 | `PAID` 100, MySQL 재고 0, outbox 100건 모두 `published` |
| 재고 100, 동시 101, 1건 결제 실패 | 보상 발생 | `PAID` 100, `CANCELED` 1, <E>Redis 재고 100으로 복구</E>, `processed_events`에 `ORDER_PAYMENT_FAILED` 1건만 기록 |
| 같은 메시지 2회 의도적 재전송 | 중복 수신 모사 | 첫 메시지만 처리, 두 번째는 `Duplicate event skipped` 로그, 재고 변동 없음 |

마지막 시나리오가 Inbox의 멱등 보장을 직접 검증합니다. Kafka UI에서 같은 `eventId`로 두 번 메시지를 보내면, 컨슈머 로그에 `Duplicate event skipped`가 한 번 찍히고 옵션 재고는 한 번만 차감됩니다.

## 남은 한계와 다음 단계

이 구조로도 처리되지 않은 영역이 세 가지 남아 있습니다.

| 영역 | 무엇이 남았나 | 다음 단계 |
|---|---|---|
| 발행 지연 | relay가 200ms 폴링 주기라 평균 100ms, 최악 200ms의 발행 지연이 있다 | Debezium 같은 CDC로 outbox 테이블의 binlog 변경을 즉시 잡아 보내는 방식으로 교체 검토 |
| DLT 누적 운영 | retry 끝까지 실패한 메시지가 `<topic>-dlt`에 쌓이면 자동 처리 흐름이 없다 | DLT 메시지를 주기적으로 점검·재처리하는 별도 콘솔 또는 cron 작업 |
| Kafka transactional producer | 현재는 단순 `send` + ack 대기 구조라 broker 측 exactly-once는 보장하지 않는다 | 운영 부하가 비례해 늘기 때문에 통합 테스트로 결과 정합성을 확인할 수 있는 한 보류 |

발행 지연은 사용자 응답 시간에 들어가지 않으므로 200ms는 sandbox 기준에서 큰 비용이 아닙니다. DLT 운영은 시리즈가 멀티 인스턴스 환경으로 옮겨가면서 다음 글에서 다룰 후보입니다.
