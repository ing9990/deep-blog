데이터는 앞으로 흐르지만 속도 불일치는 피할 수 없습니다. 생산자가 소비자보다 빠르면 어딘가에 쌓여야 하고, 쌓이는 모든 곳은 유한합니다. Backpressure는 이 불일치가 버퍼를 터뜨리기 전에 "속도를 늦춰라"는 신호를 뒤로 돌려보내는 메커니즘입니다. 이 글에서는 backpressure가 왜 필요한지, 가능한 전략이 왜 네 가지로 수렴하는지, 그리고 실제 시스템에서 어떤 선택이 어느 맥락에 맞는지를 따라갑니다.

<Note title="이 글의 학습 목표">
  - Backpressure가 "역방향 제어 신호"라는 말의 정확한 의미를 이해한다
  - Buffer, Drop, Block, Signal 네 전략이 왜 논리적으로 완결적인지 구분할 수 있다
  - 내 시스템의 맥락(유실 허용, 실시간성, 생산자 통제 여부)에 따라 어떤 전략을 선택할지의 기준을 얻는다
</Note>

## Backpressure란

"Backpressure"는 말 그대로 뒤(back)로 가해지는 압력(pressure)입니다. 데이터가 앞으로 흐르는 파이프라인에서, 하류(consumer, 받는 쪽)가 상류(producer, 주는 쪽)에게 "속도를 늦춰라"는 신호를 거슬러 올려보내는 흐름 제어 메커니즘을 가리킵니다.

직관적으로는 수도꼭지와 세면대를 떠올리면 됩니다. 수도꼭지에서 나오는 속도가 세면대가 빠지는 속도보다 빠르면 세면대가 넘칩니다. 이때 "수도꼭지를 줄여달라"고 요구하는 장치가 backpressure입니다. 핵심은 **방향**입니다. 데이터는 앞으로, 제어 신호는 뒤로. 이름의 "back"이 가리키는 것이 바로 이 제어 신호의 역방향 흐름입니다.

Backpressure는 특정 알고리즘이나 라이브러리가 아니라 **흐름 제어(flow control)의 한 범주**입니다. TCP의 수신 윈도우, Reactive Streams의 `request(n)`, Kafka consumer의 `poll()`, Node.js stream의 `.pause()`, bounded queue의 blocking put. 이들 모두가 같은 개념의 서로 다른 구현입니다. 공통점은 하나. **소비자의 capacity가 생산자의 속도를 제어하게 만드는 것**입니다.

## 왜 필요한가

Backpressure가 없으면 시스템은 **소비자와 생산자의 속도 차이가 쌓이는 곳에서** 무너집니다. 두 주체의 처리 속도가 같을 이유는 없습니다. 생산자는 자기 페이스로 이벤트를 뿜어내고, 소비자는 자기 페이스로 처리합니다. 둘 사이 속도 차가 생기면 그 차이는 **어딘가에 쌓여야** 하고, 그 "어딘가"가 버퍼(큐, 메모리, 소켓의 수신 버퍼)이며, 버퍼는 유한합니다.

버퍼가 유한한데 backpressure가 없으면 다음 세 가지 실패 모드 중 하나로 귀결됩니다.

### 1. 메모리 폭발 (OOM)

버퍼를 무한히 키우는 순진한 구현. 초당 10만 건이 들어오고 1만 건이 처리되는 상황에서 버퍼는 초당 9만 건씩 쌓입니다. 결국 프로세스가 OOM으로 죽습니다. Reactive Streams 명세가 등장한 가장 직접적인 동기가, 기존 Observable 패턴이 `onNext`를 무제한 호출해 OOM을 유발하던 문제입니다.

### 2. 지연 누적

버퍼는 있지만 처리가 따라가지 못하는 경우입니다. 큐에 100만 건이 쌓이면 방금 들어온 이벤트는 99만 번째 뒤에서 순서를 기다립니다. Kafka에서 consumer lag이 폭발적으로 증가하는 상황이 이에 해당합니다. 데이터는 살아있지만 너무 늦게 도착해 쓸모가 없는 상태입니다.

### 3. 갑작스러운 유실

버퍼가 가득 차면 뒤에 오는 것을 조용히 버리는 구현입니다. UDP, 일부 로깅 에이전트가 이렇게 동작합니다. 가장 위험한 건 문제가 없어 보이는데 데이터가 사라지는 점입니다.

세 가지 모두 **속도 불일치를 해소할 방법이 없을 때** 나타나는 증상입니다. Backpressure의 존재 이유는 단 하나. 소비자의 처리 속도를 생산자가 알게 만들어서, 버퍼가 넘치기 전에 생산을 늦추게 하는 것입니다.

<Callout type="error" title="핵심 통찰: backpressure는 문제를 해결하지 않고 이동시킨다">
  속도 차이 자체는 사라지지 않습니다. Backpressure가 하는 일은 그 차이를 "소비자의 메모리"가 아니라 "생산자가 책임지는 원천"으로 되돌려 보내는 것입니다. 네트워크 요청이 많이 들어오면 TCP는 수신 윈도우를 줄이고, 그러면 송신자가 전송을 늦추고, 결국 압력은 애플리케이션 레이어까지 거슬러 올라가 사용자 측 요청 속도를 줄이게 됩니다. 문제를 생성 지점으로 밀어 올리는 것, 이것이 backpressure 설계의 철학입니다.
</Callout>

## 동작 원리

<Callout type="warning" title="이 구조를 이해하는 핵심">
  생산자가 소비자보다 빠를 때 시스템이 할 수 있는 선택은 수학적으로 네 가지뿐입니다. **Buffer(쌓는다) · Drop(버린다) · Block(멈춘다) · Signal(협상한다)**. 이 넷은 "메시지를 어떻게 처리할 것인가"의 논리 공간을 완전히 분할하며, 실제 모든 구현은 이 넷의 조합입니다.
</Callout>

### 네 전략의 완결성

네 전략이 "이것뿐"인 이유는 **메시지 처리 논리 공간을 완전히 분할**하기 때문입니다. 보관(Buffer), 폐기(Drop), 생산 중지(Block), 생산 속도 협상(Signal). 이 넷 바깥에 다른 가능성은 없습니다.

Buffer는 가장 원시적이고, 동시에 가장 중요합니다. 모든 큐와 스트림의 기본값이지만, 문제는 "버퍼가 가득 찼을 때 어떻게 할 것인가"를 반드시 정해야 한다는 것입니다. 그 답이 나머지 세 전략입니다. Buffer는 독립 전략이라기보다 **다른 전략의 무대**로 봐야 합니다.

Drop은 "유실 허용이 설계 철학"인 곳에 나타납니다. UDP는 수신 버퍼가 가득 차면 패킷을 그냥 버립니다. 메트릭 수집기는 샘플링으로 일부만 받습니다. Netflix의 Hystrix circuit breaker가 과부하 시 요청을 즉시 거절하는 것도 drop의 한 형태입니다. 공통점은 "늦은 데이터보다 없는 데이터가 낫다"는 판단입니다.

Block은 동기 세계의 기본입니다. Java `BlockingQueue`의 `put()`은 큐가 가득 차면 호출 스레드를 잠재웁니다. 생산자가 그대로 멈춥니다. TCP의 send 버퍼가 가득 차면 `write()` 시스템 콜이 block되는 것도 같은 원리입니다. 단순하지만 **스레드를 소모**하고, 분산 환경에서는 "누가 누구를 블록하는가"가 불명확해져서 현대 비동기 시스템에서는 자주 쓰이지 않습니다.

Signal은 현대 비동기 시스템의 표준입니다. TCP 수신 윈도우가 대표적입니다. 수신자가 ACK 패킷에 "내 버퍼에 N바이트 더 받을 수 있다"는 window size를 실어 보내면, 송신자는 그 창 크기를 넘지 않도록 전송을 조절합니다. Reactive Streams의 `Subscription.request(n)`은 같은 아이디어를 애플리케이션 레이어로 끌어올린 것입니다.

```java title="Subscription.java"
public interface Subscription {
    void request(long n);   // Subscriber → Publisher: "n개 더 보내줘"
    void cancel();
}
```

Subscriber가 `subscription.request(10)`을 호출하면 Publisher는 **딱 10개까지만** `onNext`로 밀어줍니다. Subscriber가 그 10개를 처리한 뒤 다시 `request(10)`을 호출하면 다음 10개가 나옵니다. 이름은 push처럼 `onNext`로 밀어주지만 제어권은 Subscriber에 있는 pull 시스템으로, 위에서 말한 Signal 전략의 가장 직접적인 구현 형태입니다.

### Push vs Pull

Signal 방식을 더 깊이 들어가면 **push vs pull** 구도를 만납니다. Push는 생산자가 준비되면 바로 보내는 방식, Pull은 소비자가 필요할 때 당겨가는 방식입니다.

순수 push는 OOM 문제의 직접 원인이었습니다. RxJava 1.x, 초기 Observable 패턴은 순수 push였고, 소비자가 느려도 생산자가 계속 밀어붙이면서 터졌습니다. 순수 pull도 문제가 있습니다. 소비자가 계속 물어보면 polling 비용이 들고, 생산자가 데이터가 없어도 "없어요"라고 답해야 합니다. Kafka가 그래서 `long poll`(일정 시간 블로킹)을 도입했습니다.

실용적으로는 **pull이 제어권을 쥐되 서버가 적당히 버퍼링하는** hybrid 형태로 수렴했고, 이게 Reactive Streams의 `request(n)` + Publisher internal buffer 모델입니다. TCP도 같은 패턴입니다. 겉으로는 push처럼 보이지만 내부적으로는 수신자의 window advertisement에 의한 pull 제어입니다. 네트워크 스택이 수십 년 전에 이미 풀어둔 문제를, 애플리케이션 레이어가 다시 같은 모양으로 풀어낸 셈입니다.

### 왜 이토록 다양한가

네 전략을 골고루 쓰는 이유는 **어떤 제약을 감수할 것인가**가 시스템마다 다르기 때문입니다.

| 맥락 | 배제되는 전략 | 선택되는 전략 |
|---|---|---|
| 유실이 곧 장애 (금융, 주문) | Drop 불가 | Block 또는 Signal |
| 실시간성이 최우선 (비디오, 메트릭) | Block 불가 (지연 누적) | Drop 또는 Signal |
| 생산자가 외부 (네트워크 유입, 센서) | Block 불가 | Buffer + Drop |
| 멀티 소비자, 속도 상이 (Kafka consumer group) | 중앙 Block 불가 | 개별 Signal (pull) |

네 전략이 공존하는 이유는 "누가 무엇을 양보할 수 있는가"의 답이 도메인마다 다르기 때문이며, **완벽한 전략은 없고 이 맥락에서 덜 나쁜 전략만 존재**합니다. 이것이 backpressure 설계의 근본 인과입니다.

## 어디서 마주치는가

Backpressure는 다음 세 조건 중 **둘 이상이 겹칠 때** 반드시 고려해야 합니다.

- 생산자와 소비자가 서로 다른 프로세스, 스레드, 머신에 있다
- 생산 속도가 순간적으로 폭증할 수 있다 (트래픽 스파이크, 배치 트리거)
- 소비 처리에 가변 지연이 있다 (DB 쿼리, 외부 API, GC 중단)

이 세 조건이 겹치는 대표 지점은 HTTP API 서버의 요청 핸들링, 메시지 큐 consumer, 스트림 처리 파이프라인, 반응형 UI의 데이터 fetch입니다. 반대로 CPU 연산만 동기로 하는 배치 작업은 backpressure가 자동으로 해결됩니다 (생산자 곧 소비자).

### 레이어별 조합

한 시스템 안에서도 **레이어마다 전략이 다릅니다**. 예를 들어 HTTP API 서버는 네트워크 레이어에서 TCP window로 Signal을 쓰고, 애플리케이션 레이어에서 요청 큐에 bounded + drop-oldest(rate limit)를 쓰고, 내부 DB 접근에서 connection pool로 Block을 씁니다. 전체 시스템의 backpressure는 각 레이어 선택의 총합이고, 한 레이어에서 구현이 깨지면 그 층에서 압력이 새어나와 OOM으로 귀결됩니다.

### 실무 안티패턴

실제 backpressure 관련 사고의 대부분은 아래 두 가지 중 하나입니다.

### 1. Unbounded queue

"메모리 여유 있으니 일단 받자"는 판단은 backpressure를 다른 시간대로 미룰 뿐입니다. 트래픽 스파이크 때 큐는 결국 가득 차고, 그 시점에는 복구도 어렵습니다. Java의 `new LinkedBlockingQueue()`(capacity 생략)가 대표 함정입니다. 큐를 쓸 때는 항상 bounded capacity를 명시해야 backpressure가 실제로 작동합니다.

### 2. Signal 신호 무시

Reactive Streams의 Publisher를 구현할 때 `request(n)`을 받아놓고도 `n`을 무시하고 계속 push하는 구현이 의외로 흔합니다. 이러면 명세상 contract violation이고, 결과적으로 backpressure가 없는 것과 같습니다. Publisher를 직접 구현하는 경우에는 항상 "내가 요청받은 양을 넘기지 않는가"를 체크해야 합니다.

## 마무리

Backpressure의 본질은 단순합니다. **소비자와 생산자의 속도 차이를 소비자 쪽 버퍼가 아니라 생산자 쪽 원천에서 해결하도록 밀어 올리는 것**입니다. 가능한 전략은 Buffer, Drop, Block, Signal 네 가지이며, 이 넷은 메시지 처리 논리 공간을 완전히 분할합니다. 어떤 시스템을 설계하든 결국 이 넷의 조합으로 수렴합니다.

그래서 backpressure를 이해한다는 것은 "신기술 하나를 익히는 것"이 아니라, 시스템이 무너질 때 압력이 어디로 흘러가고 있는지를 읽어내는 감각을 갖는 것에 가깝습니다. OOM을 봤을 때, lag 경고를 봤을 때, 혹은 요청이 drop되고 있을 때, "지금 어느 레이어에서 어떤 전략이 빠졌는가"를 먼저 묻게 된다면, 이미 backpressure 관점으로 시스템을 보고 있는 것입니다.
