미니쿠팡에서 사용자가 결제 버튼을 누르면 주문 서비스가 재고를 잡아두고, 결제 서비스가 외부 PG에 승인을 요청합니다. 결제가 실패하면 잡아두었던 재고를 다시 풀어줘야 합니다. 그런데 주문, 결제, 상품이 각각 다른 서비스의 다른 데이터베이스를 쓰기 때문에 <E>한 번의 DB 트랜잭션으로 묶을 수 없습니다</E>. 이 글은 이 경계를 어떻게 풀었는지, 왜 2PC가 아니라 Saga를, 그중에서도 Choreography Saga를 택했는지 정리합니다.

- 주문, 결제, 상품은 각각 독립된 데이터베이스를 가진 별도 서비스입니다.
- 결제 호출은 외부 PG로 나가는 네트워크 호출이며 시간이 걸립니다.
- 정합성 조건: 결제가 실패한 주문의 재고는 다시 가용 재고로 돌아와야 합니다.

## 요구사항과 제약

기능 요구사항은 세 가지입니다.

1. 사용자는 `prepare` 단계에서 주문을 만들고, `confirm` 단계에서 결제를 마칩니다.
2. `confirm`이 외부 PG 거절, 타임아웃, 사용자 취소로 실패하면 잡혀 있던 재고가 가용 상태로 복구되어야 합니다.
3. 보상 처리는 사용자 응답 시간을 늘리지 않아야 합니다. 사용자는 실패 응답을 즉시 받습니다.

결제 실패는 PG 거절, 사용자가 결제 창을 닫는 경우, 카드 한도 초과 등으로 평시에도 일정 비율 발생합니다. 핫딜 윈도에서는 동시 보상이 누적될 수 있으므로 보상 처리량은 평시 주문 처리량에 비례해 설계해야 합니다.

## 트랜잭션 경계

`@Transactional`은 같은 데이터베이스 안에서 여러 SQL을 한 단위로 묶을 때만 동작합니다. 주문 서비스의 MySQL에 Order 행을 `CANCELED`로 바꾸고, 같은 메서드 안에서 상품 서비스의 Redis 재고를 `INCRBY`로 복구하면, 주문 서비스 트랜잭션이 롤백되어도 Redis 호출은 이미 나갔기 때문에 두 저장소 상태가 어긋납니다.

원인은 두 가지입니다.

- 상품 서비스의 Redis는 주문 서비스의 트랜잭션 매니저 밖에 있어 commit이나 rollback 신호를 받지 못합니다.
- 결제 PG는 외부 시스템이라 우리 트랜잭션 매니저가 제어할 수 없는 호출입니다.

그래서 <E>여러 서비스가 함께 하나의 비즈니스 작업을 끝맺어야 하는 흐름</E>은 단일 DB 트랜잭션이 아니라 분산 트랜잭션 패턴이 필요합니다.

## 분산 트랜잭션

분산 트랜잭션에는 크게 두 갈래가 있습니다. 2PC(Two-Phase Commit)와 Saga입니다.

| 구분 | 2PC (XA) | Saga |
|---|---|---|
| 일관성 모델 | 강한 일관성 (ACID) | 결과적 일관성 |
| 동작 방식 | 코디네이터가 prepare, commit 두 단계로 모든 참여자 잠금 | 단계별 로컬 트랜잭션 + 실패 시 보상 트랜잭션 |
| 외부 시스템 포함 | XA 트랜잭션 매니저 지원이 필요. PG 같은 HTTP API는 거의 불가 | 외부 호출도 보상 트랜잭션으로 정의 가능 |
| 잠금 보유 시간 | prepare 단계 동안 모든 참여자가 잠금 보유 | 단계별 로컬 잠금만, 짧음 |
| 실패 시 동작 | 코디네이터가 abort 신호로 모두 롤백 | 이미 끝난 단계는 보상 액션으로 되돌림 |

미니쿠팡에서 결제는 외부 PG로 나가는 HTTP 호출입니다. PG 사업자가 XA 인터페이스를 제공하지 않는 한 2PC 코디네이터에 묶을 수 없습니다. 또 결제 PG가 응답하기까지 수백 ms에서 수 초가 걸리는데, 그 시간 동안 주문, 상품, 결제 모든 서비스가 `prepare` 잠금을 들고 기다려야 한다면 동시 처리량이 급격히 떨어집니다.

그래서 미니쿠팡은 Saga를 택했습니다. 결제는 외부 호출이라 강한 일관성 자체가 현실적이지 않고, <E>실패 시 잡아둔 재고를 풀어주는 보상 액션</E>이 비즈니스적으로 자연스럽기 때문입니다.

## Saga의 두 종류

Saga는 보상 단계를 어떻게 조율하느냐에 따라 다시 두 가지로 나뉩니다.

### 1. Orchestrator Saga

<Diagram caption="Orchestrator: 코디네이터가 모든 단계를 명령으로 끌어간다">{`sequenceDiagram
    participant O as 주문 서비스
    participant C as Saga 코디네이터
    participant P as 결제 서비스
    participant S as 상품 서비스

    O->>C: 주문 시작
    C->>P: 결제 명령
    P-->>C: 결제 실패
    C->>S: 재고 복구 명령
    S-->>C: 복구 완료
    C->>O: 주문 취소 명령
`}</Diagram>

중앙에 Saga 코디네이터 서비스가 있고, 각 참여 서비스에 단계별 명령을 직접 내립니다. 흐름 전체를 한 곳에서 시작하고 끝맺기 때문에 단계가 많거나 분기가 복잡한 워크플로에 적합합니다. 대신 모든 참여 서비스가 코디네이터를 알아야 하고, 코디네이터 자체가 별도 운영 대상이 됩니다.

### 2. Choreography Saga

<Diagram caption="Choreography: 각 서비스가 이벤트만 보고 자기 책임을 수행한다">{`sequenceDiagram
    participant O as 주문 서비스
    participant K as Kafka
    participant S as 상품 서비스

    O->>O: 결제 실패 감지
    O->>O: Order CANCELED + 보상 이벤트 발행 (같은 TX)
    O->>K: order.payment-failed
    K->>S: 이벤트 수신
    S->>S: Redis 재고 복구
`}</Diagram>

중앙 코디네이터가 없습니다. 주문 서비스가 결제 실패 사실을 이벤트로 발행하면, 상품 서비스가 그 이벤트만 보고 자기 책임을 수행합니다. 서비스 간 직접 호출이 없어 결합도가 낮고 운영해야 할 추가 서비스도 없습니다. 대신 흐름이 메시지 시퀀스에 흩어져 있어 단계가 많아질수록 전체 흐름을 한눈에 보기 어렵습니다.

### 두 패턴 비교

| 구분 | Orchestrator Saga | Choreography Saga |
|---|---|---|
| 흐름 제어 | 중앙 오케스트레이터 서비스가 각 단계를 명령 | 각 서비스가 이벤트를 보고 자체 결정 |
| 결합도 | 모든 참여 서비스가 오케스트레이터를 안다 | 서비스 간 직접 의존 없음, 이벤트만 공유 |
| 가시성 | 오케스트레이터 로그가 전체 흐름을 보여줌 | 분산 추적 도구 없으면 흐름 재구성이 어려움 |
| 디버깅 | 한 곳에서 시작과 끝을 추적 가능 | 메시지 흐름을 따라가야 함 |
| 운영 비용 | 오케스트레이터 서비스 1개 추가 운영 | 메시지 인프라(Kafka 등)만 필요 |
| 적합한 상황 | 단계가 많고 분기가 복잡한 워크플로 | 단계가 적고 흐름이 선형인 경우 |

## 미니쿠팡의 선택

미니쿠팡은 Choreography를 택했습니다. 근거는 세 가지입니다.

1. <E>흐름이 선형</E>입니다. 결제 실패 보상 시나리오는 "주문 `CANCELED` → 상품 재고 복구" 한 단계입니다. 분기가 없고 단계도 짧아 오케스트레이터의 가치를 받기 어렵습니다.
2. <E>참여 서비스가 적습니다</E>. 보상에 관여하는 서비스는 주문과 상품 둘뿐입니다. 새 서비스를 하나 더 추가해서 운영 부담을 늘릴 이유가 없습니다.
3. <E>이미 Kafka가 있습니다</E>. 주문 확정 이벤트를 위해 Kafka가 도입되어 있어, 보상 이벤트도 같은 인프라 위에서 발행하면 됩니다.

Orchestrator가 더 나았을 조건은 단계가 5개 이상이거나 단계 사이에 분기와 재시도 정책이 정교하게 필요한 경우입니다. 미니쿠팡의 결제 실패 보상은 그 조건을 만족하지 않습니다.

`confirm` 단계에서 PG가 거절하면 주문 서비스는 한 트랜잭션 안에서 두 가지를 합니다. Order 상태를 `CANCELED`로 전이하고, 같은 트랜잭션 안에서 `order.payment-failed` 이벤트를 outbox 테이블에 `INSERT`합니다. 상태 변경과 발행 메시지가 같이 commit되거나 같이 롤백됩니다.

```java title="OrderService.java"
@Transactional
public void cancelOrder(Long orderId, Long memberId, String reason) {
    Order order = loadOwnedPending(orderId, memberId);
    order.markCanceled();                                                   // [!code highlight]
    var item = order.getItems().getFirst();
    OrderPaymentFailedEvent event = new OrderPaymentFailedEvent(
        order.getMemberId(),
        item.getOptionId(),
        item.getQuantity(),
        reason
    );
    outboxEventStore.save(                                                  // [!code highlight]
        EventTopic.ORDER_PAYMENT_FAILED.getName(),
        String.valueOf(item.getOptionId()),
        event
    );
}
```

발행 신뢰성은 outbox 테이블과 relay 조합으로 확보했습니다. 비즈니스 쓰기와 발행 메시지를 같은 트랜잭션 안에서 한 번에 `INSERT`하기 때문에 Order는 `CANCELED`로 바뀌었는데 발행 메시지는 사라진 어긋남이 만들어지지 않습니다. relay가 별도 스레드에서 outbox를 폴링해 Kafka로 보냅니다.

상품 서비스는 `order.payment-failed`를 수신해 자체 결정으로 Redis 재고를 `INCRBY`로 복구합니다. 이 결정은 주문 서비스가 명령한 것이 아니라 <E>상품 서비스가 이벤트만 보고 자기 책임을 수행한 결과</E>입니다. 이 점이 Choreography의 핵심입니다.

```java title="OrderEventProcessor.java"
@Transactional
public void processPaymentFailed(long eventId, OrderPaymentFailedPayload payload) {
    processedEventRepository.save(ProcessedEvent.of(eventId, "ORDER_PAYMENT_FAILED"));   // [!code highlight]
    long remaining = productStockRedisRepository.releaseStock(                           // [!code highlight]
        payload.optionId(), payload.quantity());
    if (remaining == -1) {
        log.error("Redis 재고 복구 실패: 키 없음. optionId={}, quantity={}, reason={}",
            payload.optionId(), payload.quantity(), payload.reason());
    }
}
```

`processedEventRepository.save`로 같은 이벤트가 두 번 처리되는 것을 막고, `releaseStock`이 Luascript 한 명령으로 Redis 재고를 복구합니다. 두 부속 기술의 자세한 메커니즘은 별도 글로 분리되어 있습니다.

2PC가 모든 참여자를 잠가서 강한 일관성을 만든다면, Saga는 잠그지 않고 단계별 로컬 트랜잭션과 보상으로 결과적 일관성을 만듭니다. Choreography는 그중에서도 흐름 제어 자체를 한 서비스에 집중시키지 않고, 이벤트라는 공통 언어로 책임을 분산시키는 선택입니다.

## 통합 테스트 결과

`integration-test` 모듈에서 모든 서비스와 인프라를 띄워 통합 테스트를 작성했습니다. `ExecutorService` 스레드 풀과 `CountDownLatch` 배리어를 적용해 N명의 사용자가 같은 옵션에 동시 주문하는 시나리오를 구현했습니다.

| 시나리오 | 가정 | 정합성 결과 |
|---|---|---|
| 재고 100, 동시 50 | 모두 결제 성공 | `PAID` 50, 재고 50 |
| 재고 100, 동시 100 | 모두 결제 성공 | `PAID` 100, 재고 0 |
| 재고 100, 동시 101 | 한 명은 `INSUFFICIENT` | `PAID` 100, 거절 1, 재고 0 |
| 재고 100, 결제 실패 1건 | 보상 발생 | `PAID` 0, `CANCELED` 1, <E>재고 100으로 복구</E> |

마지막 시나리오가 이 글의 보상 흐름을 직접 검증합니다. Kafka UI의 Topics 화면에서 토픽별 메시지 발행 현황을 볼 수 있는데, 여기서 `order.payment-failed` 토픽에 메시지가 발행된 것을 간단히 확인할 수 있습니다.

![Kafka UI Topics 화면, order.payment-failed 토픽에 메시지가 쌓여 있다](/images/posts/mini-coupang-choreography-saga/kafka-ui-topics.png)

토픽 안의 한 메시지를 펼치면 발행된 본문이 그대로 보입니다.

![order.payment-failed 토픽의 메시지 상세, eventType과 payload가 그대로 노출된다](/images/posts/mini-coupang-choreography-saga/order-payment-failed-detail.png)

`eventType: ORDER_PAYMENT_FAILED`, `payload.reason: SIMULATED_FAILURE`로 통합 테스트가 의도적으로 발생시킨 결제 실패가 그대로 메시지에 실려 나갔습니다. 결제 실패 메시지가 발행되고 컨슈머가 받아 Redis에 `INCR` 요청을 하는 동안 다른 사용자들은 차감된 재고를 보게 되는 트레이드오프가 있습니다.
