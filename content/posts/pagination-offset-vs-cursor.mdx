OFFSET과 Cursor는 겉보기엔 <E>페이지 번호 vs 마지막 본 값</E>의 표기 차이처럼 보이지만, DB 내부에서 실행되는 작업은 완전히 다릅니다. 이 차이에서 deep page 성능, 동시 쓰기 일관성, UX 적합성의 모든 트레이드오프가 파생됩니다. 이 글은 두 방식이 왜 다르게 동작하는지 인덱스 레벨로 따라가고, 실전에서 어떤 상황에 무엇을 고르는지 기준을 제시합니다.

<Note title="이 글의 학습 목표">
  - OFFSET과 Cursor가 내부적으로 어떻게 동작하는지 B+Tree 인덱스 레벨로 이해한다
  - Deep page 성능, 동시 쓰기 일관성, UX 적합성 세 축에서 두 방식의 차이를 구분할 수 있다
  - 서비스 성격에 맞는 페이지네이션을 선택하는 기준을 얻는다
</Note>

## 두 가지 페이지네이션

페이지네이션은 <E>정렬된 결과 집합을 N개씩 잘라 순차적으로 반환하는</E> 문제입니다. <E>다음 페이지</E>를 어떻게 정의하느냐에 따라 두 가지 근본 방식이 나뉩니다.

**OFFSET/LIMIT** (= Page-Number Pagination)은 <E>정렬된 결과의 M번째부터 N개를 달라</E>고 요청합니다. 클라이언트는 `page=3, size=20` 같은 페이지 번호만 관리하면 되고, 임의의 페이지로 점프하는 것이 자연스럽습니다.

**Cursor 기반** (= Keyset Pagination · Seek Method)은 <E>마지막으로 본 행의 정렬 키 값을 보낼 테니, 그보다 뒤에 있는 N개를 달라</E>고 요청합니다. 페이지 번호 대신 **커서**(직전 페이지 마지막 항목의 정렬 키)를 전달합니다.

<Tabs group="pagination-style">
  <Tab label="OFFSET/LIMIT">
    ```sql title="offset.sql"
    SELECT id, title, created_at FROM posts
    ORDER BY created_at DESC
    LIMIT 20 OFFSET 40;
    ```
  </Tab>
  <Tab label="Cursor (Keyset)">
    ```sql title="cursor.sql"
    SELECT id, title, created_at FROM posts
    WHERE created_at < '2026-04-20 10:00:00'
    ORDER BY created_at DESC
    LIMIT 20;
    ```
  </Tab>
</Tabs>

두 방식의 근본 차이는 한 문장으로 요약됩니다. **OFFSET은 <E>순번</E>으로 위치를 지정하고, Cursor는 <E>값</E>으로 위치를 지정합니다.** 이 차이에서 성능·일관성·UX의 모든 트레이드오프가 파생됩니다.

<Callout type="warning" title="Cursor는 단순히 id를 쓰는 것이 아니다">
  `WHERE id > ?` 패턴도 Cursor의 한 형태지만, **정렬 키와 커서 키가 일치해야** 합니다. `ORDER BY created_at`인데 커서로 `id`를 쓰면 페이지 경계가 정렬과 어긋나 중복·누락이 발생합니다. 이유는 동작 원리 섹션에서 다룹니다.
</Callout>

## 왜 Cursor가 필요한가

OFFSET/LIMIT은 페이지 번호 UI와 직관적으로 맞물려 오랫동안 표준이었습니다. 그런데 데이터가 커지고 트래픽이 몰리면서 OFFSET은 세 가지 구조적 한계를 드러냈습니다.

### 1. Deep page 문제

`OFFSET 100000 LIMIT 20`을 실행하면, DB는 **100020개 행을 읽은 뒤 앞의 100000개를 버리고** 뒤 20개만 반환합니다. 이건 엔진이 게으른 것이 아니라 OFFSET의 의미론 자체가 그렇게 동작하도록 만듭니다. 정렬된 결과의 M+N번째까지 실제로 읽어야 M번째 위치를 <E>알 수 있기</E> 때문입니다.

결과적으로 1페이지는 5ms에 끝나도, 5000페이지는 수백 ms에서 수 초까지 걸립니다. **페이지 번호에 선형 비례해서 느려지는 것이 OFFSET의 본질적 한계**입니다.

### 2. 동시 쓰기 일관성 문제

페이지를 순차적으로 넘기는 동안 데이터가 앞쪽에 추가되거나 삭제되면, OFFSET이 가리키는 <E>위치</E>가 밀립니다.

사용자가 1페이지(최신 20개)를 본 뒤 새 글 5개가 올라왔다고 합시다. 사용자가 2페이지를 요청하면 OFFSET이 20이지만, 새 글 5개가 앞으로 들어왔기 때문에 **1페이지에서 본 마지막 5개가 2페이지에 또 나타납니다**. 반대로 삭제가 일어나면 5개를 건너뜁니다. 버그가 아니라 OFFSET의 의미론이 그렇습니다.

Cursor는 <E>마지막으로 본 항목 뒤</E>를 값으로 지정하므로, 중간에 데이터가 추가되거나 삭제돼도 중복·누락이 발생하지 않습니다.

### 3. 무한 스크롤 UX와의 불일치

현대 앱(Twitter, Instagram, GitHub, Slack)은 대부분 <E>다음 페이지로</E>가 아니라 <E>아래로 스크롤하면 더 불러오기</E> 방식입니다. 이런 UX에는 페이지 번호가 없고 <E>마지막으로 본 항목 뒤 N개</E>만 필요합니다. Cursor가 이 요구에 정확히 맞습니다.

반대로 OFFSET/LIMIT은 <E>검색 결과 245페이지 중 3페이지</E> 같은 **페이지 번호 UI가 필요한 환경**(관리자 페이지, 리포트, 구식 게시판)에서는 여전히 자연스럽습니다.

## 동작 원리

이 섹션이 글의 중심입니다. OFFSET과 Cursor가 겉보기엔 한두 줄 차이지만, DB 엔진이 실행하는 실제 작업 단계가 다릅니다.

<Callout type="warning" title="이 구조를 이해하는 핵심">
  B+Tree 인덱스는 <E>N번째 행이 어디에 있는지</E>를 저장하지 않습니다. 인덱스 리프 노드는 `(정렬키, 레코드 포인터)` 쌍의 연결 리스트일 뿐, 순번 메타데이터가 없습니다. 이 단일 제약이 OFFSET과 Cursor의 성능 차이를 강제합니다.
</Callout>

### OFFSET은 왜 선형으로 느려지는가

`ORDER BY created_at DESC LIMIT 20 OFFSET 100000`을 실행하면 DB는 세 단계를 거칩니다.

1. **정렬 순서대로 행을 읽는다.** `created_at` 인덱스가 있다면 리프 노드를 순차적으로 탐색. 없으면 전체 테이블을 읽고 정렬 단계를 거칩니다.
2. **건너뛸 개수(OFFSET)만큼 버린다.** 읽긴 했지만 반환하지 않고 카운터를 증가시킵니다.
3. **그 다음 20개를 반환한다(LIMIT).**

핵심은 2단계를 DB가 skip할 수 없다는 점입니다. 왜 그럴까요? 인덱스의 리프 노드는 `(정렬키, 레코드 포인터)` 쌍의 연결 리스트일 뿐, <E>이 키가 전체에서 100001번째</E>라는 순번 메타데이터를 들고 있지 않습니다. 따라서 DB는 100001번째 항목의 값을 알려면 1번부터 100000번까지 실제로 읽어내려가야 합니다.

<Callout type="error" title="핵심 통찰: OFFSET은 자료구조가 아니라 의미론이 결정한 비용이다">
  인덱스를 아무리 잘 설계해도 OFFSET의 선형성은 사라지지 않습니다. <E>M개를 건너뛰고 그 다음 N개를 반환하라</E>는 의미론 자체가 M번째까지의 실제 순회를 요구하기 때문입니다. 선형성을 벗어나려면 질의 방식을 바꿔야 하며, 그 대안이 바로 Cursor입니다.
</Callout>

이 동작을 시각적으로 보면 차이가 명확합니다. 정렬된 행 50개에서 OFFSET=30, LIMIT=10으로 가져올 때, OFFSET 방식은 앞 30개를 읽고 버리는 반면 Cursor는 시작 위치로 바로 점프해 10개만 읽습니다.

더 나쁜 경우는 커버링 인덱스가 없어서 매 행마다 테이블 데이터 페이지에 랜덤 I/O를 일으켜야 할 때입니다. OFFSET 100000이 단순 선형을 넘어서 디스크 헤드를 10만 번 움직이는 비용이 되고, 옵티마이저는 때로 인덱스를 포기하고 Full Table Scan으로 수렴합니다.

### Cursor는 왜 일정 시간으로 수렴하는가

`WHERE created_at < '2026-04-20 10:00:00' ORDER BY created_at DESC LIMIT 20`의 실행은 두 단계입니다.

1. **B+Tree 인덱스 seek.** `created_at`이 지정한 값보다 작은 첫 리프 위치를 B+Tree 탐색으로 한 번에 찾습니다. $O(\log N)$.
2. **리프 노드를 순차적으로 20개 읽는다.** 리프 노드들은 이중 연결 리스트로 이어져 있으므로, 다음 20개를 읽는 건 $O(\text{LIMIT})$.

**버리는 단계가 없습니다.** Cursor가 제공한 값이 <E>여기부터 시작</E>을 정확히 알려주기 때문입니다. 1페이지든 10000페이지든 동일한 시간에 끝납니다. B+Tree 구조 자체가 낯설다면 먼저 아래 글을 읽어보세요.

### 정렬 키와 커서 키가 일치해야 하는 이유

Cursor 구현에서 가장 흔한 실수는 정렬 키와 커서 키를 다르게 두는 것입니다. 아래 두 쿼리 중 왼쪽은 틀렸습니다.

<Tabs group="cursor-sort-key">
  <Tab label="잘못된 구현">
    ```sql title="anti-pattern.sql"
    SELECT id, title, created_at FROM posts
    WHERE id < ?
    ORDER BY created_at DESC
    LIMIT 20;
    ```
  </Tab>
  <Tab label="올바른 구현">
    ```sql title="correct.sql"
    SELECT id, title, created_at FROM posts
    WHERE created_at < ?
    ORDER BY created_at DESC
    LIMIT 20;
    ```
  </Tab>
</Tabs>

왼쪽이 왜 틀릴까요? `id`의 순서와 `created_at`의 순서가 일치하지 않으면, <E>커서 값보다 큰 id</E>가 <E>커서 값보다 최근의 created_at</E>과 전혀 무관합니다. 결과적으로 페이지 경계가 정렬과 어긋나 일부 행이 중복되거나 누락됩니다. 오른쪽처럼 정렬 키와 커서 키가 같아야 페이지 경계가 올바르게 잡힙니다.

### 동일 정렬 키 값 처리 (Tiebreaker)

`created_at`이 밀리초 단위면 두 행의 값이 같을 확률이 생각보다 높습니다. 그러면 `WHERE created_at < ?`로 정확히 그 값을 가진 행들이 누락될 수 있고, `<=`로 바꾸면 중복이 생깁니다.

해법은 **복합 키 커서**입니다. 정렬도 복합, 커서도 복합으로 맞춥니다. `(a, b) < (x, y)`는 lexicographic 튜플 비교로 `a < x OR (a = x AND b < y)`와 동등합니다. Postgres는 이 튜플 문법을 네이티브로 지원하지만, MySQL은 OR 조건을 풀어서 써야 합니다.

<Tabs group="sql-dialect">
  <Tab label="Postgres">
    ```sql title="composite-cursor.sql"
    -- 정렬: (created_at DESC, id DESC)
    -- 커서: 직전 페이지 마지막 항목의 (created_at, id)
    SELECT id, title, created_at FROM posts
    WHERE (created_at, id) < (?, ?)
    ORDER BY created_at DESC, id DESC
    LIMIT 20;
    ```
  </Tab>
  <Tab label="MySQL">
    ```sql title="composite-cursor.sql"
    SELECT id, title, created_at FROM posts
    WHERE created_at < ?
       OR (created_at = ? AND id < ?)
    ORDER BY created_at DESC, id DESC
    LIMIT 20;
    ```
  </Tab>
</Tabs>

이렇게 하면 `created_at`이 같더라도 `id`로 tiebreak되어 순서가 완전히 결정됩니다.

### 커서 토큰 설계

커서 값을 그대로 클라이언트에 노출하면 두 가지 문제가 생깁니다. 첫째, 내부 컬럼 구조가 API에 드러나 스키마를 바꾸면 호환성이 깨집니다. 둘째, 클라이언트가 임의로 조작해 이상한 결과를 요청할 수 있습니다.

실무에서는 커서를 Base64로 인코딩하거나 HMAC 서명을 붙여 **불투명 토큰**으로 만듭니다.

```ts title="cursor-token.ts"
import crypto from 'node:crypto'

interface Cursor {
  c: string  // created_at ISO
  i: number  // id
}

const SECRET = process.env.CURSOR_SECRET!

export function encode(cursor: Cursor): string {
  const payload = Buffer.from(JSON.stringify(cursor)).toString('base64url')
  const sig = crypto.createHmac('sha256', SECRET).update(payload).digest('base64url').slice(0, 16)
  return `${payload}.${sig}`                                                   // [!code highlight]
}

export function decode(token: string): Cursor {
  const [payload, sig] = token.split('.')
  const expected = crypto.createHmac('sha256', SECRET).update(payload).digest('base64url').slice(0, 16)
  if (sig !== expected) throw new Error('Invalid cursor')
  return JSON.parse(Buffer.from(payload, 'base64url').toString('utf8'))
}
```

클라이언트는 <E>이 토큰을 그대로 돌려주라</E>는 규칙만 알면 됩니다. 내부 컬럼이 바뀌거나 정렬 키가 추가돼도 토큰 스펙만 유지하면 API 호환성이 깨지지 않습니다.

## 언제 무엇을 쓰는가

<E>무조건 Cursor가 낫다</E>는 결론이 흔하지만, 실전에서 두 방식은 서로 다른 요구에 최적화된 도구입니다. 결정을 좌우하는 세 축을 정리합니다.

### 데이터 규모와 페이지 깊이

- **작은 데이터, 얕은 페이지** (수천에서 수만 행, 대부분 1에서 10페이지): OFFSET으로 충분. 복잡도를 올릴 이유가 없습니다.
- **큰 데이터, deep page 가능성** (수십만 행 이상, 사용자가 100페이지 이상 자주 요청): Cursor 필수. OFFSET은 선형으로 무너집니다.

### UX 요구

- **페이지 번호가 필수** (관리자 리포트, 구식 게시판, <E>전체 245페이지 중</E>): OFFSET. Cursor로 페이지 번호를 흉내 내려면 매번 COUNT 쿼리가 필요해 오히려 비효율입니다.
- **무한 스크롤 · <E>더 보기</E>** (SNS 피드, 채팅 기록, 알림, 타임라인): Cursor. 페이지 번호 자체가 UI에 없습니다.
- **랜덤 점프 필요** (<E>50페이지로 바로 가기</E>): OFFSET. Cursor는 임의 위치 점프가 구조적으로 불가능합니다.

### 쓰기 빈도와 일관성 요구

- **쓰기가 드물거나 세션이 짧음** (정적 블로그 아카이브, 일일 리포트): OFFSET. 중복·누락이 실질적으로 안 생깁니다.
- **실시간 쓰기 + 긴 세션** (SNS 피드, 알림 드로어, 채팅): Cursor. <E>방금 본 항목 바로 뒤</E>를 정확히 지정해야 중복·누락이 없습니다.

현실적으로 다음 두 질문이면 대부분 결정됩니다. 첫째, 이 화면에 페이지 번호 UI가 명시적으로 필요한가. 둘째, deep page로 갈 가능성이 있는가 또는 쓰기가 빈번한가. 첫 질문에 <E>예</E>면 OFFSET, 둘째 질문에 <E>예</E>면 Cursor입니다.

### 하이브리드도 가능하다

하나만 고를 필요는 없습니다. 같은 API가 두 방식을 모두 지원할 수 있습니다. GitHub API는 `page=N` 스타일과 Link 헤더 기반 cursor를 함께 제공합니다. 관리자 도구는 OFFSET, 외부 공개 API는 Cursor로 분리하는 구성도 흔합니다.

<Callout type="warning" title="정렬이 자주 바뀌는 환경에서는 Cursor가 오히려 불편하다">
  사용자가 <E>가격순 / 인기순 / 최신순</E>을 토글하는 환경에서는 Cursor가 정렬 키 단위로만 유효하므로, 정렬이 바뀌면 커서가 무효가 됩니다. 매 토글마다 1페이지부터 다시 시작해야 합니다. 이 제약이 UX에 맞지 않으면 OFFSET이 더 낫습니다.
</Callout>

## 트레이드오프

Cursor는 공짜가 아닙니다. 성능을 얻는 대신 치르는 대가가 분명히 있습니다.

**랜덤 점프 불가.** Cursor는 순차 탐색에 최적화돼 있습니다. <E>5페이지로 바로 가기</E>, <E>마지막 페이지로</E>는 구조적으로 불가능합니다. 억지로 구현하려면 OFFSET을 중첩하거나 별도 COUNT 쿼리를 돌려야 해서 성능 이점이 사라집니다. Cursor를 채택하는 순간 UX도 <E>처음으로 / 이전 / 다음 / 더 보기</E>만 있는 형태로 정리됩니다.

**전체 개수를 모른다.** OFFSET은 종종 `SELECT COUNT(*)`를 함께 써서 <E>전체 245페이지 중 3페이지</E> 같은 정보를 제공합니다. Cursor 설계에는 보통 이 COUNT가 없고, 있어도 대용량 테이블에서 COUNT 자체가 또 다른 성능 문제입니다. 현대 앱들은 `has_next_page` 플래그만 제공하고 전체 개수를 감추는 쪽으로 정리됐습니다.

**구현 복잡도.** OFFSET는 `page, size` 두 정수면 끝이지만 Cursor는 정렬 키 확정, tiebreaker 설계, 커서 인코딩, 양방향 페이지(이전 페이지), 만료된 커서 에러 처리까지 신경 쓸 게 많습니다. OFFSET 구현이 10줄이라면 Cursor 구현은 보통 50에서 100줄에 테스트까지 붙습니다.

**정렬 제약.** Cursor를 쓰려면 정렬 키가 인덱스로 커버돼야 합니다. 사용자가 선택 가능한 모든 정렬 옵션마다 인덱스를 준비해야 하고, 인덱스는 쓰기 비용을 증가시킵니다.

**커서 영속성 없음.** 스키마 변경, 정렬 컬럼 제거, 인덱스 재구성 같은 운영 이벤트가 있으면 이전에 발급한 커서가 무효화됩니다. 사용자가 오래된 탭에서 <E>더 보기</E>를 눌렀을 때 깨질 수 있으므로 API 레벨에서 <E>커서 만료 시 400 반환 또는 재시작 안내</E> 같은 처리가 필요합니다.

정리하면 아래 표와 같습니다.

| 축 | OFFSET/LIMIT | Cursor (Keyset) |
|---|---|---|
| Deep page 성능 | $O(\text{OFFSET} + \text{LIMIT})$ 선형 악화 | $O(\log N + \text{LIMIT})$ 일정 |
| 일관성 (쓰기 중) | 중복·누락 발생 | 안정적 |
| 랜덤 점프 | 가능 | 구조적 불가 |
| 전체 개수 | COUNT으로 제공 가능 | 보통 제공 안 함 |
| 구현 복잡도 | 낮음 | 높음 |
| 정렬 유연성 | 자유 | 인덱스 커버 필요 |
| UX 적합도 | 페이지 번호 UI | 무한 스크롤 · 타임라인 |

## 마무리

OFFSET과 Cursor의 차이는 <E>순번 vs 값</E>이라는 한 문장으로 압축됩니다. 이 차이가 deep page에서는 선형 성능 악화 vs 일정 성능으로, 동시 쓰기에서는 중복·누락 vs 안정성으로, UX에서는 페이지 번호 vs 무한 스크롤로 갈라집니다. 성능만 보면 Cursor가 우위지만, 랜덤 점프·전체 개수·구현 복잡도라는 대가를 감당할 수 있어야 하므로 서비스의 성격이 진짜 기준이 됩니다. 이 글을 덮은 뒤 <E>이 화면에 페이지 번호가 필요한가, deep page가 현실적 시나리오인가</E>라는 두 질문을 먼저 떠올릴 수 있다면, 세부 구현은 자연스럽게 따라옵니다.
