감사 필드(`created_at` / `updated_at`)는 도메인의 책임이 아니라 저장소의 책임입니다. 엔티티마다 손으로 `Instant.now()`를 박는 대신, Spring Data JPA가 제공하는 Auditing 기능이 엔티티 lifecycle 콜백 위에서 이 일을 대신해 줍니다. 이 글은 `@EnableJpaAuditing`이 무엇을 배선하는지, `@CreatedDate`와 `@LastModifiedDate`가 정확히 언제 발화하는지를 내부 동작 수준에서 따라갑니다.

<Note title="이 글의 학습 목표">
  - `@EnableJpaAuditing`과 `AuditingEntityListener`가 Spring 컨테이너와 Hibernate 사이를 어떻게 배선하는지 이해한다.
  - `@PrePersist`와 `@PreUpdate`가 각각 언제 발화하는지, 세 가지 실행 경로(`persist` / 변경 감지 / 벌크 UPDATE)가 어떻게 다른지 구분할 수 있다.
  - `updated_at`이 stale이 되는 실전 함정을 피하고, 시간 주입 파이프라인을 커스터마이즈하는 기준을 얻는다.
</Note>

## 개요

### 한 문장 정의

JPA Auditing은 Spring Data JPA가 제공하는 기능으로, 엔티티가 영속화되는 순간 <E>언제 만들어졌는지(`@CreatedDate`)</E>와 <E>언제 마지막으로 수정되었는지(`@LastModifiedDate`)</E>를 자동으로 주입해 줍니다. 작성자까지 함께 추적하려면 `@CreatedBy` / `@LastModifiedBy`도 씁니다.

핵심은 **영속화 시점에 값이 박힌다**는 것입니다. 서비스 레이어에서 `entity.setCreatedAt(Instant.now())`를 손으로 부르는 코드가 사라집니다. 주입은 엔티티 lifecycle 콜백(`@PrePersist`/`@PreUpdate`)이라는 JPA 표준 훅 위에서 일어납니다.

### 손으로 할 때의 문제

감사 필드는 도메인의 책임이 아닙니다. 회원의 이메일이나 판매자의 사업자등록번호는 그 도메인이 관리하지만, `created_at`·`updated_at`은 <E>어느 시각의 상태인가</E>라는 저장소 메타데이터입니다. 그런데 이 필드를 엔티티마다, 서비스마다 손으로 박으면 다음이 망가집니다.

- **누락**: 새 엔티티를 만들 때마다 `createdAt` 세팅을 기억해야 합니다. 엔티티가 열 개면 열 번, 벌크 생성 코드에서는 더 자주 빠집니다.
- **시간 소스 불일치**: 어떤 곳에선 `LocalDateTime.now()`, 어떤 곳에선 `Instant.now()`, 어떤 곳에선 DB의 `NOW()`. 서로 다른 시각이 섞입니다.
- **경계 침범**: `Account.create(email, password)` 같은 도메인 정적 팩토리가 감사 필드까지 인자로 받으면 시그니처가 오염됩니다.

JPA Auditing은 이 셋을 한 번에 정리합니다. 엔티티는 `BaseEntity`를 상속하고, 배선은 `@EnableJpaAuditing` 한 줄로 끝납니다. 시간 주입 지점이 **Spring Data 안쪽 하나**로 수렴합니다.

### 등장인물 네 개

```
@MappedSuperclass       →  필드(컬럼)만 상속시키는 JPA 표준
@EntityListeners        →  lifecycle 콜백을 실은 listener를 엔티티에 묶는 JPA 표준
AuditingEntityListener  →  Spring Data 제공 listener. 실제 주입을 수행
@EnableJpaAuditing      →  위 listener가 Spring 컨테이너의 AuditingHandler를
                           볼 수 있게 배선하는 스위치
```

앞의 두 개는 **JPA 표준**, 뒤의 두 개는 **Spring Data 확장**입니다. 이 구분이 §3 내부 동작을 따라갈 때 결정적으로 중요합니다. JPA 스펙이 열어둔 hook 자리에 Spring Data가 자기 listener를 꽂는 구조입니다.

## 기능 및 사용법

### 기본 3단 구성

세 곳에 표시만 달면 끝납니다.

1. **엔티티**에 `@EntityListeners(AuditingEntityListener.class)`
2. **필드**에 `@CreatedDate` / `@LastModifiedDate`
3. **설정 클래스**에 `@EnableJpaAuditing`

```java title="Article.java"
@Entity
@EntityListeners(AuditingEntityListener.class)
public class Article {

    @Id @GeneratedValue
    private Long id;

    private String title;

    @CreatedDate
    @Column(updatable = false)
    private Instant createdAt;

    @LastModifiedDate
    private Instant updatedAt;
}
```

```java title="JpaConfig.java"
@Configuration
@EnableJpaAuditing
public class JpaConfig {
}
```

이걸로 `articleRepository.save(article)` 한 번에 두 필드가 자동으로 채워집니다. 필드 타입은 `Instant`, `LocalDateTime`, `Long`(epoch milli) 모두 허용됩니다. 타입 선택의 근거(특히 `Instant` vs `LocalDateTime`)는 별도 글에서 더 다룰 예정입니다.

`@Column(updatable = false)`를 `createdAt`에만 다는 관용이 있습니다. 한 번 박힌 생성 시각을 UPDATE 경로가 실수로 덮어쓰는 걸 막기 위한 컬럼 레벨 방어입니다.

### 작성자 추적

시간만이 아니라 <E>누가 만들었나</E>도 같이 추적할 수 있습니다. 두 가지가 더 필요합니다.

1. 필드에 `@CreatedBy` / `@LastModifiedBy`
2. `AuditorAware<T>` 빈 등록. Spring Data가 이 빈에 <E>지금 누구냐</E>를 물어봅니다.

```java title="AuditorAware 빈 예시"
@Bean
public AuditorAware<Long> auditorProvider() {
    return () -> Optional.ofNullable(SecurityContextHolder.getContext())
        .map(SecurityContext::getAuthentication)
        .filter(Authentication::isAuthenticated)
        .map(Authentication::getPrincipal)
        .filter(UserPrincipal.class::isInstance)
        .map(UserPrincipal.class::cast)
        .map(UserPrincipal::getUserId);
}
```

`AuditorAware<T>`의 `T`는 엔티티 필드 타입과 일치해야 합니다. 구체적 값은 인증 구현에 따라 다릅니다. Spring Security라면 `SecurityContextHolder`, 세션 기반이라면 `HttpSession` 또는 스레드 로컬에서 꺼냅니다.

로그인 전 요청에서 엔티티가 만들어지는 경로(비회원 문의 등)에서는 `Optional.empty()`를 돌려줘야 합니다. Spring Data는 `empty()`를 받으면 필드에 `null`을 둡니다.

### BaseEntity 관용 패턴

`@EntityListeners(AuditingEntityListener.class)`를 엔티티마다 다는 건 반복입니다. 공통 상위 클래스로 뽑는 것이 관용입니다.

```java title="BaseEntity.java"
@Getter
@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public abstract class BaseEntity {

    @CreatedDate
    @Column(name = "created_at", nullable = false, updatable = false)
    private Instant createdAt;

    @LastModifiedDate
    @Column(name = "updated_at", nullable = false)
    private Instant updatedAt;
}
```

자식 엔티티는 상속 한 줄이면 두 컬럼이 자기 테이블에 병합됩니다.

```java
@Entity
public class Account extends BaseEntity {
    @Id @GeneratedValue
    private Long id;
    private String email;
    // createdAt / updatedAt은 BaseEntity에서 상속
}
```

`@MappedSuperclass`는 <E>이 클래스는 테이블이 없고 필드만 자식에게 상속시킨다</E>는 선언입니다. `@Inheritance(strategy=JOINED)` 같은 테이블 상속과 **완전히 다른 축**이라는 점이 중요합니다. JPA Auditing 관용 패턴에서는 언제나 `@MappedSuperclass`만 씁니다.

### 전역 등록 방식

`@EntityListeners`를 모든 엔티티(또는 `BaseEntity`)에 다는 게 싫다면 `persistence-unit` 레벨에서 기본 listener로 선언할 수 있습니다.

```xml title="META-INF/orm.xml"
<entity-mappings xmlns="https://jakarta.ee/xml/ns/persistence/orm" version="3.0">
    <persistence-unit-metadata>
        <persistence-unit-defaults>
            <entity-listeners>
                <entity-listener class="org.springframework.data.jpa.domain.support.AuditingEntityListener"/>
            </entity-listeners>
        </persistence-unit-defaults>
    </persistence-unit-metadata>
</entity-mappings>
```

장점은 엔티티 코드가 깨끗해지는 것. 단점은 <E>이 엔티티가 audit 대상인가</E>가 코드에서 즉시 드러나지 않는 것입니다. 실전에서는 `BaseEntity` 방식이 코드 측 가시성 때문에 더 자주 선택됩니다.

### 시간 소스 커스터마이즈

기본은 JVM의 시스템 clock입니다. 이걸 교체해야 하는 실전 사례는 두 가지입니다.

1. **테스트에서 시각 고정**: 통합 테스트에서 `createdAt`이 정확히 특정 시각이어야 한다는 검증이 필요할 때.
2. **DB의 현재 시각 사용**: 여러 JVM 인스턴스 사이에 시계 오차가 의심되면 앱이 아니라 DB의 `NOW()`를 권위 소스로 삼고 싶을 수 있습니다.

```java title="테스트용 고정 Clock"
@Bean
public DateTimeProvider fixedClockProvider() {
    Clock fixed = Clock.fixed(Instant.parse("2026-04-22T00:00:00Z"), ZoneOffset.UTC);
    return () -> Optional.of(OffsetDateTime.now(fixed));
}

@Configuration
@EnableJpaAuditing(dateTimeProviderRef = "fixedClockProvider")
public class TestJpaConfig { }
```

`DateTimeProvider.getNow()`의 반환 타입은 `Optional<TemporalAccessor>`입니다. 무엇을 돌려주든 Spring Data가 엔티티 필드 타입으로 변환합니다. 이 변환 메커니즘은 다음 섹션에서 풀이합니다.

## 내부 동작

<Callout type="warning" title="이 섹션의 핵심 포인트">
  `@CreatedDate`와 `@LastModifiedDate`는 **`save()` 호출 시점이 아니라 Hibernate가 실제로 SQL을 내보낼 때** 값이 박힙니다. 이 미묘한 차이가 벌크 UPDATE 우회, 변경 없는 `save`, 타임존 오차 같은 실전 함정의 근원입니다.
</Callout>

### 부팅 시 배선

`@EnableJpaAuditing` 한 줄이 무엇을 연결하는지가 이 섹션의 출발점입니다. 이 애노테이션은 `JpaAuditingRegistrar`라는 `ImportBeanDefinitionRegistrar`를 import합니다. 그 registrar가 애플리케이션 시작 시점에 **두 개의 빈을 등록**합니다.

```
@EnableJpaAuditing
    └─ imports JpaAuditingRegistrar
          ├─ registers  AuditingHandler                    (실제 주입을 수행하는 워커)
          └─ registers  AuditingBeanFactoryPostProcessor   (listener ↔ 핸들러 배선)
```

`AuditingEntityListener` 자체는 JPA가 만드는 객체입니다. JPA 스펙상 `@EntityListeners`에 선언된 클래스는 JPA 프로바이더(Hibernate)가 기본 생성자로 인스턴스화합니다. 그렇게 만들어진 listener 객체는 Spring 컨테이너를 전혀 모르는 상태이므로, 그 상태로는 `AuditingHandler`를 볼 방법이 없습니다. 여기서 `AuditingBeanFactoryPostProcessor`가 개입합니다.

이 후처리기는 다음 두 가지를 배선합니다.

1. `AuditingEntityListener`를 **Spring 빈 정의로 등록**합니다. 이로써 listener 인스턴스가 Spring 컨테이너를 거쳐 생성될 수 있게 됩니다.
2. Hibernate에게 <E>listener를 만들 때 Spring 컨테이너를 사용하라</E>고 지시하는 연결(`SpringBeanContainer`)이 활성화됩니다. Spring Boot는 `HibernatePropertiesCustomizer`로 이 연결을 자동 구성합니다.

결과적으로 Hibernate가 listener를 새로 찍을 때마다 Spring이 개입해 `ObjectFactory<AuditingHandler>`를 setter로 주입합니다. listener는 핸들러 참조를 들고 런타임에 진입합니다.

`@EnableJpaAuditing`을 빠뜨리면 이 모든 배선이 걸리지 않습니다. `AuditingEntityListener`는 JPA가 콜백은 부를지 몰라도, 내부 핸들러 참조가 없어 아무 필드도 채우지 못합니다. 예외도 로그도 없이 `createdAt`이 `null`로 남습니다. 이게 실전에서 가장 흔한 <E>조용한 실패</E> 모드입니다.

### 실행 경로 세 갈래

listener 입장에서 엔티티는 **세 가지 경로**로 DB에 도달합니다. 각 경로에서 audit 필드의 운명이 다릅니다.

**경로 A: `persist` (신규 INSERT)**

```
em.persist(account)
    ↓
(entity state = NEW → MANAGED 전이 직전)
    ↓
Hibernate fires @PrePersist callbacks
    ↓
AuditingEntityListener.touchForCreate(target)
    ↓
AuditingHandler.markCreated(target)
    ├─  @CreatedDate  필드에 now 세팅
    └─  @LastModifiedDate 필드에도 같은 now 세팅
    ↓
persistence context에 MANAGED 상태로 등록
    ↓
(flush 시점에 SQL INSERT)
```

핵심은 **`@PrePersist`가 INSERT 시점이 아니라 `persist()` 호출 시점에 발화**한다는 것. 그리고 이 경로에서 `createdAt`과 `updatedAt`이 **같은 값으로 함께 세팅**됩니다. <E>신규 생성 엔티티는 `updatedAt`이 `null`일 것</E>이라는 가정은 틀립니다.

**경로 B: 변경 감지 (UPDATE)**

```
(managed 엔티티의 필드를 코드에서 수정)
    ↓
트랜잭션 commit / em.flush()
    ↓
Hibernate dirty checking → "이 엔티티 바뀜"
    ↓
fires @PreUpdate callbacks
    ↓
AuditingEntityListener.touchForUpdate(target)
    ↓
AuditingHandler.markModified(target)
    └─  @LastModifiedDate 필드에만 now 세팅
    ↓
SQL UPDATE
```

`@PreUpdate`는 **flush 시점에 dirty checking을 통과한 엔티티에 대해서만** 발화합니다.

**경로 C: 벌크 UPDATE (콜백 우회)**

```java
@Modifying
@Query("UPDATE Account a SET a.emailVerified = true WHERE a.id IN :ids")
int markVerified(@Param("ids") List<Long> ids);
```

```
JPQL UPDATE 실행
    ↓
(persistence context를 거치지 않음)
    ↓
곧바로 SQL UPDATE
    ↓
@PreUpdate 발화 안 함
    ↓
updated_at 그대로 (stale)
```

이 경로는 listener 세계와 **완전히 무관**합니다. JPQL이든 native query든 벌크 UPDATE는 JPA의 엔티티 생명주기를 우회해 바로 SQL을 내보냅니다.

<Callout type="error" title="핵심 통찰: updated_at은 호출 시점이 아니라 DB 쓰기 시점을 기록한다">
  Auditing의 계약은 <E>엔티티를 수정하면 시각이 올라간다</E>가 아니라 <E>**Hibernate가 실제로 UPDATE를 내보내면** 시각이 올라간다</E>입니다. 평소에는 두 기준이 겹치기 때문에 이 차이가 드러나지 않지만, 변경 없는 `save()`, 벌크 UPDATE, readonly 트랜잭션 경계에서 그 차이가 갈라집니다.
</Callout>

### 값이 언제 박히는가

경로 A와 B의 발화 시점 차이는 JPA 스펙이 규정합니다. 표로 정리하면 다음과 같습니다.

| 시점 | `@PrePersist` | `@PreUpdate` |
|---|---|---|
| 호출 순간 | `em.persist()` 내부 | `em.flush()` 직전 (트랜잭션 commit 포함) |
| 엔티티 상태 | NEW → MANAGED 전이 직전 | MANAGED, dirty checking 통과 |
| 발화 조건 | `persist()` 혹은 그 cascade | flush 시점 dirty 필드 존재 |
| 발화 안 하는 조건 | 없음(`persist`를 부르면 무조건) | dirty 필드 없음, readonly 트랜잭션, 벌크 UPDATE |

<E>`save()`를 부르면 `updatedAt`이 갱신된다</E>는 가정은 대체로 맞지만, **엄밀히 말해서 틀립니다**. Spring Data JPA의 `SimpleJpaRepository.save(entity)`는 내부에서 `entityInformation.isNew(entity)`를 봅니다.

- `isNew()`가 true면 `em.persist()` → 경로 A (`@PrePersist` 발화, `createdAt`/`updatedAt` 둘 다 세팅)
- `isNew()`가 false면 `em.merge()` → merged 엔티티가 managed 상태로 들어오고, flush 시점에 dirty 검사 수행

후자에서 변경된 필드가 하나도 없으면 `@PreUpdate`는 **발화하지 않습니다**. 이 지점이 경로 B와 함께 앞의 핵심 통찰을 정당화합니다. audit는 <E>`save()` 호출 횟수</E>가 아니라 <E>**Hibernate가 실제로 UPDATE를 내보내는 순간**</E>을 기준으로 움직입니다.

### 시간 소스 파이프라인

`AuditingHandler.markCreated(target)` 안으로 한 발 더 들어가 보겠습니다. 핵심 로직은 다음 두 단계입니다.

1. **시간 획득**: `dateTimeProvider.getNow()` 호출. 반환 타입은 `Optional<TemporalAccessor>`.
2. **필드 주입**: 획득한 `TemporalAccessor`를 엔티티의 audit 필드 타입(`Instant` / `LocalDateTime` / `Long` 등)으로 변환해 리플렉션으로 세팅.

```
AuditingHandler.markCreated(target)
    ↓
dateTimeProvider.getNow()
    → Optional<TemporalAccessor>   (기본: LocalDateTime.now())
    ↓
AuditableBeanWrapper로 target의 audit 필드 발견
    ↓
필드 타입에 맞춰 TemporalAccessor 변환
    ├─ LocalDateTime → 그대로
    ├─ Instant       → zone 기반 변환
    └─ Long          → epoch milli
    ↓
필드에 reflective set
```

`DateTimeProvider`는 인터페이스입니다. 기본 구현은 `CurrentDateTimeProvider`이고 `LocalDateTime.now()`를 돌려줍니다. `@EnableJpaAuditing(dateTimeProviderRef = "myProvider")`로 교체할 수 있다는 것이 앞 섹션에서 본 커스터마이즈 훅입니다.

필드 타입과 provider 반환 타입이 다를 때의 변환 경로가 미묘합니다. 기본 provider가 `LocalDateTime`을 돌려주는데 엔티티 필드가 `Instant`면, 변환 시점에 **시스템 기본 타임존**이 개입합니다. 이 경계에서 생기는 이슈는 바로 다음 소절에서 다룹니다.

### 실전 함정

배선과 실행 흐름을 이해하면 다음 세 가지가 같은 뿌리의 증상이라는 게 보입니다. 공통점은 <E>`save()`만 부르면 알아서 될 것</E>이라는 기대가 깨지는 경계에 있다는 것입니다.

**(1) 벌크 UPDATE의 `updated_at` stale**

경로 C의 증상입니다. `@Modifying` JPQL이나 native UPDATE는 listener를 타지 않습니다. 이 한 번의 호출로 수천 건의 필드가 바뀌어도 `updated_at`은 움직이지 않습니다. 캐시 invalidation이나 외부 동기화를 `updated_at` 기준으로 돌리고 있다면, 이런 벌크 연산이 데이터를 조용히 과거에 묶어둡니다.

해결은 두 가지. 쿼리 안에서 직접 `SET updated_at = :now`를 넣거나, 건수가 크지 않으면 엔티티 로드 후 수정 → flush 경로로 바꾸는 것입니다.

```java
@Modifying
@Query("UPDATE Account a SET a.emailVerified = true, a.updatedAt = :now WHERE a.id IN :ids")
int markVerified(@Param("ids") List<Long> ids, @Param("now") Instant now);
```

**(2) 변경 없는 `save()`가 `updatedAt`을 안 올림**

`@PreUpdate`는 dirty checking이 **실제 변경**을 찾은 엔티티에만 발화합니다. 불러와서 아무 필드도 바꾸지 않고 `save()`를 다시 부르면 UPDATE SQL 자체가 나가지 않습니다. <E>무언가 찍혔다는 사실</E>을 기록하려고 `updatedAt`을 강제로 올리고 싶다면 의도적으로 dummy 필드를 건드려야 합니다.

이건 버그가 아니라 정의의 문제입니다. `updatedAt`은 <E>`save()` 호출 횟수</E>가 아니라 <E>**Hibernate가 실제로 UPDATE를 내보낸 순간**</E>을 기록합니다. 애초부터 그게 약속이었습니다.

**(3) DateTimeProvider 타입 변환이 시스템 기본 타임존을 끌어온다**

기본 `CurrentDateTimeProvider`는 `LocalDateTime`(타임존 없는 벽시계)을 돌려줍니다. 엔티티 필드가 `Instant`(UTC 절대 시각)면 Spring Data가 변환을 수행하는데, 이 변환 경로에 타임존 정보가 필요합니다. 결국 **JVM의 시스템 기본 타임존**(`user.timezone` 또는 OS 로케일)이 개입합니다.

앱 컨테이너를 UTC로 띄웠는지 `Asia/Seoul`로 띄웠는지에 따라 같은 코드가 **9시간 차이 나는 값을 저장**할 수 있습니다. `Instant.now()` 한 줄로 끝나는 것이 아닙니다.

대응은 두 가지. 배포 환경의 TZ를 명시적으로 고정(`-Duser.timezone=UTC`)하거나, 커스텀 `DateTimeProvider`를 만들어 zone을 못 박은 `Instant`를 직접 돌려주는 것입니다.

```java
@Bean
public DateTimeProvider utcInstantProvider() {
    return () -> Optional.of(Instant.now());
}
```

타임존 자체의 선택 근거(왜 `Instant`를 골라야 하는지, `LocalDateTime`은 언제 적합한지)는 별도 글에서 다룰 예정입니다.

## 마무리

JPA Auditing은 <E>엔티티 lifecycle 콜백 위에 올라탄 얇은 자동화</E>입니다. 그래서 콜백이 발화하는 지점에서만 작동하고, 콜백을 우회하는 모든 경로(벌크 UPDATE, 변경 없는 `save`)에서 침묵합니다. 이 단순한 계약을 기억하면 실전에서 만나는 대부분의 함정이 같은 뿌리의 증상으로 읽힙니다.

배선은 `@EnableJpaAuditing` 한 줄이면 끝이지만, 그 한 줄 뒤에는 `JpaAuditingRegistrar` → `AuditingBeanFactoryPostProcessor` → `SpringBeanContainer` → Hibernate listener 인스턴스화까지의 긴 체인이 있습니다. 이 체인이 성립한다는 전제를 이해하면, `createdAt`이 조용히 `null`로 남는 순간에도 어디를 먼저 의심해야 할지가 자명해집니다.
