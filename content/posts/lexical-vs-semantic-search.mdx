검색 엔진이 <E>관련 있는 문서</E>를 뽑아주는 방식은 겉보기에 하나의 문제처럼 보이지만, 실제로는 서로 다른 두 축에서 풀립니다. 하나는 쿼리 토큰이 문서에 글자 그대로 등장하는지 보는 Lexical, 다른 하나는 쿼리와 문서를 벡터로 바꿔 의미적 거리를 재는 Semantic입니다. 이 글은 두 축의 내부 메커니즘과 한계, 그리고 둘을 결합할 때 왜 RRF가 기본 선택지가 되는지 정리합니다.

## 두 축의 정의

Lexical search는 쿼리 토큰이 문서 안에 **문자 단위로** 등장하는지를 기준으로 관련성을 계산합니다. <E>결제</E>라는 토큰이 문서에 몇 번 나오는지(Term Frequency), 그 단어가 전체 코퍼스에서 얼마나 드문지(Inverse Document Frequency), 문서 길이가 평균보다 얼마나 긴지 같은 **표면 형태의 통계**로 점수를 매깁니다. Elasticsearch, OpenSearch, Lucene, Solr, PostgreSQL `tsvector`가 모두 이 계열이고, 표준 스코어링 함수는 [BM25](/posts/bm25)입니다.

Semantic search는 쿼리와 문서를 고정 차원 embedding 벡터로 변환한 뒤 **벡터 공간에서의 거리**로 관련성을 계산합니다. <E>노트북</E>과 <E>랩탑</E>은 글자는 완전히 다르지만 잘 학습된 embedding 모델이 둘을 공간상 거의 같은 위치에 매핑해 두었기 때문에 벡터 거리가 가깝게 나옵니다. 표준 저장소는 [Vector Database](/posts/vector-database-primer)(Qdrant, Milvus, pgvector 등)이고, 핵심 연산은 cosine 유사도입니다.

한 축으로 축약하면, **Lexical은 단어의 형태(form)**, **Semantic은 단어의 의미(meaning)**를 봅니다. 도서관에서 책을 찾을 때 제목 철자로 카드 카탈로그를 뒤지는 것이 Lexical, 사서에게 비슷한 주제의 책을 추천받는 것이 Semantic이라고 비유할 수 있습니다. 같은 <E>관련 있는 책</E>을 찾는 일이지만 기준이 다릅니다.

## 왜 둘 다 필요한가

Lexical 단독으로는 **언어의 유연성**을 잡지 못합니다. 사용자가 <E>노트북 배터리가 금방 닳아요</E>라고 물었을 때 FAQ에 <E>랩탑 방전 문제 해결법</E>이라는 문서가 있어도, 두 문장의 공통 토큰이 거의 없어서 BM25 점수가 0에 가깝습니다. 동의어, 패러프레이즈, 언어 혼용, 오타가 섞인 자연어 질의에서 lexical은 본질적으로 문자가 일치한 것만 볼 수 있습니다. 동의어 사전을 수동으로 관리하는 방법도 있지만 도메인이 넓어질수록 유지 비용이 기하급수로 커집니다.

Semantic 단독으로는 **정확한 어휘의 변별력**을 잃습니다. 제품 코드 `XR-7A`, 에러 코드 `E2BIG`, 특정 버전 `iOS 18.2.1` 같은 고유 토큰은 embedding 모델이 의미 있게 분리하지 못합니다. 숫자 `15`와 `16`의 차이, 오타 `postgres`와 `postgrse`의 차이가 벡터 공간에서는 거의 같은 위치로 매핑되기 쉽습니다. 또 embedding은 학습 데이터의 편향을 물려받아 드문 도메인 용어(의료 코드, 법률 조항 번호, 사내 제품명)에서는 거의 무용지물이 됩니다.

결국 두 방식은 서로가 못 푸는 문제를 서로가 푸는 관계입니다. Lexical은 정확한 토큰 일치로, Semantic은 의미적 근접으로 상위에 올리기 때문에 상보적입니다. 이 상호보완성 때문에 Elasticsearch 8.x, OpenSearch, 대부분의 RAG 파이프라인이 기본적으로 **하이브리드** 구조로 설계되어 있고, 실무의 의사결정은 <E>둘 중 어느 쪽</E>이 아니라 <E>둘을 어떻게 결합하는가</E>로 이동합니다.

### Lexical 파이프라인

Lexical 엔진의 핵심 자료구조는 **inverted index**입니다. 문서를 수집할 때 텍스트를 토크나이저에 통과시켜 얻은 각 토큰에 대해 `term → [(doc_id, tf, positions...), ...]` 형태의 **posting list**를 만듭니다. <E>결제</E>라는 토큰이 문서 42, 103, 789에 각각 3번, 1번, 7번 나왔다면 그대로 리스트에 기록됩니다. 이 구조의 강점은 내용이 전부 정수열이라 델타 인코딩과 압축, 병합이 효율적이고, 질의 시 쿼리 토큰들의 posting list만 AND/OR로 결합하면 후보 문서가 결정된다는 것입니다.

```python title="inverted_index.py"
# 개념적 구조. 실제 Lucene posting list는 압축된 정수 스트림
inverted_index = {
    "결제": [(42, 3, [12, 45, 89]), (103, 1, [7]), (789, 7, [3, 14, ...])],
    "실패": [(42, 2, [46, 90]), (201, 5, [...])],
    "로그": [(103, 4, [8, 22, 55, 73]), (789, 1, [31])],
}
```

쿼리가 들어오면 같은 토크나이저로 분해한 뒤 각 토큰의 posting list에서 후보 문서를 모으고, 각 `(쿼리 토큰, 문서)` 쌍에 대해 **BM25 스코어**를 계산해 합산합니다. BM25는 세 가지를 반영합니다. 첫째, 문서 안 토큰 빈도(TF)는 반복될수록 포화 곡선으로 증가해 스팸 문서의 영향을 억제합니다. 둘째, 전체 코퍼스에서 드문 단어일수록 IDF가 높아 변별력에 가중치를 줍니다. 셋째, 문서가 평균보다 길면 길이 정규화로 점수를 조금 깎습니다. 수식 감각과 파라미터 $k_1$, $b$의 디테일은 별도 글에 있습니다.

이 파이프라인의 속도와 한계는 동전의 양면입니다. 수십억 문서 규모에서도 posting list 병합은 수 ms 안에 끝나고, 스코어가 설명 가능해서 어느 토큰이 얼마나 기여했는지 추적할 수 있으며, 오타 없는 고유명사와 제품 코드에는 거의 완벽하게 작동합니다. 대신 토큰 동치가 깨지는 순간, 즉 동의어, 패러프레이즈, 언어 혼용이 섞이면 점수가 급격히 0으로 떨어집니다. 이 빈틈을 Semantic이 메웁니다.

### Semantic 파이프라인

Semantic 파이프라인은 **embedding 모델**로 시작합니다. BERT 계열(Sentence-BERT, bge-m3), OpenAI `text-embedding-3`, Cohere `embed-v3` 같은 모델이 임의 길이 텍스트를 고정 차원 벡터(보통 D = 384, 768, 1024, 3072)로 변환합니다. 이 모델은 <E>의미가 비슷한 문장 쌍은 가깝게, 다른 쌍은 멀게</E> 배치되도록 대조 학습(contrastive learning)으로 훈련되어 있어서, 학습이 잘 된 경우 <E>노트북 배터리</E>와 <E>랩탑 방전</E>이 벡터 공간의 거의 같은 지역에 놓입니다. 문서 수집 시점에 모든 문서를 벡터화해 저장하고, 질의 시점에는 쿼리도 같은 모델로 벡터화합니다. 다른 모델을 쓰면 벡터 공간 자체가 달라 비교가 의미 없습니다.

```python title="semantic_search.py"
# 개념적 흐름. 실제로는 ANN 인덱스가 후보를 미리 좁힘
query_vec = embed("결제 실패 로그")  # → float[768]

scores = [
    (doc.id, cosine_similarity(query_vec, doc.vec))
    for doc in corpus
]
top_k = sorted(scores, key=lambda x: -x[1])[:10]
```

관련성 판단은 벡터 간 거리로 환원됩니다. 세 가지 척도가 표준인데, cosine(방향만), dot product(벡터가 L2-normalize 되어 있으면 cosine과 등가), L2(절대 거리)입니다. 검색 용도에서는 cosine이 가장 흔합니다. 문제는 수십만 ~ 수억 문서와 쿼리 벡터 사이의 거리를 전부 계산하면 단일 질의에 수 초가 걸린다는 것. 그래서 **ANN (Approximate Nearest Neighbor)** 인덱스가 필수이고, HNSW(계층형 그래프를 타고 내려가며 이웃 후보를 좁힘)와 IVF(벡터 공간을 파티션으로 나눠 일부만 스캔)가 대표적입니다. 정확도(recall)를 약간 양보하는 대가로 질의 시간을 $O(\log N)$ 수준으로 끌어내립니다.

이 파이프라인의 강점은 형태가 달라도 의미가 가까우면 상위에 올린다는 것, 그리고 다국어 embedding 모델을 쓰면 한국어 쿼리로 영어 문서를 검색하는 cross-lingual search가 자연스럽게 된다는 것입니다. 약점은 세 가지입니다. 학습 분포를 벗어난 도메인 용어와 제품 코드, 숫자의 변별에 약하고, 문서 수집 시점에 임베딩 API 호출 비용이 들며(대규모 코퍼스에서 무시 못 할 금액), 스코어가 <E>왜 이 문서가 상위인가</E>를 설명하기 어렵습니다.

### Hybrid 결합 (RRF)

두 축을 합치는 가장 쉬운 발상은 <E>점수를 더하자</E>인데, 이는 거의 항상 실패합니다. BM25 스코어는 무제한 양수로 코퍼스 통계에 따라 0.5에서 30까지 출렁이고, cosine 유사도는 $[-1, 1]$ 범위에 보통 0.2 ~ 0.9 사이에 분포합니다. 단순 덧셈은 BM25 쪽이 수치적으로 지배해서 semantic 기여가 노이즈 수준이 됩니다. Min-max 정규화나 z-score로 보정해도 질의마다 분포가 달라 안정되지 않습니다. 즉 스코어 기반 결합은 스케일 문제로 근본이 약합니다.

현업에서 표준으로 자리 잡은 해법이 **RRF (Reciprocal Rank Fusion)**입니다. 각 축에서 top-N을 뽑아 순위(rank)만 쓰고 점수는 버립니다. 공식은 다음과 같습니다.

$$
\text{score}(d) = \sum_{i} \frac{1}{k + \text{rank}_i(d)}
$$

여기서 $\text{rank}_i(d)$는 축 $i$에서 문서 $d$의 순위(1등이면 1), $k$는 60 전후의 상수(논문 기본값)입니다. 예를 들어 lexical에서 3등, semantic에서 7등인 문서는 $\frac{1}{63} + \frac{1}{67} \approx 0.0308$을 받습니다. 핵심은 순위만 쓰므로 스케일 차이가 원천적으로 사라진다는 점입니다. 한 축에만 top-N 안에 있어도 다른 축의 기여가 0이 아니라 <E>순위 밖</E>으로 취급되어 자연스럽게 단일 축 검색보다 보수적인 랭킹이 됩니다.

RRF가 잘 먹히는 이유는 **두 축이 서로 다른 종류의 실수**를 하기 때문입니다. Lexical이 놓친 동의어 쿼리는 semantic이 top-10에 올려주고, semantic이 뭉갠 고유명사 쿼리는 lexical이 top-3에 박아줍니다. 두 오류가 상관되지 않을수록 RRF의 이득이 커집니다. Elasticsearch 8.9+, OpenSearch 2.11+, Vespa, Weaviate가 모두 RRF를 내장 기능으로 제공하고, 파라미터 $k$는 대부분 60으로 두고 거의 안 건드립니다. 가장 안 건드려도 잘 동작하는 랭킹 결합이 RRF의 강점입니다.

## 어디서 쓰는가

**Lexical 단독**이 맞는 상황은 세 조건이 겹칠 때입니다. 첫째, 질의가 고유명사, 제품 코드, 에러 코드 중심인 경우, 즉 사내 로그 검색, 법률 판례 검색, 제품 SKU 조회. 둘째, 임베딩 비용과 지연을 감당할 수 없는 저예산, 저지연 환경. 문서 수집 단계의 GPU 추론 비용과 쿼리당 임베딩 API 호출이 부담스러우면 lexical만으로 충분한 경우가 많습니다. 셋째, 스코어 설명 가능성이 요구사항인 경우, 감사 로그, 규제 대응처럼 <E>왜 이 문서가 상위인지</E> 답해야 할 때 BM25는 토큰별 기여도를 그대로 내려줍니다.

**Semantic 단독**이 맞는 상황은 반대쪽 분포입니다. FAQ 검색, 추천, QnA 봇처럼 자연어 질의의 비중이 압도적이고 사용자가 쓰는 어휘와 문서의 어휘가 자주 어긋나는 경우. 다국어 코퍼스에서 한국어 쿼리로 영어, 일본어 문서까지 동시에 당겨야 할 때도 multilingual embedding 한 벌이 lexical + 동의어 사전 조합보다 훨씬 단순합니다. RAG의 retriever도 의미 유사로 <E>프롬프트에 넣을 chunk</E>를 고르는 일이라 semantic 단독이나 hybrid가 대부분이고 pure lexical은 거의 쓰지 않습니다.

**Hybrid**가 맞는 상황은 실무에서 가장 흔한 기본값입니다. 위 두 분포가 섞여 있을 때, 즉 사용자 질의가 한편으론 자연어(<E>아이들과 놀기 좋은 주말 여행지</E>), 한편으론 고유명사(<E>롯데월드</E>)로 섞여 들어오는 대부분의 서비스 검색, 이커머스 검색, 엔터프라이즈 검색이 여기 해당합니다. RAG 시스템 중에서도 도메인 고유 용어(의료 코드, 법률 조항 번호, 사내 프로젝트명)가 많은 코퍼스는 semantic만으로 recall이 떨어져 hybrid가 사실상 필수입니다. 실질적 판단 기준은 <E>질의 로그에 자연어와 고유 토큰이 섞여 있는가</E>이고, 섞여 있다면 RRF 결합이 기본값입니다.

## 마무리

Lexical과 Semantic은 경쟁 관계가 아니라 **상보 관계**입니다. 자연어 질의가 '형태'와 '의미'로 이중 구조를 가지고 있고, 한 축의 투영만으로는 원본 의도를 복원할 수 없기 때문에 두 축이 필요합니다. Lexical은 형태의 정확 일치로, Semantic은 의미의 근접으로 서로 다른 종류의 실수를 교정하고, RRF는 그 둘을 가장 단순하게 결합하는 접착제입니다.

실무에서 내려야 할 판단은 <E>어느 쪽이 더 좋은가</E>가 아니라 <E>지금 내 질의 로그의 분포가 어느 쪽에 치우쳐 있는가</E>입니다. 고유 토큰이 압도적이면 Lexical만으로도 충분하고, 자연어 비중이 크면 Semantic이 필요하며, 둘이 섞여 있다면 Hybrid가 기본값입니다. 이 축을 의식하고 선택한다면, 검색 품질의 개선은 단일 스코어링 함수를 튜닝하는 일에서 <E>두 축의 상보성을 설계하는</E> 일로 전환됩니다.
