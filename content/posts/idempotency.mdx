Idempotency는 같은 요청을 여러 번 보내도 한 번 보낸 것과 동일한 결과를 보장하는 성질입니다. 단순한 수학 정의에서 출발한 이 개념이 왜 분산 시스템 설계의 핵심 장치가 되는지, 그리고 내부적으로 어떻게 구현되는지를 이 글에서 정리합니다.

## 멱등성이란

수학에서 어떤 연산 $f$가 $f(f(x)) = f(x)$를 만족하면 idempotent라고 부릅니다. 한 번 적용하든 여러 번 적용하든 결과가 같다는 뜻입니다. 예시로는 절댓값 함수 `abs`가 있습니다. `abs(abs(-5)) = abs(-5) = 5`이고, 집합 합집합도 $A \cup A = A$로 동일합니다.

시스템 문맥으로 옮기면 정의가 살짝 달라집니다. <E>같은 요청을 N번 보내도 시스템의 **최종 상태**가 1번 보낸 것과 동일하다</E>는 성질입니다. 주의할 것은 <E>응답이 매번 같아야 한다</E>가 아니라 **상태 변화의 관점에서 한 번만 반영된다**는 점입니다. `DELETE /users/42`를 두 번 보내면 첫 번째는 `204 No Content`, 두 번째는 `404 Not Found`가 올 수 있지만 서버 상태는 <E>users 42가 없음</E>으로 동일하므로 멱등입니다.

<Callout type="warning" title="조회는 멱등 논의의 대상이 아닙니다">
  <E>조회는 서버 상태를 바꾸지 않으니 당연히 멱등</E>은 맞지만, 멱등성이 진짜 필요한 곳은 **상태를 변경하는 쓰기 요청**입니다. 네트워크가 불안정할 때 클라이언트는 요청을 재시도해야 하는데, 재시도가 안전하려면 그 쓰기 연산이 멱등해야 하기 때문입니다. HTTP 스펙이 `PUT`과 `DELETE`를 굳이 멱등으로 규정한 이유가 여기에 있습니다.
</Callout>

## 왜 필요한가

분산 시스템에서 원격 호출의 결과는 세 가지입니다: 성공, 실패, 그리고 <E>불확실</E>. 클라이언트가 성공 응답을 받으면 완료, 실패 응답을 받으면 실패로 확정하면 됩니다. 문제는 세 번째입니다. 요청을 보냈는데 타임아웃이 나거나 커넥션이 끊기거나 응답 패킷이 사라진 경우, 서버가 요청을 받았는지, 처리했는지, 응답을 보냈는데 중간에 소실됐는지를 클라이언트는 알 수 없습니다. 이 <E>불확실</E>이 멱등성이 존재해야 하는 근본 이유입니다.

<RemoteCallOutcomes />

이 <E>불확실</E>을 해결하는 유일한 방법은 재시도입니다. 하지만 재시도는 이미 처리된 요청을 또 처리할 위험을 동반합니다. <E>결제 100만원 요청 → 타임아웃 → 재시도</E> 하면 200만원이 빠져나갈 수 있습니다. 그래서 전 세계 대부분의 메시지 시스템, 큐, HTTP API, RPC 프레임워크가 결국 **at-least-once delivery** 전략으로 수렴했고, 이 중복을 무해하게 만드는 장치가 바로 멱등성입니다.

근거는 두 개의 고전적 결과입니다. Two Generals Problem은 비동기 네트워크에서 두 당사자가 <E>양쪽 다 메시지를 받았다</E>에 확정적으로 합의하는 것이 불가능함을 보입니다. FLP Impossibility는 비동기 환경 + 단 한 노드의 실패 가능성 하에서 deterministic consensus가 불가능함을 증명합니다. 이 두 결과의 실무적 귀결은 분명합니다: exactly-once 전달은 특수 조건에서만 비싸게 가능하고, at-most-once는 데이터 손실을 허용해야 해서 대부분의 비즈니스에서는 at-least-once 전달 + 멱등한 수신측이 사실상 유일한 실무 해법입니다.

<Callout type="info" title="HTTP 메서드와 트랜잭션은 멱등성을 보장하지 않는다">
  HTTP 스펙의 <E>`PUT`은 멱등해야 한다</E>는 규정은 메서드의 의미론적 약속이기 때문에 실제 동작은 서버 구현이 책임집니다. `PUT /counters/42 { increment: 1 }` 같은 구현은 스펙 위반이지만 코드 레벨에서 막아주는 장치가 따로 없습니다. 트랜잭션도 마찬가지입니다. 트랜잭션은 한 요청 안의 원자성을 보장하는 도구이기 때문에, 같은 요청이 두 번 도착했다는 사실 자체는 인지하지 못합니다. 두 트랜잭션 모두 각자의 관점에서는 정상 실행되어 결과가 두 번 반영됩니다. 그래서 멱등성은 메서드나 트랜잭션이 아니라 <E>같은 요청을 식별해 두 번째 처리를 차단하는 별도의 장치</E>(Idempotency-Key, 자연 멱등 설계)로 풀어야 합니다.
</Callout>

## 동작 원리

<Callout type="warning" title="이 구조를 이해하는 핵심">
  멱등성 구현은 현재의 CS 제약(비동기 네트워크에서 <E>양측이 메시지 수신 여부에 합의할 수 없다</E>는 Two Generals Problem) 하에서 필연적인 모습으로 작동합니다. 이 제약을 이해하면 멱등성이 왜 **HTTP 메서드 의미론**, **Idempotency-Key 패턴**, **자연 멱등 설계**라는 세 겹의 레이어로 귀결되는지 자연스럽게 따라옵니다.
</Callout>

<Callout type="error" title="핵심 통찰: 멱등성은 네트워크 불확실성이 강제한 필연이다">
  분산 시스템에서 호출 결과는 성공·실패·불확실 세 가지이고, 불확실을 해결할 유일한 방법은 재시도입니다. 재시도가 가능한 시스템은 at-least-once 전달로 수렴하고, 수신측은 자동으로 <E>중복을 어떻게 무해하게 만들 것인가</E>라는 문제에 마주칩니다. 멱등성은 이 문제의 답이며, 설계 취향이 아니라 CS 제약의 강제 결과입니다.
</Callout>

### 1. HTTP 메서드 의미론

HTTP 스펙은 메서드를 멱등 / 비멱등으로 나눕니다. 왜 이렇게 나뉘는지가 중요합니다.

| 메서드 | 멱등 | 이유 |
|---|---|---|
| `GET`, `HEAD` | ✅ | 상태 변화 없음. <E>safe</E> 속성 |
| `PUT` | ✅ | <E>대체(replace)</E> 의미론. N번 덮어써도 최종 상태 동일 |
| `DELETE` | ✅ | <E>없는 상태</E> 수렴. 두 번째 이후는 no-op |
| `POST` | ❌ | <E>생성(create)</E> 의미론. N번 요청 시 N개 리소스 |
| `PATCH` | ❌ | 증분 연산 허용 (`{balance: balance + 100}`) |

핵심은 **의미론이 구조를 강제한다**는 점입니다. `PUT /users/42 { name: "Alice" }`는 <E>42번을 Alice로 대체</E>라는 의미라서 N번 보내도 최종 상태가 동일합니다. 반면 `POST /users { name: "Alice" }`는 <E>새 리소스 생성</E>이라 서버가 매번 새로 만들기 때문에 N번 보내면 N개가 생깁니다. 어떤 연산이 중복에도 안전한가는 동사의 정의에서 출발합니다.

### 2. Idempotency-Key 패턴

현실의 결제나 주문 생성은 본질적으로 `POST`입니다. <E>주문 하나 생성</E>은 기존 상태를 덮어쓰기가 아니기 때문입니다. 그래서 Stripe, PayPal, AWS 등이 수렴한 패턴이 클라이언트가 요청마다 UUID를 발급해 `Idempotency-Key` 헤더로 보내는 것입니다.

서버 내부 로직은 세 단계입니다.

1. **키 조회**: `SELECT ... FROM idempotency_keys WHERE key = ?`
2. **없으면**: 비즈니스 로직 실행 → 결과와 응답(status + body)을 키에 저장
3. **있으면**: 비즈니스 로직을 건너뛰고 저장된 응답을 그대로 재생(replay)

주의할 것은 3번입니다. <E>멱등 = 상태 변화 한 번</E>뿐 아니라 **응답도 동일하게 재생**해야 클라이언트가 일관되게 동작합니다. 재시도마다 응답 시맨틱이 달라지면 클라이언트 로직이 깨집니다.

<IdempotencyKeyFlow />

```py title="idempotent_charge.py"
def charge(user_id: str, amount: int, idempotency_key: str):
    existing = keys.find(idempotency_key)              # 1. 키 조회
    if existing:
        return existing.response                        # 3. 있으면 replay

    with transaction():                                 # 2. 없으면 처리
        deduct_balance(user_id, amount)
        response = build_response(status=200, body=...)
        keys.insert(idempotency_key, response)          # 상태+응답 동시 커밋 // [!code highlight]
    return response
```

하이라이트된 라인이 핵심입니다. 상태 변경(잔액 차감)과 키 저장이 **같은 트랜잭션**으로 커밋되어야 <E>상태는 변했는데 응답 기록이 없는</E> 중간 상태가 생기지 않습니다.

### 3. 자연 멱등 설계

Idempotency-Key 테이블이 부담스러운 경우의 대안입니다. 연산 자체를 최종 상태 기준으로 재정의합니다. 예: `POST /orders`를 `PUT /orders/{clientOrderId}`로 바꾸면, clientOrderId가 있는 상태에서 또 `PUT` 해도 <E>이미 존재 → 업데이트 또는 무시</E>로 끝납니다. 또 다른 예: `DELETE /users/42`는 없으면 없는 상태로 유지하는 것이 자연 멱등입니다.

이 접근은 테이블 저장 부담이 없지만 응답 시맨틱 설계가 필요합니다. 두 번째 `DELETE`에 `404`를 줄지 `204`를 줄지, `PUT`에 생성 vs 업데이트를 구분할지 같은 판단이 추가됩니다.

## 어디서 마주치는가

### 1. 적용이 필수인 경우

**돈/재고가 걸린 상태 변경**: 결제, 출금, 주문 생성, 포인트 적립, 재고 차감. 여기서 멱등성 없이는 재시도 한 번으로 중복 결제나 재고 오차가 발생합니다.

**Webhook 수신측**: 서버가 외부로 보내는 webhook은 수신자 다운 / 타임아웃 시 대부분 재전송합니다. Stripe는 기본적으로 최대 3일까지 지수 백오프로 재시도합니다. 수신측이 멱등하지 않으면 운영자가 통제할 수 없는 중복이 쌓입니다.

**큐 기반 비동기 processor**: SQS, Kafka, RabbitMQ는 모두 at-least-once를 기본으로 하므로 consumer는 항상 멱등이어야 합니다.

### 2. 과설계가 되는 경우

**조회**(`GET`): 이미 자동 멱등이라 별도 설계가 필요 없습니다. <E>safe</E> 속성은 <E>멱등</E>을 포함하므로 `GET`에 Idempotency-Key를 붙이는 건 낭비입니다.

**Append-only 로그 / 이벤트 수집**: 관측 데이터는 오히려 중복이 정확할 수 있습니다. 같은 이벤트가 두 번 들어왔으면 <E>정말 두 번 일어났다</E>로 해석하는 게 맞는 도메인이 많기 때문입니다. 사용자 클릭 추적, impression 로깅 등에서 강제 멱등을 하면 실제 빈도를 잃게 됩니다.

**본질적으로 1회성인 UX 플로우**: 사용자가 UI 확인 다이얼로그를 넘어 수동으로 누른 삭제 버튼 같은 경우, 실용적으로는 버튼 disable + 낙관적 UI로 충분하고 서버단 멱등 설계까지 요구하지 않기도 합니다. 이 판단은 책임의 경계를 정하는 것이라 팀 컨벤션에 따라 다릅니다.

### 3. 판단 기준

두 질문만 던지면 충분합니다.

1. 이 요청이 타임아웃 시 **자동 재시도** 대상인가?
2. 중복이 **실행 비용**(돈·재고·외부 호출)을 발생시키는가?

둘 중 하나라도 Yes면 멱등 필수. 둘 다 No인 조회나 로그는 멱등 설계에 공을 들일 필요가 없습니다.

## 트레이드오프

### 1. 저장 비용과 TTL 딜레마

Idempotency-Key 방식은 키 + 응답 바디 + HTTP status를 테이블에 계속 쌓습니다. 결제 트래픽이 초당 1,000건이면 하루 8,600만 개의 행이 생깁니다. 무한 보존은 비현실적이라 TTL을 설정하는데, 여기에 딜레마가 있습니다.

**너무 짧으면**(예: 1시간) 클라이언트가 지연 재시도(모바일 오프라인 후 재접속 등)할 때 TTL 밖이 되어 <E>중복 감지 실패 → 중복 실행</E> 위험이 생깁니다. **너무 길면**(예: 30일) 저장 폭증이 됩니다. Stripe는 24시간을 표준으로 잡습니다. 합리적 재시도 윈도우와 저장 비용의 현실적 타협점입니다.

### 2. 동시성 race condition

같은 키로 **동시에** 두 요청이 도착하는 경우가 진짜 까다롭습니다. 순서가 엇갈리면 둘 다 <E>키 조회 → 없음 → 처리</E>로 진입해 중복 실행이 발생합니다. 해결은 두 방향입니다.

| 접근 | 메커니즘 | 유의할 점 |
|---|---|---|
| DB UNIQUE 제약 | `UNIQUE(idempotency_key)`로 두 번째 INSERT가 실패하면 첫 번째 결과 대기 후 replay | 실패한 쪽의 대기 로직이 필요 |
| 분산 락 | Redis `SET NX`로 키별 임계구역 직렬화 | 락 홀더 장애 시 fencing token 문제 재등장 |

추가로 <E>같은 키, 다른 body</E> 문제도 같이 처리해야 합니다. Stripe는 body의 해시를 함께 저장해, 같은 키로 다른 body가 오면 `409 Conflict`를 반환합니다. 오사용 방지 장치입니다.

### 3. 응답 replay의 지점

멱등성 구현의 원자성 경계는 비즈니스 로직 DB와 같은 트랜잭션이어야 합니다. Redis처럼 별도 스토어를 쓰면 <E>상태는 변했는데 응답 기록 없음 → 다음 재시도 시 중복 실행</E> 위험이 생기기 쉽습니다.

또한 저장된 응답을 언제 재생할지에 대한 판단이 필요합니다. 관례상 **4xx는 결정적 오류라 replay하고, 5xx는 재시도를 허용**합니다. 첫 요청 처리 중 DB 일시 장애로 `500`을 받았던 경우 재시도가 오면 다시 시도할 기회를 주는 편이 현실적입니다.

## 마무리

Idempotency는 수학의 작은 정의 $f(f(x)) = f(x)$에서 출발해, 분산 시스템이 네트워크 불확실성과 싸우기 위해 필연적으로 도달한 설계 원칙입니다. HTTP 메서드 의미론, Idempotency-Key 패턴, 자연 멱등 설계는 모두 <E>같은 요청이 두 번 도착해도 한 번처럼 행동하라</E>는 단일 요구사항을 풀어낸 세 가지 구현 방법입니다.

실무에서 이 글을 가져갈 때 기억할 질문은 두 개입니다. <E>이 요청이 자동 재시도 대상인가?</E> <E>중복이 실행 비용을 발생시키는가?</E> 둘 중 하나라도 Yes면 멱등은 선택이 아니라 필수입니다. 조회나 단순 로그 수집까지 끌고 가는 과설계만 피하면, 멱등성은 재시도를 안전하게 만들어주는 가장 비용 효율적인 장치입니다.
