## 접근 권한 최소화

잘 설계된 컴포넌트는 클래스 내부 데이터와 구현 정보를 숨겨 <E>캡슐화(encapsulation)</E> 또는 <E>정보 은닉(information hiding)</E>이 잘 되어 있다. 외부에서 알 필요가 없는 것은 보이지 않게 하고, 외부 API로 약속한 것만 노출한다. 이렇게 분리해 두면 내부 구현을 자유롭게 바꿔도 외부 코드가 깨지지 않는다.

자바의 접근 제어자는 네 단계다.

| 제어자 | 가시 범위 |
|---|---|
| `private` | 선언한 클래스 안에서만 |
| package-private (default) | 같은 패키지 안 |
| `protected` | 같은 패키지 + 하위 클래스 |
| `public` | 모든 곳 |

기본 원칙은 단순하다. <E>모든 클래스와 멤버의 접근성을 가능한 한 좁힌다.</E> 톱레벨 클래스는 패키지 외부에서 쓸 일이 없으면 `package-private`로, 멤버는 `private`을 기본으로 두고 같은 패키지의 다른 클래스가 써야 할 때만 한 단계씩 푼다.

특히 자주 무너지는 지점이 두 개 있다. 하나는 <E>public 가변 필드</E>, 다른 하나는 <E>public 배열·컬렉션 필드</E>다. 가변 필드를 외부에 그대로 열면 누구나 값을 바꿀 수 있어 클래스가 자기 상태를 보장하지 못하고, 배열을 그대로 노출하면 길이가 0이 아닌 한 내부 데이터가 통째로 새어 나간다.

<Tabs group="access-control">
  <Tab label="Before: public 노출">
```java title="Order.java"
public class Order {
    public OrderId id;
    public List<LineItem> lines;       // 외부에서 add/remove 자유
    public OrderStatus status;
    public LineItem[] snapshot;        // 배열도 그대로 공개
}
```
  </Tab>
  <Tab label="After: 최소 공개">
```java title="Order.java"
public final class Order {
    private final OrderId id;
    private final List<LineItem> lines;
    private OrderStatus status;

    public OrderId id() {
        return id;
    }

    public List<LineItem> lines() {
        return List.copyOf(lines);     // 방어적 복사
    }

    public OrderStatus status() {
        return status;
    }
}
```
  </Tab>
</Tabs>

After 쪽은 필드를 모두 `private`로 감추고 필요한 것만 메서드로 연다. `lines()`는 내부 리스트를 그대로 돌려주지 않고 `List.copyOf`로 <E>읽기 전용 복사본</E>을 반환한다. 외부가 가져간 리스트를 수정해도 `Order` 내부 상태는 그대로다.

<Callout type="info" title="기억할 한 줄">
public 가변 필드는 거의 항상 잘못된 신호다. 노출이 필요하면 메서드를 통해, 컬렉션이라면 불변 복사본으로.
</Callout>

## 불변 객체 만들기

변경 가능성을 줄이는 가장 직접적인 방법은 <E>불변 객체(immutable object)</E>를 만드는 것이다. 불변 객체는 단순하다. 생성된 시점부터 파괴되는 시점까지 동일한 값을 유지한다. 동기화를 고려할 필요가 없으며 사용에 안전하고, 여러 스레드가 공유해도 문제가 없다. 단점이 있다면 새 값이 필요할 때마다 객체를 새로 만들어야 한다는 것이다.

불변 클래스를 만드는 규칙은 다섯 가지다.

- 객체 상태를 변경하는 메서드(setter 등)를 제공하지 않는다.
- 클래스를 확장할 수 없게 한다 (보통 `final`).
- 모든 필드를 `final`로 선언한다.
- 모든 필드를 `private`으로 선언한다.
- 자신 외에는 내부의 가변 컴포넌트에 접근할 수 없게 한다.

자주 쓰이는 패턴은 <E>final 클래스 + private 생성자 + 정적 팩토리</E>다. 정적 팩토리를 두면 자주 쓰이는 값을 캐싱해 같은 인스턴스를 재사용할 수 있고, 나중에 하위 타입으로 교체할 자유도 남는다.

<Tabs group="immutable-money">
  <Tab label="Before: 가변 Money">
```java title="Money.java"
public class Money {
    private long amount;
    private Currency currency;

    public Money(long amount, Currency currency) {
        this.amount = amount;
        this.currency = currency;
    }

    public void setAmount(long amount) {
        this.amount = amount;
    }

    public void setCurrency(Currency currency) {
        this.currency = currency;
    }
}
```
  </Tab>
  <Tab label="After: 불변 Money">
```java title="Money.java"
public final class Money {
    private static final Money ZERO_KRW =
        new Money(0L, Currency.getInstance("KRW"));

    private final long amount;
    private final Currency currency;

    private Money(long amount, Currency currency) {
        this.amount = amount;
        this.currency = currency;
    }

    public static Money of(long amount, Currency currency) {
        if (amount == 0L && "KRW".equals(currency.getCurrencyCode())) {
            return ZERO_KRW;        // 캐싱된 인스턴스 재사용
        }
        return new Money(amount, currency);
    }

    public Money plus(Money other) {
        requireSameCurrency(other);
        return new Money(this.amount + other.amount, this.currency);
    }

    public long amount() {
        return amount;
    }

    public Currency currency() {
        return currency;
    }
}
```
  </Tab>
</Tabs>

After 쪽 `plus`에 주목한다. 메서드 이름이 `add`가 아니라 <E>`plus`</E>인 이유는 자기 상태를 바꾸지 않고 새 객체를 반환한다는 함수형 의도를 이름에 박아 두기 위해서다. `BigInteger.add`, `String.concat`, `LocalDate.plusDays`가 모두 같은 패턴이다.

모든 클래스를 불변으로 만들 수는 없다. 다만 불변으로 만들 수 없는 클래스라도 변경 가능한 부분을 최소한으로 줄이면 객체 상태를 예측하기 쉬워지고 오류 가능성이 줄어든다. 변경이 꼭 필요한 필드를 제외한 나머지는 `final`로 선언한다.

<Callout type="info" title="기억할 한 줄">
다른 합당한 이유가 없다면 모든 필드는 `private final`이어야 한다.
</Callout>

## 상속보다 컴포지션

상속은 강력한 도구지만, 잘못 사용하면 캡슐화를 깨뜨린다. 상위 클래스의 구현이 하위 클래스에 그대로 드러나기 때문이다. 상위 클래스가 어느 시점에 어느 메서드를 어떤 순서로 호출하는지가 하위 클래스 동작에 영향을 주므로, 상위 클래스가 릴리스마다 내부 구현을 바꾸면 하위 클래스도 따라 깨질 수 있다.

이펙티브 자바의 고전 예시는 `HashSet`을 상속해 <E>지금까지 추가된 원소 수</E>를 세려는 시도다. `add`와 `addAll`을 함께 재정의해 카운트를 올린다. 그런데 `HashSet.addAll`은 내부에서 `add`를 호출하도록 구현되어 있어, `addAll(c)`를 부르면 카운트가 두 번씩 증가한다. 상위 클래스의 자기 사용(self-use) 패턴이 바뀌면 하위 클래스가 함께 무너진다.

<Tabs group="composition-vs-inheritance">
  <Tab label="Before: 상속: 깨지기 쉬움">
```java title="InstrumentedHashSet.java"
public class InstrumentedHashSet<E> extends HashSet<E> {
    private int addCount = 0;

    @Override
    public boolean add(E e) {
        addCount++;
        return super.add(e);
    }

    @Override
    public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();          // (1)
        return super.addAll(c);        // (2) 내부에서 add 재호출
    }

    public int getAddCount() {
        return addCount;
    }
}

// 사용
var s = new InstrumentedHashSet<String>();
s.addAll(List.of("a", "b", "c"));
s.getAddCount();                       // 3이 아니라 6. 두 번 카운트
```
  </Tab>
  <Tab label="After: 컴포지션: 안정">
```java title="ForwardingSet.java"
public class ForwardingSet<E> implements Set<E> {
    private final Set<E> delegate;

    public ForwardingSet(Set<E> delegate) {
        this.delegate = delegate;
    }

    @Override public boolean add(E e)                    { return delegate.add(e); }
    @Override public boolean addAll(Collection<? extends E> c)
                                                         { return delegate.addAll(c); }
    @Override public boolean contains(Object o)          { return delegate.contains(o); }
    @Override public int size()                          { return delegate.size(); }
    @Override public Iterator<E> iterator()              { return delegate.iterator(); }
    // 나머지 Set 메서드도 동일하게 위임
    // ...
}

public class InstrumentedSet<E> extends ForwardingSet<E> {
    private int addCount = 0;

    public InstrumentedSet(Set<E> s) {
        super(s);
    }

    @Override
    public boolean add(E e) {
        addCount++;
        return super.add(e);
    }

    @Override
    public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return super.addAll(c);        // ForwardingSet → delegate.addAll
    }

    public int getAddCount() {
        return addCount;
    }
}
```
  </Tab>
</Tabs>

After 쪽은 두 단계로 나뉜다. 먼저 `ForwardingSet`이 실제 `Set` 구현체에 모든 호출을 위임하는 얇은 래퍼 역할을 한다. 그 위에 `InstrumentedSet`이 카운트만 추가한다. 이제 위임 대상이 무엇이든 카운트는 정확히 한 번만 올라간다. 위임받는 `Set`은 `HashSet`이든 `TreeSet`이든 상관없다.

상속은 <E>순수한 is-a 관계</E>일 때만 사용한다. 그 경우에도 상위 클래스가 확장을 염두에 두고 설계됐는지를 점검한다. 두 조건 모두를 만족하지 못하면 컴포지션이 안전한 기본값이다.

## 상속용 설계와 문서화

그래도 상속을 허용해야 한다면, 클래스를 <E>상속용으로 설계하고 문서화</E>해야 한다. 핵심은 두 가지다.

첫째, 재정의 가능한 메서드를 클래스 내부에서 어떻게 사용하는지 공개한다. 어떤 시점에 어떤 메서드를 어떤 순서로 호출하는지가 곧 하위 클래스가 의지하게 될 약속이다. Javadoc의 `@implSpec` 태그가 이 용도로 쓰인다.

둘째, 중간 과정에 끼어들 수 있는 <E>훅(hook) 메서드</E>를 `protected`로 제공한다. 외부 API는 깔끔하게 두되, 하위 클래스만 필요할 만한 확장 지점을 따로 연다.

문서만으로는 부족하다. 클래스를 배포하기 전에 <E>최소 세 개 이상의 하위 클래스</E>를 만들어 직접 검증해 본다. 그중 한두 개는 자신이 작성하지 않은 사람이 만들어야 안 보이던 가정이 드러난다.

또 하나 흔한 지점이 있다. <E>상위 클래스 생성자에서 재정의 가능한 메서드를 호출하지 말라.</E> 상위 생성자는 하위 생성자보다 먼저 실행되므로, 재정의된 메서드가 하위 클래스 필드에 접근하면 그 시점에 그 필드는 초기화 전이다.

<Tabs group="constructor-overridable">
  <Tab label="Before: 생성자에서 재정의 가능 호출">
```java title="ConstructorPitfall.java"
public class Super {
    public Super() {
        overrideMe();                  // 하위 생성자 전에 호출됨
    }

    public void overrideMe() {
    }
}

public class Sub extends Super {
    private final Instant instant;

    Sub() {
        instant = Instant.now();       // (a)
    }

    @Override
    public void overrideMe() {
        System.out.println(instant);   // (b) 첫 호출 시 null 출력
    }
}

public static void main(String[] args) {
    Sub sub = new Sub();
    sub.overrideMe();                  // 두 번째 호출은 정상
}
// 출력
// null
// 2026-04-29T...
```
  </Tab>
  <Tab label="After: 생성자에서 호출 금지">
```java title="ConstructorSafe.java"
public class Super {
    public Super() {
        // 재정의 가능 메서드 호출 없음
    }

    public final void runSafely() {
        prepare();                     // 호출은 생성자 외부에서
    }

    protected void prepare() {
    }
}

public class Sub extends Super {
    private final Instant instant;

    Sub() {
        instant = Instant.now();
    }

    @Override
    protected void prepare() {
        System.out.println(instant);   // 항상 초기화 후 호출됨
    }
}
```
  </Tab>
</Tabs>

같은 규칙이 `Cloneable.clone`, `Serializable.readObject`에도 적용된다. 두 메서드 모두 사실상 새 객체를 만들어 내는 생성자처럼 동작하므로, 재정의 가능한 메서드를 직접 또는 간접적으로 호출하면 같은 지점에 빠진다.

<Note title="상속용 클래스 자가 검증 체크리스트">
  - 재정의 가능 메서드의 자기 사용 패턴을 `@implSpec`으로 문서화했는가
  - `protected` 훅을 정말 필요한 곳에만 신중히 노출했는가
  - 하위 클래스를 최소 세 개 만들어 가정을 깼는가
  - 생성자, `clone`, `readObject`에서 재정의 가능 메서드를 호출하지 않는가
</Note>

## 인터페이스 우선

자바에는 다중 구현 메커니즘이 두 가지 있다. <E>추상 클래스</E>와 <E>인터페이스</E>다. 자바 8부터 인터페이스도 디폴트 메서드를 가질 수 있게 되면서, 둘 다 <E>인스턴스 메서드의 구현을 제공할 수 있다</E>는 점에서 비슷해 보인다. 그러나 큰 차이가 있다. 추상 클래스를 구현하려면 그 추상 클래스를 단일 조상으로 두어야 한다. 자바는 단일 상속만 허용하므로, 한 클래스가 가질 수 있는 추상 조상은 하나뿐이다.

반면 인터페이스는 여러 개를 동시에 구현할 수 있다. 인터페이스는 <E>믹스인(mixin) 타입</E>으로 동작하며, 주된 타입 외에 선택적 행위를 추가로 선언하는 효과를 준다. `Comparable`은 자신을 구현한 클래스의 인스턴스들끼리 순서를 정할 수 있음을 의미하고, `AutoCloseable`은 `try-with-resources`에 들어갈 수 있음을 의미한다.

같은 `Order`라도 도메인에 따라 조합이 달라진다. 가격순으로 정렬해야 하면 `Comparable<Order>`를 구현하고, JSON 직렬화 대상이면 `Serializable`을 추가하는 식이다.

```java title="Order.java"
public final class Order implements Comparable<Order>, Serializable {
    private final OrderId id;
    private final Money total;

    @Override
    public int compareTo(Order other) {
        return this.total.amount() < other.total.amount() ? -1
             : this.total.amount() > other.total.amount() ? 1
             : 0;
    }
}
```

자바 8부터는 인터페이스가 디폴트 메서드를 제공할 수 있다. 골격이 명확한 동작은 인터페이스 안에 직접 구현해 두면 구현 클래스가 일일이 다시 짜지 않아도 된다. `Collection.removeIf`, `List.replaceAll`, `Iterable.forEach`가 모두 같은 방식으로 들어왔다.

```java title="Discountable.java"
public interface Discountable {
    Money price();

    default Money discounted(int percent) {
        long discountAmount = price().amount() * percent / 100;
        return Money.of(price().amount() - discountAmount, price().currency());
    }
}

public final class LineItem implements Discountable {
    private final ProductId productId;
    private final int quantity;
    private final Money unitPrice;

    @Override
    public Money price() {
        return Money.of(unitPrice.amount() * quantity, unitPrice.currency());
    }
}
```

`LineItem`은 `price()`만 구현하면 `discounted(int)`를 자동으로 얻는다. 추상 클래스로 같은 일을 하려면 `LineItem`이 단일 추상 조상에 묶여야 했고, 다른 행위를 더 끼우기가 어려웠을 것이다.

다만 디폴트 메서드는 만능이 아니다. `equals`, `hashCode`, `toString` 같은 `Object` 메서드는 디폴트 메서드로 제공할 수 없고, 인터페이스에는 인스턴스 필드를 둘 수 없다. 추상 클래스가 더 자연스러운 자리도 분명히 있다. 그래서 표준 라이브러리는 자주 <E>인터페이스 + 골격 구현체(skeletal implementation)</E> 쌍으로 제공한다. `Collection`, `List`, `Set` 같은 인터페이스 옆에 `AbstractCollection`, `AbstractList`, `AbstractSet`이 함께 있는 이유다.

<Callout type="info" title="선택 기준 한 줄">
다중 구현이나 믹스인 의도가 있다면 인터페이스, 공통 상태와 골격 구현이 핵심이면 추상 클래스. 둘 다 필요하면 인터페이스와 골격 구현체를 함께 제공한다.
</Callout>

## 태그 대신 계층

태그 달린 클래스는 한 클래스 안에 두 가지 이상의 의미를 섞어 놓고, <E>태그 필드</E>와 분기로 구분하는 패턴이다. 도형을 예로 들면, 원과 사각형을 한 클래스에 담고 `Type.CIRCLE` 또는 `Type.RECTANGLE` 태그로 구분하는 식이다.

코드는 분기로 가득 차고, 사용하지 않는 필드까지 모든 인스턴스가 함께 들고 다닌다. 메모리 효율이 떨어지고, 의미 없는 필드가 객체에 섞여 있어 가독성도 함께 무너진다. 새 도형을 추가하려면 태그 enum, 분기, 생성자, 메서드 모두에 손을 대야 한다.

<Tabs group="tagged-vs-hierarchy">
  <Tab label="Before: 태그 달린 클래스">
```java title="Shape.java"
public class Shape {
    enum Type { CIRCLE, RECTANGLE }

    private final Type type;

    // 사각형일 때만 사용
    private double length;
    private double width;

    // 원일 때만 사용
    private double radius;

    public Shape(double radius) {
        this.type = Type.CIRCLE;
        this.radius = radius;
    }

    public Shape(double length, double width) {
        this.type = Type.RECTANGLE;
        this.length = length;
        this.width = width;
    }

    public double area() {
        switch (type) {
            case CIRCLE -> {
                return Math.PI * radius * radius;
            }
            case RECTANGLE -> {
                return length * width;
            }
            default -> throw new AssertionError(type);
        }
    }
}
```
  </Tab>
  <Tab label="After: 클래스 계층 구조">
```java title="Shape.java"
public abstract class Shape {
    public abstract double area();
}

public final class Circle extends Shape {
    private final double radius;

    public Circle(double radius) {
        this.radius = radius;
    }

    @Override
    public double area() {
        return Math.PI * radius * radius;
    }
}

public final class Rectangle extends Shape {
    private final double length;
    private final double width;

    public Rectangle(double length, double width) {
        this.length = length;
        this.width = width;
    }

    @Override
    public double area() {
        return length * width;
    }
}
```
  </Tab>
</Tabs>

After 쪽은 분기가 없다. 각 도형이 자기 의미에 맞는 필드만 들고, `area()`는 다형성으로 호출된다. 정사각형 같은 새 도형을 추가하려면 `Rectangle`을 상속한 새 클래스만 만들면 된다. 기존 코드를 수정하지 않는다.

태그 달린 클래스는 <E>계층 구조를 흉내 낸 어색한 시도</E>로 봐도 좋다. 태그 필드와 `switch`가 보이면 거의 항상 클래스 계층으로 풀 수 있는지 먼저 점검한다.

## 정적 멤버 클래스

자바의 중첩 클래스는 네 종류다. <E>정적 멤버 클래스</E>, <E>비정적 멤버 클래스</E>, <E>익명 클래스</E>, <E>지역 클래스</E>. 이 절은 앞의 두 종류 사이의 선택만 다룬다.

비정적 멤버 클래스의 인스턴스는 암묵적으로 바깥 클래스 인스턴스와 연결된다. 그래서 비정적 멤버 클래스 안에서 `OuterClass.this`로 바깥 인스턴스를 참조할 수 있다. 이 연결 정보가 인스턴스 안에 만들어지므로 메모리를 더 차지하고 생성 시간도 더 든다.

더 위험한 건 <E>숨은 외부 참조</E>다. `static`을 빠뜨린 멤버 클래스는 자신이 명시적으로 외부를 참조하지 않더라도 바깥 인스턴스로의 참조를 항상 들고 있다. 멤버 클래스 인스턴스가 어디선가 살아 있는 한 바깥 인스턴스도 가비지 컬렉터가 회수하지 못한다. <E>의도하지 않은 메모리 누수</E>가 자주 여기서 시작된다.

원칙은 단순하다. <E>멤버 클래스에서 바깥 인스턴스에 접근할 일이 없다면 반드시 `static`을 붙인다.</E> 바깥 인스턴스에 접근해야 할 정당한 이유가 있을 때만 비정적 멤버 클래스로 둔다. 어댑터(adapter) 구현이 그런 자리의 대표 사례다.

<Tabs group="static-member-class">
  <Tab label="Before: 비정적 멤버 클래스: 외부 참조 불필요">
```java title="Order.java"
public final class Order {
    private final OrderId id;
    private final List<LineItem> lines;

    // 외부 참조가 필요 없는데 비정적
    public class Summary {
        private final int lineCount;
        private final Money total;

        public Summary(int lineCount, Money total) {
            this.lineCount = lineCount;
            this.total = total;
        }
    }

    public Summary summarize() {
        return new Summary(lines.size(), totalOf(lines));
    }
}
```
  </Tab>
  <Tab label="After: static 멤버 클래스">
```java title="Order.java"
public final class Order {
    private final OrderId id;
    private final List<LineItem> lines;

    // 바깥 인스턴스가 필요 없으므로 static
    public static final class Summary {
        private final int lineCount;
        private final Money total;

        public Summary(int lineCount, Money total) {
            this.lineCount = lineCount;
            this.total = total;
        }
    }

    public Summary summarize() {
        return new Summary(lines.size(), totalOf(lines));
    }
}
```
  </Tab>
</Tabs>

반대로, 바깥 인스턴스가 정말로 필요한 경우의 정석 예시는 <E>이터레이터 구현</E>이다. `Order`가 자신의 `LineItem`들을 순회할 수 있도록 `Iterator`를 제공한다고 하자. 이터레이터는 바깥 `Order`의 `lines`를 들여다봐야 하므로 비정적 멤버 클래스로 두는 것이 자연스럽다.

```java title="Order.java"
public final class Order implements Iterable<LineItem> {
    private final List<LineItem> lines;

    @Override
    public Iterator<LineItem> iterator() {
        return new LineItemIterator();
    }

    // 바깥 인스턴스의 lines가 필요 → 비정적
    private final class LineItemIterator implements Iterator<LineItem> {
        private int cursor = 0;

        @Override
        public boolean hasNext() {
            return cursor < lines.size();
        }

        @Override
        public LineItem next() {
            if (!hasNext()) {
                throw new NoSuchElementException();
            }
            return lines.get(cursor++);
        }
    }
}
```

`LineItemIterator`는 `Order.this.lines`를 직접 사용한다. 이런 자리에서는 `static`을 붙이면 오히려 동작이 안 된다. 핵심은 <E>외부 참조가 정말 필요한지 한 번 점검</E>해 보고, 필요 없으면 `static`을 붙이는 습관이다.

<Callout type="info" title="기억할 한 줄">
멤버 클래스의 기본값은 `static`. `static`을 빼는 결정에는 명시적 이유가 있어야 한다.
</Callout>

## 정리

7가지 아이템을 한 줄씩 다시 적어 두면 다음과 같다.

- <E>Item 15.</E> 외부에 보이는 면적을 가능한 한 좁힌다. `private`을 기본으로, public 가변 필드는 거의 항상 잘못된 신호다.
- <E>Item 17.</E> 변경 가능성을 줄이는 가장 단순한 방법은 불변 객체다. 다른 합당한 이유가 없다면 모든 필드는 `private final`.
- <E>Item 18.</E> is-a가 아니거나 상위 클래스가 확장을 고려해 설계되지 않았다면, 컴포지션과 위임이 안전한 기본값이다.
- <E>Item 19.</E> 상속을 허용한다면 자기 사용 패턴을 문서화하고, 훅을 `protected`로 노출하고, 하위 클래스 셋 이상으로 검증한다. 생성자에서 재정의 가능 메서드를 호출하지 않는다.
- <E>Item 20.</E> 다중 구현과 믹스인 의도가 있다면 인터페이스, 공통 상태와 골격 구현이 핵심이면 추상 클래스. 둘 다 필요하면 인터페이스와 골격 구현체를 함께.
- <E>Item 23.</E> 태그 필드와 `switch` 분기는 거의 항상 클래스 계층 구조로 풀어낼 수 있다. 다형성에 일을 맡긴다.
- <E>Item 24.</E> 멤버 클래스의 기본값은 `static`. 바깥 인스턴스가 정말 필요할 때만 비정적으로 둔다.

객체의 생성과 파괴가 자바 코드의 첫 줄과 마지막 줄을 정의했다면, 클래스와 인터페이스는 그 사이의 <E>모양과 결합도</E>를 정의한다. 이 7가지 아이템의 공통점은 분명하다. <E>외부에 약속할 면적을 좁히고, 변할 수 있는 부분을 줄이며, 상속보다는 합성으로 결합도를 낮춘다</E>는 것이다.
