부하 테스트 도구를 고를 때 가장 성가신 것은 <E>테스트를 어디에 어떻게 기록하느냐</E> 입니다. k6는 이 질문에 간결한 답을 내놓습니다. 시나리오도, 부하 프로파일도, 합격 기준도 전부 하나의 JavaScript 파일입니다. 이 글은 k6를 처음 만지는 사람이 VU 개념부터 스크립트 구조, 실행, 결과 해석까지 한 번에 훑을 수 있도록 정리합니다.

<Note title="이 글의 학습 목표">
  - k6가 무엇이고 왜 개발자 친화적인 부하 테스트 도구로 쓰이는지 이해한다
  - VU 개념과 스크립트 구조(default function, options, setup, teardown)를 구분할 수 있다
  - 스테이지 설정, 응답 검증, 그룹·태그, 실행 결과 해석의 기초를 얻는다
</Note>

## k6란

k6는 개발자를 위한 오픈소스 부하 테스트 도구입니다. 2017년 Load Impact(현 Grafana Labs)가 만들었고, 핵심 구조는 **부하 시나리오는 JavaScript로 작성하지만 부하 생성 엔진은 Go**가 담당한다는 점입니다. 사용자는 익숙한 JS로 시나리오를 쓰고, 실행은 Go의 높은 동시성 능력 위에서 돌아갑니다.

부하 테스트가 필요한 이유는 단순합니다. 운영 투입 전 <E>내 서버가 얼마나 버티는가</E>를 재현해야 하기 때문입니다. 평상시 p95가 120ms인 API도 초당 500명이 동시에 치면 p95가 2초로 치솟을 수 있습니다. k6는 이 재현을 위한 엔진이고, 실제로 하는 일은 세 가지입니다.

1. **부하 생성**: 지정한 가상 사용자 수만큼 동시에 HTTP, gRPC, WebSocket 요청을 보냅니다.
2. **메트릭 수집**: 응답 시간, 상태 코드, 실패 여부를 요청별로 기록합니다.
3. **결과 집계와 판정**: p50/p95/p99, RPS, 에러율을 출력하고, 미리 정한 기준(`thresholds`)을 통과했는지 판정합니다.

실행 모델도 단순합니다. `k6 run script.js` 한 줄입니다. 별도 UI나 설정 파일이 없고 스크립트 하나로 테스트가 정의되므로, Git에 그대로 커밋해 버전 관리할 수 있습니다.

## VU 모델

<Callout type="warning" title="이 글의 핵심 포인트">
  k6의 모든 실행은 **VU가 default function을 무한 반복**하는 단 하나의 모델 위에서 돌아갑니다. 이 모델만 잡아두면 이후에 나오는 옵션, 스테이지, 그룹, 메트릭이 자연스럽게 연결됩니다.
</Callout>

VU는 Virtual User의 줄임말이고, k6의 기본 실행 단위입니다. 스크립트를 <E>동시에 50 VU로 10분간</E> 이라고 지시하면, k6는 **50개의 독립된 실행 흐름**을 만들어 각각이 `export default function`을 **무한히 반복** 실행합니다. 한 VU가 이 함수를 한 번 완주하면 이를 **1 iteration**이라고 부릅니다.

내부적으로 한 VU는 **하나의 goroutine + 하나의 JavaScript VM 인스턴스(Goja)** 로 구현됩니다. OS 스레드가 아닙니다. `k6/http` 같은 모듈은 실제 HTTP I/O를 Go 쪽으로 위임하므로, 수천 VU를 한 머신에서 돌려도 스레드 컨텍스트 스위칭 비용이 거의 없습니다. <E>VU = 사람 한 명</E> 이라는 추상이 유지되면서, 비용은 가벼운 goroutine 수준에 머무는 점이 k6 설계의 핵심입니다.

<Callout type="error" title="핵심 통찰: 스크립트가 곧 테스트다">
  k6에는 UI도, 별도의 설정 파일도 없습니다. VU 수, 부하 프로파일, 검증 기준이 모두 하나의 JS 파일에 모입니다. 이 파일을 Git에 커밋하는 순간 <E>이 테스트는 이렇게 돌렸다</E>가 팀 안에서 재현 가능한 자산이 됩니다.
</Callout>

VU가 RPS가 아닌 <E>사용자 수</E> 단위인 이유는 실제 서비스의 부하 형성 방식과 맞추기 위해서입니다. 사용자는 페이지를 열고, 잠시 머물고, 다음 페이지로 넘어갑니다. k6의 VU도 같은 흐름을 모사합니다. 스크립트 안에서 `sleep(1)` 같은 호출로 <E>사용자가 1초 머문다</E>를 표현하고, 이 합이 실제 요청 속도를 결정합니다.

개념 확인용 최소 스크립트는 이렇게 생겼습니다.

```js title="minimal.js"
import http from 'k6/http';
import { sleep } from 'k6';

export const options = {
  vus: 10,          // 동시에 10명
  duration: '30s',  // 30초간
};

export default function () {
  http.get('https://test.k6.io');
  sleep(1);
}
```

이 예시는 30초 동안 10개 VU가 각각 <E>요청 → 1초 대기 → 요청 → 1초 대기</E>를 반복합니다. 한 VU가 30초간 약 30 iteration을 돌고, 전체로는 약 300 iteration이 됩니다.

## 스크립트 구조

k6 스크립트는 **정해진 자리에 정해진 것을 export 하는 JS 파일**입니다. 일반 JS와 다른 점은, <E>이 이름으로 export된 것</E>을 k6가 특별하게 해석한다는 것입니다. 외울 자리는 네 개입니다.

| 자리 | 역할 | 실행 횟수 |
|---|---|---|
| `export default function` | VU가 반복 실행하는 본체 | VU × iteration |
| `export const options` | 테스트 설정 오브젝트 | 1회 (로드 시) |
| `export function setup()` | 테스트 시작 전 공통 준비 | 1회 |
| `export function teardown(data)` | 테스트 종료 후 정리 | 1회 |

`default function` 은 부하의 몸통입니다. HTTP 요청, 검증, 대기 로직이 모두 여기에 들어갑니다. `setup`이 리턴한 값이 있다면 첫 파라미터로 전달됩니다.

`options` 는 실행 설정입니다. VU 수, 지속 시간, 부하 프로파일, 통과 기준(`thresholds`)이 여기에 모입니다. CLI 플래그(`k6 run --vus 10 --duration 30s script.js`)로도 지정할 수 있지만, 스크립트 안에 `options`로 적는 것이 표준입니다. 이유는 재현성입니다. 스크립트만 보면 <E>어떤 부하를 줬는지</E>가 즉시 드러납니다.

```js title="options-basic.js"
export const options = {
  vus: 10,
  duration: '30s',
  thresholds: {
    http_req_duration: ['p(95)<500'],
  },
};
```

`setup` 과 `teardown` 은 부하가 시작되기 전과 끝난 후 한 번씩 호출됩니다. 대표적인 쓰임은 로그인 토큰 발급과 테스트 데이터 정리입니다.

```js title="setup-teardown.js"
import http from 'k6/http';

export function setup() {
  const res = http.post('https://api.example.com/login', {
    email: 'load@test',
    password: 'pw',
  });
  return { token: res.json('token') };
}

export default function (data) {
  http.get('https://api.example.com/me', {
    headers: { Authorization: `Bearer ${data.token}` },
  });
}

export function teardown(data) {
  http.del('https://api.example.com/sessions/current', null, {
    headers: { Authorization: `Bearer ${data.token}` },
  });
}
```

실행 순서는 항상 동일합니다. `setup` → (VU들이 각자 `default` 반복) → `teardown`. 이 네 개의 자리가 k6 스크립트 문법의 뼈대이고, 나머지는 일반 JS 모듈과 동일하게 `import`, 헬퍼 함수, 파일 분리를 자유롭게 사용합니다.

## 부하 설정

`options` 안에서 **부하의 크기와 시간**을 정하는 부분입니다. 가장 단순한 형태는 고정 부하입니다.

```js title="constant-load.js"
export const options = {
  vus: 20,
  duration: '1m',
};
```

시작 즉시 20 VU가 동시에 돌고, 1분이 지나면 일괄 종료됩니다. 단일 API의 기본 응답 특성을 보거나, 정상 부하 구간에서 에러가 나는지 확인할 때 쓰는 가장 간단한 프로파일입니다.

실제 서비스 트래픽은 평평하지 않습니다. 점진적으로 늘다가, 피크에서 머물다가, 다시 줄어듭니다. 이 패턴을 재현하는 것이 `stages` 입니다. 각 스테이지는 <E>얼마 동안(`duration`) VU를 몇까지(`target`) 올리거나 내린다</E>를 의미합니다.

```js title="stages-load.js"
export const options = {
  stages: [
    { duration: '30s', target: 20 }, // 30초간 0 → 20 VU 램프업
    { duration: '1m',  target: 20 }, // 1분간 20 VU 유지
    { duration: '30s', target: 50 }, // 30초간 20 → 50 VU 램프업
    { duration: '1m',  target: 50 }, // 1분간 50 VU 유지
    { duration: '30s', target: 0 },  // 30초간 50 → 0 VU 램프다운
  ],
};
```

k6는 이전 스테이지의 끝 VU 수에서 이번 `target`까지 **선형 보간**으로 VU를 조정합니다. 위 예시는 3분 30초짜리 테스트가 되고, 그래프로 그리면 사다리꼴 모양이 됩니다.

`stages`의 전형적 쓰임은 세 가지입니다.

| 목적 | 전형적 프로파일 | 관찰 포인트 |
|---|---|---|
| Load test | 평균과 피크를 램프업·유지·다운 | 예상 부하에서 SLO 통과 여부 |
| Stress test | `target`을 한계까지 계속 상승 | 응답이 무너지는 지점 |
| Soak test | 중간 부하 + 긴 `duration` (예: 2시간) | 메모리 누수, 커넥션 고갈 |

한 가지 알아둘 점은, `vus` + `duration`과 `stages`는 같은 `options` 안에서 **함께 쓰지 않습니다**. `stages`가 있으면 `vus`와 `duration`은 무시됩니다. 처음에는 `vus` + `duration`으로 시작해 감을 잡고, 램프업이 필요해지면 `stages`로 바꾸는 흐름이 자연스럽습니다.

## 응답 검증

부하만 주는 것으로는 부족합니다. <E>**응답이 실제로 올바르게 돌아왔는가**</E>를 매 iteration 확인해야 합니다. HTTP 상태 코드가 200이라고 끝나지 않습니다. 본문에 필수 필드가 있는지, 응답 시간이 기준 안에 들어오는지도 확인 대상입니다. 이 역할을 하는 것이 `check` 입니다.

```js title="check-basic.js"
import http from 'k6/http';
import { check, sleep } from 'k6';

export default function () {
  const res = http.get('https://test.k6.io/products/1');

  check(res, {
    'status is 200':     (r) => r.status === 200,
    'body has id field': (r) => r.json('id') !== undefined,
    'response < 500ms':  (r) => r.timings.duration < 500,
  });

  sleep(1);
}
```

`check`는 첫 번째 인자로 검증 대상을, 두 번째 인자로 `{ 라벨: (대상) => boolean }` 형태의 오브젝트를 받습니다. 각 항목이 true면 통과, false면 실패로 카운트됩니다.

두 가지 성질을 알아둬야 합니다.

첫째, **check 실패는 스크립트를 중단시키지 않습니다**. false가 나와도 VU는 다음 코드 줄을 계속 실행하고 다음 iteration으로 넘어갑니다. 실패는 **메트릭**으로 집계되어, 실행 종료 시 <E>이 check는 몇 퍼센트가 성공했다</E>가 리포트에 찍힙니다. 1000번 실행 중 950번만 성공이면 95% passed로 표시됩니다.

둘째, **check는 기록이지 판정이 아닙니다**. 테스트를 실패로 만들어 CI를 빨갛게 하고 싶다면 `options.thresholds`에 기준을 적어야 합니다. 예를 들어 `thresholds: { checks: ['rate>0.99'] }` 라고 하면 <E>모든 check의 성공률이 99% 이상이어야 한다</E>가 되고, 미만일 때 k6가 exit code 99로 종료됩니다. check는 데이터를 모으고, thresholds는 합격 여부를 정한다, 이 역할 분담이 k6의 검증 모델입니다.

자주 쓰는 응답 헬퍼는 네 가지로 거의 충분합니다.

| 헬퍼 | 의미 |
|---|---|
| `r.status` | HTTP 상태 코드 (숫자) |
| `r.json('path')` | JSON 응답 내부 경로 값 |
| `r.timings.duration` | 총 응답 시간(ms) |
| `r.body` | 원문 문자열 |

## 시나리오 조직화

스크립트가 커지면 **여러 단계로 이루어진 사용자 행동**을 한 iteration 안에 담게 됩니다. <E>홈 진입 → 상품 목록 조회 → 상품 상세 열기 → 장바구니 담기</E> 같은 흐름입니다. 이때 각 요청의 메트릭이 전부 `http_req_duration` 한 양동이에 섞이면, <E>상품 상세가 느린 건지 장바구니가 느린 건지</E>를 구분하지 못합니다. 이 문제를 푸는 두 도구가 `group`과 `tag` 입니다.

`group(이름, 함수)` 은 이름 붙은 블록을 만듭니다. 블록 안에서 발생한 메트릭에는 그 이름이 라벨로 붙고, 블록 자체의 소요 시간이 `group_duration` 으로 별도 집계됩니다.

```js title="groups.js"
import http from 'k6/http';
import { group, sleep } from 'k6';

export default function () {
  group('home', () => {
    http.get('https://shop.example.com/');
  });

  group('product list', () => {
    http.get('https://shop.example.com/products');
  });

  group('product detail', () => {
    http.get('https://shop.example.com/products/1');
    http.get('https://shop.example.com/products/1/reviews');
  });

  sleep(1);
}
```

`tag` 는 좀 더 일반적인 라벨 도구입니다. HTTP 요청, check, 커스텀 메트릭 어디에나 임의의 `key=value` 라벨을 붙일 수 있습니다. 가장 흔한 쓰임은 요청에 직접 이름을 다는 것입니다.

```js title="tags.js"
http.get('https://shop.example.com/products/1', {
  tags: { name: 'ProductDetail', endpoint: 'products/:id' },
});
```

`tags.name` 을 쓰는 이유는 URL 집계 문제 때문입니다. k6는 기본적으로 URL을 그대로 메트릭 라벨로 씁니다. `products/1`, `products/2`, `products/3`이 각각 다른 엔드포인트로 집계됩니다. `name: 'ProductDetail'` 을 달면 이 모든 요청이 한 라벨로 묶이고 <E>ProductDetail API의 p95가 얼마</E>를 볼 수 있게 됩니다.

두 도구의 역할을 정리하면 `group`은 **사용자 여정의 단계**를 표현하는 도구, `tag`는 **메트릭을 슬라이스하는 라벨**을 다는 도구입니다. `group`이 자동으로 `group` 태그를 붙이므로, 대시보드에서는 group 필터와 tag 필터를 함께 활용하게 됩니다.

## 실행과 결과

스크립트가 준비되면 실행은 `k6 run script.js` 한 줄입니다. 설치는 플랫폼별로 다음과 같습니다.

```bash title="install.sh"
# macOS
brew install k6

# Docker
docker run -i --rm grafana/k6 run - <script.js

# Linux (Debian/Ubuntu) 는 공식 APT 저장소 사용
sudo gpg -k
sudo gpg --no-default-keyring --keyring /usr/share/keyrings/k6-archive-keyring.gpg \
```

실행하면 먼저 **시작 배너**가 뜨고(사용 스크립트, 출력 대상, scenarios 설정), 실시간 진행 바가 흐른 뒤, 종료 시 **요약 리포트**가 출력됩니다.

```text title="k6 run 출력 예시"
     execution: local
        script: script.js
        output: -

     scenarios: (100.00%) 1 scenario, 10 max VUs, 1m30s max duration
              * default: 10 looping VUs for 1m0s

     data_received..................: 1.2 MB  20 kB/s
     data_sent......................: 88 kB   1.5 kB/s
     http_req_blocked...............: avg=1.2ms   p(95)=5µs
     http_req_connecting............: avg=800µs   p(95)=0s
     http_req_duration..............: avg=145ms   p(95)=210ms  p(99)=350ms
     http_req_failed................: 0.50%   ✓ 3    ✗ 597
     http_req_receiving.............: avg=2ms     p(95)=5ms
     http_req_sending...............: avg=50µs    p(95)=100µs
     http_req_waiting...............: avg=142ms   p(95)=205ms
     http_reqs......................: 600     10/s
     iteration_duration.............: avg=1.14s
     iterations.....................: 600     10/s
     vus............................: 10      min=10  max=10
     vus_max........................: 10
```

리포트는 크게 **세 덩어리**로 읽으면 됩니다.

첫 번째는 **요청 단위 메트릭**입니다. `http_req_duration`이 가장 중요합니다. <E>요청을 보내고 응답을 다 받기까지의 시간</E>이며, `avg`(평균), `p(95)`, `p(99)`로 리포트됩니다. 평균은 이상치에 약하므로 실무에서는 p95, p99를 기준으로 성능 판단을 합니다. 내부적으로 `http_req_duration` 은 `http_req_sending + http_req_waiting + http_req_receiving`의 합이며, 이 중 `waiting`(서버 처리 시간, TTFB)이 보통 대부분을 차지합니다.

두 번째는 **처리량 메트릭**입니다. `http_reqs`는 전체 요청 수와 RPS를, `iterations`는 전체 iteration 수와 초당 iteration 수를 보여줍니다. <E>내가 이번 테스트에서 실제로 몇 RPS를 줬는가</E>는 이 값으로 확인합니다.

세 번째는 **실패율 메트릭**입니다. `http_req_failed`는 실패한 요청 비율입니다. 위 예시의 `0.50% ✓ 3 ✗ 597` 는 <E>실패 3건, 성공 597건, 실패율 0.5%</E>라는 의미입니다. 기호가 관례적으로 반대로 보일 수 있으므로 비율과 숫자를 같이 보는 것이 안전합니다.

CI 연동은 종료 코드만 챙기면 됩니다.

| exit code | 의미 |
|---|---|
| 0 | 정상 종료 |
| 99 | `thresholds` 중 하나 이상 실패 |
| 107 | 스크립트 실행 에러 |

GitHub Actions, Jenkins, GitLab CI 같은 환경에서 `k6 run`의 exit status만 체크하면 통과 여부가 자동으로 연결됩니다.

부하 프로파일이 `stages`로 구성돼 있어도 위 리포트는 전체 실행 기준 집계만 담고 있습니다. 단계별 추이를 보려면 Prometheus remote-write나 InfluxDB로 내보내 Grafana 대시보드로 시계열을 봐야 하는데, 이 부분은 기초 범위 밖이고 다음 글에서 이어갑니다.

## 마무리

k6의 기초는 결국 하나의 문장으로 압축됩니다. **하나의 JS 파일에 VU, 부하 프로파일, 검증 기준을 모두 담고, `k6 run` 한 줄로 돌린다**. VU 모델만 이해하고 들어오면 `options`, `stages`, `check`, `group`, `tag`, 그리고 실행 리포트의 각 메트릭이 같은 실로 꿰어 있는 것이 보입니다.

다음 단계는 이 리포트를 시계열로 뽑아 대시보드로 보는 것입니다. 단계별 램프업에서 p95가 어느 구간부터 벌어지는지, 어느 그룹의 요청이 먼저 무너지는지를 한 장의 화면에서 추적하려면 Prometheus remote-write와 Grafana 연동이 다음 관문입니다. 이 파이프라인은 후속 글에서 다루겠습니다.
