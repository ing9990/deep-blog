이펙티브 자바 3판 6장은 <E>열거 타입(enum)과 애너테이션</E>을 다룬다. 자바 5에서 들어온 두 기능은 단순한 문법 추가가 아니라 그 이전 관행을 대체하기 위해 설계되었다. 열거 타입은 정수 상수 패턴을 대체하고, 애너테이션은 메서드 이름에 의미를 새겨 넣는 명명 패턴을 대체한다. 이 글은 6장의 여덟 아이템을 짧은 설명과 Before/After 코드 블록으로 빠르게 정리한다.

## int 상수 대신 열거 타입

자바 5 이전에는 한 묶음의 상수를 표현할 때 `public static final int`를 나열하는 정수 열거 패턴(int enum pattern)을 썼다. 이 패턴은 타입 안전성이 없다. 메서드 시그니처가 `int`를 받기 때문에 의미가 다른 두 묶음을 섞어 넘겨도 컴파일러가 막지 못한다. 출력하면 그저 숫자고, 디버거에서도 어떤 상수인지 알 수 없다.

자바의 `enum`은 클래스다. 각 상수에 해당하는 인스턴스를 JVM이 미리 하나씩 만들어두고, 그 외에는 새 인스턴스를 만들 수 없다(인스턴스 통제). 그래서 `==`로 동일성을 비교해도 안전하고, `switch`에 그대로 쓸 수 있으며, 메서드까지 추가할 수 있다.

<Tabs group="payment-enum">
  <Tab label="Before: int 상수">
```java title="PaymentMethod.java"
public class PaymentMethod {
    public static final int CARD          = 0;
    public static final int BANK_TRANSFER = 1;
    public static final int MOBILE        = 2;
}

// 호출부
int method = PaymentMethod.CARD;
process(method); // int 면 무엇이든 통과한다
process(99);     // 컴파일러는 막지 못한다
```
  </Tab>
  <Tab label="After: 열거 타입">
```java title="PaymentMethod.java"
public enum PaymentMethod {
    CARD, BANK_TRANSFER, MOBILE;
}

// 호출부
process(PaymentMethod.CARD);
// process(99); // 컴파일 에러
```
  </Tab>
</Tabs>

여기에 더해 enum은 <E>상수별 메서드 구현(constant-specific method implementation)</E>이라는 강력한 도구를 제공한다. 각 상수가 자신만의 동작을 가진 객체가 된다. 책의 정통 예시인 `Operation`이 가장 깔끔하다.

```java title="Operation.java"
public enum Operation {
    PLUS   { public double apply(double x, double y) { return x + y; } },
    MINUS  { public double apply(double x, double y) { return x - y; } },
    TIMES  { public double apply(double x, double y) { return x * y; } },
    DIVIDE { public double apply(double x, double y) { return x / y; } };

    public abstract double apply(double x, double y);
}

// 호출부
double r = Operation.PLUS.apply(2, 3); // 5.0
```

`switch`로 분기를 만들면 새 상수가 추가될 때마다 분기를 갱신하는 책임이 호출 쪽에 떨어진다. 상수별 메서드 구현은 그 책임을 enum 자체로 옮긴다.

## ordinal 대신 인스턴스 필드

`enum`이 제공하는 `ordinal()`은 그 상수가 선언된 순서(0부터 시작)를 반환한다. 이 값을 데이터로 쓰는 코드는 enum 상수의 순서가 바뀌는 순간 함께 바뀐다. 새 상수를 중간에 끼워 넣거나 같은 의미의 상수를 둘로 쪼개면 모든 데이터가 한 칸씩 밀린다.

데이터를 표현해야 한다면 별도 인스턴스 필드를 두고, `ordinal()` 대신 그 필드를 반환한다.

<Tabs group="ensemble-ordinal">
  <Tab label="Before: ordinal 그대로 사용">
```java title="Ensemble.java"
public enum Ensemble {
    SOLO, DUET, TRIO, QUARTET, QUINTET;

    public int numberOfMusicians() {
        return ordinal() + 1; // 순서가 바뀌는 즉시 깨진다
    }
}
```
  </Tab>
  <Tab label="After: 인스턴스 필드">
```java title="Ensemble.java"
public enum Ensemble {
    SOLO(1), DUET(2), TRIO(3), QUARTET(4), QUINTET(5);

    private final int numberOfMusicians;

    Ensemble(int size) { this.numberOfMusicians = size; }

    public int numberOfMusicians() { return numberOfMusicians; }
}
```
  </Tab>
</Tabs>

책은 `ordinal()`을 enum 자체가 사용하는 자료구조(`EnumSet`, `EnumMap`) 외의 자리에서는 쓰지 말라고 권한다.

## 비트 필드 대신 EnumSet

플래그를 OR로 합치는 비트 필드 패턴은 자바 이전부터 있었다. 작은 메모리에 여러 플래그를 담을 수 있고 비트 연산이 빠르지만, `int` 한 덩어리이기 때문에 `toString` 결과가 의미 없는 숫자고 모든 플래그를 순회하기도 까다롭다.

`EnumSet`은 내부적으로 비트 벡터로 구현되어 비트 필드와 같은 성능을 내면서, 외부로는 `Set<E>` 인터페이스를 노출한다. 가독성, 타입 안전, 반복, `toString`이 모두 정상이고 비용은 비트 필드와 같다.

<Tabs group="text-style-bitfield">
  <Tab label="Before: 비트 필드">
```java title="Text.java"
public class Text {
    public static final int STYLE_BOLD          = 1 << 0;
    public static final int STYLE_ITALIC        = 1 << 1;
    public static final int STYLE_UNDERLINE     = 1 << 2;
    public static final int STYLE_STRIKETHROUGH = 1 << 3;

    public void applyStyles(int styles) { /* ... */ }
}

text.applyStyles(STYLE_BOLD | STYLE_ITALIC);
```
  </Tab>
  <Tab label="After: EnumSet">
```java title="Text.java"
public class Text {
    public enum Style { BOLD, ITALIC, UNDERLINE, STRIKETHROUGH }

    public void applyStyles(Set<Style> styles) { /* ... */ }
}

text.applyStyles(EnumSet.of(Style.BOLD, Style.ITALIC));
// toString: [BOLD, ITALIC]
```
파라미터 타입은 구체 타입(`EnumSet`) 대신 인터페이스(`Set`)로 받는 편이 유연하다.
  </Tab>
</Tabs>

## ordinal 인덱싱 대신 EnumMap

enum 상수를 키로 어떤 데이터(주로 컬렉션)를 묶을 때, `ordinal()` 값을 배열 인덱스로 쓰는 코드를 만들 수 있다. 이 방식은 비검사 형변환(`new List[..]`)을 만들고, 정수와 enum 사이 매핑을 사람이 추적해야 하며, Item 35의 ordinal 의존성을 그대로 떠안는다.

`EnumMap`은 enum을 키로 쓰는 `Map` 구현이다. 내부적으로 배열로 동작하므로 성능은 ordinal 인덱싱과 동등하지만, 타입 안전하고 키-값 의미가 코드에 그대로 드러난다.

<Tabs group="orders-by-status">
  <Tab label="Before: ordinal 배열">
```java title="OrderGrouper.java"
List<Order>[] byStatus = new List[OrderStatus.values().length];
for (int i = 0; i < byStatus.length; i++) byStatus[i] = new ArrayList<>();

for (Order o : orders) {
    byStatus[o.getStatus().ordinal()].add(o);
}

System.out.println(byStatus[OrderStatus.PAID.ordinal()]);
```
  </Tab>
  <Tab label="After: EnumMap">
```java title="OrderGrouper.java"
Map<OrderStatus, List<Order>> byStatus =
        new EnumMap<>(OrderStatus.class);
for (OrderStatus s : OrderStatus.values()) byStatus.put(s, new ArrayList<>());

for (Order o : orders) {
    byStatus.get(o.getStatus()).add(o);
}

// 스트림 방식
Map<OrderStatus, List<Order>> grouped = orders.stream()
    .collect(groupingBy(Order::getStatus,
                        () -> new EnumMap<>(OrderStatus.class),
                        toList()));
```
  </Tab>
</Tabs>

## 확장 가능한 열거 타입은 인터페이스로

enum은 다른 enum을 상속(extends)할 수 없다. 자바의 모든 enum은 자동으로 `Enum`을 상속하기 때문이다. 그렇지만 enum이 인터페이스를 <E>구현(implements)</E>하는 것은 가능하다. 이 사실을 이용하면 클라이언트가 자신의 enum을 추가해 기능을 확장할 수 있다.

<Tabs group="operation-extensible">
  <Tab label="Before: 단일 enum">
```java title="Operation.java"
public enum Operation {
    PLUS  { public double apply(double x, double y) { return x + y; } },
    MINUS { public double apply(double x, double y) { return x - y; } };

    public abstract double apply(double x, double y);
}

// 클라이언트는 새 연산을 추가할 방법이 없다
```
  </Tab>
  <Tab label="After: 인터페이스 + 구현 enum">
```java title="Operation.java"
public interface Operation {
    double apply(double x, double y);
}

public enum BasicOperation implements Operation {
    PLUS  { public double apply(double x, double y) { return x + y; } },
    MINUS { public double apply(double x, double y) { return x - y; } }
}

// 클라이언트가 자신의 구현 enum을 추가할 수 있다
public enum ExtendedOperation implements Operation {
    EXP       { public double apply(double x, double y) { return Math.pow(x, y); } },
    REMAINDER { public double apply(double x, double y) { return x % y; } }
}

// 받는 쪽은 Operation 또는 Class<T extends Enum<T> & Operation> 으로 받는다
public static <T extends Enum<T> & Operation> void test(Class<T> opType) {
    for (Operation op : opType.getEnumConstants()) {
        System.out.println(op.apply(2, 3));
    }
}
```
  </Tab>
</Tabs>

이 패턴의 한 가지 약점은 구현체 사이에 코드를 공유하기 어렵다는 점이다. 공통 동작이 길면 helper 클래스로 빼서 위임한다.

## 명명 패턴 대신 애너테이션

JUnit 3는 테스트 메서드 이름이 `test`로 시작해야 하는 명명 패턴을 썼다. 이 방식은 오타를 막을 길이 없고(`tsetMethod()`는 그냥 무시된다), 의도한 자리에만 적용했는지 보장할 수 없으며, 매개변수를 전달할 방법도 없다.

애너테이션은 그 모든 한계를 해결한다. 컴파일러가 형식을 검증하고, 매개변수를 받을 수 있으며, 적용 대상(`@Target`)을 명시해 잘못된 자리에 붙는 것을 막는다.

<Tabs group="test-marker">
  <Tab label="Before: 명명 패턴">
```java title="SafetyTests.java"
public class SafetyTests {
    public void testSomething()  { /* ... */ }
    public void tsetTypoSafety() { /* ... 오타. 영영 실행되지 않는다 */ }
}

// Runner
for (Method m : cls.getDeclaredMethods()) {
    if (m.getName().startsWith("test")) m.invoke(cls.newInstance());
}
```
  </Tab>
  <Tab label="After: 마커 애너테이션">
```java title="Test.java"
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface Test { }

public class SafetyTests {
    @Test public void doesSomething() { /* ... */ }
    @Test public void doesAnother()   { /* ... */ }
}

// Runner
for (Method m : cls.getDeclaredMethods()) {
    if (m.isAnnotationPresent(Test.class)) m.invoke(...);
}
```
  </Tab>
</Tabs>

매개변수가 필요하면 애너테이션 요소(element)를 정의한다. 예를 들어 "특정 예외가 던져져야 통과"하는 테스트라면 `@ExceptionTest(ArithmeticException.class)`처럼 클래스 객체를 인수로 받는다.

## @Override를 일관되게

`@Override`는 그 메서드가 상위 타입의 메서드를 재정의하고 있음을 컴파일러에게 알리는 애너테이션이다. 모든 재정의 자리에 빠짐없이 붙이면 컴파일러가 시그니처 실수를 걸러낸다.

가장 자주 등장하는 사고는 `Object.equals(Object)`를 재정의하려다 `equals(MyType)`을 정의해버리는 것이다. 두 메서드는 시그니처가 달라서 오버로딩일 뿐 오버라이딩이 아니다. `Object.equals`는 그대로 남아 있고, 사용자가 만든 `equals(MyType)`은 동치 비교가 필요한 자리(`HashMap`, `HashSet`)에서 호출되지 않는다.

<Tabs group="override-equals">
  <Tab label="Before: @Override 누락">
```java title="Bigram.java"
public class Bigram {
    private final char first, second;

    public boolean equals(Bigram b) {       // 오버라이딩이 아니다
        return b.first == first && b.second == second;
    }

    public int hashCode() { return 31 * first + second; }
}

Set<Bigram> s = new HashSet<>();
s.add(new Bigram('a', 'b'));
s.contains(new Bigram('a', 'b'));   // false. Object.equals 가 호출됨
```
  </Tab>
  <Tab label="After: @Override 일관 적용">
```java title="Bigram.java"
public class Bigram {
    private final char first, second;

    @Override
    public boolean equals(Object o) {
        if (!(o instanceof Bigram b)) return false;
        return b.first == first && b.second == second;
    }

    @Override
    public int hashCode() { return 31 * first + second; }
}
// 만약 처음에 equals(Bigram b) 자리에 @Override 를 붙였다면
// 컴파일러가 즉시 "상위 메서드 없음" 으로 막아준다
```
  </Tab>
</Tabs>

추상 메서드를 구현하는 자리는 빼먹으면 컴파일이 안 되므로 컴파일러가 잡아낼 실수가 없다. 그래도 IDE 점프와 코드 리뷰의 일관성을 위해 그 자리에도 붙여두는 편이 일반적이다.

## 마커 인터페이스

빈 인터페이스(메서드 없음)를 마커로 쓰는 패턴이 있다. `Serializable`이 가장 익숙한 예다. 같은 일을 마커 애너테이션(`@Target` 등으로 만든 빈 애너테이션)으로도 할 수 있는데, 두 도구는 어디에 어떻게 다른지가 분명하다.

마커 인터페이스는 그 자체로 <E>타입</E>이다. 따라서 메서드 시그니처에 그 타입을 받게 만들면 컴파일러가 호출 시점에 검사할 수 있다. 책은 `ObjectOutputStream.write`가 `Object`가 아니라 `Serializable`을 받았더라면 직렬화 불가 객체를 컴파일 타임에 거를 수 있었다고 지적한다.

마커 애너테이션은 클래스, 메서드, 필드 등 더 다양한 자리에 붙일 수 있고, 애너테이션 요소를 추가해 정보를 담을 수 있다. 그 외에는 단순 마커로서의 기능이다.

```java title="Marker.java"
// 마커 인터페이스. 그 자체로 타입이다
public interface Serializable { }

public class ObjectOutputStream {
    // 만약 이 시그니처라면 컴파일 타임 타입 체크가 가능하다
    public void writeObject(Serializable o) { /* ... */ }
}

// 마커 애너테이션. 컴파일러는 타입으로 인식하지 않는다
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
public @interface MyMarker { }

@MyMarker
public class Foo { /* ... */ }
```

선택 기준은 단순하다. 마킹된 객체를 받는 메서드를 만들 일이 있다면 마커 인터페이스, 단순히 "이 클래스에 이런 속성이 있다"는 정보만 남기고 싶다면 마커 애너테이션을 쓴다. 클래스나 인터페이스가 아닌 자리(예: 메서드 한정)에 붙여야 한다면 자연히 마커 애너테이션 쪽이다.

## 정리

- <E>Item 34.</E> int 상수 대신 enum을 쓴다. 타입 안전성, 인스턴스 통제, 메서드 추가가 따라온다.
- <E>Item 35.</E> enum의 `ordinal`은 데이터 표현에 쓰지 않는다. 인스턴스 필드를 둔다.
- <E>Item 36.</E> 비트 필드가 필요해 보이면 `EnumSet`을 쓴다. 같은 성능에 가독성과 타입 안전을 모두 얻는다.
- <E>Item 37.</E> enum을 키로 묶을 때는 `EnumMap`을 쓴다. ordinal 배열 인덱싱은 형변환과 의미 추적 비용을 만든다.
- <E>Item 38.</E> enum을 확장하고 싶으면 enum 자체가 아니라 인터페이스를 정의하고 enum이 그 인터페이스를 구현하게 한다.
- <E>Item 39.</E> 명명 패턴 대신 애너테이션을 쓴다. 오타, 오용, 매개변수 전달 모두 컴파일러가 검증해준다.
- <E>Item 40.</E> 재정의하는 모든 메서드에 `@Override`를 붙인다. 시그니처 실수를 컴파일러가 막아준다.
- <E>Item 41.</E> 타입을 정의하는 마커는 인터페이스, 정보만 남기는 마커는 애너테이션. 컴파일 타임 타입 체크가 필요한지가 갈림길이다.

여덟 아이템의 공통점은 분명하다. <E>의도가 있다면 코드에 명시적으로 표현하라</E>는 것이다. 정수에 의미를 얹지 말고 enum으로, 메서드 이름에 의미를 새기지 말고 애너테이션으로, 빈 인터페이스로 표시할 수 있는 속성은 인터페이스로. 컴파일러가 검증할 수 있는 형태로 의도를 옮길수록 그 코드는 견고해진다.
