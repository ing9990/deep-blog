Redis를 쓰는 Spring 애플리케이션에서 가장 먼저 만나는 클래스가 `RedisTemplate`입니다. Redis 명령을 Java나 Kotlin 메서드 호출처럼 쓸 수 있게 감싸 둔 facade인데, 여기에 의존성, 직렬화, 자료구조별 ops 같은 작은 함정들이 입문자를 가장 많이 막습니다. 이 글은 그 함정을 한 번에 통과하기 위한 최소 지도입니다.

<Note title="이 글의 학습 목표">
  - RedisTemplate과 StringRedisTemplate이 내부에서 어떻게 다른지 이해한다
  - Serializer 4-슬롯과 ConnectionFactory 자동 구성을 구분할 수 있다
  - 7종 `opsForXxx` 진입점을 골라 캐시, 카운터, 프로필 같은 시나리오에 적용하는 기준을 얻는다
</Note>

## RedisTemplate란

`RedisTemplate`은 Spring Data Redis가 제공하는 Redis 연동의 표준 추상 클래스입니다. 한 문장으로 줄이면 <E>Redis 명령을 Java나 Kotlin 메서드 호출처럼 쓸 수 있게 감싸 둔 facade</E>입니다.

내부를 펼쳐 보면 세 층이 쌓여 있습니다.

```text title="호출 흐름"
[ RedisTemplate / StringRedisTemplate ]   ← 자료구조별 ops, 직렬화, 예외 변환
            │
[ RedisConnection (Lettuce | Jedis) ]    ← 실제 socket 통신, 명령 인코딩
            │
[ Redis Server ]                          ← redis-cli로 보는 그 서버
```

`RedisTemplate` 자체가 네트워크 IO를 하는 게 아니라, 하부의 `RedisConnectionFactory`(기본은 `LettuceConnectionFactory`)에서 connection을 빌려와 명령을 보냅니다. 우리가 `redisTemplate.opsForValue().set(...)`이라 쓰면 안에서는 connection 획득, SET 명령 인코딩, 응답 디코딩, connection 반환의 흐름이 자동으로 돌아갑니다.

여기서 입문자가 가장 먼저 헷갈리는 것은 **두 가지 템플릿이 비슷하게 생겼다**는 점입니다.

| 클래스 | Key/Value 타입 | 직렬화 | 적합한 용도 |
|---|---|---|---|
| `StringRedisTemplate` | `String` 고정 | `StringRedisSerializer` 고정 | 카운터, 토큰, 단순 문자열 캐시 |
| `RedisTemplate<K, V>` | 제네릭 | Serializer 직접 주입 | 객체 저장(JSON), Hash, 그 외 모든 케이스 |

Redis 자체가 무엇이고 왜 단일 스레드 이벤트 루프인지 같은 deep-dive는 별도 글이 있으니, 이 글에서는 다음 한 줄만 기억하면 충분합니다. **Redis는 원격 자료구조 서버, RedisTemplate은 그 명령을 Java나 Kotlin에서 호출하기 위한 클라이언트 측 facade**.

## 셋업

셋업은 두 단계입니다. 의존성 추가와 ConnectionFactory 자동 구성 확인입니다. Spring Boot Starter가 대부분을 처리해주지만, 어떤 빈이 자동으로 떠오르는지 알아야 다음 절에서 직렬화 재정의가 필요한 이유를 이해할 수 있습니다.

### 의존성 추가

`spring-boot-starter-data-redis`는 Lettuce 드라이버를 기본으로 끌어옵니다. Lettuce는 Netty 기반의 비차단 Redis 클라이언트로, 단일 connection을 여러 스레드가 안전하게 공유할 수 있어 별도 풀 없이도 동작합니다. 반대로 Jedis는 connection-per-thread 모델이라 풀이 거의 필수입니다.

<Tabs group="dsl">
  <Tab label="Groovy DSL">
    ```groovy title="build.gradle"
    dependencies {
        implementation 'org.springframework.boot:spring-boot-starter-data-redis'
    }
    ```
  </Tab>
  <Tab label="Kotlin DSL">
    ```kotlin title="build.gradle.kts"
    dependencies {
        implementation("org.springframework.boot:spring-boot-starter-data-redis")
    }
    ```
  </Tab>
</Tabs>

Jedis로 바꾸려면 Lettuce를 명시적으로 제외하고 Jedis를 추가합니다.

<Tabs group="dsl">

  </Tab>
  <Tab label="Kotlin DSL">

    ```kotlin title="build.gradle.kts"
            exclude(group = "io.lettuce", module = "lettuce-core")

    }
    ```
  </Tab>
</Tabs>

### 연결 정보

Spring Boot 3.x부터 prefix는 `spring.data.redis`입니다. 이전(2.x 이하) `spring.redis`에서 옮겨졌으므로 마이그레이션 시 이 부분에서 자주 막힙니다.

```yaml title="application.yml"
spring:
  data:
    redis:
      host: localhost
      port: 6379
      password: ""
      timeout: 2s
      lettuce:
        pool:
          max-active: 8
          max-idle: 8
          min-idle: 0
```

### 자동 등록되는 빈

`RedisAutoConfiguration`이 다음 빈을 컨테이너에 띄웁니다.

- `LettuceConnectionFactory`: 위 yml을 읽어 생성
- `RedisTemplate<Object, Object>`: JDK Serializer 기본
- `StringRedisTemplate`: `String` Serializer 고정

코드에서는 그냥 주입받아 씁니다. 생성자 주입을 권장합니다.

<Tabs group="lang">
  <Tab label="Java">
    ```java title="UserCacheService.java"
    @Service
    public class UserCacheService {
        private final StringRedisTemplate stringRedisTemplate;
        private final RedisTemplate<String, Object> redisTemplate;

        public UserCacheService(
            StringRedisTemplate stringRedisTemplate,
            RedisTemplate<String, Object> redisTemplate
        ) {
            this.stringRedisTemplate = stringRedisTemplate;
            this.redisTemplate = redisTemplate;
        }
    }
    ```
  </Tab>
  <Tab label="Kotlin">
    ```kotlin title="UserCacheService.kt"
    @Service
    class UserCacheService(
        private val stringRedisTemplate: StringRedisTemplate,
        private val redisTemplate: RedisTemplate<String, Any>,
    )
    ```
  </Tab>
</Tabs>

여기서 한 가지 함정이 있습니다. 자동 등록된 `RedisTemplate<Object, Object>`의 기본 Serializer는 JDK 직렬화라, 그대로 `set("user:1", userObject)`을 호출하면 redis-cli에 `\xAC\xED\x00\x05`로 시작하는 바이너리가 들어갑니다. 입문자가 <E>왜 CLI에 키가 안 보이지?</E>로 가장 자주 막히는 지점입니다. 다음 절에서 이 부분을 본격적으로 다룹니다.

## 직렬화

<Callout type="warning" title="이 글의 핵심 포인트">
  RedisTemplate에는 **Serializer 슬롯이 4개** 있습니다. 한 슬롯만 빠뜨려도 redis-cli 화면에 바이너리가 박힙니다. 이 4-슬롯 모델만 잡아두면 직렬화 관련 문제 대부분이 한 자리에서 풀립니다.
</Callout>

### 4-슬롯 모델

| 슬롯 | 적용 대상 | 적용되는 명령 예시 |
|---|---|---|
| `keySerializer` | 최상위 Key | `SET user:1 ...` 의 `user:1` |
| `valueSerializer` | 최상위 Value | 위 명령의 value 자리 |
| `hashKeySerializer` | Hash field | `HSET user:1 name ...` 의 `name` |
| `hashValueSerializer` | Hash field value | 위의 value 자리 |

`RedisTemplate<K, V>`의 제네릭 타입 `K, V`는 최상위 키와 값에만 적용됩니다. Hash 안의 field와 그 value는 별도로 지정해야 한다는 점이 헷갈리는 부분입니다. 4개 모두 명시하지 않으면 비어 있는 자리에 JDK Serializer가 들어가 바이너리가 박힙니다.

<Callout type="error" title="핵심 통찰: 직렬화 슬롯 4개가 사용성의 분기점이다">
  RedisTemplate의 사용성은 빌더나 어노테이션이 아니라, **이 4개 슬롯을 무엇으로 채웠는가**로 결정됩니다. 키는 `String`, 값은 JSON이라는 한 가지 조합만 잡아두면 redis-cli에서 키를 식별할 수 있고 값은 사람이 읽을 수 있는 형태로 저장됩니다.
</Callout>

### 자주 쓰는 Serializer

- `StringRedisSerializer`: UTF-8 문자열. CLI에서 그대로 보임
- `GenericJackson2JsonRedisSerializer`: 임의 객체를 JSON으로 변환, `@class` 타입 메타데이터 포함 → 역직렬화 시 타입 안전
- `Jackson2JsonRedisSerializer<T>`: 타입 고정. `@class` 없음, 다른 언어 클라이언트와 공유에 적합하지만 한 템플릿이 한 타입만 다룰 수 있음

가장 흔한 조합은 키는 `String`, 값은 JSON입니다. CLI에서 키 식별이 가능하고, 값은 사람이 읽을 수 있는 JSON으로 디버깅이 쉽습니다.

### 커스텀 RedisTemplate 빈 등록

<Tabs group="lang">
  <Tab label="Java">
    ```java title="RedisConfig.java"
    @Configuration
    public class RedisConfig {

        @Bean
        public RedisTemplate<String, Object> redisTemplate(
            RedisConnectionFactory connectionFactory
        ) {
            RedisTemplate<String, Object> template = new RedisTemplate<>();
            template.setConnectionFactory(connectionFactory);

            StringRedisSerializer stringSerializer = new StringRedisSerializer();
            GenericJackson2JsonRedisSerializer jsonSerializer =
                new GenericJackson2JsonRedisSerializer();

            template.setKeySerializer(stringSerializer);
            template.setValueSerializer(jsonSerializer);
            template.setHashKeySerializer(stringSerializer);
            template.setHashValueSerializer(jsonSerializer);

            template.afterPropertiesSet();
            return template;
        }
    }
    ```
  </Tab>
  <Tab label="Kotlin">
    ```kotlin title="RedisConfig.kt"
    @Configuration
    class RedisConfig {

        @Bean
        fun redisTemplate(
            connectionFactory: RedisConnectionFactory,
        ): RedisTemplate<String, Any> {
            val stringSerializer = StringRedisSerializer()
            val jsonSerializer = GenericJackson2JsonRedisSerializer()

            return RedisTemplate<String, Any>().apply {
                setConnectionFactory(connectionFactory)
                keySerializer = stringSerializer
                valueSerializer = jsonSerializer
                hashKeySerializer = stringSerializer
                hashValueSerializer = jsonSerializer
                afterPropertiesSet()
            }
        }
    }
    ```
  </Tab>
</Tabs>

`afterPropertiesSet()`을 빠뜨리면 내부 검증이 안 돌아 일부 동작이 NPE를 던집니다. 빈 정의 마지막에 반드시 호출하는 관용구로 익숙해지면 됩니다.

### 결과 비교

직렬화를 재정의하기 전후로 redis-cli에 보이는 모습이 완전히 달라집니다.

```text title="JDK Serializer 기본 (재정의 전)"
127.0.0.1:6379> KEYS *
1) "\xac\xed\x00\x05t\x00\x06user:1"
127.0.0.1:6379> GET "\xac\xed..."
"\xac\xed\x00\x05sr\x00\x1ccom.example.User..."
```

```text title="String + JSON Serializer (재정의 후)"
127.0.0.1:6379> KEYS user:*
1) "user:1"
127.0.0.1:6379> GET user:1
"{\"@class\":\"com.example.User\",\"id\":1,\"name\":\"Alice\"}"
```

이 차이가 실서비스에서 거의 모든 팀이 RedisTemplate Serializer를 재정의하는 이유입니다.

## ops 진입점

`RedisTemplate`은 자료구조마다 별도 진입점을 제공합니다. `redisTemplate.opsForXxx()` 메서드로 받아 명령을 호출하는 방식입니다. Redis가 7가지 자료구조를 지원하므로 ops도 7종입니다.

| 메서드 | Redis 자료구조 | 인터페이스 | 대표 명령 |
|---|---|---|---|
| `opsForValue()` | String | `ValueOperations` | `SET`, `GET`, `INCR`, `SETNX` |
| `opsForList()` | List | `ListOperations` | `LPUSH`, `RPUSH`, `LRANGE`, `LPOP` |
| `opsForSet()` | Set | `SetOperations` | `SADD`, `SMEMBERS`, `SISMEMBER` |
| `opsForZSet()` | Sorted Set | `ZSetOperations` | `ZADD`, `ZRANGE`, `ZRANGEBYSCORE` |
| `opsForHash()` | Hash | `HashOperations` | `HSET`, `HGET`, `HGETALL` |
| `opsForStream()` | Stream | `StreamOperations` | `XADD`, `XREAD` |
| `opsForGeo()` | Geo | `GeoOperations` | `GEOADD`, `GEORADIUS` |

각 자료구조 자체의 의미는 별도 글에서 다루므로, 여기서는 RedisTemplate 메서드 이름과 Redis 명령의 매핑만 짚고 넘어갑니다.

### opsForValue: String

<Tabs group="lang">
  <Tab label="Java">
    ```java title="ValueOperations 사용"
    ValueOperations<String, Object> ops = redisTemplate.opsForValue();

    ops.set("user:1:name", "Alice");                              // SET
    ops.set("session:abc", token, Duration.ofMinutes(30));        // SET ... EX
    Object name = ops.get("user:1:name");                         // GET
    Boolean acquired = ops.setIfAbsent("lock:order:42", "owner"); // SETNX
    Long views = ops.increment("page:home:views");                // INCR
    ```
  </Tab>
  <Tab label="Kotlin">
    ```kotlin title="ValueOperations 사용"
    val ops = redisTemplate.opsForValue()

    ops.set("user:1:name", "Alice")                               // SET
    ops.set("session:abc", token, Duration.ofMinutes(30))         // SET ... EX
    val name = ops.get("user:1:name")                             // GET
    val acquired = ops.setIfAbsent("lock:order:42", "owner")      // SETNX
    val views = ops.increment("page:home:views")                  // INCR
    ```
  </Tab>
</Tabs>

`setIfAbsent`가 `SETNX`라는 점은 분산 락의 출발점입니다. 락 자체의 안전성(TTL과 해제의 원자성, 락 홀더 식별)은 별도 주제입니다.

### opsForHash: Hash

Hash는 4-슬롯 직렬화에서 `hashKeySerializer`와 `hashValueSerializer`가 적용되는 지점입니다.

<Tabs group="lang">
  <Tab label="Java">
    ```java title="HashOperations 사용"
    HashOperations<String, String, Object> ops = redisTemplate.opsForHash();

    ops.put("user:42", "name", "Alice");                          // HSET
    ops.putAll("user:42", Map.of("age", 30, "city", "Seoul"));    // HMSET
    Object name = ops.get("user:42", "name");                     // HGET
    Map<String, Object> all = ops.entries("user:42");             // HGETALL
    ```
  </Tab>
  <Tab label="Kotlin">
    ```kotlin title="HashOperations 사용"
    val ops: HashOperations<String, String, Any> = redisTemplate.opsForHash()

    ops.put("user:42", "name", "Alice")                           // HSET
    ops.putAll("user:42", mapOf("age" to 30, "city" to "Seoul"))  // HMSET
    val name = ops.get("user:42", "name")                         // HGET
    val all = ops.entries("user:42")                              // HGETALL
    ```
  </Tab>
</Tabs>

`HashOperations`의 제네릭은 `<H, HK, HV>` (Hash key, Hash field, Hash value) 3개입니다. RedisTemplate의 4 슬롯 중 `hashKeySerializer`가 `HK`, `hashValueSerializer`가 `HV`에 매핑됩니다.

### opsForList, opsForSet, opsForZSet

리스트, 집합, 정렬 집합은 명령명이 직관적이라 사용법만 빠르게 훑습니다.

<Tabs group="lang">
  <Tab label="Java">
    ```java title="List, Set, ZSet"
    redisTemplate.opsForList().leftPush("queue:tasks", "task-1");      // LPUSH
    List<Object> tasks = redisTemplate.opsForList().range("queue:tasks", 0, -1); // LRANGE 0 -1

    redisTemplate.opsForSet().add("tags:post:1", "redis", "spring");   // SADD
    Set<Object> tags = redisTemplate.opsForSet().members("tags:post:1"); // SMEMBERS

    redisTemplate.opsForZSet().add("leaderboard", "alice", 1500);      // ZADD
    Set<Object> top10 = redisTemplate.opsForZSet().reverseRange("leaderboard", 0, 9); // ZREVRANGE
    ```
  </Tab>
  <Tab label="Kotlin">
    ```kotlin title="List, Set, ZSet"
    redisTemplate.opsForList().leftPush("queue:tasks", "task-1")       // LPUSH
    val tasks = redisTemplate.opsForList().range("queue:tasks", 0, -1) // LRANGE 0 -1

    redisTemplate.opsForSet().add("tags:post:1", "redis", "spring")    // SADD
    val tags = redisTemplate.opsForSet().members("tags:post:1")        // SMEMBERS

    redisTemplate.opsForZSet().add("leaderboard", "alice", 1500.0)     // ZADD
    val top10 = redisTemplate.opsForZSet().reverseRange("leaderboard", 0, 9) // ZREVRANGE
    ```
  </Tab>
</Tabs>

### Key 자체에 대한 명령

ops 바깥에서 키 자체를 다루는 명령(`EXPIRE`, `DEL`, `EXISTS`, `TYPE`)은 RedisTemplate에 직접 메서드로 노출됩니다.

<Tabs group="lang">
  <Tab label="Java">
    ```java title="Key-level 명령"
    redisTemplate.expire("user:42", Duration.ofHours(1));   // EXPIRE
    Boolean exists = redisTemplate.hasKey("user:42");       // EXISTS
    redisTemplate.delete("user:42");                        // DEL
    ```
  </Tab>
  <Tab label="Kotlin">
    ```kotlin title="Key-level 명령"
    redisTemplate.expire("user:42", Duration.ofHours(1))    // EXPIRE
    val exists = redisTemplate.hasKey("user:42")            // EXISTS
    redisTemplate.delete("user:42")                         // DEL
    ```
  </Tab>
</Tabs>

여기까지가 RedisTemplate API의 큰 지도입니다. 메서드 이름이 Redis 명령과 거의 1:1로 대응하므로, 명령 이름을 알면 IDE 자동완성으로 메서드를 찾을 수 있습니다.

## 시나리오

이제 앞서 본 셋업, 직렬화, ops를 묶어 작은 시나리오 세 개를 돌려봅니다. 각 예제는 한 화면 안에 들어가는 최소 코드로, 개념이 실제로 어떻게 호출되는가를 보여주는 게 목적입니다.

### 시나리오 1: TTL 캐시

DB 조회 결과를 10분간 캐시했다가 만료 후 자동으로 다시 채우는 가장 단순한 read-through 흉내입니다.

<Tabs group="lang">
  <Tab label="Java">
    ```java title="UserCacheService.java"
    @Service
    public class UserCacheService {
        private final RedisTemplate<String, Object> redisTemplate;
        private final UserRepository userRepository;

        public UserCacheService(
            RedisTemplate<String, Object> redisTemplate,
            UserRepository userRepository
        ) {
            this.redisTemplate = redisTemplate;
            this.userRepository = userRepository;
        }

        public User findById(Long id) {
            String key = "user:" + id;
            Object cached = redisTemplate.opsForValue().get(key);
            if (cached != null) {
                return (User) cached;
            }
            User user = userRepository.findById(id).orElseThrow();
            redisTemplate.opsForValue().set(key, user, Duration.ofMinutes(10));
            return user;
        }
    }
    ```
  </Tab>
  <Tab label="Kotlin">
    ```kotlin title="UserCacheService.kt"
    @Service
    class UserCacheService(
        private val redisTemplate: RedisTemplate<String, Any>,
        private val userRepository: UserRepository,
    ) {
        fun findById(id: Long): User {
            val key = "user:$id"
            val cached = redisTemplate.opsForValue().get(key) as? User
            return cached ?: userRepository.findById(id)
                .orElseThrow()
                .also { redisTemplate.opsForValue().set(key, it, Duration.ofMinutes(10)) }
        }
    }
    ```
  </Tab>
</Tabs>

직렬화 절에서 본 설정 덕분에 redis-cli로 `GET user:1`을 쳤을 때 사람이 읽을 수 있는 JSON이 떨어집니다.

### 시나리오 2: 페이지 뷰 카운터

`opsForValue().increment(key)`는 INCR 명령을 호출합니다. Redis 단일 스레드 특성 때문에 별도 락 없이 안전하게 카운트가 누적됩니다.

<Tabs group="lang">
  <Tab label="Java">
    ```java title="PageViewCounter.java"
    @Service
    public class PageViewCounter {
        private final StringRedisTemplate stringRedisTemplate;

        public PageViewCounter(StringRedisTemplate stringRedisTemplate) {
            this.stringRedisTemplate = stringRedisTemplate;
        }

        public Long incrementView(String pageId) {
            String key = "page:" + pageId + ":views";
            return stringRedisTemplate.opsForValue().increment(key);
        }

        public Long currentViews(String pageId) {
            String value = stringRedisTemplate.opsForValue().get("page:" + pageId + ":views");
            return value == null ? 0L : Long.parseLong(value);
        }
    }
    ```
  </Tab>
  <Tab label="Kotlin">
    ```kotlin title="PageViewCounter.kt"
    @Service
    class PageViewCounter(
        private val stringRedisTemplate: StringRedisTemplate,
    ) {
        fun incrementView(pageId: String): Long? =
            stringRedisTemplate.opsForValue().increment("page:$pageId:views")

        fun currentViews(pageId: String): Long =
            stringRedisTemplate.opsForValue().get("page:$pageId:views")?.toLong() ?: 0L
    }
    ```
  </Tab>
</Tabs>

이 시나리오에서는 객체를 다룰 일이 없어 `StringRedisTemplate`이 더 단순합니다. 직렬화 설정도 필요 없고 redis-cli에서 그대로 보입니다.

### 시나리오 3: 사용자 프로필 Hash

여러 필드를 가진 사용자 정보를 Hash로 저장하면, 이름만 바뀐 경우 이름 필드만 갱신할 수 있습니다. `String`에 JSON으로 저장하면 전체를 다시 직렬화해야 합니다.

<Tabs group="lang">
  <Tab label="Java">
    ```java title="UserProfileStore.java"
    @Service
    public class UserProfileStore {
        private final RedisTemplate<String, Object> redisTemplate;

        public UserProfileStore(RedisTemplate<String, Object> redisTemplate) {
            this.redisTemplate = redisTemplate;
        }

        public void save(Long userId, String name, int age, String city) {
            String key = "user:" + userId;
            redisTemplate.opsForHash().putAll(
                key,
                Map.of("name", name, "age", age, "city", city)
            );
            redisTemplate.expire(key, Duration.ofDays(1));
        }

        public void updateName(Long userId, String newName) {
            redisTemplate.opsForHash().put("user:" + userId, "name", newName);
        }

        public Map<Object, Object> load(Long userId) {
            return redisTemplate.opsForHash().entries("user:" + userId);
        }
    }
    ```
  </Tab>
  <Tab label="Kotlin">
    ```kotlin title="UserProfileStore.kt"
    @Service
    class UserProfileStore(
        private val redisTemplate: RedisTemplate<String, Any>,
    ) {
        fun save(userId: Long, name: String, age: Int, city: String) {
            val key = "user:$userId"
            redisTemplate.opsForHash<String, Any>().putAll(
                key,
                mapOf("name" to name, "age" to age, "city" to city),
            )
            redisTemplate.expire(key, Duration.ofDays(1))
        }

        fun updateName(userId: Long, newName: String) {
            redisTemplate.opsForHash<String, Any>().put("user:$userId", "name", newName)
        }

        fun load(userId: Long): Map<Any, Any> =
            redisTemplate.opsForHash<Any, Any>().entries("user:$userId")
    }
    ```
  </Tab>
</Tabs>

세 시나리오 모두 공통 패턴이 보입니다. **빈 주입, ops 진입점 호출, 명령 실행**의 3단 흐름입니다. RedisTemplate이 익숙해지면 새 자료구조도 같은 방식으로 바로 쓸 수 있습니다.

## 마무리

여기까지가 RedisTemplate 사용법 입문의 전부입니다. 의존성 추가, 직렬화 재정의, ops 호출, 시나리오 적용의 한 사이클이 익숙해지면, 그 위에 쌓이는 응용 주제들이 자연스럽게 보입니다. 가장 중요한 한 가지를 다시 짚으면, **Serializer 4-슬롯을 의식해 키는 `String`, 값은 JSON으로 한 번만 잡아두면** 이후의 작업이 모두 redis-cli에서 식별 가능한 형태로 떨어진다는 점입니다.

이 글은 어디서부터 시작하는가에 집중했으므로, 다음 단계는 별도 글로 이어집니다.

- 분산 락: `setIfAbsent`(SETNX)만으로는 부족합니다. TTL과 락 해제의 원자성, 락 홀더 식별, 네트워크 파티션은 별도 주제(Redisson, Lua 스크립트, Redlock 논쟁)
- `@Cacheable` 와 RedisCacheManager: Spring Cache 추상의 Redis 백엔드, 어노테이션 기반 선언적 캐싱
- Pub/Sub 와 Streams: 메시징 영역, `MessageListenerContainer` 셋업과 Streams 컨슈머 그룹
- Lua 스크립트(`execute(RedisScript)`): 여러 명령을 원자적으로 묶는 패턴
