같은 파드를 N 개 유지하는 일은 이미 `ReplicaSet`이 합니다. 그런데 실제 운영에서는 `ReplicaSet`을 직접 만드는 자리가 거의 없고, 사람이 만드는 객체는 `Deployment`입니다. 이 글은 `Deployment`가 `ReplicaSet` 위에 한 층을 더 두는 이유, YAML이 어떻게 거의 같은지, 그리고 `kubectl get`으로 본 3 단 계층의 모양을 한 자리에 정리합니다.

## 왜 Deployment가 따로 있는가

`ReplicaSet`은 <E>같은 파드 N 개를 항상 유지한다</E>를 보장합니다. 파드 한 개가 죽으면 즉시 새 파드를 만들고, 노드가 빠지면 다른 노드로 옮겨 띄웁니다. 이 보장만 보면 `ReplicaSet`을 직접 다뤄도 될 것 같습니다.

문제가 드러나는 자리는 새 버전을 배포하는 순간입니다. 운영 중인 `nginx:1.25` 파드 3 개를 `nginx:1.26`으로 바꾸려면, `ReplicaSet`만으로는 두 가지 중 하나를 골라야 합니다. 옛 RS를 통째로 지우고 새 RS를 띄우면 잠깐 동안 트래픽을 받을 파드가 0 개가 됩니다. 옛 RS와 새 RS를 동시에 유지하면서 새 RS의 `replicas`를 1, 2, 3 으로 늘리고 옛 RS의 `replicas`를 3, 2, 1 로 줄여 가면 무중단이 되지만, 이 절차를 사람이 손으로 챙기는 것은 실수가 너무 잦습니다.

`Deployment`는 바로 이 절차를 자동으로 해주는 객체입니다. 사용자가 새 이미지로 `Deployment`를 업데이트하면 `Deployment`는 새 `ReplicaSet`을 하나 만들고, 옛 `ReplicaSet`과 새 `ReplicaSet` 사이에서 `replicas`를 단계적으로 옮깁니다. 배포가 잘못됐다고 판단되면 옛 `ReplicaSet`을 다시 채워 이전 상태로 되돌립니다. 롤링 업데이트와 롤백은 둘 다 <E>두 RS 사이에서 replicas를 옮기는 동작</E>이 본질이며, 이 동작을 한 객체가 책임지게 한 것이 `Deployment`입니다.

이 글의 범위는 그 한 층이 끼어 들어간 모양 자체까지입니다. 롤링 업데이트의 단계별 동작·`maxSurge`·`maxUnavailable`·롤백 명령은 후속 글에서 다룹니다.

<Callout type="warning" title="핵심 포인트: Deployment는 ReplicaSet의 한 층 위 wrapper다">
  `Deployment`가 단독으로 하는 일은 `ReplicaSet`과 다르지 않습니다. `Deployment`의 가치는 같은 `selector`로 새 `ReplicaSet`을 더 띄우고 옛 `ReplicaSet`을 줄이는 능력에서 나옵니다. 이 능력 위에 롤링 업데이트와 롤백이 얹힙니다.
</Callout>

## Deployment YAML 구조

가장 작은 `Deployment` 정의입니다.

```yaml title="deployment-definition.yml"
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-deployment
  labels:
    app: myapp
    type: front-end
spec:
  replicas: 3
  selector:
    matchLabels:
      type: front-end
  template:
    metadata:
      name: myapp-pod
      labels:
        app: myapp
        type: front-end
    spec:
      containers:
        - name: nginx-container
          image: nginx
```

`ReplicaSet`을 다뤄 본 사람에게 이 YAML은 익숙할 것입니다. `kind`만 `Deployment`로 바뀌었고 나머지(`replicas`, `selector`, `template`, `spec.template.spec.containers`)는 그대로입니다. 이 사실은 우연이 아닙니다. `Deployment`가 만드는 `ReplicaSet`은 결국 이 `template`을 그대로 복제해 자기 `template`으로 씁니다. 사람이 보는 자리(=`Deployment`)와 실제 파드를 만드는 자리(=`ReplicaSet`) 사이에 같은 모양이 흐르도록 설계되어 있어서, `Deployment`를 안다는 것은 `ReplicaSet`을 안다는 것과 거의 같은 작업이 됩니다.

| 항목 | `ReplicaSet` | `Deployment` |
|---|---|---|
| `apiVersion` | `apps/v1` | `apps/v1` |
| `kind` | `ReplicaSet` | `Deployment` |
| `spec.replicas` | 동일 | 동일 |
| `spec.selector` | 동일 | 동일 |
| `spec.template` | 동일 | 동일 |
| 추가로 가지는 것 | 없음 | 롤링 업데이트·롤백 메타(`strategy`, 리비전 이력) |

만든 뒤 클러스터에 적용하는 명령도 같습니다.

```bash
kubectl create -f deployment-definition.yml
# 또는 (선언적, 권장)
kubectl apply -f deployment-definition.yml

kubectl get deployments
```

`kubectl create`는 한 번만 만들고 같은 파일로 또 호출하면 <E>이미 있다</E>고 거절합니다. `kubectl apply`는 같은 파일을 반복해 호출해도 차이만 적용하므로 운영에서는 `apply`가 권장됩니다. 이 차이는 `Deployment`에만 해당하는 게 아니라 모든 K8s 리소스에 동일합니다.

## Deployment, ReplicaSet, Pod 3 단 계층

`Deployment` 하나를 만들고 클러스터를 들여다보면 객체가 세 종류 등장합니다. 사용자가 만든 것은 `Deployment` 한 개뿐인데, `ReplicaSet`이 자동으로 한 개 따라오고, 그 `ReplicaSet`이 `replicas` 수만큼 파드를 만듭니다.

<DeploymentLayerStack />

### 자동으로 따라오는 ReplicaSet

`Deployment`를 적용하면 `Deployment`는 자기 안의 `template`을 해싱해 `myapp-deployment-7c9fbb` 형태의 이름을 짓고, 그 이름으로 `ReplicaSet`을 하나 만듭니다. `kubectl get rs`로 확인할 수 있습니다.

```bash
kubectl get replicaset
# 또는
kubectl get rs

# NAME                        DESIRED   CURRENT   READY   AGE
# myapp-deployment-7c9fbb     3         3         3       12s
```

`ReplicaSet`의 이름이 `Deployment` 이름으로 시작한다는 점이 중요합니다. 이 이름은 우연한 표기가 아니라, <E>이 RS는 myapp-deployment 라는 Deployment에 속한다</E>를 표현하는 식별자입니다. 같은 이름의 다른 `Deployment`가 있을 수 없는 이유도 여기에 있습니다.

뒤의 짧은 해시(`7c9fbb`)는 `Deployment`의 `template`을 입력으로 만든 PodTemplate 해시입니다. `template`이 한 글자라도 바뀌면 다른 해시가 나오고, 이 차이가 곧 새 `ReplicaSet`을 만드는 단서가 됩니다. 다음 글에서 다룰 롤링 업데이트의 핵심 메커니즘이 여기서 시작됩니다.

### Pod 이름이 두 번 해싱된 이유

`ReplicaSet`이 만든 파드는 `kubectl get pods`로 확인할 수 있습니다.

```bash
kubectl get pods

# NAME                              READY   STATUS    RESTARTS   AGE
# myapp-deployment-7c9fbb-2k4sd     1/1     Running   0          12s
# myapp-deployment-7c9fbb-fnp7q     1/1     Running   0          12s
# myapp-deployment-7c9fbb-x8r2c     1/1     Running   0          12s
```

파드 이름이 `myapp-deployment-7c9fbb-2k4sd`처럼 두 번 해싱된 모양으로 나옵니다. 가운데 `7c9fbb`는 방금 본 `ReplicaSet`의 PodTemplate 해시이고, 끝의 `2k4sd`는 `ReplicaSet`이 같은 `template`으로 여러 파드를 만들 때 각 파드를 구분하기 위한 무작위 접미사입니다. 이름의 두 부분이 곧 <E>이 파드는 어느 RS에서 만들어졌는가</E>와 <E>같은 RS 안의 다른 파드들과 어떻게 구분되는가</E>를 동시에 담고 있습니다.

이 작명 규칙은 디버깅에서 즉시 쓸모를 보입니다. `myapp-deployment-7c9fbb`로 시작하는 파드 3 개와 `myapp-deployment-9d2acc`로 시작하는 파드 1 개가 동시에 보인다면, 그 클러스터는 지금 두 `ReplicaSet`을 동시에 유지하고 있다는 뜻이고, 이는 곧 롤링 업데이트가 진행 중이라는 신호입니다.

## kubectl get all

`Deployment` 하나를 만든 결과를 한 화면에서 보고 싶을 때 쓰는 명령이 `kubectl get all`입니다.

```bash
kubectl get all

# NAME                                    READY   STATUS    RESTARTS   AGE
# pod/myapp-deployment-7c9fbb-2k4sd       1/1     Running   0          12s
# pod/myapp-deployment-7c9fbb-fnp7q       1/1     Running   0          12s
# pod/myapp-deployment-7c9fbb-x8r2c       1/1     Running   0          12s
#
# NAME                       READY   UP-TO-DATE   AVAILABLE   AGE
# deployment/myapp-deployment   3/3   3            3           12s
#
# NAME                                       DESIRED   CURRENT   READY   AGE
# replicaset/myapp-deployment-7c9fbb         3         3         3       12s
```

이 한 줄로 `Deployment` 1 개, `ReplicaSet` 1 개, `Pod` 3 개가 한꺼번에 보이고, 이름의 prefix만으로 세 객체가 하나의 가족이라는 사실이 드러납니다.

다만 이름이 주는 인상과 달리 `kubectl get all`은 클러스터의 <E>모든</E> 오브젝트를 보여주지 않습니다. CKAD 시험에서 자주 자기 트랩이 되는 자리이기도 합니다. 기본적으로 표시되는 것은 워크로드 계열(`Pod`, `Deployment`, `ReplicaSet`, `StatefulSet`, `DaemonSet`, `Job`, `CronJob`)과 `Service` 정도이며, `ConfigMap`, `Secret`, `Ingress`, `PersistentVolumeClaim`, `ServiceAccount`, `Role`, `RoleBinding` 같은 리소스는 빠집니다. 이들을 함께 보고 싶으면 다음처럼 종류를 명시합니다.

```bash
kubectl get all,configmap,secret,ingress
```

운영에서 클러스터 상태를 한눈에 잡고 싶을 때는 `kubectl get all`보다 명세적인 명령이 더 안전합니다. 이 한계를 알고 쓰는 명령으로 두는 정도가 적당합니다.

자주 쓰는 `Deployment` 명령은 [Kubernetes Cheatsheet](/posts/kubernetes-cheatsheet)에 누적됩니다.

<Callout type="error" title="핵심 통찰: 이름이 곧 계층의 단서다">
  `Deployment`, `ReplicaSet`, `Pod`는 별개 객체이지만 K8s는 부모-자식 관계를 별도 그래프로 저장하지 않습니다. 대신 이름의 prefix와 라벨이 그 관계를 표현합니다. `myapp-deployment-7c9fbb-2k4sd`라는 한 이름 안에는 <E>어느 Deployment에서 왔는가</E>(`myapp-deployment`)와 <E>어느 ReplicaSet에서 왔는가</E>(`7c9fbb`)가 모두 들어 있고, 라벨은 `selector`로 누가 누구를 관리하는지를 결정합니다. 이름과 라벨이 곧 토폴로지라는 점이 K8s 컨트롤러 패턴의 일관된 문법입니다.
</Callout>

## 마무리

`Deployment`는 `ReplicaSet`을 직접 다루지 않기 위해 한 층을 더 둔 객체입니다. 정의된 YAML은 `ReplicaSet`과 거의 같고, 만들어진 결과를 `kubectl get`으로 보면 `Deployment` 1 개, `ReplicaSet` 1 개, 그 아래 파드들이 이름 prefix로 묶여 보입니다. 이 한 층이 진짜 가치를 발휘하는 자리는 배포 시점이며, 다음 글에서는 `Deployment`가 두 `ReplicaSet`을 동시에 다루며 만들어 내는 롤링 업데이트와 롤백을 다룹니다.
