데이터베이스에 쓴 변경을 어떻게 다른 시스템이 알 수 있을까. 이 질문의 가장 자연스러워 보이는 답(애플리케이션이 둘 다 직접 갱신한다)이 왜 구조적으로 실패하는지, 그리고 CDC가 DB의 **이미 존재하는 트랜잭션 로그**를 재활용해 어떻게 이 문제를 우회하는지를 따라갑니다.

## CDC란

**Change Data Capture**는 데이터베이스에 일어난 변경(INSERT, UPDATE, DELETE)을 포착해서 다른 시스템으로 안정적으로 전파하는 패턴입니다. 한 줄로 풀면, <E>DB가 지금 들고 있는 최종 상태</E>가 아니라 <E>DB에서 일어난 일(이벤트) 자체</E>를 전송 단위로 삼는 접근입니다.

이 한 줄이 가진 파급력이 생각보다 큽니다. 대다수의 시스템은 <E>A가 DB에 뭔가 썼고, B가 그 결과를 알아야 한다</E>는 구조인데, B가 그 결과를 아는 역사적 방법은 두 가지였습니다. (1) B가 A의 DB를 직접 조회하거나, (2) A가 DB에 쓰고 난 뒤 B에게 직접 메시지를 보내거나. CDC는 세 번째 길입니다. A도 B도 건드리지 않고, **DB 바깥에서 DB의 변경을 낚아채는** 레이어를 둡니다.

이름 그대로 읽으면 됩니다. <E>Change Data Capture</E>. 여기서 `Capture`라는 단어가 중요합니다. DB가 자발적으로 변경을 publish하는 게 아니라 **외부에서 낚아채는** 모델이라는 뉘앙스입니다. 이 이름은 1990년대 데이터 웨어하우스 ETL에서 시작됐습니다. 매일 밤 OLTP DB 전체를 통째로 떠서 웨어하우스에 다시 적재하던 방식이 너무 비쌌기 때문에, <E>지난 밤 이후 바뀐 것만 뽑아 오자</E>는 아이디어에서 출발했습니다. 그때 수단은 `updated_at` 컬럼 폴링이었고, DB의 트랜잭션 로그를 직접 읽는 방식은 훗날 등장합니다.

2010년대 들어 microservices와 event-driven architecture가 퍼지면서 CDC는 완전히 다른 맥락으로 부활했습니다. <E>서비스 A의 DB 변경을 서비스 B, C, D가 각자 받아가게 하자</E>, <E>검색 인덱스와 캐시를 DB와 동기화하자</E>, <E>이벤트 로그를 사실상 진실의 원천(source of truth)으로 쓰자</E> 같은 새로운 요구들이 같은 패턴을 다시 끌어올렸습니다. 오늘날 Debezium, AWS DMS, Airbyte, Fivetran 같은 도구들이 다루는 문제가 모두 이 <E>변경을 포착해 어딘가로 흘려보내기</E>입니다.

용어 정리를 하나만 해두면 다음 섹션이 편합니다. **source**는 변경이 일어난 DB, **sink**는 그 변경을 받아가는 쪽(검색 인덱스, 다른 서비스, 메시지 큐, 웨어하우스), **CDC 파이프라인**은 둘 사이에 끼어서 변경을 옮기는 레이어 전체입니다.

## 왜 필요한가

CDC가 해결하는 **유일한 가장 큰 문제**는 이름이 있습니다. **Dual-write 문제**. 한 요청을 처리하면서 두 개의 저장소를 동시에 갱신해야 할 때, 이 둘을 원자적으로 묶을 방법이 없다는 사실에서 출발합니다.

구체적인 예를 들어보겠습니다. 상품 가격을 수정하는 API가 있고, 이 API는 (a) PostgreSQL의 `products` 테이블을 업데이트하고, (b) Elasticsearch 검색 인덱스도 함께 갱신해야 합니다. 가장 순진한 코드는 이렇게 됩니다.

```kotlin title="ProductService.kt"
@Transactional
fun updatePrice(id: ProductId, price: Money) {
  productRepository.update(id, price)   // (a) DB 커밋
  searchIndex.update(id, price)         // (b) ES 호출
}
```

보기엔 멀쩡하지만 이 코드에는 원자적으로 만들 방법이 없는 **세 가지 실패 창**이 있습니다.

<DualWriteFailureWindows />

시나리오를 풀어 말하면 이렇습니다. **(1) DB는 커밋됐는데 외부 호출이 네트워크 실패**: DB에는 새 가격이 들어갔지만 검색 인덱스는 과거 가격으로 남습니다. **(2) 외부 호출을 먼저 한 뒤 DB 롤백**: 검색 인덱스는 갱신됐지만 DB는 제약 위반 등으로 롤백됩니다. DB에 없는 상태가 검색 인덱스에만 존재하는 유령 데이터가 됩니다. **(3) 커밋 후 외부 호출 직전 크래시**: DB는 새 가격이 들어갔고, 재시작해도 (b) 호출을 수행할 방법이 사라졌습니다. 어느 경우든 두 저장소는 서로 다른 세상을 들고 있게 됩니다.

<E>그러면 2-phase commit(2PC) 쓰면 되지 않나?</E>라는 반문이 자연스럽습니다. 하지만 실전에서 2PC가 거의 쓰이지 않는 이유도 메커니즘적으로 분명합니다.

첫째, 2PC는 coordinator의 합의를 요구하는데, 코디네이터가 죽는 순간 참여자들은 `prepared` 상태에서 락을 쥔 채 멈춥니다(유명한 <E>blocking 문제</E>). 둘째, 대부분의 현대 시스템(Kafka, Elasticsearch, Redis, 외부 HTTP API)은 XA 트랜잭션 프로토콜을 아예 지원하지 않습니다. 셋째, 지원하더라도 성능이 무너집니다. 한 트랜잭션을 처리하는 동안 여러 시스템의 락이 동시에 잡혀 있기 때문입니다. 결과적으로 <E>2PC는 이론적으로 옳지만 실전에서 안 쓰는 도구</E>가 됐습니다. 2-시스템을 원자적으로 동기화할 수 없다는 이 구조적 불가능성은 Two Generals' Problem의 현실 판본이기도 합니다.

<RelatedPost slug="two-generals-problem" type="prerequisite" />

그래서 많은 팀이 역방향으로 해결을 시도합니다. 받는 쪽(b)이 원본(a)을 주기적으로 조회하는 방식이죠.

```sql
SELECT * FROM products WHERE updated_at > :last_seen ORDER BY updated_at;
```

이게 바로 쿼리 기반 CDC의 가장 원시적인 형태지만, 여기에도 근본적 한계가 있습니다. 우선 **삭제를 감지할 수 없습니다**. `DELETE FROM products WHERE id = X`는 행 자체가 사라지므로 `updated_at` 쿼리로는 영원히 잡히지 않습니다. 또 폴링 간격 사이에 같은 행이 여러 번 수정되면 **중간 상태가 전부 사라집니다**. 예컨대 1초 간격으로 폴링하는데 그 사이 가격이 `1000 → 900 → 1100`으로 바뀌면, 받는 쪽은 `900`을 아예 관측하지 못합니다. 이벤트 스트림 관점에서는 심각한 누락입니다.

CDC의 통찰은 여기서 나옵니다. **DB는 이미 자기 자신을 위해 변경 이벤트를 쓰고 있습니다.** PostgreSQL의 WAL, MySQL의 binlog, MongoDB의 oplog. 이들은 DB가 크래시 복구와 복제(replication)를 위해 **반드시** 남기는 로그이고, 여기엔 삭제를 포함한 모든 변경이 시간 순서대로 들어 있습니다. CDC는 이 로그를 읽어서 DB 바깥으로 흘려보내는 것이 본질입니다. 애플리케이션은 dual-write를 하지 않고 **한 번만** DB에 쓰고, 변경 전파는 DB의 기존 내부 메커니즘을 재활용해 해결합니다.

## 동작 원리

<Callout type="warning" title="이 구조를 이해하는 핵심">
  CDC의 세 구현 방식은 전부 <E>**DB 변경을 외부에서 어떻게 아는가**</E>라는 같은 질문에 답하지만, 답의 성격이 다릅니다. 쿼리 기반은 바깥에서 상태를 추측하고, 트리거 기반은 쓰기 경로에 새 경로를 추가하며, 로그 기반은 DB가 이미 가진 로그에 구독자 한 명을 얹습니다. 이 <E>기존 자원의 재활용</E> 여부가 모든 성능·정확성 차이의 원천입니다.
</Callout>

CDC를 구현하는 방식은 역사적으로 세 가지로 수렴했습니다. 각각은 같은 질문에 대한 서로 다른 답이며, 세 방식을 차례로 보면 왜 현대의 CDC가 **로그 기반**으로 거의 통일됐는지가 자연스럽게 보입니다.

### 쿼리 기반

쿼리 기반은 말 그대로 `SELECT`로 변경을 찾아내는 방식입니다. 각 테이블에 `updated_at TIMESTAMP`(또는 단조 증가 `version`) 컬럼을 두고, 외부 프로세스가 주기적으로 `SELECT * FROM <table> WHERE updated_at > :last_seen ORDER BY updated_at`을 실행합니다. 반환된 행이 <E>지난 폴링 이후의 변경</E>입니다.

구현이 자명해서 누구나 몇 시간 안에 만들 수 있고, DB 서버에 특별한 권한도 필요 없습니다. 하지만 아래 **네 가지 근본 한계**는 설계 변경으로도 해결되지 않습니다.

1. **삭제를 볼 수 없다.** `DELETE`는 행 자체를 사라지게 하므로 `updated_at` 쿼리에 절대 잡히지 않습니다. 실무에서는 <E>soft delete</E>(별도 `deleted_at` 컬럼 + 실제 행은 보존)로 우회하지만, 이건 애플리케이션 전반에 걸쳐 삭제 의미론을 바꾸는 침습적 결정입니다.
2. **중간 상태를 잃는다.** 폴링 간격 1초 동안 한 행이 `1000 → 900 → 1100`으로 바뀌면, 폴링 시점에는 `1100`만 남아 있습니다. <E>이벤트 로그로서의 변경</E>이 아니라 <E>현재 상태의 스냅샷</E>만 얻는 셈입니다.
3. **폴링 간격과 DB 부하의 양자택일.** 간격을 짧게 하면 DB에 끊임없는 인덱스 스캔이 가해집니다. 길게 하면 지연이 커집니다. 두 축이 제로섬이라 튜닝의 좋은 지점이 존재하지 않습니다.
4. **트랜잭션 경계의 소실.** 한 트랜잭션에서 10개 행을 바꿔도, 쿼리 기반은 이들이 같은 트랜잭션에서 일어났다는 사실을 복원할 방법이 없습니다. 각 행을 독립 이벤트로 볼 뿐입니다.

### 트리거 기반

트리거 기반은 각 테이블에 `AFTER INSERT/UPDATE/DELETE` 트리거를 달아서, 변경이 일어날 때마다 **그림자 테이블**(shadow table, 흔히 `audit_log` 또는 `change_log`)에 이벤트를 복사합니다. 이후 외부 프로세스는 그림자 테이블만 폴링하면 됩니다.

```sql title="product_audit_trigger.sql"
CREATE TRIGGER product_audit AFTER UPDATE ON products
FOR EACH ROW INSERT INTO product_changes
  (op, id, old_price, new_price, ts)
VALUES
  ('U', OLD.id, OLD.price, NEW.price, now());
```

이 방식은 쿼리 기반의 한계를 대부분 극복합니다. 삭제도 잡히고(트리거가 `DELETE`에도 반응), 중간 상태도 남고(매 변경마다 새 행), 트랜잭션 경계도 보존됩니다(트리거는 원본 트랜잭션 안에서 실행되므로 원본 롤백 시 그림자 테이블 기록도 같이 롤백됨).

그런데 **비용의 성격이 바뀝니다.** 모든 쓰기가 이제 <E>원본 테이블 1회 + 그림자 테이블 1회</E> 두 번의 쓰기를 동반하고, 둘 다 같은 트랜잭션 안에서 벌어집니다. OLTP 트래픽이 높은 서비스에서는 쓰기 지연이 눈에 띄게 늘고, 그림자 테이블의 크기가 폭발적으로 커집니다(이걸 주기적으로 청소하는 배치가 또 붙습니다). 더 중요하게, **스키마 변경이 어렵습니다.** 원본 테이블에 컬럼을 추가하면 트리거도 같이 바꿔야 하고, 이 둘이 동기화되지 않으면 포착이 깨집니다. 운영상의 마찰이 상당합니다.

### 로그 기반

<Callout type="error" title="핵심 통찰: CDC는 새 인프라가 아니라 기존 인프라의 구독자다">
  DB는 크래시 복구(ACID의 D)와 복제를 위해 **반드시** 변경을 로그에 기록합니다. 이 로그는 이미 <E>시간순·정확·트랜잭션 경계 보존된</E> 이벤트 스트림이고, primary와 replica 사이를 오가는 공식 인터페이스입니다. 로그 기반 CDC는 이 스트림에 **외부 구독자 한 명을 추가할 뿐**입니다. 이 관점이 왜 로그 기반이 실전 표준이 되었는지를 한 줄로 설명합니다.
</Callout>

로그 기반은 완전히 다른 관점에서 출발합니다. 애플리케이션이 DB에 쓸 때 DB가 뭘 하는지 보면, **DB 엔진 자체는 이미 모든 변경을 로그로 쓰고 있습니다.** 이 로그를 부르는 이름은 DB마다 다릅니다.

| DB | 로그 이름 | 본래 용도 |
|---|---|---|
| PostgreSQL | WAL (Write-Ahead Log) | 크래시 복구 + 논리 복제 |
| MySQL / MariaDB | binlog (Binary Log) | 복제 (primary → replica) |
| MongoDB | oplog (Operation Log) | replica set 동기화 |
| SQL Server | Transaction Log | 복구 + replication |

이 로그들은 <E>CDC 때문에 만들어진 부가 기능</E>이 아닙니다. PostgreSQL은 크래시에서 살아남기 위해 먼저 WAL에 변경을 기록하고, 실제 데이터 페이지에 반영하기 전에 디스크에 flush해둡니다. MySQL의 binlog은 replica가 primary의 변경을 받아가기 위한 공식 인터페이스입니다. 즉 이 로그는 이미 <E>시간순으로 모든 변경이 담긴, 정확한, 트랜잭션 경계가 보존된</E> 이벤트 스트림입니다.

구현 관점에서 로그 기반 CDC는 DB의 **복제 프로토콜을 흉내 냅니다**. PostgreSQL에서는 `CREATE_REPLICATION_SLOT`으로 논리 복제 슬롯을 만들고 `pgoutput` 또는 `wal2json` 플러그인으로 WAL을 해석해 스트림으로 받습니다. MySQL에서는 CDC 프로세스가 자신을 <E>가짜 replica</E>로 등록해서 binlog 이벤트를 수신합니다. Debezium이 실제로 하는 일이 이것입니다.

```kotlin title="LogicalStreamReader.kt (개념 코드)"
// 논리 복제 슬롯 생성 (1회성)
runSql("CREATE_REPLICATION_SLOT cdc_slot LOGICAL pgoutput")

// 슬롯을 통해 WAL 스트림 수신
val stream = connection.openReplicationStream("cdc_slot", startLsn = lastConfirmedLsn)
while (true) {
  val msg = stream.readNext() // INSERT/UPDATE/DELETE 이벤트 단위
  sink.publish(msg.toEvent())
  stream.setFlushedLsn(msg.lsn) // 처리 완료 확인 → PG는 WAL 이 부분 지워도 됨
}
```

한 가지 주목할 점은 `setFlushedLsn(msg.lsn)` 라인입니다. CDC 컨슈머가 이 LSN까지 처리했다고 알려줘야 PostgreSQL이 해당 WAL 구간을 재사용할 수 있습니다. 뒤집어 말하면 **컨슈머가 오래 멈춰 있으면 WAL이 쌓여 디스크를 잠식할 위험**이 있다는 뜻입니다. 로그 기반의 모든 장점이 이 <E>슬롯 → 디스크 공간 커플링</E>이라는 운영상의 대가 하나를 낳습니다.

### 세 방식 비교

위의 차이를 한 표로 정리하면 이렇습니다.

| 요구 | 쿼리 기반 | 트리거 기반 | 로그 기반 |
|---|---|---|---|
| 삭제 감지 | 불가 (soft delete 우회) | 가능 | 가능 |
| 중간 상태 보존 | 불가 (폴링 간격 유실) | 가능 | 가능 |
| 트랜잭션 경계 | 불가 | 가능 | 가능 |
| 쓰기 경로 오버헤드 | 없음 | **2배 쓰기** | 없음 |
| DB 부하 | 폴링 쿼리 부하 | 트리거 실행 부하 | **없음 (이미 존재)** |
| 지연 | 폴링 간격만큼 | 폴링 간격만큼 | 거의 실시간 |
| 스키마 변경 대응 | 앱 책임 | 트리거 재작성 | 메타데이터 자동 추적 |

마지막 두 행이 결정적입니다. **애플리케이션 쪽 쓰기 경로에 아무것도 추가하지 않고, DB의 성능 오버헤드도 없는데, 정확성은 트리거 기반과 동등합니다.** 공짜에 가까워 보이는데, 실제로도 이게 공짜에 가까운 이유는 앞서 말했듯 <E>**DB가 자기를 위해 이미 하고 있는 일에 얹어가는 것**</E>이기 때문입니다.

### 왜 로그 기반이 실전 표준이 되었나

정리하면 인과 사슬은 이렇게 이어집니다. (1) DB는 ACID의 D(Durability)를 구현하기 위해 반드시 WAL 같은 로그를 쓴다. (2) 이 로그는 동시에 레플리카 복제의 포맷으로 쓰인다, primary와 replica 사이에 <E>상태</E>가 아닌 <E>이벤트</E>를 흘려보내야 하기 때문. (3) 이 로그는 이미 외부 시스템이 구독 가능한 형태로 **정의되고 안정화된 인터페이스**다. (4) CDC는 이 인터페이스에 구독자 하나를 추가할 뿐이므로, 애플리케이션과 DB 양쪽 모두에 구조적인 비용을 거의 추가하지 않는다.

반면 트리거 기반은 <E>없던 쓰기 경로를 새로 만드는</E> 접근이고, 쿼리 기반은 <E>있는 것을 재활용하지 않고 바깥에서 상태를 추측하는</E> 접근입니다. 둘 다 <E>DB가 이미 가진 것</E>을 활용하지 못합니다. 이것이 Debezium, AWS DMS, Airbyte 같은 현대 CDC 도구가 전부 로그 기반을 기본으로 채택한 이유입니다. 쿼리 기반은 <E>DB 로그에 접근할 권한이 없는 legacy</E>에서만 fallback으로, 트리거 기반은 <E>로그를 지원하지 않는 특수 DB</E>에서만 씁니다.

흥미롭게도 이 아이디어는 Kafka의 log-based replication과 친척입니다. 둘 다 <E>로그야말로 진실의 원천이고, 다른 모든 것은 그것의 파생</E>이라는 같은 관점 위에 서 있습니다.

## 어디서 마주치는가

CDC가 강력하다고 해서 모든 시스템에 어울리는 건 아닙니다. 핵심 기준은 하나입니다. **CDC는 본질적으로 비동기·최종 일관성(eventual consistency) 모델**이며, 이 성질이 문제와 맞으면 최고의 해법이고 맞지 않으면 잘못된 도구입니다.

### 적합한 상황

**Microservice 간 데이터 전파**에서 소유권이 분리된 경우. 상품 서비스가 `products` 테이블의 유일한 소유자이고, 검색·추천·가격 비교 서비스가 <E>상품 정보가 바뀌면 알아야 한다</E>면, CDC는 이상적입니다. 각 consumer 서비스가 자기 속도로, 자기 실패에 독립적으로, 자기 저장소에 맞춘 변형을 수행할 수 있습니다. 상품 서비스는 메시지 발행의 책임에서 완전히 빠지고, 그냥 자기 DB에 쓰기만 합니다.

**검색 인덱스와 캐시 동기화**. Elasticsearch, OpenSearch, Meilisearch 같은 검색 엔진은 DB의 정식 replica가 되기 어렵습니다(스키마 모델이 다르고, 트랜잭션 경계도 다름). 이런 경우 <E>DB가 진실의 원천이고, 검색 인덱스는 CDC로 파생된 view</E>라는 관점이 깔끔합니다. 인덱스가 어긋나면 reindex하면 되고, 검색 인덱스 장애가 DB 쓰기 경로에 영향을 주지 않습니다.

**Data warehouse / analytics 파이프라인**. CDC의 원래 고향입니다. OLTP DB에서 OLAP 시스템(Snowflake, BigQuery, Redshift, ClickHouse)으로 변경을 흘려보낼 때, 매일 전체 스냅샷을 뜨는 방식 대비 비용과 신선도 양쪽에서 큰 차이가 납니다.

**Outbox 패턴의 구현 수단**. 애플리케이션이 비즈니스 테이블에 쓰는 것과 **같은 트랜잭션**에서 `outbox` 테이블에 도메인 이벤트를 함께 씁니다. 그리고 CDC가 `outbox` 테이블의 INSERT만 구독해서 외부로 흘립니다. 이 조합이 dual-write 없이 메시지 발행의 원자성을 얻는 표준 레시피입니다. <E>비즈니스 테이블 변경을 바로 내보내는 것</E>과 달리, 애플리케이션이 의도한 **도메인 이벤트의 모양**으로 내보낼 수 있다는 차이도 있습니다.

**Audit trail / 규정 대응**. <E>누가 언제 무엇을 바꿨는가</E>를 모든 테이블에 대해 수집해야 하는 경우, 애플리케이션 코드에 audit 로직을 흩뿌리는 대신 CDC 한 레이어로 모읍니다.

### 부적합한 상황

**Read-after-write 일관성을 consumer가 요구할 때.** 사용자가 상품 가격을 수정하고 바로 그 요청의 응답에 <E>새 가격으로 계산된 재고 평가액</E>을 포함해서 반환해야 하는 경우, 재고 평가 서비스가 CDC를 통해 가격 변경을 받는 구조라면 수십에서 수백 ms의 지연이 발생합니다. 응답 경로는 CDC로 풀 수 없고, 동기 RPC나 같은 DB 조회로 풀어야 합니다. CDC는 **요청-응답 경로가 아니라 배경 전파 경로**의 도구입니다.

**Consumer가 각 이벤트에 강한 트랜잭션 보장을 기대할 때.** CDC 컨슈머는 적어도 at-least-once 의미론이며(재시작·재처리로 동일 이벤트가 두 번 도착 가능), 여러 테이블의 변경을 하나의 원자 단위로 묶어 받는 것은 설계적으로 가능은 해도 복잡합니다. 컨슈머에 강한 exactly-once + cross-row 원자성이 필요하면 CDC는 잘못된 도구이거나, 컨슈머 쪽에 **멱등 처리**를 강제하는 등 별도 보강이 필요합니다.

<RelatedPost slug="idempotency" type="deep-dive" />

**이벤트의 의미가 <E>행 변경</E>과 맞지 않을 때.** CDC는 본질적으로 row-level 이벤트입니다. <E>주문이 결제됐다</E>처럼 비즈니스 수준의 이벤트는 한 행의 UPDATE로 표현되지 않는 경우가 많습니다(주문 상태 + 결제 테이블 + 재고 테이블 + 포인트 테이블 동시 변경). 이럴 때 row 이벤트 여러 개를 consumer가 모아서 <E>비즈니스 이벤트</E>로 합성하는 건 결합도가 깨지기 쉽습니다. 이 경우는 Outbox 패턴으로 애플리케이션이 **직접 도메인 이벤트를 쓰는 편**이 낫고, CDC는 그 outbox 테이블을 옮기는 역할에 집중하면 됩니다.

**변경 빈도가 매우 낮은 소규모 시스템.** CDC는 커넥터, 메시지 브로커(보통 Kafka), 스키마 레지스트리, 컨슈머 관리 등 상당한 운영 인프라를 요구합니다. 하루에 수백 건 수준의 변경에 이 인프라를 얹는 건 과도합니다. 작은 시스템에서는 애플리케이션 레벨의 이벤트 발행(멱등 보장 + 재시도)이 더 저렴합니다.

**DB 로그 접근이 막혀 있는 환경.** 매니지드 DB 중 일부는 replication slot 생성이나 binlog 접근을 제한합니다(또는 엔터프라이즈 플랜에서만 허용). 트리거 기반으로 fallback할 수는 있지만 앞서 본 비용을 감수해야 합니다.

## 트레이드오프

로그 기반 CDC가 구조적으로 싸다고 해서 공짜는 아닙니다. 실제 도입 시 감수해야 하는 대가가 있습니다.

**Replication slot과 디스크의 커플링**. PostgreSQL의 논리 복제 슬롯은 <E>마지막으로 컨슈머가 처리한 LSN</E>을 기록하고, 그 이전의 WAL은 안전하게 재사용(recycle)됩니다. 뒤집어 말하면 컨슈머가 장기간 멈춰 있으면 WAL이 쌓여 DB 디스크가 찹니다. 운영에서 슬롯의 `lag`을 모니터링하고, 컨슈머 장애 시 어떻게 복구할지의 플레이북이 필요합니다.

**스키마 변경의 전파 지연**. DDL(ALTER TABLE 등)은 CDC 이벤트로 함께 흘러가지만, consumer 쪽이 새 스키마를 받아들일 준비가 되어 있지 않으면 파이프라인이 깨집니다. Debezium은 스키마 변경 이벤트를 별도로 내보내지만, 그걸 어떻게 해석할지는 애플리케이션의 책임입니다. 스키마 레지스트리(Confluent Schema Registry 등)를 함께 쓰는 이유가 여기 있습니다.

**순서 보장의 범위**. 단일 파티션/테이블 안에서는 순서가 보존되지만, 여러 테이블에 걸친 <E>transactionally consistent snapshot</E>을 받는 것은 별개의 문제입니다. Debezium의 `transaction metadata` 기능으로 같은 트랜잭션의 이벤트들을 묶어 받을 수 있지만, 이걸 consumer가 제대로 소비하려면 설계가 단단해야 합니다.

**초기 snapshot의 부담**. CDC를 도입하는 순간, 기존 데이터 전체를 sink에 <E>한 번 뿌리는</E> 초기 snapshot 단계가 필요합니다. 큰 테이블일수록 이 단계가 길고, 그 사이에 source DB 부하가 올라갑니다. Debezium은 `incremental snapshot`으로 이를 완화하지만 완전히 공짜는 아닙니다.

**At-least-once 전파의 사후 처리**. 브로커(Kafka)와 consumer 사이에서는 같은 이벤트가 재배달될 수 있습니다. Consumer는 반드시 멱등 처리를 설계해야 하며, 이 설계 비용이 초기 CDC 도입의 은근한 복잡도를 만듭니다.

이런 대가는 <E>CDC 쓰지 말라</E>는 결론이 아니라, <E>공짜가 아니다</E>라는 정직한 체크리스트입니다. 대체 접근인 dual-write + 재시도가 만드는 구조적 상태 불일치보다는 운영 가능한 복잡성입니다.

## 마무리

이 글의 한 문장 요약은 이것입니다. **CDC는 새로운 인프라를 만드는 게 아니라, DB가 이미 만들고 있는 로그에 외부 구독자 한 명을 추가하는 패턴이다.**

Dual-write 문제는 원자적 해결이 구조적으로 불가능하고, 2PC는 이론적으로 옳지만 실전에서 쓰이지 않으며, 쿼리 기반은 삭제와 중간 상태를 못 보는 근본 한계를 지닙니다. 로그 기반 CDC가 실전 표준이 된 이유는 영리해서가 아니라, **DB의 ACID Durability와 replication이 강제하는 기존 자원에 거의 비용 없이 얹혀 있기** 때문입니다. 한 단계 높은 관점에서 보면 <E>로그가 진실의 원천이고, 다른 상태는 그것의 파생</E>이라는 모델이 microservices와 스트리밍 시대의 설계 원칙과 맞물리면서, 오래된 ETL 패턴이 다시 백엔드 아키텍처의 중심으로 돌아온 셈입니다.

자신의 시스템에 CDC가 어울리는지 판단할 때는 단순한 기준 하나를 기억하면 됩니다. <E>**DB가 진실의 원천이고 다른 시스템은 그 파생인가?**</E> 이 물음에 <E>그렇다</E>고 답할 수 있다면 CDC가 깔끔한 답입니다. <E>대등한 책임을 가진 여러 시스템이 동시에 갱신돼야 한다</E>거나 <E>응답 경로에서 동기 일관성이 필요하다</E>면, CDC가 아니라 다른 도구를 먼저 검토하는 편이 옳습니다.
