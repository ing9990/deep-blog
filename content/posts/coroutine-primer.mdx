백엔드 서버가 하는 일의 대부분은 <E>기다림</E>입니다. DB 응답, 외부 API, Redis 조회가 요청 시간의 대부분을 차지합니다. 코루틴은 이 대기 시간을 낭비하지 않으면서도 동기적 문법의 가독성을 유지하는 타협점입니다. 이 글은 코루틴이 왜 필요했고, `suspend`와 `resume`이 CPU 레벨에서 실제로 어떻게 동작하는지를 Python과 Kotlin 예제를 나란히 놓고 풀어냅니다.

## 코루틴이란

**코루틴은 실행 도중에 스스로 멈췄다가 나중에 그 지점부터 다시 시작할 수 있는 함수입니다.**

일반 함수와의 차이부터 보겠습니다. 일반 함수를 호출하면 <E>실행 → 반환</E> 두 단계로 끝납니다. 중간에 멈추는 개념이 없습니다. 코루틴은 여기에 <E>잠시 제어권을 돌려주고 나중에 재개</E>라는 세 번째 옵션을 추가합니다. 실행 흐름이 <E>실행 → 중단 → 재개 → ... → 반환</E>으로 확장됩니다.

이 변화의 의미는 한 가지로 압축됩니다. 기다려야 하는 함수가 CPU를 붙잡지 않게 됩니다. 네트워크 응답을 기다리는 함수가 있다고 해봅시다. 일반 함수로 짜면 응답이 올 때까지 스레드를 점유하고 아무것도 못 합니다. 코루틴으로 짜면 <E>응답이 올 때까지 잠깐 양보할게</E>라고 선언하고, 같은 스레드가 그 사이 다른 코루틴을 실행합니다.

중요한 구분 하나. 코루틴은 **협력적 멀티태스킹** 모델입니다 (cooperative multitasking). OS 스레드는 선점형이라 커널이 강제로 스레드를 빼앗지만, 코루틴은 `await` 또는 `suspend` 같은 명시적 키워드로만 중단됩니다. 코루틴이 무한 루프를 돌면 같은 스레드 위 다른 코루틴은 전부 굶습니다. 이 제약이 단점이자 성능의 원천이기도 합니다.

<Callout type="warning" title="코루틴은 경량 스레드가 아니다">
  흔한 표현과 달리 코루틴은 스레드의 가벼운 버전이 아닙니다. 정확히는 **OS 스레드 위에서 돌아가는 논리적 실행 단위**입니다. 1개 스레드 위에 수천에서 수만 개의 코루틴이 올라갈 수 있습니다. 스레드는 OS가 관리하는 물리 자원이고, 코루틴은 언어 런타임이 관리하는 논리 흐름입니다. 계층이 다릅니다.
</Callout>

## 왜 필요한가

백엔드의 주된 일은 CPU 연산이 아니라 기다림입니다. DB 쿼리, 외부 API 호출, Redis 조회, 파일 I/O가 요청 시간의 대부분을 차지합니다. 전통적인 Thread-per-request 모델(Tomcat 기본)에서 한 요청을 처리하는 스레드는 이 대기 동안 아무것도 안 하면서 메모리 8MB와 스레드 슬롯 하나를 계속 점유합니다. 동시 10,000개 요청이 모두 DB 응답을 기다리면 서버는 <E>CPU 놀고 있음 + 스레드 1만 개 메모리 80GB 점유</E> 상태가 됩니다. 이것이 유명한 C10K 문제의 본질입니다.

업계는 이 문제를 두 방향으로 해결해왔습니다.

### Event Loop 방식

Node.js, Nginx가 선택한 길입니다. 한 스레드가 수많은 연결을 돌려가며 `epoll`로 <E>누가 준비됐나?</E>를 묻는 논블로킹 I/O 모델입니다. 성능은 좋지만 코드가 콜백 지옥(callback hell)이 됩니다.

```js title="callback-hell.js"
fetchUser(id, (user) => {
  fetchOrders(user, (orders) => {
    fetchInventory(orders, (inventory) => {
      // 계단처럼 들여쓰기가 무너진다
    })
  })
})
```

### Coroutine 방식

문법은 동기처럼 쓰되, 런타임이 알아서 비동기로 처리하게 하는 길입니다. 개발자는 위에서 아래로 읽히는 코드를 씁니다. 그런데 함수가 I/O 대기에 들어가는 순간, 컴파일러가 몰래 삽입한 중단 지점에서 이 코루틴은 멈추고 스레드는 다른 코루틴을 실행하러 떠납니다.

<Tabs group="coroutine-lang">
  <Tab label="Kotlin">
    ```kotlin title="Handler.kt"
    suspend fun handleRequest(userId: Long): Response {
        val user = fetchUser(userId)           // [!code highlight]
        val orders = fetchOrders(user)         // [!code highlight]
        return Response(user, orders)
    }
    ```
  </Tab>
  <Tab label="Python">
    ```python title="handler.py"
    async def handle_request(user_id):
        user = await fetch_user(user_id)       // [!code highlight]
        orders = await fetch_orders(user)      // [!code highlight]
        return {"user": user, "orders": orders}
    ```
  </Tab>
</Tabs>

코드는 동기, 실행은 비동기. 두 세계의 장점을 합친 타협이 코루틴입니다.

### 숫자로 본 차이

동시 연결 10,000개 처리 시 세 가지 모델의 비용 구조는 다음과 같습니다.

| 모델 | 스레드 수 | 스레드 메모리 | 코드 가독성 |
|---|---|---|---|
| Thread-per-request (Tomcat 구형) | 10,000 | 약 80 GB | 동기 문법 ✅ |
| Event loop (Node.js) | 1–4 | 약 32 MB | 콜백 지옥 ❌ |
| Coroutine (Kotlin, Python asyncio) | 1–4 + 코루틴 10,000 | 약 50 MB | 동기 문법 ✅ |

코루틴은 비동기 I/O를 동기 문법으로 쓰게 해 주는 문법 설탕에 그치지 않고 실행 모델 자체가 다릅니다. 콜백 기반 비동기는 함수가 반환되는 순간 스택이 사라져 다음에 실행될 코드가 별도 함수로 등록되지만, 코루틴은 중단된 상태(로컬 변수, 실행 지점)가 힙 위 객체로 살아남았다가 재개됩니다. 그래서 비동기 흐름이 동기 코드처럼 위에서 아래로 읽혀도 실제 실행은 중단·재개를 반복합니다. 이 차이가 다음 섹션의 출발점입니다.

## 동작 원리

<Callout type="warning" title="이 구조를 이해하는 핵심">
  코루틴은 런타임 마법이 아닙니다. 컴파일러가 함수를 상태 머신으로 재작성하고, 중단 지점에서 <E>나머지 할 일</E>을 힙 위 Continuation 객체로 포획하며, Event Loop가 I/O 완료 시 이 Continuation을 다시 실행하도록 조율합니다. 세 조각의 공동 작업이 전체입니다.
</Callout>

핵심 질문 하나로 시작합니다. `await fetchUser()` 한 줄이 실행되고 <E>잠시 멈췄다가 나중에 재개</E>될 때 CPU 레벨에서 실제로 어떤 일이 일어나는가?

<Callout type="error" title="핵심 통찰: 코루틴은 컴파일러가 만든 상태 머신이다">
  <E>중단했다가 재개</E>라는 동작은 런타임 트릭이 아닙니다. 컴파일러가 `await`와 `suspend` 지점을 경계로 함수를 상태 머신으로 쪼개고, 중단 시점에 남은 일을 힙 위 Continuation 객체로 포획합니다. 호출 스택에서는 실제로 빠져나가며, 같은 스레드는 다른 코루틴을 실행하러 떠납니다. 이것이 수만 코루틴이 수 개 스레드로 굴러가는 근본 이유입니다.
</Callout>

### 상태 머신 변환

컴파일러는 `suspend fun` 또는 `async def`로 선언된 함수를 받으면, 중단 키워드 지점을 경계로 여러 조각으로 쪼갠 뒤 switch-case 상태 머신으로 재작성합니다. 원래 위에서 아래로 흐르던 코드가 `state = 0, 1, 2, ...` 라벨을 가진 점프 테이블로 바뀝니다.

아래는 2개 중단 지점이 있는 원본 함수가 컴파일러 내부에서 어떤 모양으로 변환되는지의 의사 코드입니다. 언어와 무관하게 비슷한 모양을 갖습니다.

```text title="컴파일러가 내부적으로 만드는 상태 머신 (의사 코드)"
function handleRequest_stateMachine(state, result):
    switch state:
        case 0:
            future = fetchUser(userId)
            registerContinuation(future, label=1)   // [!code highlight]
            return    // 함수가 스택에서 빠져나감
        case 1:
            user = result
            future = fetchOrders(user)
            registerContinuation(future, label=2)   // [!code highlight]
            return
        case 2:
            orders = result
            return Response(user, orders)
```

주목할 점: 각 state마다 Future를 반환하고 함수가 **종료**됩니다. <E>중단</E>은 호출 스택에서 실제로 빠져나가는 것이지 멈춰 서 있는 게 아닙니다. 스레드는 자유로워지고 다른 일을 할 수 있습니다.

### Continuation 객체

함수가 스택에서 빠져나가도 <E>아직 해야 할 나머지 일</E>은 어딘가 저장되어야 재개할 수 있습니다. 이 나머지 일을 하나의 객체로 포획한 것이 **Continuation** (Kotlin) 또는 **coroutine frame** (Python)입니다.

Continuation 객체에는 다음이 담깁니다.

| 필드 | 역할 |
|---|---|
| state 번호 | 다음에 이어 실행할 라벨 |
| 로컬 변수 | 중단 시점의 `user`, `orders` 같은 값 |
| 부모 Continuation | 완료 시 결과를 돌려줄 대상 |

결정적인 점 하나. 이 Continuation 객체는 스택이 아니라 **힙**에 있습니다. 그래서 스레드가 교체되어도, 시간이 한참 지나도 살아남을 수 있습니다. 수만 개 코루틴이 1개 스레드 위에서 돌아갈 수 있는 이유가 여기 있습니다. 각 코루틴은 활성 스레드 하나와 힙 위 Continuation 객체 하나만 점유하면 됩니다.

### Event Loop가 이어달리기를 조율한다

Continuation 객체만으로는 부족합니다. <E>I/O가 끝났으니 이 Continuation을 다시 실행해줘</E>라고 누군가가 호출해야 재개가 일어납니다. 이 역할이 Python `asyncio` Event Loop이고, Kotlin에서는 `Dispatcher`입니다.

다음 인터랙티브 시각화에서 Event Loop가 3개 코루틴을 어떻게 조율하는지 한 단계씩 따라가봅시다. <E>다음</E> 버튼을 눌러가며 각 틱마다 코루틴의 상태 변화를 관찰하세요.

<EventLoopDance />

여기서 결정적인 포인트가 하나 더 드러납니다. 재개되는 스레드는 중단되던 당시의 스레드와 **다를 수 있습니다**. 코루틴은 스레드에 묶여 있지 않습니다. 이 성질이 뒤에서 다룰 `ThreadLocal` 지점의 원인이 됩니다.

### Stackless vs Stackful

마지막으로 언어별 구현 분기를 짚습니다. Python asyncio와 Kotlin Coroutines는 **Stackless** 방식입니다. `await`/`suspend` 키워드가 있는 함수 경계에서만 중단 가능하고, 실제 CPU 스택을 저장하지 않고 Continuation 객체에 필요한 변수만 담습니다. 메모리 효율은 최고지만 <E>suspend 함수는 suspend 함수에서만 호출 가능</E>이라는 제약이 붙습니다.

Go goroutine과 JVM Virtual Thread는 **Stackful** 방식입니다. 실제 가상 스택을 가지고 있어 어느 지점에서든 중단 가능하며, 일반 블로킹 코드를 호출해도 런타임이 알아서 전환합니다. 대신 스택 크기 (수 KB)가 필요하고 구현이 복잡합니다.

| 방식 | 대표 언어 | 중단 지점 | 메모리 | 특징 |
|---|---|---|---|---|
| Stackless | Python asyncio, Kotlin | `await`/`suspend` 경계 | 수십 B – 수 KB | <E>async 전염</E> 문제 있음 |
| Stackful | Go goroutine, JVM Virtual Thread | 어느 지점에서든 | 수 KB 이상 | 블로킹 코드도 그대로 사용 가능 |

동시에 여러 I/O를 띄우려면 코루틴도 병렬 호출 문법을 제공합니다. 두 언어 모두 <E>여러 I/O를 동시에 띄우고 모두 끝날 때까지 기다린다</E>를 한 줄로 표현할 수 있습니다.

<Tabs group="coroutine-lang">
  <Tab label="Kotlin">
    ```kotlin title="Handler.kt"
    suspend fun handleRequest(userId: Long): Response = coroutineScope {
        val user = async { fetchUser(userId) }           // [!code highlight]
        val orders = async { fetchOrders(userId) }       // [!code highlight]
        val inventory = async { fetchInventory(userId) } // [!code highlight]
        Response(user.await(), orders.await(), inventory.await())
    }
    ```
  </Tab>
  <Tab label="Python">
    ```python title="fanout.py"
    import asyncio

    async def handle_request(user_id):
        user, orders, inventory = await asyncio.gather(  // [!code highlight]
            fetch_user(user_id),
            fetch_orders(user_id),
            fetch_inventory(user_id),
        )
        return {"user": user, "orders": orders, "inventory": inventory}
    ```
  </Tab>
</Tabs>

300ms짜리 순차 호출이 100ms 병렬 호출로 줄어드는 순간이 이 문법으로 표현됩니다.

## 언제 쓰는가

코루틴은 만능이 아닙니다. 적합한 영역과 오히려 독이 되는 영역이 명확합니다. 판단 기준을 한 줄로 압축하면 <E>기다림이 많은가, 계산이 많은가</E>입니다.

### 적합한 경우

외부 I/O가 요청 시간의 대부분을 차지하는 API 서버가 첫 번째입니다. DB 쿼리 40ms + 외부 API 호출 80ms + Redis 5ms 구성에서 실제 CPU 시간은 수 ms 이하입니다. 이런 작업을 Thread-per-request로 돌리면 스레드가 대기 중 놀고 있어 메모리 낭비입니다. 코루틴으로 바꾸면 스레드 수를 코어 수준 (4에서 16개 정도)으로 유지하면서 동시 연결 수천에서 수만을 처리할 수 있습니다.

두 번째는 연결 수가 많고 트래픽이 간헐적인 서버입니다. 채팅, Server-Sent Events, WebSocket, long-polling이 모두 여기 해당합니다. 각 연결은 대부분 조용히 대기 상태로 있다가 가끔 메시지를 주고받습니다. 이런 <E>대부분 기다림</E> 패턴에 코루틴이 가장 잘 맞습니다. 10만 커넥션을 4개 스레드로 처리하는 것도 가능합니다.

세 번째는 팬-아웃 I/O가 흔한 경우입니다. 한 요청 처리 중 여러 외부 서비스를 병렬 호출해야 할 때 위에서 본 `asyncio.gather`나 `coroutineScope { async { } }` 패턴으로 자연스럽게 표현됩니다.

### 피해야 하는 경우

CPU-bound 작업이 첫 번째입니다. 이미지 인코딩, 암호화, 대용량 JSON 파싱, ML 추론. 이런 코드에는 `suspend` 지점이 없어서 Event Loop 또는 Dispatcher 스레드를 끝까지 블록합니다. 같은 스레드 위 다른 코루틴은 전부 굶습니다. 해법은 별도 스레드 풀로 오프로드하는 것입니다.

<Tabs group="coroutine-lang">
  <Tab label="Kotlin">
    ```kotlin title="CpuOffload.kt"
    suspend fun handleRequest(imageBytes: ByteArray): Result =
        withContext(Dispatchers.Default) {         // [!code highlight]
            heavyCpuWork(imageBytes)
        }
    ```
  </Tab>
  <Tab label="Python">
    ```python title="cpu_offload.py"
    import asyncio
    from concurrent.futures import ProcessPoolExecutor

    async def handle_request(image_bytes):
        loop = asyncio.get_running_loop()
        result = await loop.run_in_executor(      // [!code highlight]
            None, heavy_cpu_work, image_bytes
        )
        return result
    ```
  </Tab>
</Tabs>

두 번째는 동기 블로킹 라이브러리만 있는 환경입니다. 오래된 JDBC 드라이버, 동기 HTTP 클라이언트가 여기 해당합니다. 코루틴 안에서 블로킹 호출을 하면 이벤트 루프가 묶이고 전체 처리량이 추락합니다. 이 현상을 **블로킹 오염** (blocking pollution)이라고 부릅니다. 대안은 비동기 드라이버 (R2DBC, asyncpg, aiopg)로 교체하거나 `Dispatchers.IO` 같은 전용 스레드 풀에 격리하는 것입니다.

세 번째는 단일 요청이 CPU만 쓰는 간단한 서비스입니다. 이미지 리사이저, 계산 서비스처럼 I/O가 거의 없는 경우입니다. 이런 서비스에 코루틴을 도입하면 복잡도만 올라가고 이득이 없습니다. 차라리 Thread-per-request 또는 JVM Virtual Thread가 더 단순합니다.

### 판단 기준 요약

| 상황 | 권장 |
|---|---|
| I/O 대기가 요청의 70% 이상 | 코루틴 ✅ |
| 동시 연결 수 10,000 이상 | 코루틴 ✅ |
| 팬-아웃 병렬 I/O 자주 등장 | 코루틴 ✅ |
| CPU 연산이 요청의 70% 이상 | 스레드 풀 (또는 코루틴 + 오프로드) |
| 블로킹 드라이버만 존재 | 코루틴 ❌ (Virtual Thread 고려) |
| 기존 동기 코드 유지 + 처리량만 상승 | Virtual Thread ✅ |

핵심은 이렇습니다. 코루틴은 모든 서버를 빠르게 만들지 않습니다. 기다림이 많은 서버를 스레드 비용 없이 빠르게 만듭니다. 계산이 병목이면 해법은 코루틴이 아니라 CPU 추가 또는 알고리즘 개선입니다.

## 트레이드오프

코루틴은 실행 모델의 변화라서 비용이 문법 레벨에서 끝나지 않습니다. 도입 시 거의 모두가 부딪히는 5가지를 정리합니다.

### 1. 스택 트레이스가 조각난다

코루틴이 중단됐다가 다른 스레드에서 재개되면, 재개된 지점의 스택 트레이스에는 원래 호출자의 스택이 보이지 않습니다. 호출자가 이미 스택에서 빠져나갔기 때문입니다. Python asyncio에서 예외가 발생하면 traceback이 `asyncio/events.py`, `asyncio/base_events.py` 같은 이벤트 루프 내부 코드까지만 이어지고, <E>이 예외가 어느 비즈니스 로직에서 시작됐는가</E>를 추적하기 어렵습니다. Kotlin은 `kotlinx-coroutines-debug` 플러그인이나 `-Dkotlinx.coroutines.debug` JVM 옵션으로 논리적 호출 스택을 복원해주지만, 운영 환경에서 상시 활성화하기에는 부담이 있습니다.

### 2. 블로킹 오염

코루틴은 협력적이라 `suspend` 지점에서만 양보합니다. 누군가 코루틴 안에서 블로킹 함수 하나 (`Thread.sleep`, 동기 JDBC, 파일 read)를 호출하면 그동안 같은 Dispatcher 또는 Event Loop 위의 모든 코루틴이 얼어붙습니다. 눈에 잘 안 보이는 지점입니다. 라이브러리가 <E>비동기 지원</E>이라고 문서에 써 있어도 내부 어딘가에서 동기 호출을 하고 있으면 그대로 오염됩니다. 실무에서는 `BlockHound` (JVM)나 `asyncio.get_event_loop().set_debug(True)` (Python) 같은 도구로 감시합니다.

### 3. ThreadLocal과 MDC 전파

재개되는 스레드가 중단되던 스레드와 다를 수 있다는 동작 원리가 여기서 문제가 됩니다. `ThreadLocal`에 저장한 사용자 ID, SLF4J MDC에 넣은 trace ID, Spring Security `SecurityContext` 같은 것들은 원본 스레드에만 묶여 있으므로 재개된 스레드에서는 비어 있습니다.

해결책은 명시적 전파입니다.

<Tabs group="coroutine-lang">
  <Tab label="Kotlin">
    ```kotlin title="MdcContext.kt"
    import kotlinx.coroutines.slf4j.MDCContext

    suspend fun handle(userId: Long) {
        MDC.put("userId", userId.toString())
        withContext(MDCContext()) {            // [!code highlight]
            doWork()
            // 재개 스레드에서도 MDC 값이 유지된다
        }
    }
    ```
  </Tab>
  <Tab label="Python">
    ```python title="context.py"
    import contextvars

    user_id_var = contextvars.ContextVar("user_id")

    async def handle(user_id):
        user_id_var.set(user_id)               // [!code highlight]
        await do_work()
        # do_work 내부에서도 user_id_var.get() 으로 조회 가능
    ```
  </Tab>
</Tabs>

### 4. async 전염 (Async Coloring)

Stackless 코루틴의 특성상 `suspend` 함수는 `suspend` 함수에서만 호출 가능합니다. 데이터 접근 함수 하나를 코루틴으로 바꾸면, 그걸 부르는 서비스 함수도 `suspend`가 돼야 하고, 그걸 부르는 컨트롤러도 `suspend`가 됩니다. 이 체인이 프로젝트 전체를 타고 번져나갑니다. 2015년 Bob Nystrom이 <E>What Color is Your Function?</E>에서 이 현상을 <E>함수에 색깔이 생긴 문제</E>라고 불렀습니다. 일부분만 코루틴으로 바꾸는 게 생각보다 어렵고, 도입을 결정하면 거의 전면 도입에 가깝게 됩니다. Stackful인 Go goroutine이나 JVM Virtual Thread는 이 문제가 없다는 점이 최근 Virtual Thread가 주목받는 이유 중 하나입니다.

### 5. 구조화 동시성 학습 곡선

코루틴의 진짜 강점 중 하나지만 학습 비용이 큽니다. `coroutineScope`, `supervisorScope`, `CancellationException`, `Job` 계층, Python `asyncio.TaskGroup` (3.11 이상) 같은 새 개념이 필요합니다. 자식 코루틴 하나가 실패하면 형제들이 모두 취소되고 예외가 부모로 전파되는 의도된 계층적 생명주기입니다. 이걸 모른 채 <E>왜 내 코루틴이 알아서 취소됐지?</E>에 당황하는 게 도입 초기 흔한 풍경입니다. 잘 이해하면 스레드 모델에서는 불가능했던 <E>누수 없는 동시성</E>을 얻습니다.

## 마무리

코루틴은 단순한 문법 설탕이 아닙니다. 컴파일러가 함수를 상태 머신으로 재작성하고, 중단된 상태를 힙 위 Continuation 객체로 포획하며, Event Loop가 I/O 완료 시 이 객체를 다시 실행시키는 실행 모델의 근본적 변화입니다. 스레드 수를 OS 한계 아래로 유지하면서 수만 개의 <E>동시 실행되는 것처럼 보이는 작업</E>을 돌릴 수 있는 힘이 여기서 나옵니다.

다만 그 이득은 I/O를 많이 기다리는 서버에서만 유의미하고, CPU-bound 작업이나 블로킹 라이브러리 생태계와는 정직한 충돌을 일으킵니다. 스택 트레이스 조각, 블로킹 오염, ThreadLocal 전파, async 전염, 구조화 동시성까지 도입의 대가도 분명합니다. 자신의 시스템이 기다림 중심인지 계산 중심인지를 먼저 판단하고, 그다음 코루틴을 쓸지 Virtual Thread를 쓸지 결정하는 순서가 맞습니다.
