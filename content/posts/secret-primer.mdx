ConfigMap은 환경 설정을 Pod 정의에서 분리해 한 곳에 모읍니다. 그런데 한 곳에 모이는 값 중에는 데이터베이스 접속 비밀번호나 외부 API 토큰처럼 아무나 보면 안 되는 값도 있습니다. 이런 값을 ConfigMap에 그대로 담으면 어떻게 될까요.

`kubectl describe configmap`은 ConfigMap에 든 키-값을 `Data` 항목 아래에 평문 그대로 출력합니다. 비밀번호를 ConfigMap에 넣어 두면, 그 명령을 칠 수 있는 사람은 누구나 비밀번호를 콘솔에서 그대로 읽습니다.

쿠버네티스는 이런 민감한 값을 위해 ConfigMap과 닮은 별개의 오브젝트를 둡니다. 그것이 Secret입니다. 이 글은 Secret이 ConfigMap과 무엇이 다른지, Secret을 만들고 Pod에 주입하는 방법, 그리고 흔히 오해하는 `base64`가 왜 암호화가 아닌지를 정리합니다.

## ConfigMap과 Secret의 차이

Secret도 ConfigMap처럼 키-값 쌍을 담는 쿠버네티스 오브젝트입니다. Pod와 분리된 별개의 오브젝트라는 점, 여러 Pod가 같은 것을 참조할 수 있다는 점, Pod에 주입하는 방식의 골격까지 둘은 거의 같습니다.

차이는 두 가지입니다.

첫째는 저장하는 값의 표현입니다. ConfigMap의 `data`는 값을 평문 그대로 담습니다. Secret은 값을 `base64`로 인코딩한 형태로 담습니다.

둘째는 조회할 때 값을 드러내는 정도입니다. `kubectl describe configmap`은 값을 그대로 출력하지만, `kubectl describe secret`은 값을 출력하지 않고 그 자리에 바이트 길이만 표시합니다. 콘솔을 어깨너머로 보는 사람에게 값이 그대로 노출되는 일을 줄이려는 장치입니다.

용도로 정리하면, 화면 색상이나 실행 모드 같은 일반 설정은 ConfigMap에 담고, 비밀번호나 토큰처럼 노출되면 안 되는 값은 Secret에 담습니다.

## Secret 만들기

Secret을 만드는 방식은 ConfigMap과 똑같이 두 가지입니다. 명령으로 바로 만드는 명령형 방식과, 정의 파일을 작성해 적용하는 선언형 방식입니다.

### 명령형 방식

`kubectl create secret` 명령을 씁니다. ConfigMap과 달리 Secret에는 종류가 있어 `generic`을 함께 적습니다. `generic`은 일반 키-값 Secret이고, 이 외에 도커 레지스트리 인증용 `docker-registry`, TLS 인증서용 `tls` 종류가 있습니다.

```bash
kubectl create secret generic app-secret \
  --from-literal=DB_PASSWORD=P@ssw0rd! \
  --from-literal=DB_USER=admin
```

`--from-literal`로 키-값을 직접 적거나 `--from-file`로 파일을 통째로 넘기는 것까지 ConfigMap과 같습니다. 명령형 방식에서는 평문을 그대로 적어도 됩니다. 쿠버네티스가 저장 시점에 값을 `base64`로 인코딩합니다.

### 선언형 방식

선언형 방식에서는 `kind`가 `Secret`인 정의 파일을 작성합니다. 여기서 ConfigMap과 갈라집니다. ConfigMap은 `data` 아래에 평문을 적었지만, Secret의 `data` 아래에는 `base64`로 인코딩한 값을 적어야 합니다.

평문을 `base64`로 인코딩하려면 `base64` 명령을 씁니다.

```bash
echo -n 'P@ssw0rd!' | base64
# UEBzc3cwcmQh
```

`echo`의 `-n`은 끝에 줄바꿈 문자를 붙이지 않게 합니다. 줄바꿈이 섞이면 인코딩 결과에 그 줄바꿈까지 들어가 값이 달라집니다.

인코딩한 값을 `data` 아래에 적습니다.

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: app-secret
data:
  DB_PASSWORD: UEBzc3cwcmQh
```

매번 손으로 인코딩하는 일이 번거롭다면 `data` 대신 `stringData`를 씁니다. `stringData`에는 평문을 그대로 적고, 쿠버네티스가 적용 시점에 인코딩합니다.

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: app-secret
stringData:
  DB_PASSWORD: P@ssw0rd!
```

두 파일은 같은 Secret을 만듭니다. 만든 Secret은 `kubectl get secrets`로 목록을 보고, `kubectl describe secret app-secret`으로 어떤 키가 들어 있는지 확인합니다. 앞서 말한 대로 `describe`는 값 대신 길이만 보여줍니다.

## Pod에 Secret 주입하기

만든 Secret을 Pod에 주입하는 방식은 ConfigMap과 똑같이 세 가지입니다. ConfigMap을 주입하던 세 방식에서 키워드만 Secret용으로 바뀝니다.

| 주입 방식 | ConfigMap | Secret |
|---|---|---|
| 전체를 환경 변수로 | `envFrom` + `configMapRef` | `envFrom` + `secretRef` |
| 키 하나를 환경 변수로 | `valueFrom` + `configMapKeyRef` | `valueFrom` + `secretKeyRef` |
| 파일로 마운트 | `volumes` + `configMap` | `volumes` + `secret` |

예를 들어 Secret의 키 하나를 환경 변수로 주입하려면, `valueFrom` 아래에 `configMapKeyRef` 대신 `secretKeyRef`를 적습니다.

```yaml
spec:
  containers:
    - name: simple-webapp
      image: simple-webapp
      env:
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: app-secret
              key: DB_PASSWORD
```

세 방식이 각각 컨테이너 안에 값을 어떤 형태로 들여놓는지는 ConfigMap과 동일하므로, 자세한 동작은 ConfigMap 글로 미룹니다.

<Callout type="warning" title="핵심 포인트: Secret 주입은 ConfigMap 주입과 골격이 같다">
Secret을 새로 배우는 부담은 생각보다 작습니다. ConfigMap 주입 세 방식을 이미 안다면, Secret은 `configMap`이 들어가던 자리에 `secret`을, `configMapKeyRef`가 들어가던 자리에 `secretKeyRef`를 적는 것으로 끝납니다. 새로운 점은 주입 방식이 아니라 값이 `base64`로 저장된다는 한 가지입니다.
</Callout>

## 암호화가 아닌 base64

여기서 오해가 생깁니다. Secret의 값이 `base64`로 인코딩되어 저장된다는 사실 때문에, Secret에 담은 값이 안전하게 보호된다고 여기기 쉽습니다.

`base64`는 암호화가 아닙니다. 데이터를 다른 문자 집합으로 바꿔 표현하는 인코딩일 뿐입니다. 인코딩에는 키가 없습니다. 그래서 `base64`로 인코딩한 값을 손에 넣은 사람은 누구나 키 없이 평문으로 되돌립니다.

```bash
echo -n 'UEBzc3cwcmQh' | base64 --decode
# P@ssw0rd!
```

암호화라면 키를 가진 쪽만 평문을 복원할 수 있습니다. `base64`에는 그런 잠금이 없습니다. Secret 정의 파일이나 `etcd`에 저장된 값이 `base64` 형태라는 것은, 그 값을 본 사람이 평문을 그대로 읽을 수 있다는 뜻입니다. Secret이라는 오브젝트에 담았다는 사실만으로 값이 보호되지는 않습니다.

## Secret을 안전하게 다루는 실천

쿠버네티스 공식 문서를 비롯한 여러 글이 Secret을 민감한 데이터를 다루는 <E>더 안전한 선택</E>이라고 설명합니다. 틀린 말은 아니지만, 안전한 것은 Secret이라는 오브젝트 자체가 아닙니다. 안전한 것은 Secret을 둘러싼 운영 실천입니다.

Secret을 일반 설정과 분리된 오브젝트로 두면, 민감한 값에만 다른 취급을 적용할 자리가 생깁니다. 그 자리에서 다음 두 가지 실천이 실제 안전성을 만듭니다.

첫째, Secret 정의 파일을 소스 코드 저장소에 커밋하지 않습니다. 앞에서 본 대로 `data`에 적힌 `base64` 값은 누구나 디코딩합니다. 정의 파일을 Git 저장소에 올리면 비밀번호를 평문으로 올린 것과 다를 바가 없습니다. 저장소에 접근할 수 있는 사람, 저장소가 공개로 바뀌는 사고, 커밋 이력에 남는 흔적까지 모두 노출 경로가 됩니다.

둘째, `etcd`의 Encryption at Rest를 활성화합니다. 쿠버네티스의 모든 오브젝트는 `etcd`에 저장되고, Secret도 기본 상태에서는 `base64` 형태 그대로 `etcd`에 들어갑니다. Encryption at Rest를 켜면 `etcd`에 쓰기 전에 값이 암호화되어, 디스크에 저장된 `etcd` 데이터를 직접 들여다봐도 평문이 보이지 않습니다.

## 쿠버네티스가 Secret을 다루는 방식

오브젝트 자체의 안전성과 별개로, 쿠버네티스는 Secret을 ConfigMap보다 조심스럽게 다룹니다. 노출 범위와 흔적을 줄이는 세 가지 처리입니다.

첫째, Secret은 그것을 필요로 하는 Pod가 떠 있는 노드에만 전달됩니다. 클러스터의 모든 노드에 Secret을 뿌리지 않으므로, 한 노드가 뚫려도 그 노드에서 실행 중인 Pod가 쓰는 Secret만 영향을 받습니다.

둘째, `kubelet`은 전달받은 Secret을 디스크가 아니라 메모리에 올라가는 파일 시스템인 `tmpfs`에 저장합니다. Secret 값이 노드의 디스크에 기록되지 않으므로, 디스크를 떼어내 분석하는 식의 접근으로는 Secret을 얻을 수 없습니다.

셋째, Secret을 쓰던 Pod가 삭제되면 `kubelet`은 그 노드에 두었던 Secret의 로컬 복사본도 함께 지웁니다. 더 이상 필요하지 않은 민감한 값이 노드에 남지 않습니다.

## 더 안전한 비밀 관리

Secret과 그 주변 실천만으로 충분하지 않은 환경도 있습니다. 비밀 값의 교체 주기 관리, 접근 감사 로그, 짧은 수명의 동적 자격 증명 같은 요구가 더해지면 쿠버네티스 기본 Secret만으로는 부족합니다.

이런 경우 Helm Secrets나 HashiCorp Vault 같은 전용 도구를 함께 씁니다. Helm Secrets는 Helm 차트에 들어가는 Secret 값을 암호화한 채로 저장소에 보관하게 해 주고, HashiCorp Vault는 비밀 값을 중앙에서 발급하고 교체하고 회수하는 별개의 시스템입니다. 두 도구의 동작 원리는 이 글의 범위를 넘으므로 이름만 언급해 둡니다.

<Callout type="error" title="핵심 통찰: 안전한 것은 Secret이 아니라 Secret을 둘러싼 실천이다">
Secret의 값은 `base64`로 인코딩될 뿐 암호화되지 않습니다. 인코딩에는 키가 없으므로, Secret이라는 오브젝트 하나만으로는 ConfigMap보다 더 안전하지 않습니다. 실제 안전성은 Secret을 일반 설정과 분리해 둔 덕분에 적용할 수 있게 된 실천에서 나옵니다. 정의 파일을 저장소에 올리지 않고, `etcd`의 Encryption at Rest를 켜고, `kubelet`이 Secret을 노드 메모리에만 두었다가 Pod 삭제 시 지우는 처리가 그것입니다.
</Callout>
