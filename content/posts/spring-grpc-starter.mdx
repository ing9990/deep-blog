spring-grpc는 gRPC를 다시 구현한 프레임워크가 아니라, `grpc-java`의 `Server`와 `ManagedChannel`을 Spring Boot의 라이프사이클·설정 모델 위에 올리는 얇은 스타터입니다. 이 글에서는 어떤 보일러플레이트가 어떤 어노테이션과 설정 키로 치환되는지 따라가며, 서버와 클라이언트를 한 번 구성해 봅니다.

<RelatedPost slug="grpc-essentials" type="prerequisite" />

## spring-grpc란

spring-grpc는 [Spring 공식 프로젝트](https://github.com/spring-projects/spring-grpc)로 만들어진 gRPC 통합 스타터입니다. Spring Boot 3.x(특히 3.5+)를 타겟으로 하며, 내장 Netty 기반 gRPC 서버와 Servlet 컨테이너에 공존하는 gRPC 서버 두 변형을 starter 아티팩트로 나눠 제공합니다.

이 이름을 쓰는 라이브러리는 두 계열이 있습니다. 오랫동안 사실상 표준 역할을 해 온 커뮤니티판 `net.devh:grpc-spring-boot-starter`와, 2024년부터 GA한 Spring 공식판 `org.springframework.grpc:spring-grpc-*`. 이 글은 공식판 기준입니다. 두 라이브러리는 어노테이션 패키지, 프로퍼티 키, 자동설정 구조가 달라 서로 호환되지 않으므로 한 프로젝트에 하나만 씁니다.

구조적으로 spring-grpc는 세 부분으로 나뉩니다. (1) 서버 사이드로 `@GrpcService` 빈을 찾아 내장 서버에 등록, (2) 클라이언트 사이드로 protoc가 생성한 스텁 클래스를 Spring 빈으로 자동 등록, (3) `SslBundles`, Micrometer Observation, Actuator Health 같은 Spring Boot 공용 인프라 훅이 gRPC 쪽에도 연결. 이 세 축을 아래에서 순서대로 풀어냅니다.

## 왜 필요한가

순수 `grpc-java`로 서버·클라이언트를 띄우면 전형적으로 이런 보일러플레이트가 생깁니다. 서버는 `ServerBuilder`로 직접 포트를 열고 종료 훅을 수동으로 엮어야 하고, 클라이언트는 `ManagedChannelBuilder`로 채널을 만든 뒤 스텁을 꺼내 두는 과정을 서비스마다 반복합니다.

```java title="RawGrpcApp.java"
public class RawGrpcApp {
    public static void main(String[] args) throws Exception {
        Server server = ServerBuilder.forPort(9090)
                .addService(new GreeterServiceImpl())
                .intercept(new LoggingInterceptor())
                .build()
                .start();

        ManagedChannel channel = ManagedChannelBuilder
                .forAddress("localhost", 9090)
                .usePlaintext()
                .build();
        GreeterGrpc.GreeterBlockingStub stub = GreeterGrpc.newBlockingStub(channel); // [!code highlight]

        Runtime.getRuntime().addShutdownHook(new Thread(() -> {
            channel.shutdown();
            server.shutdown();
        }));
        server.awaitTermination();
    }
}
```

spring-grpc가 이 배선을 대신 처리합니다. 크게 네 가지입니다.

| 자동화 영역 | spring-grpc가 대신 하는 일 |
|---|---|
| 서버 라이프사이클 | `@GrpcService` 빈을 모아 Boot 기동 시 포트 열기, `ApplicationContext` 종료 시 graceful shutdown |
| 채널·스텁 배선 | 생성된 `*Grpc$...Stub`을 자동 스캔해 빈으로 등록, 이름 채널과 묶어줌 |
| 외부 설정화 | 포트·TLS·keepalive·메시지 크기 상한을 `application.properties`로 외부화 |
| 공용 인프라 | `SslBundles`, Micrometer Observation, Actuator Health를 gRPC 쪽에도 연결 |

한 가지 오해만 짚어 두면, spring-grpc는 gRPC 자체를 대체하지 않습니다. 내부적으로는 여전히 `grpc-java`의 `Server`와 `ManagedChannel`을 씁니다. 스타터는 이 객체들을 만들고 라이프사이클에 맞춰 관리하고 설정 소스와 묶어주는 <E>배선 층</E>만 Spring Boot 스타일로 표준화한 것입니다. 따라서 `ServerInterceptor`, `ClientInterceptor`, `Metadata` 같은 `grpc-java` API는 그대로 유효합니다.

## 기초 문법

<Callout type="warning" title="이 글의 핵심 포인트">
  spring-grpc는 `grpc-java`를 대체하지 않고 감쌉니다. 아래 다섯 가지 문법 단위는 전부 기존 `grpc-java` API 위에 Spring Boot의 자동설정, 의존성 주입, 외부 설정을 얹은 얇은 층입니다. 각 어노테이션과 설정 키를 볼 때 <E>이게 원래 `grpc-java`에서는 무엇이었는가</E>를 떠올리면 구조가 선명해집니다.
</Callout>

<Callout type="error" title="핵심 통찰: spring-grpc는 새로운 RPC가 아니라 Boot 규칙으로의 재배선">
  spring-grpc의 모든 어노테이션과 설정 키는 결국 `grpc-java`의 `Server`, `ManagedChannel`, `BindableService` 객체를 Spring이 대신 만들고 연결해 주는 것으로 환원됩니다. 스타터가 만드는 것은 새로운 RPC가 아니라, 기존 gRPC 배선을 Boot의 라이프사이클·설정·DI 규칙 안으로 끌어오는 변환 층입니다.
</Callout>

### 의존성 선택

스타터는 서버 런타임에 따라 아티팩트가 나뉩니다. 둘을 동시에 선언하면 자동설정이 충돌하므로 하나만 고릅니다. 클라이언트만 쓰는 프로세스라면 client starter만 넣으면 됩니다.

<Tabs>
  <Tab label="Netty 서버">
    ```kotlin title="build.gradle.kts"
    dependencies {
        implementation("org.springframework.grpc:spring-grpc-spring-boot-starter")
        implementation("io.grpc:grpc-services") // Reflection, Health
    }
    ```
    gRPC만 띄우는 전용 프로세스에 적합. Boot가 Netty 서버를 독립 포트로 띄운다.
  </Tab>
  <Tab label="Servlet 공존 서버">
    ```kotlin title="build.gradle.kts"
    dependencies {
        implementation("org.springframework.grpc:spring-grpc-server-web-spring-boot-starter")
    }
    ```
    같은 포트와 Servlet 컨테이너에서 HTTP와 gRPC를 함께 서비스할 때. 내부적으로 `grpc-servlet-jakarta`를 쓴다.
  </Tab>
  <Tab label="클라이언트 전용">
    ```kotlin title="build.gradle.kts"
    dependencies {
        implementation("org.springframework.grpc:spring-grpc-client-spring-boot-starter")
    }
    ```
    다른 gRPC 서버를 호출만 하는 프로세스. 서버 자동설정을 가져오지 않는다.
  </Tab>
</Tabs>

### 서버 구현

protoc-gen-grpc-java가 만들어 준 `*ImplBase`를 상속한 클래스를 Spring 빈으로 등록하기만 하면, 자동설정이 `BindableService`를 전부 모아 내장 서버에 `addService()`로 붙입니다. `@GrpcService`를 써도 되고 평범한 `@Service`, `@Component`를 써도 동작합니다. 차이는 `@GrpcService`가 서비스 단위 인터셉터 attribute(`interceptors`)를 받는다는 점뿐입니다.

```java title="GreeterService.java"
@Service
class GreeterService extends GreeterGrpc.GreeterImplBase {

    @Override
    public void sayHello(HelloRequest req, StreamObserver<HelloReply> res) {
        HelloReply reply = HelloReply.newBuilder()
                .setMessage("Hello " + req.getName())
                .build();
        res.onNext(reply);
        res.onCompleted();
    }
}
```

### 설정 키

서버 포트와 클라이언트 채널 주소는 전부 `application.properties`로 외부화됩니다. 클라이언트 채널은 **이름**으로 등록하고, 스텁이 주입될 때 같은 이름 채널이 자동으로 연결됩니다. 채널 단위로 주소를 쓰므로 한 프로세스가 여러 원격 대상을 부르는 구조도 그대로 표현 가능합니다.

```properties title="application.properties"
# 서버
spring.grpc.server.port=9090

# 클라이언트 채널 (이름: local)
spring.grpc.client.channels.local.address=static://localhost:9090
spring.grpc.client.channels.local.negotiation-type=plaintext
```

`spring.grpc.server.port=0`이면 랜덤 포트가 할당됩니다. 통합 테스트에서 자주 쓰는 값입니다.

### 클라이언트 주입

스텁을 주입받는 방법은 두 가지입니다. 대부분의 경우 자동 등록(`@ImportGrpcClients`)으로 충분하고, 주소를 런타임에 결정해야 할 때만 수동(`GrpcChannelFactory`)으로 내려갑니다.

<Tabs>
  <Tab label="자동 (@ImportGrpcClients)">
    ```java title="DemoApp.java"
    @SpringBootApplication
    @ImportGrpcClients(basePackageClasses = DemoApp.class) // 기본값이라 생략 가능
    class DemoApp { }

    @Service
    class HelloClient {
        private final GreeterGrpc.GreeterBlockingStub stub;

        HelloClient(GreeterGrpc.GreeterBlockingStub stub) { // 자동 주입 // [!code highlight]
            this.stub = stub;
        }

        String call(String name) {
            return stub.sayHello(
                    HelloRequest.newBuilder().setName(name).build()
            ).getMessage();
        }
    }
    ```
    `*BlockingStub`, `*Stub`, `*FutureStub`이 자동 빈으로 등록된다. 기본 채널 이름은 스텁 클래스 이름에서 유도되며, `application.properties`의 같은 이름 채널 설정과 자동 매칭된다.
  </Tab>
  <Tab label="수동 (GrpcChannelFactory)">
    ```java title="StubConfig.java"
    @Configuration
    class StubConfig {

        @Bean
        GreeterGrpc.GreeterBlockingStub greeterStub(GrpcChannelFactory channels) {
            return GreeterGrpc.newBlockingStub(
                    channels.createChannel("local") // [!code highlight]
            );
        }
    }
    ```
    `GrpcChannelFactory#createChannel(name)`은 `spring.grpc.client.channels.<name>` 설정을 그대로 사용한다. 동적 주소 결정, 같은 스텁 타입을 여러 채널에 번갈아 쓰는 경우에 쓴다.
  </Tab>
</Tabs>

### 테스트 포트

통합 테스트에서는 서버를 `spring.grpc.server.port=0`으로 띄워 포트 충돌을 피합니다. 이때 클라이언트 스텁 빈은 `@LocalGrpcPort`로 결정된 포트를 받아야 하고, 빈 생성 시점이 포트 결정보다 빠르면 안 되므로 `@Lazy`를 반드시 붙입니다.

```java title="TestStubConfig.java"
@TestConfiguration
class TestStubConfig {

    @Bean
    @Lazy // [!code highlight]
    GreeterGrpc.GreeterBlockingStub testStub(
            GrpcChannelFactory channels,
            @LocalGrpcPort int port) {
        return GreeterGrpc.newBlockingStub(
                channels.createChannel("0.0.0.0:" + port)
        );
    }
}
```

## 기능 소개

스타터가 `grpc-java` 위에 얹어 둔 훅 중 실무에서 자주 켜는 네 가지를 훑어봅니다. 전부 빈 하나 추가 또는 프로퍼티 한 줄로 활성화됩니다.

### 인터셉터

`grpc-java`의 `ServerInterceptor`와 `ClientInterceptor`를 그대로 쓰되, 스프링 빈으로 올리고 어노테이션으로 스코프를 지정합니다. 전역 인터셉터는 `@GlobalServerInterceptor`나 `@GlobalClientInterceptor`로 선언하고 `@Order`로 순서를 제어합니다. 특정 서비스에만 붙이려면 `@GrpcService(interceptors = ...)`를 씁니다.

```java title="Interceptors.java"
@Configuration
class Interceptors {

    @Bean
    @Order(100)
    @GlobalServerInterceptor // [!code highlight]
    ServerInterceptor authInterceptor() {
        return new AuthServerInterceptor();
    }
}

@GrpcService(interceptors = RateLimitInterceptor.class) // [!code highlight]
class OrderService extends OrderGrpc.OrderImplBase {
    // ...
}
```

### TLS

spring-grpc는 Boot 3의 `SslBundles` 인프라에 올라가 있어, WebMVC나 WebFlux에서 쓰는 번들 선언을 그대로 참조할 수 있습니다. 키스토어 선언은 한 번, 그걸 gRPC 쪽이 번들 이름으로 바인딩합니다.

```properties title="application.properties"
spring.grpc.server.ssl.bundle=grpc-tls

spring.ssl.bundle.jks.grpc-tls.keystore.location=classpath:server.p12
spring.ssl.bundle.jks.grpc-tls.keystore.password=${KS_PW}
spring.ssl.bundle.jks.grpc-tls.keystore.type=PKCS12
```

클라이언트 쪽도 같은 방식으로 `spring.grpc.client.channels.<name>.ssl.bundle` 한 줄로 번들 이름만 참조합니다. mTLS가 필요하면 번들의 `truststore.*`까지 함께 채우면 됩니다.

### Reflection

`grpcurl`이나 Postman의 gRPC 탐색 기능은 서버에 Reflection 서비스가 등록되어 있어야 동작합니다. spring-grpc는 `io.grpc:grpc-services`가 클래스패스에 있으면 Reflection 서비스를 자동으로 서버에 붙입니다.

```kotlin title="build.gradle.kts"
dependencies {
    implementation("io.grpc:grpc-services") // [!code highlight]
}
```

이후 `grpcurl -plaintext localhost:9090 list`로 서비스와 메서드를 탐색할 수 있습니다. Reflection은 운영 환경에서는 보통 끄므로 profile로 분리하거나 네트워크 레벨에서 막습니다.

### Observability

Actuator와 Micrometer가 클래스패스에 있으면 gRPC 호출마다 Observation이 자동으로 만들어집니다. 메트릭은 `grpc.server.call`과 `grpc.client.call` 계열로 `rpc.method`, `rpc.service`, `grpc.status` 태그와 함께 노출되고, OpenTelemetry bridge를 붙여 두면 trace도 같은 span으로 전파됩니다. 즉 Spring MVC Observation과 동일한 파이프라인을 공유합니다.

```properties title="application.properties"
management.endpoints.web.exposure.include=health,metrics,prometheus
management.observations.annotations.enabled=true
```

## Gotchas

처음 붙일 때 반복적으로 부딪히는 다섯 가지입니다. 전부 <E>사용법 앵커</E> 성격으로, 에러 메시지와 해결책을 함께 두었습니다.

<Callout type="warning" title="Netty 스타터와 Servlet 스타터 동시 선언">
  `spring-grpc-spring-boot-starter`(Netty)와 `spring-grpc-server-web-spring-boot-starter`(Servlet) 둘 다 있으면 자동설정이 경쟁해 `GrpcServerFactory`가 두 개 생기거나 포트 바인딩 시점에 의도하지 않은 쪽이 선택됩니다. 프로세스당 하나만 남겨야 합니다.
</Callout>

<Callout type="warning" title="@ImportGrpcClients base package가 스텁을 포함하지 못함">
  protoc 출력 디렉터리(`build/generated/source/proto/main/grpc`)가 `@SpringBootApplication` 패키지와 다른 루트에 만들어지면 자동 스캔이 스텁을 찾지 못합니다. `No qualifying bean of type 'GreeterBlockingStub'` 에러가 뜨면 의심해 볼 지점입니다. `@ImportGrpcClients(basePackages = "com.example.grpc.generated")`로 생성 패키지를 명시하거나 생성 경로를 앱 base package 하위로 맞춥니다.
</Callout>

<Callout type="warning" title="@LocalGrpcPort 주입 빈에 @Lazy 누락">
  `spring.grpc.server.port=0`은 `ApplicationContext`가 살아난 뒤에야 포트를 결정합니다. 스텁 빈이 일반 싱글톤이면 포트 결정 전에 생성되어 고정된 잘못된 값을 받거나 `UNAVAILABLE: io exception`으로 실패합니다. 스텁 빈에 `@Lazy`를 붙여 사용 시점에 포트를 읽도록 해야 합니다.
</Callout>

<Callout type="warning" title="클라이언트 negotiation-type과 서버 TLS 설정 불일치">
  서버는 `spring.grpc.server.ssl.bundle`로 TLS를 켜 놨는데 클라이언트가 `negotiation-type=plaintext`로 붙으면 채널이 열리자마자 `UNAVAILABLE: Network closed for unknown reason` 또는 SSL handshake 실패로 떨어집니다. 반대 방향도 같은 증상입니다. 양쪽이 동일 번들 이름을 공유하도록 맞추는 게 안전합니다.
</Callout>

<Callout type="warning" title="Reflection 의존성 없이 grpcurl 호출">
  `io.grpc:grpc-services`가 없는 상태에서 `grpcurl localhost:9090 list`를 치면 `server does not support the reflection API`로 거절됩니다. 로컬, 개발 환경에서만 의존성을 포함하는 profile 분리가 가장 흔한 해법입니다.
</Callout>

## 마무리

spring-grpc 위에서 작성하는 모든 코드는 결국 `grpc-java`의 `Server`, `ManagedChannel`, `BindableService`로 환원됩니다. 스타터가 해 주는 일은 이 객체들을 Spring Boot의 라이프사이클, DI, 외부 설정, 공용 인프라 규칙에 맞춰 대신 배선해 주는 것입니다. 어노테이션과 설정 키를 볼 때마다 `grpc-java`의 어떤 개념을 대신하고 있는지 매핑해 두면, 새로운 훅이 등장해도 구조가 흔들리지 않습니다.
