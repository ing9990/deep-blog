Cache-Aside는 대부분의 백엔드가 "일단 캐시를 도입할 때 이걸로 시작한다"의 자리를 차지하는 패턴입니다. 간단해 보이는 세 줄 레시피(조회·채움·무효화) 뒤에 쓰기 경합, stale read, stampede 같은 고유 문제가 자연히 따라옵니다. 이 글에서는 왜 이 패턴이 기본값이 되었는지, 무엇을 포기해야 하는지, 그리고 언제 다른 패턴으로 옮겨가야 하는지를 살펴봅니다.

<Note title="이 글의 학습 목표">
  - Cache-Aside가 왜 다른 캐싱 패턴보다 먼저 채택되는지 그 구조적 이유를 이해한다
  - 앱·캐시·DB 3자 상호작용의 내부 동작과 쓰기 경로의 race condition을 구분할 수 있다
  - Read-Through, Write-Through, Write-Behind, Write-Around 중 상황에 맞는 패턴을 선택하는 기준을 얻는다
</Note>

## Cache-Aside란

Cache-Aside는 **앱이 캐시와 DB를 직접 제어하는** 캐싱 패턴입니다. Look-Aside Cache, Lazy Loading이라고도 부릅니다. 이 셋은 모두 같은 패턴의 다른 이름입니다.

정체성은 한 문장으로 요약됩니다: "앱이 주체이고, 캐시는 수동적인 key-value store다." 캐시는 DB 옆에 붙어 있는 보조 저장소일 뿐이며 DB를 읽거나 쓰는 방법을 모릅니다. 읽기·쓰기 경로의 모든 결정권이 앱 코드에 있습니다.

동작은 두 가지 경로로 분리됩니다.

**읽기 (Read)**
1. 앱이 캐시에서 key로 조회한다
2. Cache hit이면 값을 그대로 반환
3. Cache miss이면 DB에서 조회 → 결과를 캐시에 저장(TTL 포함) → 반환

**쓰기 (Write)**
1. 앱이 DB에 값을 쓴다
2. 해당 key를 캐시에서 무효화(보통 `DEL`로 삭제)

```kotlin title="UserService.kt"
fun getUser(id: Long): User {
    val cached = cache.get("user:$id")                // 1. 캐시 조회
    if (cached != null) return cached                 // 2. Hit
    val user = userRepository.findById(id)            // 3. Miss → DB
    cache.set("user:$id", user, ttl = 5.minutes)      // 4. 캐시 채움
    return user
}

fun updateUser(user: User) {
    userRepository.save(user)                         // 1. DB 쓰기
    cache.delete("user:${user.id}")                   // 2. 캐시 무효화
}
```

Read-Through나 Write-Through는 앱이 캐시 라이브러리에게 위임하고, Write-Behind는 캐시가 DB 쓰기를 대신합니다. Cache-Aside는 그 반대 방향으로 **앱이 주체**이고 캐시는 수동적입니다. 그래서 "Look-Aside"(옆에 두고 참조)라는 별명이 붙었습니다.

이 글에서 반복 등장하는 용어를 먼저 정리합니다.

| 용어 | 의미 |
|---|---|
| Cache hit / miss | 찾는 key가 캐시에 있었는가 / 없었는가 |
| Invalidation | 더 이상 맞지 않는 캐시 항목을 제거(삭제 또는 갱신) |
| TTL (Time To Live) | 항목이 자동 만료되는 시간 |
| Lazy Loading | 처음 요청될 때만 캐시에 올리는 방식. Cache-Aside의 다른 이름 |

## 왜 필요한가

Cache-Aside의 위치를 이해하려면 "있을 때 vs 없을 때"를 먼저 봅니다. 차이는 **앱이 보는 지연**이 아니라 **DB가 감당하는 부하**에 있습니다.

**없을 때**: 상품 조회 API가 초당 5,000 요청을 받는다고 합시다. 이 요청들이 결국 같은 hot row를 반복해서 읽습니다. 캐시가 없으면 DB는 동일한 쿼리 5,000개를 전부 실행합니다. DB의 버퍼풀이 어느 정도 완충해주지만, 쿼리 파싱, 플래닝, 네트워크 왕복 비용은 회피할 수 없습니다. 흔한 B2C 서비스에서 DB CPU의 60%에서 80%가 "똑같은 hot row 반복 읽기"에 소모되는 이유입니다.

**있을 때**: Cache hit이면 요청은 DB 근처에도 가지 않습니다. Redis 기준 sub-millisecond 메모리 조회 한 번으로 끝납니다. Miss일 때만 DB를 치고, 그 결과를 캐시에 올려 다음 요청부터는 다시 hit으로 수렴합니다. 결과적으로 DB로 가는 실제 트래픽은 "고유 key 수 + TTL 만료 주기"에 비례하며, 전체 요청량과 디커플링됩니다.

그런데 "캐시를 둔다"는 선택지는 Cache-Aside 외에도 여럿 있습니다. 왜 하필 이걸 먼저 고르는가. 이유는 세 가지입니다.

### 장애 격리가 강하다

캐시가 다운되어도 앱은 `if (cached != null)` 분기를 타지 않고 DB로 직접 폴백하면 됩니다. 코드 한 줄로 우회 가능합니다. Read-Through의 경우 캐시 레이어 자체가 읽기 경로에 **끼어 있어**, 캐시 장애가 DB 장애처럼 전파됩니다. Cache-Aside는 이 분리가 자연히 이뤄집니다.

### 언제든 도입 가능하다

이미 동작하는 서비스에 캐시를 추가할 때, 기존 DB 접근 코드를 래핑만 하면 됩니다. 데이터 모델 변경도, 프레임워크 교체도 필요 없습니다. Write-Through는 캐시 라이브러리나 플랫폼이 DB write를 중개할 능력이 있어야 하고, 대부분의 Redis, Memcached 기본 구성에는 그런 기능이 없습니다.

### 유연한 캐시 키와 TTL

앱이 캐시 키를 만드므로 `user:123:profile`, `user:123:orders:recent`처럼 도메인에 맞는 key 설계가 자유롭습니다. 같은 user row를 서로 다른 목적의 여러 key로 캐싱할 수도 있습니다. 라이브러리가 key를 강제하지 않습니다.

<Callout type="warning" title="흔한 오해: TTL만 짧게 잡으면 일관성 문제는 해결된다">
  아닙니다. TTL은 "언젠가 캐시가 DB로 수렴한다"를 보장할 뿐, 쓰기 시점의 race condition을 막을 수 없습니다. 예를 들어 TTL 5초라도 쓰기 직후 5초 동안 잘못된 값이 캐시에 남아 있으면 그 창 안의 모든 요청이 잘못된 값을 읽습니다. 일관성 문제는 TTL이 아니라 쓰기 순서로 푸는 것이며, 이는 다음 섹션에서 다룹니다.
</Callout>

## 내부 동작

<Callout type="warning" title="이 글의 핵심 포인트">
  Cache-Aside는 **3자 상호작용**입니다. 앱, 캐시, DB 세 주체가 있고 앱이 지휘자 역할을 합니다. 이 섹션은 "어떤 일이 벌어지는가"보다 **어떤 순서로, 어디서 실패할 수 있는가**를 중심으로 봅니다. 패턴의 버그는 대부분 이 순서의 미묘한 차이에서 나옵니다.
</Callout>

### Read path: Hit

가장 단순한 경로입니다. 캐시가 값을 반환하면 끝납니다. DB는 건드리지 않습니다.

```text
[App] ── get("user:123") ──▶ [Cache]
[App] ◀── value ─────────── [Cache]
```

이 경로의 성능은 "앱 ↔ 캐시" 네트워크 RTT와 캐시 내부 연산으로 결정됩니다. 같은 데이터센터의 Redis라면 sub-millisecond 수준입니다.

주의할 미묘한 점 하나: "nil을 받았다"와 "DB에 데이터가 없다"는 다른 상태입니다. 캐시가 nil을 반환했다는 건 "이 key를 모른다"일 뿐이고, DB에 진짜 데이터가 없을 수도, 있지만 아직 캐시에 안 올라간 상태일 수도 있습니다. 이 구분이 뒤에 나올 cache penetration 문제의 씨앗입니다.

### Read path: Miss

```text
[App] ── get("user:123") ────────────▶ [Cache]
[App] ◀── nil ────────────────────── [Cache]
[App] ── SELECT ... ───────────────▶ [DB]
[App] ◀── row ───────────────────── [DB]
[App] ── set("user:123", v, EX=300) ▶ [Cache]
[App] ◀── OK ──────────────────── [Cache]
```

Miss 경로는 왕복이 3번입니다. 문제는 "이 3번이 하나의 원자적 동작이 아니다"라는 점입니다. 앱이 DB를 조회하는 사이, 같은 key에 대한 다른 요청이 동시에 들어오면 **모두 miss**를 보고 **모두 DB를 치게** 됩니다. 이것이 캐시 스탬피드의 원형 시나리오이며, 자세한 완화 전략은 별도 글에서 다룹니다.

<RelatedPost slug="cache-stampede" type="deep-dive" />

한 가지 더: `set`을 할 때 TTL을 빠뜨리면 안 됩니다. TTL 없이 저장된 키는 명시적 삭제 전까지 영원히 살아 있고, DB에서 값이 바뀌어도 반영되지 않습니다. "캐시가 이상한 값을 들고 있다"는 대부분의 사고는 여기서 시작합니다.

### Write path: 두 선택지

쓰기 경로에는 두 가지 선택지가 있고, 둘은 서로 다른 tradeoff를 만듭니다.

<Tabs>
  <Tab label="방식 A (권장): DB 쓰기 → 캐시 삭제">
    ```kotlin
    fun updateUser(user: User) {
        userRepository.save(user)           // DB에 새 값
        cache.delete("user:${user.id}")     // 캐시 삭제
    }
    ```

    다음 읽기 요청이 miss를 보고 DB에서 새 값을 다시 로드합니다. 현실의 대부분 Cache-Aside 구현이 이 패턴입니다.
  </Tab>
  <Tab label="방식 B (위험): DB 쓰기 → 캐시 갱신">
    ```kotlin
    fun updateUser(user: User) {
        userRepository.save(user)           // DB에 새 값
        cache.set("user:${user.id}", user)  // 캐시에 새 값
    }
    ```

    얼핏 더 효율적으로 보입니다. 다음 읽기는 바로 hit. 하지만 동시 쓰기에서 문제가 생깁니다(아래 참조).
  </Tab>
</Tabs>

방식 B는 동시 쓰기가 들어오는 순간 깨집니다.

```text
T1: UPDATE name='Alice' → DB 적용
T2: UPDATE name='Bob'   → DB 적용 (T1 이후)
T2: SET cache='Bob'     → Cache=Bob
T1: SET cache='Alice'   → Cache=Alice  ← 뒤집힘
```

DB의 최종값은 `Bob`인데 캐시는 `Alice`를 들고 있습니다. 네트워크 지연이나 GC pause 등으로 `SET` 도착 순서가 DB 적용 순서와 뒤집힐 수 있기 때문입니다. 반면 방식 A는 두 요청이 모두 `DEL`을 하므로 순서가 뒤집혀도 결과가 같습니다. `DEL`은 멱등하기 때문입니다. 이것이 "삭제 후 재로드"가 "바로 갱신"보다 선호되는 이유입니다.

### 왜 DB 먼저, 캐시 나중인가

Cache-Aside에서 가장 미묘한 부분입니다. 두 순서를 비교해봅니다.

<Callout type="error" title="핵심 통찰: Cache-Aside의 일관성은 순서가 만든다">
  "DB 쓰기 → 캐시 삭제" 순서를 따르는 이유는 역순일 때 **캐시가 옛 값으로 재채움(re-population)** 되는 창이 너무 길기 때문입니다. 이 순서는 eventual consistency를 보장하는 최소한의 합의이며, 순서를 어기면 TTL이 만료될 때까지 옛 값이 캐시에 고정됩니다.
</Callout>

**순서 A (권장): DB 쓰기 → 캐시 삭제**

DB가 먼저 새 값을 들고 있고, 그 다음 캐시를 지웁니다. 캐시 삭제 직전까지 누군가 읽으면 옛 값을 봅니다. 캐시가 지워진 이후 읽으면 miss가 되어 DB에서 새 값을 로드합니다. 짧은 창에서의 stale read는 있지만 최종 상태는 항상 수렴합니다.

**순서 B (역순): 캐시 삭제 → DB 쓰기**

캐시를 먼저 지우고 DB를 씁니다. 그 사이 창(DB write 완료 전)에 읽기 요청이 들어오면 miss가 되고, **DB에서 옛 값을 읽어 캐시를 다시 채웁니다**. 이후 DB write가 완료되어도 캐시는 옛 값을 들고 있고, TTL이 만료될 때까지 풀리지 않습니다.

```text
T1: DEL cache           → 캐시 비움
T2: GET cache → miss
T2: SELECT → 옛 값 V0 읽음
T2: SET cache=V0        ⚠️ 캐시를 옛 값으로 다시 채움
T1: UPDATE DB=V1        → DB는 새 값
[최종] DB=V1, Cache=V0 (TTL 만료 전까지 옛 값 반환)
```

순서 A는 이 재채움 창이 "캐시 지우기 직전"이라 매우 짧지만, 순서 B는 "DB write가 끝날 때까지" 창이 길어 재캐싱 사고가 훨씬 쉽게 발생합니다. Facebook의 "Scaling Memcache at Facebook"(NSDI '13) 논문도 동일한 결론에 도달했습니다.

### 읽기와 쓰기가 섞일 때

순서 A를 써도 완벽하지는 않습니다. 다음 시나리오가 "Cache-Aside는 eventual consistency"라고 말할 때의 그 eventual이 어떤 의미인지 보여줍니다.

```text
T1: GET cache → miss
T1: SELECT → V0 읽음
T2: UPDATE DB → V1
T2: DEL cache → (이미 비어 있음, no-op)
T1: SET cache=V0        ⚠️ 새 값이 지워진 후 옛 값이 들어감
[최종] DB=V1, Cache=V0
```

T1이 DB에서 V0을 읽은 후, T2가 DB를 V1로 업데이트하고 캐시를 지웠는데, T1이 뒤늦게 V0을 캐시에 올려버립니다. 순서 A로도 이 race는 남아 있습니다.

완화책은 세 방향입니다.

| 방법 | 원리 | 한계 |
|---|---|---|
| TTL 축소 | 수렴 속도를 높여 잘못된 값이 보이는 창을 줄인다 | miss율 증가로 DB 부하 상승 |
| Double delete | DB 쓰기 후 캐시 삭제, N ms 대기, 캐시 재삭제 | 지연된 race까지 덮지는 못함 |
| CDC 연동 | Debezium 등으로 DB 변경을 구독해 자동 무효화 | 인프라 복잡도 상승, 지연 발생 |

"Cache-Aside로는 strict consistency를 보장할 수 없다"는 사실을 받아들이는 것이 첫걸음이고, 그 위에서 이 세 완화책의 조합을 선택하는 것이 실전입니다.

## 실전 문제

Cache-Aside의 "3-step 레시피"는 단순하지만, 프로덕션에서는 네 가지 고유 문제와 자주 만납니다. 각 문제는 패턴 자체의 구조에서 나오며, 대부분 read-write race와 "캐시와 DB가 서로 다른 저장소라는 사실"에서 유래합니다.

### Stale Read

DB가 업데이트되고 캐시 삭제가 도착하기 전의 아주 짧은 구간, 그리고 앞 섹션의 read-write race 구간에 "최신이 아닌 값"이 읽힙니다. Cache-Aside는 **본질적으로 eventual consistency** 모델입니다.

대부분의 서비스에서는 이 창이 ms 단위이고, 읽기가 "캐시에 미리 올라간 옛 값"보다는 "캐시 hit"으로 수렴하므로 수용 가능한 수준입니다. 하지만 금액, 재고, 좌석 예약처럼 strict consistency가 필요한 도메인에서는 Cache-Aside 대신 DB 직접 조회와 트랜잭션으로 가야 합니다. "캐시 hit이어도 strict해야 한다"는 요구는 Cache-Aside로 풀 문제가 아닙니다.

### Cache Stampede

인기 key의 TTL이 만료되는 순간 동시에 들어온 요청들이 모두 miss를 보고 DB를 칩니다. 짧은 시간 동안 DB가 "동일 쿼리 N번"을 처리하게 됩니다. Cache-Aside의 구조(Read path: Miss)가 이 문제를 **자연히 만듭니다**. 미스 경로가 원자적이지 않기 때문입니다.

완화 전략(Mutex Lock, Single Flight, Probabilistic Early Expiration, Stale-While-Revalidate)과 각 전략의 트레이드오프는 별도 글에서 깊이 다룹니다. 본 글은 "왜 이 문제가 Cache-Aside에서 자연히 생기는가"만 짚습니다.

### Cache Penetration

DB에 없는 key, 예를 들어 존재하지 않는 상품 ID `-1`을 앱이 반복 조회할 때 문제가 생깁니다. 캐시는 계속 miss를 돌려주고 요청은 매번 DB로 갑니다. 악의적 공격자가 이 패턴으로 DB를 공격할 수도 있습니다.

완화는 두 가지입니다.

1. **Negative caching**: "없음" 자체를 짧은 TTL(10초에서 60초)로 캐시합니다. `cache.set("product:-1", NULL_SENTINEL, EX=30)`. 단점은 방금 생성된 데이터가 sentinel TTL 동안 안 보이는 것.
2. **Bloom filter**: 존재하는 key 집합을 Bloom filter로 앱 메모리에 두고, 조회 전에 "이 key가 DB에 있을 가능성"을 먼저 체크합니다. 새 key가 추가되면 filter를 갱신해야 하므로 운영 부담이 있습니다.

앞서 언급한 "nil과 empty의 구분"(Read path: Hit 섹션)의 실전 귀결입니다.

### Cache Avalanche

자정에 일괄 배치로 캐시를 채운 경우, 동일 TTL로 들어간 수천 개 key가 24시간 뒤 자정에 동시에 만료됩니다. 이 순간 모든 key가 miss가 되어 DB로 몰리며 부하 스파이크가 발생합니다. 스탬피드의 "전사적 버전"입니다.

완화는 간단합니다. TTL에 랜덤 jitter를 더합니다.

```kotlin
val baseTtl = 3600.seconds
val jitter = Random.nextInt(0, 600).seconds
cache.set(key, value, ttl = baseTtl + jitter)
```

만료 시점이 1시간 범위에 분산되어 스파이크가 평탄화됩니다. 간단하지만 효과적이고, 실전에서 가장 먼저 적용하는 방어입니다.

### 진실 불일치의 운영 부담

앞의 네 가지가 기술적 문제라면, 운영에서 더 자주 부딪히는 것은 **디버깅의 어려움**입니다. "캐시에 뭐가 들어있는지"와 "DB에 뭐가 있는지"가 서로 다를 수 있다는 가능성만으로 장애 원인 추적이 2배 이상 복잡해집니다.

"왜 사용자가 옛 이름을 보는가?"라는 질문 하나에도 답은 세 가지 이상입니다. 캐시 삭제 실패, 재캐싱 race, TTL 잔여. 프로덕션 이슈에서 `redis-cli GET <key>`와 `SELECT ... FROM ...`을 나란히 비교하는 루틴이 일상이 됩니다.

완화는 관찰가능성으로 합니다. cache hit/miss 비율, 재캐싱 빈도, 쓰기 경로 지연을 메트릭으로 노출합니다. 의심 상황에서 즉시 "캐시 무효화 후 재조회" 운영 도구를 만들어 두면 MTTR이 크게 줄어듭니다.

## 트레이드오프

Cache-Aside는 다섯 개의 "고전적 캐싱 패턴" 중 하나입니다. 나머지 넷을 함께 보면 Cache-Aside의 위치가 훨씬 선명해집니다. 각 패턴이 "**무엇을 앱 바깥으로 밀어내는가**"로 구분됩니다.

### 다섯 패턴의 축

| 패턴 | 읽기 주체 | 쓰기 주체 | 캐시↔DB 연결 |
|---|---|---|---|
| Cache-Aside | 앱 | 앱 | 없음 (앱이 중개) |
| Read-Through | 캐시 라이브러리 | 앱 | 읽기 경로 |
| Write-Through | 앱 | 캐시 라이브러리 (동기) | 쓰기 경로 |
| Write-Behind | 앱 | 캐시 라이브러리 (비동기) | 쓰기 경로 |
| Write-Around | 앱 | DB 직접 (캐시 우회) | 없음 |

- **Read-Through**: 앱은 캐시에게만 `get`을 요청하고, miss이면 캐시 라이브러리가 DB를 대신 조회해 채웁니다. Cache-Aside의 read path를 캐시 레이어로 옮긴 형태.
- **Write-Through**: 앱은 캐시에 `SET`만 하고, 캐시 라이브러리가 동기적으로 DB에도 씁니다. 쓰기 지연은 "캐시 + DB" 합산이지만 항상 캐시와 DB가 같습니다.
- **Write-Behind (Write-Back)**: 앱은 캐시에 쓰고, 캐시 라이브러리가 **비동기로** DB에 씁니다. 쓰기 지연은 캐시만 보이지만, 캐시 장애 시 DB 반영 안 된 데이터가 유실될 수 있습니다.
- **Write-Around**: 쓰기는 DB에만 하고 캐시는 건드리지 않습니다. 다음 읽기가 miss되어 새 값이 캐시에 올라옵니다. "한 번 쓰고 거의 안 읽는" 데이터(로그, 이벤트)에 적합.

### 상황별 선택 기준

| 상황 | 1순위 | 2순위 | 이유 |
|---|---|---|---|
| 일반 read-heavy 서비스 | Cache-Aside | Read-Through | 장애 격리, 유연한 key 설계 |
| 캐시-DB 일관성이 엄격 | Write-Through | Cache-Aside + Double Delete | 쓰기 성공이 곧 둘 다 성공 |
| 쓰기가 잦고 지연에 민감 | Write-Behind | Cache-Aside | 쓰기 지연을 캐시만 감당 |
| 한 번 쓰고 드물게 읽음 | Write-Around | Cache-Aside | 캐시 오염 방지 |
| 레거시에 캐시 추가 | Cache-Aside | Read-Through | 기존 코드 래핑만으로 도입 |

Cache-Aside의 "기본값" 지위는 이 표에서 나옵니다. 1순위 후보가 되는 상황이 가장 넓고, 그 외 상황에서도 2순위는 자주 됩니다. 반대로 Write-Through와 Write-Behind는 특정 조건에서만 유리합니다.

### Cache-Aside가 맞지 않을 때

세 가지입니다.

1. **Strict consistency가 필요한 도메인**: 금액, 재고, 좌석 예약. Cache-Aside의 eventual window가 비즈니스 규칙을 깹니다. 이 경우 캐시를 아예 두지 않거나, 둘 때도 "읽기 전용 스냅샷" 용도로 제한합니다.
2. **쓰기가 읽기보다 많은 워크로드**: Cache-Aside는 "쓰기 시 캐시 삭제"가 기본이라 쓰기가 많으면 캐시가 계속 비어 있고 read miss가 잦아져 캐시의 이점이 사라집니다. Write-Behind 또는 "캐시를 쓰지 않는 결정"이 나을 수 있습니다.
3. **캐시 라이브러리가 Read-Through / Write-Through를 네이티브 지원할 때**: Caffeine, EhCache 같은 로컬 캐시는 `CacheLoader`로 Read-Through를 자연히 구현합니다. 굳이 Cache-Aside로 래핑하지 않고 라이브러리 기본 모드를 쓰는 게 깔끔합니다.

### 하이브리드가 실전이다

<Callout type="success" title="실무 팁: 패턴을 섞어 쓰는 것이 정상">
  실전 시스템은 데이터 성격별로 다른 패턴을 씁니다. 같은 서비스 안에서 상품 정보(read-heavy)는 Cache-Aside, 장바구니(일관성 엄격)는 Write-Through, 액세스 로그(write-once)는 Write-Around가 공존합니다. "어느 패턴 하나를 선택한다"가 아니라 "데이터 성격별로 맞는 패턴을 고른다"가 실전입니다.
</Callout>

## 마무리

Cache-Aside는 "단순해 보이지만 단순하지 않은" 패턴의 전형입니다. 세 줄 레시피(조회·채움·무효화) 뒤에는 3자 상호작용의 race condition, 쓰기 순서의 미묘함, eventual consistency의 불가피성이 자리 잡고 있습니다. 이 구조를 이해하지 않은 채 "캐시를 썼는데 데이터가 안 맞는다"는 사고를 디버깅하면 원인이 보이지 않습니다.

이 글에서 가장 가져가야 할 것은 하나입니다. **Cache-Aside의 일관성은 TTL이 아니라 쓰기 순서가 만든다.** DB를 먼저 쓰고 캐시를 나중에 삭제하는 것, 갱신이 아니라 삭제를 택하는 것, 그리고 남은 race에는 TTL 축소나 double delete 같은 완화책을 얹는 것. 이 세 가지가 다른 캐싱 패턴과 구분되는 Cache-Aside의 운영 기술입니다.
