검색창에 "ap"를 치면 즉시 "apple, app, apricot"이 뜨는 동작을 HashMap으로는 구현할 수 없습니다. HashMap은 "정확 일치" 질의만 답할 수 있고, 접두어 질의는 전체 키를 스캔해야 하기 때문입니다. 트라이는 이 접두어 문제를 구조 자체로 해결하도록 1960년 Edward Fredkin이 설계한 자료구조입니다. 이 글에서는 노드 구조와 삽입/탐색의 내부 메커니즘, CS 제약 세 가지가 왜 이 구조를 강제했는지, 그리고 메모리 폭발을 완화하는 Compressed Trie, Radix Tree, Aho-Corasick 같은 진화의 방향을 살펴봅니다.

<Note title="이 글의 학습 목표">

  - 트라이의 노드 구조와 삽입/탐색 내부 동작 원리를 구분할 수 있다
  - 언제 트라이가 맞고 언제 틀린지, 메모리 폭발을 완화하는 변형을 선택하는 기준을 얻는다
</Note>

## 트라이란

트라이(Trie)는 **각 노드가 문자 하나를 담고, 루트에서 특정 노드까지의 경로가 하나의 문자열을 이루는** 트리 자료구조입니다. 이름은 "retrieval"의 중간 글자에서 따왔고(Edward Fredkin, 1960), **Prefix Tree** 또는 **Digital Tree** 라고도 불립니다. 원래 발음은 "tree"와 구별되는 "trai"였지만, 한국에서는 "트라이"로 굳어졌습니다.

구조적으로 각 노드는 다음 두 필드만 있으면 됩니다.

| 필드 | 설명 |
|---|---|
| `children` | 문자 → 자식 노드 맵 (또는 알파벳 크기의 배열) |
| `isEnd` | 이 노드에서 단어가 끝나는지 여부 |

예를 들어 빈 트라이에 `apple`을 삽입하면 `a → p → p → l → e` 경로의 5개 노드가 생성되고, 마지막 `e` 노드의 `isEnd = true`가 됩니다. 이어서 `app`을 삽입하면 앞의 `a → p → p` 경로는 재사용하고, 중간 `p` 노드의 `isEnd`만 true로 변경됩니다. 여기서 **리프가 아닌 노드도 단어의 끝이 될 수 있다**는 특성이 중요합니다. 이것이 일반 이진 탐색 트리와 가장 다른 점입니다.

## 왜 필요한가

"단어 집합을 저장하고 검색한다"는 문제는 얼핏 HashMap만 있으면 끝난 것처럼 보입니다. HashMap은 단어 존재 여부를 $O(L)$ 시간(L = 단어 길이)에 확인할 수 있습니다. 하지만 **HashMap은 '정확 일치'만 가능합니다**. "`ap`로 시작하는 모든 단어"를 찾는 접두어 질의는 HashMap으로 불가능해서 전체 키를 스캔($O(N \times L)$, N = 단어 개수)해야 합니다.

정렬된 배열 + 이진 탐색으로 접두어 구간을 찾는 방법도 있지만, 읽기 전용일 때만 유효합니다. 단어 삽입/삭제가 잦으면 $O(N)$ 이동 비용이 발생합니다.

<Callout type="warning" title="HashMap이 O(1)이니까 항상 빠르다?">
  그렇지 않습니다. 자료구조의 성능 비교는 **질의 형태를 고정한 상태에서만** 의미가 있습니다. 정확 일치 질의에서는 HashMap이 최고, 접두어/범위 질의에서는 트라이나 정렬 자료구조가 맞습니다. 질의 형태가 다르면 비교 자체가 무의미합니다.
</Callout>

트라이는 이 접두어 문제를 **구조 자체로** 해결합니다. `ap`로 시작하는 모든 단어를 찾는 질의는 루트에서 `a → p` 경로를 따라간 뒤, 그 서브트리의 모든 `isEnd` 노드를 수집하면 됩니다. **단어 개수 N과 무관하게 $O(L)$ 시간에 접두어 노드를 찾을 수 있습니다**. 여기서 자동완성(검색창 "ap" → "apple, app, apricot..."), IP 라우팅 테이블의 최장 접두어 매칭, 사전, 맞춤법 검사 같은 실전 시나리오가 나옵니다.

## 동작 원리

<Callout type="warning" title="이 구조를 이해하는 핵심">
  트라이는 세 가지 CS 제약이 동시에 걸릴 때 거의 반드시 도달하는 형태입니다: (1) 문자열이 문자 시퀀스라는 본질, (2) 공통 접두어를 공유해야 한다는 요구, (3) 문자당 $O(1)$ 분기 탐색이 필요하다는 요구. 이 제약을 이해하면 구조 전체가 자연스럽게 따라옵니다.
</Callout>

<Callout type="error" title="핵심 통찰: 트라이는 미학적 선택이 아니라 문자열의 본질이 강제한 형태다">
  문자열은 본질적으로 문자 시퀀스이며, 접두어를 공유하는 단어들은 자연스럽게 공통 경로를 가집니다. 이 두 특성과 "문자당 $O(1)$ 분기 탐색" 요구를 동시에 만족하려면 "문자 단위 분기 트리 + 단어 끝 표시"라는 구조에 거의 반드시 수렴합니다. 1960년 Fredkin의 원안과 2023년 CPU 캐시 최적화 구현이 뼈대를 공유하는 이유가 여기에 있습니다.
</Callout>

삽입, 탐색, 삭제의 기본 알고리즘을 TypeScript로 먼저 정리합니다.

```ts title="Trie.ts"
class TrieNode {
  children = new Map<string, TrieNode>()
  isEnd = false
}

class Trie {
  private root = new TrieNode()

  insert(word: string): void {
    let node = this.root
    for (const ch of word) {
      if (!node.children.has(ch)) {
        node.children.set(ch, new TrieNode()) // [!code highlight]
      }
      node = node.children.get(ch)!
    }
    node.isEnd = true // [!code highlight]
  }

  search(word: string): boolean {
    const node = this.traverse(word)
    return node !== null && node.isEnd // [!code highlight]
  }

  startsWith(prefix: string): boolean {
    return this.traverse(prefix) !== null // isEnd 체크 생략
  }

  private traverse(s: string): TrieNode | null {
    let node = this.root
    for (const ch of s) {
      const next = node.children.get(ch)
      if (!next) return null
      node = next
    }
    return node
  }
}
```

`insert`와 `search`의 구조적 차이는 한 줄입니다. 둘 다 문자 순회로 경로를 따라가지만, `search`는 마지막에 `isEnd`를 확인해 "단어"와 "접두어"를 구분합니다. `startsWith`는 `isEnd` 검사를 생략해 접두어 존재 여부만 반환합니다.

### 삭제의 까다로움

삭제는 세 가지 경우를 구분해야 합니다.

| 상황 | 처리 |
|---|---|
| 단어 끝 노드에 자식이 있음 | `isEnd = false`로만 변경, 노드는 보존 |
| 단어 끝 노드에 자식이 없음 | 역방향으로 노드 제거, 단 다른 단어가 쓰는 노드는 보존 |
| 단어가 존재하지 않음 | 아무 일도 하지 않음 |

두 번째 경우가 까다롭습니다. `{apple, app}`에서 `apple`만 삭제하면 `e`와 `l` 노드는 제거할 수 있지만, `a`, `p`, `p`는 `app`이 여전히 사용 중이라 보존해야 합니다. 아래 스냅샷으로 확인하세요.

### 왜 이 구조로 수렴했는가

트라이의 형태는 "자료구조 설계자의 미학적 선택"이 아니라 **세 가지 CS 요구의 논리적 결과**입니다.

1. **문자 시퀀스 본질**: 문자열은 본질적으로 문자 시퀀스입니다. 문자 단위로 분기하는 구조가 가장 자연스럽습니다.
2. **공통 접두어 공유**: 같은 접두어를 공유하는 단어들은 자연스럽게 공통 경로를 가져야 합니다. 포인터 기반 트리가 이 요구를 가장 단순하게 만족합니다.
3. **문자당 $O(1)$ 분기**: 자식 배열 인덱싱(알파벳이 고정 크기) 또는 해시맵으로 문자당 $O(1)$ 분기 탐색이 필요합니다.

이 세 요구를 동시에 만족하려면 "문자 단위 분기 트리 + 단어 끝 표시"에 거의 반드시 도달합니다. **1960년 Fredkin의 원안과 2023년 CPU 캐시 최적화 구현이 뼈대를 공유하는 이유가 여기에 있습니다**. 자료구조는 발견에 가깝고, 발명이 아닙니다.

## 어디서 마주치는가

트라이가 빛나는 상황은 크게 네 가지입니다.

### 1. 자동완성 / 검색 추천

사용자가 `ap`를 치면 `apple, app, apricot, apply`를 즉시 제안하는 UI입니다. 검색창, IDE 코드 자동완성, 전화번호부 검색이 모두 같은 형태입니다. 질의 복잡도는 $O(L + K)$ (L = 접두어 길이, K = 결과 개수)입니다.

### 2. IP 라우팅 테이블

라우터는 목적지 IP 주소를 받으면 자신의 라우팅 테이블에서 **가장 긴 접두어로 매칭되는 서브넷**을 찾습니다. 예를 들어 `192.168.1.42`에 대해 `192.168.0.0/16`과 `192.168.1.0/24` 두 항목이 모두 매칭된다면 더 구체적인 `/24`가 승리합니다. 이를 최장 접두어 매칭(Longest Prefix Match, LPM)이라고 부릅니다. HashMap으로는 정확 일치만 가능하므로 답할 수 없는 질의이며, Patricia Trie나 하드웨어 TCAM으로 구현됩니다.

### 3. 사전과 맞춤법 검사

단어 존재 여부 확인과 유사 단어 제안(edit distance 기반)이 필요할 때 트라이가 기반 구조로 쓰입니다. 사전에 100만 단어가 있어도 사용자 입력의 오타 후보를 $O(L \times 26^d)$ (d = edit distance) 수준에 찾을 수 있습니다.

### 4. 패턴 매칭 알고리즘

Aho-Corasick의 다중 패턴 매칭, Suffix Trie의 부분 문자열 검색이 모두 트라이를 확장한 구조입니다. 아래 트레이드오프 섹션에서 더 다룹니다.

반대로 **단순 정확 일치** (key-value lookup)라면 HashMap이 훨씬 빠르고 메모리 효율적입니다. "유저 ID로 유저 정보 찾기"에 트라이는 오버엔지니어링입니다. **키 분포가 sparse한 경우** (UUID, 해시값 등 공통 접두어가 거의 없는 키)도 나쁜 선택입니다. 경로 공유 이득이 사라지고 메모리만 낭비하기 때문입니다.

판단 기준은 한 줄로 정리됩니다: **접두어/범위 질의가 있는가, 그리고 키들이 공통 접두어를 충분히 공유하는가**.

## 트레이드오프

트라이의 가장 큰 비용은 **메모리**입니다. 각 노드는 자식 포인터 배열을 가지는데, 알파벳 크기 K가 26(영문 소문자)이면 노드 하나당 $26 \times 8 = 208$ 바이트가 필요합니다. 최악의 경우 N개 단어 × 평균 길이 L만큼의 노드가 생성되어 **총 메모리가 $O(K \times N \times L)$** 에 도달할 수 있습니다. 100만 단어, 평균 10자, 26 포인터, 8바이트를 곱하면 약 2GB(희박 케이스). 접두어 공유로 실제는 줄어들지만, HashMap 대비 여전히 큽니다. 더 큰 문제는 **유니코드 전체를 지원하면 K가 수만으로 늘어난다**는 점입니다.

이 메모리 문제 때문에 여러 최적화 변형이 등장했습니다.

### 1. 경로 압축 변형

분기 없는 연속 노드들을 하나의 간선으로 압축합니다. `c → a → r → s`처럼 자식이 하나뿐인 경로를 `"cars"` 간선 하나로 바꿉니다. 노드 수와 포인터 오버헤드가 크게 줄어듭니다. Compressed Trie, Radix Tree, Patricia Trie는 세부 구현 차이가 있지만 같은 아이디어 계열입니다.

| 사용처 | 설명 |
|---|---|
| 리눅스 커널 라우팅 테이블 | IPv4/IPv6 LPM에 Radix Tree 사용 |
| Redis Streams | 스트림 ID 인덱스가 Radix Tree 기반 |
| 인메모리 DB (HyPer, DuckDB) | ART(Adaptive Radix Tree)로 B+Tree 대체 |

### 2. DAWG

Directed Acyclic Word Graph의 약자로, 한 걸음 더 나아가 **공통 접미어**까지 공유합니다. 기본 트라이는 접두어만 공유하지만, DAWG는 공통 끝부분을 가진 단어들도 노드를 공유합니다. 편집 불가한 대신 극도의 압축이 가능해 **영어 사전 같은 고정 집합에 적합**합니다. 스크래블 게임 단어 사전이 대표 사용처입니다.

### 3. Double Array

자식 배열을 `(base, check)` 두 개의 정수 배열로 압축합니다. 노드 간 참조를 포인터가 아닌 배열 인덱스 산술로 표현해 캐시 친화적입니다. 일본어 형태소 분석기 **MeCab**이 대표 사용처입니다.

### 응용 알고리즘의 기반

트라이는 "저장 구조"를 넘어 다른 알고리즘의 기반 구조로도 쓰입니다.

**Aho-Corasick**은 트라이에 "failure link"를 추가해 여러 패턴을 텍스트에서 동시에 찾는 다중 패턴 매칭을 $O(N + M + Z)$ 시간에 해냅니다(N = 텍스트 길이, M = 패턴 전체 길이, Z = 매칭 개수). `grep -f`, 스팸 필터, IDS 서명 매칭이 대표 용례입니다.

**Suffix Trie**는 한 문자열의 모든 접미어를 트라이에 넣어 부분 문자열 검색을 $O(M)$으로 만듭니다. DNA 시퀀스 분석과 표절 탐지 같은 생물정보학, 자연어처리 영역에서 쓰입니다.

### 현대 CPU 관점의 약점

트라이는 **포인터 체이스**가 많아 캐시 미스율이 높습니다. 노드가 메모리상 흩어져 있기 때문에 트리를 내려갈 때마다 새로운 캐시 라인을 로드합니다. SIMD, 벡터화 최적화도 적용하기 어렵습니다. 그래서 B+Tree나 정렬 배열 같은 **캐시 친화적인 구조가 여전히 경쟁력을 가지는 영역이 남아 있습니다**. 디스크 기반 시스템(데이터베이스 인덱스)에서 B+Tree가 여전히 표준인 이유 중 하나입니다.

## 마무리

트라이는 "자동완성 잘 만들려면 쓰는 자료구조" 이상의 의미를 가집니다. **접두어 검색이라는 질의 형태 앞에서 HashMap은 구조적으로 작동할 수 없고, 정렬 배열은 쓰기에 비싸다는 제약**이 이 구조를 만들었습니다. 그리고 한 번 만들어진 구조는 1960년대부터 지금까지 IP 라우팅, 형태소 분석, 패턴 매칭 같은 전혀 다른 분야로 퍼져 나갔습니다. 자료구조를 읽을 때 가장 중요한 질문은 "어떻게 동작하는가"가 아니라 "어떤 제약이 이 형태를 강제했는가"입니다. 트라이는 그 질문에 가장 선명하게 답하는 사례 중 하나입니다.
