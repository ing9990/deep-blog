이 글에서는 동시 주문이 몰리는 서버에서 재고를 안전하게 차감하는 방법을 단계별로 비교합니다. 단일 스레드 통합 테스트는 통과하지만, 재고 100인 옵션에 200 스레드가 한꺼번에 주문하면 200건이 모두 성공으로 기록되고 재고가 56에서 멈춥니다. 락 없는 상태에서 출발해 `synchronized` + `TransactionTemplate`, 비관적 락, Redis 분산 락 + 원자 UPDATE까지 같은 200 스레드 시나리오로 성공 건수, 재고 부족 응답, 최종 재고가 어떻게 달라지는지 확인합니다.

- 상품의 재고는 초기 100개라고 가정합니다.
- 200명의 사용자가 같은 옵션에 동시에 주문하는 시나리오 테스트입니다.
- 정합성을 지키면 성공 100건, 재고 부족 100건, 최종 재고 0이 되어야 합니다.

## 요구사항과 제약

### 기능 요구

- 회원이 옵션 ID와 수량(=1)으로 단건 주문을 생성한다
- 재고는 옵션(SKU 단위)으로 관리되며 주문 성공 시 차감
- 재고 부족 시 `INSUFFICIENT_AMOUNT` 에러로 거절
- 동시성과 무관하게 정합성: `success_count ≤ initial_stock`, `final_stock ≥ 0`

## 1. 락 없음 (출발점)

### 개요

JVM 동기화도, DB 행 락도, 분산 락도 없습니다. 도메인 메서드 `OptionStock.decrease`가 자기 조건(요청 수량이 현재 quantity보다 큰가)만 검사하고 차감을 진행합니다. 단일 스레드에서는 잘 동작하지만, 동시에 들어온 트랜잭션이 같은 옵션 행을 보면 조회와 쓰기 사이의 race로 정합성이 깨지는 출발점입니다.

### 구현

```java title="OptionStock.java"
public void decrease(long delta) {
    validatePositiveDelta(delta, "차감");
    if (delta > this.quantity) {                                          // [!code highlight]
        throw new BusinessException(ErrorCode.INSUFFICIENT_STOCK,
            "재고가 부족합니다: 보유 " + this.quantity + ", 요청 " + delta);
    }
    this.quantity = this.quantity - delta;                                // [!code highlight]
}
```

```java title="OrderServiceNoLock.java"
@Transactional
public PlaceOrderResult placeOrder(Long accountId, PlaceOrderCommand command) {
    // member, option 조회 (생략)
    OptionStock stock = optionStockRepository.findByOptionId(command.optionId()) // [!code highlight]
        .orElseThrow(() -> new BusinessException(ErrorCode.STOCK_NOT_FOUND));
    stock.decrease(command.quantity());                                          // [!code highlight]
    // Order 조립 + INSERT (생략)
}
```

JPA dirty checking이 만드는 UPDATE는 `SET quantity = 99` 같은 계산된 값이지, `SET quantity = quantity - 1`의 DB-side 차감이 아니라는 점이 핵심입니다.

### 테스트 코드 및 결과

동시성 테스트는 세 단계 모두 같은 200 스레드 / 재고 100 시나리오를 사용합니다.

```java title="PlaceOrder<Stage>ConcurrencyTest.java"
@Test
@DisplayName("재고 100에 같은 SKU로 200 스레드가 동시 주문하면 100건만 성공해야 한다")
void place_200concurrent_sameSku_stock100_only100succeed() throws Exception {
    ExecutorService executor = Executors.newFixedThreadPool(THREADS);
    CountDownLatch barrier = new CountDownLatch(1);
    CountDownLatch done = new CountDownLatch(THREADS);
    AtomicInteger success = new AtomicInteger();
    AtomicInteger insufficient = new AtomicInteger();
    AtomicInteger other = new AtomicInteger();

    for (int i = 0; i < THREADS; i++) {
        executor.submit(() -> {
            try {
                barrier.await();
                orderService.placeOrder(prepared.memberAccountId(),
                    new PlaceOrderCommand(prepared.optionId(), 1L));
                success.incrementAndGet();
            } catch (BusinessException e) {                                  // [!code highlight]
                if (e.errorCode() == ErrorCode.INSUFFICIENT_AMOUNT) {        // [!code highlight]
                    insufficient.incrementAndGet();                          // [!code highlight]
                } else {
                    other.incrementAndGet();
                }
            } catch (Exception e) {
                other.incrementAndGet();
            } finally {
                done.countDown();
            }
        });
    }
    barrier.countDown();
    done.await(60, TimeUnit.SECONDS);
    // ... assert 결과: success / insufficient / 최종 재고
}
```

`BusinessException + ErrorCode.INSUFFICIENT_AMOUNT`만 재고 부족으로 카운트하고 그 외 예외는 `other`로 분리해, 의도하지 않은 거절(예: `OPTION_NOT_FOUND`)이 success 누락으로 위장되는 것을 막습니다.

![1단계 락 없음 200 스레드 측정 결과](/images/posts/mini-coupang-order-concurrency-locks/a-no-lock-200-thread-result.png)

| 항목 | 기대 | 실측 |
|---|---|---|
| `threads` | 200 | 200 |
| `initial stock` | 100 | 100 |
| `success` | 100 | **200** |
| `insufficient` | 100 | **0** |
| `other` | 0 | 0 |
| `final stock` | 0 | **56** |

읽기. 200 트랜잭션이 모두 `quantity=100` snapshot을 본 채 검사를 통과(insufficient=0)했습니다. 차감은 200번 시도되었으나 DB에 반영된 것은 `100 - 56 = 44회`, 56회분 차감이 lost update입니다. 주문 200건은 모두 INSERT되어 sum amount가 두 배로 부풀었습니다.

### 다음 단계: synchronized 도입

가장 직접적인 해법은 `synchronized`로 조회·검사·차감·커밋을 한 줄로 세우는 것입니다. 단일 인스턴스에서는 성공 100건, 재고 부족 100건, 최종 재고 0으로 정합성이 회복되지만, 잠금을 트랜잭션 커밋 안쪽에 둬야 한다는 함정이 새로 등장합니다.

## 2. synchronized + TransactionTemplate

### 개요

1단계에서 lost update가 일어난 이유는 조회와 차감 사이에 다른 트랜잭션이 같은 행의 오래된 값을 잡았기 때문입니다. JVM 안에서 가장 단순한 해법은 `synchronized`로 그 구간을 한 줄로 세우는 것입니다. `OrderService` 안에 `private final Object lock = new Object();`를 두고 `placeOrder`가 항상 그 모니터를 잡고 진입합니다.

함정이 하나 있습니다.

<Callout type="warning" title="@Transactional + synchronized 만으로는 부족하다">
  `@Transactional`만 두고 메서드 자체를 `synchronized`로 바꾸면 잠금이 트랜잭션 커밋보다 먼저 풀립니다. Spring AOP 프록시의 호출 순서는 `tx start → real method (synchronized 진입, 작업, 잠금 해제) → tx commit`이라, 락이 풀린 직후 다른 스레드가 진입하지만 첫 트랜잭션은 아직 커밋 전이라 다시 옛 stock 행을 봅니다. 1단계와 동일한 lost update가 그대로 재현됩니다.
</Callout>

이를 막으려면 잠금 안쪽에서 `TransactionTemplate`으로 트랜잭션을 직접 열고 닫아 잠금이 커밋까지 포함하도록 합니다.

### 구현

```java title="OrderServiceSynchronized.java"
@Service
public class OrderServiceSynchronized {

    private final TransactionTemplate transactionTemplate;
    private final Object lock = new Object();                                          // [!code highlight]

    public OrderServiceSynchronized(
        // ... 4 repositories ...
        PlatformTransactionManager transactionManager
    ) {
        // ...
        this.transactionTemplate = new TransactionTemplate(transactionManager);
    }

    public PlaceOrderResult placeOrder(Long accountId, PlaceOrderCommand command) {
        synchronized (lock) {                                                          // [!code highlight]
            return transactionTemplate.execute(status -> doPlaceOrder(accountId, command)); // [!code highlight]
        }
    }

    // doPlaceOrder: 1단계와 동일한 stock 조회 → decrease → 주문 INSERT
}
```

핵심은 두 가지.

1. **잠금 → 트랜잭션 → 커밋 → 잠금 해제** 순서가 `synchronized` 블록 안에 `transactionTemplate.execute(...)`를 두는 형태로 보장된다.
2. `lock`은 인스턴스 필드라 `OrderServiceSynchronized` 빈 단 하나가 모든 주문을 직렬화한다 (옵션과 무관하게).

### 테스트 코드 및 결과

### 다음 단계: 비관적 락

`synchronized`로 정합성은 회복했지만, 이 해결책은 단일 JVM 한정입니다. 두 가지 방향으로 깨집니다.

1. **Scale-Out으로 무력화.** WAS가 두 대 이상 떠 있으면 각 인스턴스가 자기 모니터만 가집니다. 두 JVM의 `OrderServiceSynchronized` 빈은 서로 다른 `lock` 객체를 쥐고 있어, 서로 다른 인스턴스로 라우팅된 두 주문이 같은 옵션 행에 동시에 차감을 시도하면 1단계의 lost update가 그대로 돌아옵니다. 핫딜 트래픽은 정확히 이런 부하를 만듭니다.
2. **`Map<Long, Object>` per-optionId 잠금도 같은 한계.** 개선 후보로 자주 꺼내지는 옵션 ID 단위 락 풀(`ConcurrentHashMap<Long, Object>`에서 옵션 ID별 모니터를 꺼내 잠그는 형태)은 단일 인스턴스 내부 처리량은 늘리지만 여전히 in-memory라 분산 환경에서는 동일하게 무력합니다. JVM monitor든, ReentrantLock per-key 풀이든, 잠금 객체가 한 프로세스 메모리에만 존재하는 한 결론은 같습니다.

다음 단계는 잠금을 JVM 메모리에서 MySQL 행 락으로 옮깁니다.

## 3. 비관적 락

### 개요

`SELECT ... FOR UPDATE`는 트랜잭션이 커밋/롤백될 때까지 해당 행에 대한 다른 모든 트랜잭션의 쓰기 락 획득을 막습니다. 인스턴스가 몇 개든 동일 행을 가리키는 트랜잭션을 직렬화합니다.

JPA에서는 `@Lock(LockModeType.PESSIMISTIC_WRITE)`와 JPQL 한 줄로 같은 효과를 얻습니다. 옵션 stock 행을 조회하는 시점에 락을 획득하고, `@Transactional` 경계에서 자동으로 풀립니다. 2단계의 `TransactionTemplate` 같은 명시적 트랜잭션 제어가 필요 없습니다 (락 자체가 DB 트랜잭션 라이프사이클에 묶여 있기 때문입니다).

### 구현

```java title="OptionStockRepository.java"
public interface OptionStockRepository extends JpaRepository<OptionStock, Long> {

    Optional<OptionStock> findByOptionId(Long optionId);

    @Lock(LockModeType.PESSIMISTIC_WRITE)                                       // [!code highlight]
    @Query("select s from OptionStock s where s.optionId = :optionId")          // [!code highlight]
    Optional<OptionStock> findByOptionIdForUpdate(@Param("optionId") Long optionId);
}
```

```java title="OrderService.java"
@Service
@RequiredArgsConstructor
public class OrderService {

    @Transactional
    public PlaceOrderResult placeOrder(Long accountId, PlaceOrderCommand command) {
        // member, option 조회 (생략)
        OptionStock stock = optionStockRepository.findByOptionIdForUpdate(command.optionId()) // [!code highlight]
            .orElseThrow(() -> new BusinessException(ErrorCode.STOCK_NOT_FOUND));
        stock.decrease(command.quantity());                                                    // [!code highlight]
        // Order 조립 + INSERT (생략)
    }
}
```

2단계와 비교한 두 가지 차이.

1. `synchronized (lock)` 블록과 `TransactionTemplate.execute(...)`가 사라졌다. `@Transactional` 한 줄로 잠금 라이프사이클이 트랜잭션 경계에 일치한다.
2. `findByOptionId` → `findByOptionIdForUpdate` 한 글자 차이. 발행되는 SQL 끝에 `for update`가 붙고 MySQL/H2(MySQL 모드)는 그 행에 X 락을 건다.

### 다음 단계: Redis 분산 락

비관적 락이 정합성을 회복한 대가는 세 가지 비용입니다.

| 비용 | 무엇이 묶이나 | 영향 |
|---|---|---|
| 락 보유 시간 = 트랜잭션 길이 | stock 차감 외에 Order INSERT, OrderItem INSERT까지 한 트랜잭션 | 다른 트랜잭션이 대기 큐에 쌓임 |
| DB connection 점유 | 락 보유 동안 connection 함께 점유 | 풀 사이즈(HikariCP 기본 10)와 충돌, 빠른 connection 고갈 |
| 핫 row 라인업 | 인기 옵션 1개에 트래픽 집중 | 처리량이 1행 × 1 connection × 1 트랜잭션 시간으로 묶임 |

세 번째 비용은 본질적으로 단일 DB 인스턴스 가정에서 비롯됩니다. 다음 단계는 잠금 주체를 DB 행 밖으로 옮길 수 있는지 시도합니다. Redis 분산 락(Redisson `RLock`)이 가장 흔한 후보지만, 2단계의 트랜잭션 경계 함정이 다시 따라오고, 결과적으로 정합성 책임이 어디에 남는지 다시 묻게 됩니다.

## 4. Redis 분산 락 + 원자 UPDATE

### 개요

비관적 락이 닫지 못한 마지막 가정은 단일 DB 인스턴스입니다. 읽기 전용 복제본 분리, 멀티 클러스터, 또는 단순히 DB 행 락 외에는 의지하지 않겠다는 정책 아래에서는 잠금을 DB 행보다 외부에 두고 싶어집니다. 자연스러운 후보가 Redis 같은 인메모리 KV 저장소이고, 가장 흔한 구현이 Redisson `RLock`입니다.

### 구현

OptionStockRepository에 원자 차감 메서드를 추가합니다.

```java title="OptionStockRepository.java"
public interface OptionStockRepository extends JpaRepository<OptionStock, Long> {

    Optional<OptionStock> findByOptionId(Long optionId);

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("select s from OptionStock s where s.optionId = :optionId")
    Optional<OptionStock> findByOptionIdForUpdate(@Param("optionId") Long optionId);

    @Modifying                                                                       // [!code highlight]
    @Query("update OptionStock s set s.quantity = s.quantity - :qty " +              // [!code highlight]
        "where s.optionId = :optionId and s.quantity >= :qty")                       // [!code highlight]
    int decreaseQuantityIfEnough(@Param("optionId") Long optionId,                   // [!code highlight]
                                 @Param("qty") long qty);                            // [!code highlight]
}
```

WHERE 절의 `quantity >= :qty`가 재고 부족 검사를 SET 절과 한 번에 수행합니다. 반환값 affected가 1이면 차감 성공, 0이면 재고 부족입니다.

```java title="OrderServiceDistributedLock.java"
@Transactional
public PlaceOrderResult placeOrder(Long accountId, PlaceOrderCommand command) {
    RLock lock = redissonClient.getLock("lock:option:" + command.optionId());        // [!code highlight]
    try {
        boolean acquired = lock.tryLock(3, TimeUnit.SECONDS);                        // [!code highlight]
        if (!acquired) {
            throw new BusinessException(ErrorCode.LOCK_ACQUIRE_FAILED);
        }
        return doPlaceOrder(accountId, command);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        throw new BusinessException(ErrorCode.LOCK_INTERRUPTED, e);
    } finally {
        lock.unlock();
    }
}

private PlaceOrderResult doPlaceOrder(Long accountId, PlaceOrderCommand command) {
    // member, option 조회 (생략)
    int updated = optionStockRepository.decreaseQuantityIfEnough(                    // [!code highlight]
        command.optionId(), command.quantity());                                     // [!code highlight]
    if (updated == 0) {                                                              // [!code highlight]
        throw new BusinessException(ErrorCode.INSUFFICIENT_AMOUNT);                  // [!code highlight]
    }
    // Order 조립 + INSERT (생략)
}
```

3단계 대비 두 가지 차이.

1. `findByOptionIdForUpdate(...).orElseThrow().decrease(...)` 3 단계가 `decreaseQuantityIfEnough` 한 줄로 압축됐다. 조회·검사·차감이 한 SQL UPDATE에 들어간다.
2. `@Transactional` 메서드 안에서 Redis 락을 잡지만, 정합성은 락이 풀려도 깨지지 않는다. 행 X 락이 커밋까지 유지되기 때문이다.

`tryLock(3, TimeUnit.SECONDS)` 시그니처는 leaseTime을 명시하지 않습니다. 그러면 Redisson의 watchdog 모드가 활성화돼 락 보유 동안 약 10초 주기로 만료를 자동 연장합니다 (default lock watchdog timeout 30초). 트랜잭션이 길어져도 만료 race가 발생하지 않고, 클라이언트가 죽으면 watchdog도 멈춰 default timeout 후 자동 해제됩니다 (deadlock 방지).

### 테스트 코드 및 결과

3단계와 다른 점은 Redis가 필요하다는 것입니다. Testcontainers로 테스트 컨텍스트마다 Redis를 띄웁니다.

```java title="PlaceOrderDistributedLockConcurrencyTest.java"
@SpringBootTest
@ActiveProfiles("test")
@Testcontainers
@Import(PlaceOrderDistributedLockConcurrencyTest.DistributedLockTestConfig.class)
class PlaceOrderDistributedLockConcurrencyTest {

    @Container
    static final GenericContainer<?> redis = new GenericContainer<>("redis:7.4-alpine")
        .withExposedPorts(6379);

    @TestConfiguration
    static class DistributedLockTestConfig {

        @Bean(destroyMethod = "shutdown")
        RedissonClient redissonClient() {
            Config config = new Config();
            config.useSingleServer()
                .setAddress("redis://" + redis.getHost() + ":" + redis.getMappedPort(6379));
            return Redisson.create(config);
        }

        @Bean                                                                        // [!code highlight]
        OrderServiceDistributedLock orderServiceDistributedLock(/* repos + redissonClient */) {
            return new OrderServiceDistributedLock(/* ... */);
        }
    }

    @Autowired private OrderServiceDistributedLock orderService;                     // [!code highlight]
    // ... @Autowired repositories + 200 thread 시나리오 (3단계와 동일) ...
}
```

`@TestConfiguration`에서 `OrderServiceDistributedLock`을 빈으로 등록하는 부분이 핵심입니다. `@Transactional`이 적용되려면 Spring AOP 프록시를 거쳐야 하는데, `new`로 직접 인스턴스화하면 프록시가 없어 `@Modifying` 쿼리가 트랜잭션 없이 실행되고 실패합니다. 운영 코드에 `@Service`를 붙여 전역 빈으로 등록하는 대신, 테스트 컨텍스트 안에서만 빈을 만들어 다른 테스트에 영향을 주지 않습니다.

### 발견된 한계: 정합성 책임의 위치

4단계의 코드는 분산 락처럼 보이지만, 정합성 보증의 책임은 여전히 DB에 있습니다. Redis 락을 빼도 `@Modifying` UPDATE 한 줄이 행 X 락으로 직렬화를 강제하므로 lost update가 발생하지 않습니다. 즉, 4단계의 Redis 락은 정합성 보증이 아니라 DB 진입을 줄이는 코디네이션 도구입니다.

진정한 의미로 잠금을 DB 밖으로 빼는 길은 다음 두 후보입니다.

| 다음 후보 | 무엇을 옮기나 | 새 한계 |
|---|---|---|
| 재고 자체를 Redis로 이동 | quantity를 Redis 키 값으로 보관, DB는 정산 후 동기화 | DB와 Redis 사이 동기화 윈도, 영속성 보장 |
| Lua atomic decrement | 조회·검사·차감을 EVAL 한 호출에 묶어 락 자체 제거 | 스크립트 디버깅 난도, fence token 부재, Redis 단일 실패 지점 |

이 두 후보는 별도 글에서 다룹니다. 이 글은 잠금 위치 시리즈의 마지막 단계로 4단계까지를 닫습니다.

## 결론

4 단계 누적 표.

| 단계 | 잠금 주체 | success | insufficient | final stock | 적용 조건 |
|---|---|---|---|---|---|
| 1단계 락 없음 | 없음 | 200 | 0 | 56 | 단일 스레드만 |
| 2단계 synchronized + TxTemplate | JVM 모니터 | 100 | 100 | 0 | 단일 JVM |
| 3단계 비관적 락 | DB 행 락 | 100 | 100 | 0 | 단일 DB 인스턴스 |
| 4단계 Redis 분산 락 + 원자 UPDATE | DB 행 락 (코디네이션은 Redis) | 100 | 100 | 0 | 정합성은 단일 DB, 코디네이션은 분산 |

<Callout type="error" title="핵심 통찰: 잠금은 없앨 수 없고 어디에 둘지를 정할 뿐이다">
  잠금 위치를 도메인 메서드 안(1단계) → JVM 모니터(2단계) → DB 행(3단계) → Redis + DB 행(4단계)으로 옮긴 것이 이 글의 전부입니다. 4단계에서 가장 흥미로운 발견은 락을 외부로 빼려고 시도했더니 정합성 책임이 다시 DB로 돌아왔다는 점입니다. 어느 곳에 두느냐가 처리량, 분산 가능성, 운영 비용을 결정합니다.
</Callout>

남은 한계와 다음 단계.

| 한계 | 무엇을 줄이나 | 트레이드오프 |
|---|---|---|
| 정합성이 여전히 DB 행 락에 묶임 | 재고 자체를 Redis로 이동, DB는 정산 후 동기화 | DB와 Redis 동기화 윈도, 영속성 보장 |
| 핫 row 직렬화 | Lua atomic decrement로 조회·검사·차감을 Redis 안에서 압축 | 스크립트 디버깅 난도, fence token 부재 |
| 분산 락의 운영 한계 | fence token, 클럭 스큐 대응, 단일 실패 지점 분리 | 인프라 복잡도, 합의 알고리즘 비용 |

이 세 한계는 별도 글에서 다룹니다. 잠금을 in-memory KV로 진짜로 옮기는 길과, 잠금 자체를 없애려는 길입니다.
