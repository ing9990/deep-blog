단건 주문 API가 단일 스레드 통합 테스트는 통과합니다. 재고 100인 옵션에 200 스레드가 동시에 주문을 던지자, 200건이 모두 성공으로 기록됐고 재고는 56에서 멈췄습니다. 이 글은 `OptionStock.decrease`를 어디서 어떻게 보호할 것인가를 세 가지 구조 (락 없음, `synchronized` + `TransactionTemplate`, 비관적 락) 로 단계별 구현하고 같은 200-thread 테스트로 success / insufficient / finalStock 분포 변화를 닫습니다.

## 요구사항과 제약

### 기능 요구

- 회원이 옵션 ID와 수량(=1)으로 단건 주문을 생성한다
- 재고는 옵션(SKU 단위)으로 관리되며 주문 성공 시 차감
- 재고 부족 시 `INSUFFICIENT_AMOUNT` 에러로 거절
- 동시성과 무관하게 정합성: `success_count ≤ initial_stock`, `final_stock ≥ 0`

### 평시 SLO

| 메트릭 | 목표 | 출처 |
|---|---|---|
| 단건 주문 p95 | 150ms 이하 | 가설 |
| 재고 정합성 위반 | 0건 (lost update 0) | 도메인 invariant |
| 옵션당 평시 처리량 | 50 RPS | 가설 |

### 트래픽 시나리오

| 윈도 | 옵션당 RPS | 배수 | 비고 |
|---|---|---|---|
| 평시 | 50 | 1× | baseline |
| 인기 상품 | 300 | 6× | 광고 노출 직후 |
| 한정 수량 핫딜 | 1000–3000 | 20–60× | 초 단위 spike, 재고 빠르게 0 도달 |

테스트가 모사하는 것은 한정 핫딜의 극단(200 thread × stock 100)입니다. 본 글의 정합성 목표는 SLO 완화가 아니라 무손실 invariant입니다.

번호 결정.

1. 재고를 도메인 엔티티 상태로 (`OptionStock.quantity`) 보관. 결제·주문이 같은 행을 공격하므로 invariant는 도메인이 책임진다.
2. `@Transactional` 단일 트랜잭션 안에서 SELECT, 검사, 차감, INSERT order/items를 한 번에.
3. 락 없이 시작. 측정 전에 락을 깔면 어떤 락이 어떤 효과를 내는지 비교 base가 사라진다.

임계 영역은 위 도해의 빨간 노드(`OptionStockRepository` → `option_stocks` 행)입니다. 이 글은 그 임계 영역을 어디에 두느냐를 세 단계로 옮기는 이야기입니다.

## A. 락 없음 (baseline)

### 개요

JVM 동기화도, DB 행 락도, 분산 락도 없습니다. 도메인 메서드 `OptionStock.decrease`가 자기 invariant(요청 수량이 현재 quantity보다 큰가)만 검사하고 차감을 진행합니다. 단일 스레드 시나리오에서는 정상 작동하지만, 동시 트랜잭션이 같은 옵션 행을 공격할 때 read-modify-write race가 정합성을 깨뜨리는 시작 지점입니다.

### 구현

```java title="OptionStock.java"
public void decrease(long delta) {
    validatePositiveDelta(delta, "차감");
    if (delta > this.quantity) {                                          // [!code highlight]
        throw new BusinessException(ErrorCode.INSUFFICIENT_STOCK,
            "재고가 부족합니다: 보유 " + this.quantity + ", 요청 " + delta);
    }
    this.quantity = this.quantity - delta;                                // [!code highlight]
}
```

```java title="OrderServiceNoLock.java"
@Transactional
public PlaceOrderResult placeOrder(Long accountId, PlaceOrderCommand command) {
    // member, option 조회 (생략)
    OptionStock stock = optionStockRepository.findByOptionId(command.optionId()) // [!code highlight]
        .orElseThrow(() -> new BusinessException(ErrorCode.STOCK_NOT_FOUND));
    stock.decrease(command.quantity());                                          // [!code highlight]
    // Order 조립 + INSERT (생략)
}
```

JPA dirty checking이 만드는 UPDATE는 `SET quantity = 99` 같은 계산된 값이지, `SET quantity = quantity - 1`의 DB-side 차감이 아니라는 점이 핵심입니다.

### 테스트 코드 및 결과

동시성 테스트는 §A · §B · §C 모두 같은 200 thread / stock 100 시나리오를 사용합니다.

```java title="PlaceOrder<Stage>ConcurrencyTest.java"
@Test
@DisplayName("재고 100에 같은 SKU로 200 스레드가 동시 주문하면 100건만 성공해야 한다")
void place_200concurrent_sameSku_stock100_only100succeed() throws Exception {
    ExecutorService executor = Executors.newFixedThreadPool(THREADS);
    CountDownLatch barrier = new CountDownLatch(1);
    CountDownLatch done = new CountDownLatch(THREADS);
    AtomicInteger success = new AtomicInteger();
    AtomicInteger insufficient = new AtomicInteger();
    AtomicInteger other = new AtomicInteger();

    for (int i = 0; i < THREADS; i++) {
        executor.submit(() -> {
            try {
                barrier.await();
                orderService.placeOrder(prepared.memberAccountId(),
                    new PlaceOrderCommand(prepared.optionId(), 1L));
                success.incrementAndGet();
            } catch (BusinessException e) {                                  // [!code highlight]
                if (e.errorCode() == ErrorCode.INSUFFICIENT_AMOUNT) {        // [!code highlight]
                    insufficient.incrementAndGet();                          // [!code highlight]
                } else {
                    other.incrementAndGet();
                }
            } catch (Exception e) {
                other.incrementAndGet();
            } finally {
                done.countDown();
            }
        });
    }
    barrier.countDown();
    done.await(60, TimeUnit.SECONDS);
    // ... assert success/insufficient/finalStock
}
```

`BusinessException + ErrorCode.INSUFFICIENT_AMOUNT`만 재고 부족으로 카운트하고 그 외 예외는 `other`로 분리해, 의도하지 않은 거절(예: `OPTION_NOT_FOUND`)이 success 누락으로 위장되는 것을 막습니다.

|---|---|---|
| `threads` | 200 | 200 |
| `initial stock` | 100 | 100 |

읽기. 200 트랜잭션이 모두 `quantity=100` snapshot을 본 채 검사를 통과(insufficient=0)했습니다. 차감은 200번 시도되었으나 DB에 반영된 것은 `100 - 56 = 44회`, 56회분 차감이 lost update입니다. 주문 200건은 모두 INSERT되어 sum amount가 두 배로 부풀었습니다.

### 다음 단계 (B 소개)

가장 직설적인 해법은 `synchronized`로 read, 검사, 차감, 커밋의 윈도를 직렬화하는 것입니다. 단일 인스턴스에서는 `success=100/insufficient=100/finalStock=0`으로 정합성이 회복되지만, 잠금이 트랜잭션 커밋 안쪽이어야 한다는 함정이 등장합니다.

## B. synchronized + TransactionTemplate

### 개요

§A의 lost update는 read와 차감 사이에 다른 트랜잭션이 같은 행의 stale snapshot을 잡았기 때문입니다. JVM 안에서 가장 단순한 해법은 `synchronized`로 그 윈도를 직렬화하는 것. `OrderService` 안에 `private final Object lock = new Object();`를 두고 `placeOrder`가 항상 그 모니터를 잡고 진입합니다.

함정이 하나 있습니다.

<Callout type="warning" title="@Transactional + synchronized 만으로는 부족하다">
  `@Transactional`만 두고 메서드 자체를 `synchronized`로 바꾸면 잠금이 트랜잭션 커밋보다 먼저 풀립니다. Spring AOP 프록시의 호출 순서는 `tx start → real method (synchronized 진입, 작업, 잠금 해제) → tx commit`이라, 락이 풀린 직후 다른 스레드가 진입하지만 첫 트랜잭션은 아직 커밋 전이라 또다시 stale한 stock 행을 봅니다. §A와 동일한 lost update가 그대로 재현됩니다.
</Callout>

이를 막으려면 잠금 안쪽에서 `TransactionTemplate`으로 트랜잭션을 직접 열고 닫아 잠금이 커밋까지 포함하도록 합니다.

### 구현

```java title="OrderServiceSynchronized.java"
@Service
public class OrderServiceSynchronized {

    private final TransactionTemplate transactionTemplate;
    private final Object lock = new Object();                                          // [!code highlight]

    public OrderServiceSynchronized(
        // ... 4 repositories ...
        PlatformTransactionManager transactionManager
    ) {
        // ...
        this.transactionTemplate = new TransactionTemplate(transactionManager);
    }

    public PlaceOrderResult placeOrder(Long accountId, PlaceOrderCommand command) {
        synchronized (lock) {                                                          // [!code highlight]
            return transactionTemplate.execute(status -> doPlaceOrder(accountId, command)); // [!code highlight]
        }
    }

    // doPlaceOrder: §A 와 동일한 stock 조회 → decrease → 주문 INSERT
}
```

핵심은 두 가지.

1. **잠금 → 트랜잭션 → 커밋 → 잠금 해제** 순서가 `synchronized` 블록 안에 `transactionTemplate.execute(...)`를 두는 형태로 보장된다.
2. `lock`은 인스턴스 필드라 `OrderServiceSynchronized` 빈 단 하나가 모든 주문을 직렬화한다 (옵션과 무관하게).

### 다음 단계 (C 소개)

`synchronized`로 정합성은 회복했지만, 이 해결책은 단일 JVM 한정입니다. 두 가지 방향으로 깨집니다.

1. **Scale-Out으로 무력화.** WAS가 두 대 이상 떠 있으면 각 인스턴스가 자기 모니터만 가집니다. 두 JVM의 `OrderServiceSynchronized` 빈은 서로 다른 `lock` 객체를 쥐고 있어, 서로 다른 인스턴스로 라우팅된 두 주문이 같은 옵션 행에 동시에 차감을 시도하면 §A의 lost update가 그대로 돌아옵니다. 핫딜 트래픽은 정확히 이런 부하를 만듭니다.
2. **`Map<Long, Object>` per-optionId 잠금도 같은 한계.** 개선 후보로 자주 꺼내지는 옵션 ID 단위 락 풀(`ConcurrentHashMap<Long, Object>`에서 옵션 ID별 모니터를 꺼내 잠그는 형태)은 단일 인스턴스 내부 처리량은 늘리지만 여전히 in-memory라 분산 환경에서는 동일하게 무력합니다. JVM monitor든, ReentrantLock per-key 풀이든, 잠금 객체가 한 프로세스 메모리에만 존재하는 한 결론은 같습니다.

다음 단계 §C는 잠금 주체를 JVM 메모리에서 MySQL 행 락으로 옮깁니다.

## C. 비관적 락

### 개요

`SELECT ... FOR UPDATE`는 트랜잭션이 커밋/롤백될 때까지 해당 행에 대한 다른 모든 트랜잭션의 쓰기 락 획득을 막습니다. 인스턴스가 몇 개든 동일 행을 가리키는 트랜잭션을 직렬화합니다.

JPA에서는 `@Lock(LockModeType.PESSIMISTIC_WRITE)`와 JPQL 한 줄로 같은 효과를 얻습니다. 옵션 stock 행의 read 시점에 락을 획득하고, `@Transactional` 경계에서 자동으로 해제됩니다. §B의 `TransactionTemplate` 같은 명시적 트랜잭션 제어가 필요 없습니다 (락 자체가 DB 트랜잭션 라이프사이클에 묶여 있기 때문).

### 구현

```java title="OptionStockRepository.java"
public interface OptionStockRepository extends JpaRepository<OptionStock, Long> {

    Optional<OptionStock> findByOptionId(Long optionId);

    @Lock(LockModeType.PESSIMISTIC_WRITE)                                       // [!code highlight]
    @Query("select s from OptionStock s where s.optionId = :optionId")          // [!code highlight]
    Optional<OptionStock> findByOptionIdForUpdate(@Param("optionId") Long optionId);
}
```

```java title="OrderService.java"
@Service
@RequiredArgsConstructor
public class OrderService {

    @Transactional
    public PlaceOrderResult placeOrder(Long accountId, PlaceOrderCommand command) {
        // member, option 조회 (생략)
        OptionStock stock = optionStockRepository.findByOptionIdForUpdate(command.optionId()) // [!code highlight]
            .orElseThrow(() -> new BusinessException(ErrorCode.STOCK_NOT_FOUND));
        stock.decrease(command.quantity());                                                    // [!code highlight]
        // Order 조립 + INSERT (생략)
    }
}
```

§B와 비교한 두 가지 차이.

1. `synchronized (lock)` 블록과 `TransactionTemplate.execute(...)`가 사라졌다. `@Transactional` 한 줄로 잠금 라이프사이클이 트랜잭션 경계에 일치한다.
2. `findByOptionId` → `findByOptionIdForUpdate` 한 글자 차이. 발행되는 SQL 끝에 `for update`가 붙고 MySQL/H2(MySQL 모드)는 그 행에 X 락을 건다.

### 발견된 한계 (D 소개)

비관적 락이 정합성을 해결한 대가는 세 가지 비용으로 돌아옵니다.

| 비용 | 무엇이 묶이나 | 영향 |
|---|---|---|
| 락 보유 시간 = 트랜잭션 길이 | stock 차감 외에 Order INSERT, OrderItem INSERT까지 한 트랜잭션 | 다른 트랜잭션이 대기 큐에 쌓임 |
| DB connection 점유 | 락 보유 동안 connection 함께 점유 | 풀 사이즈(HikariCP 기본 10)와 충돌, 빠른 connection 고갈 |
| 핫 row 라인업 | 인기 옵션 1개에 트래픽 집중 | 처리량이 1행 × 1 connection × 1 트랜잭션 시간으로 묶임 |

다음 글에서 다룰 후보는 Redis 기반 분산 락과 Lua atomic decrement입니다. 잠금 주체를 DB에서 in-memory 키-값 저장소로 옮기면 락 보유 시간이 sub-millisecond 단위로 줄고, Lua 스크립트로 read-check-decrement를 atomic 한 번으로 묶어 락 자체를 생략하는 길도 열립니다. 그 대신 새로운 한계(Redis 단일 실패 지점, fence token, 클럭 스큐, 키 만료 race)가 따라옵니다.

## 결론

3 단계 누적 표.

| 단계 | 잠금 주체 | success | insufficient | final stock | 적용 조건 |
|---|---|---|---|---|---|
| §A no-lock | 없음 | 200 | 0 | 56 | 단일 스레드만 |
| §B synchronized + TxTemplate | JVM 모니터 | 100 | 100 | 0 | 단일 JVM |
| §C 비관적 락 | DB 행 락 | 100 | 100 | 0 | 단일 DB 인스턴스 |

<Callout type="error" title="핵심 통찰: 잠금은 없앨 수 없고 어디에 둘지를 정할 뿐이다">
  임계 영역을 도메인 메서드 안(§A) → JVM 모니터(§B) → DB 행(§C)으로 옮긴 것이 본 글의 전부입니다. 어느 곳에 두느냐가 처리량, 분산 가능성, 운영 비용을 결정합니다.
</Callout>

남은 한계와 다음 단계.

| 한계 | 무엇을 줄이나 | 트레이드오프 |
|---|---|---|
| 락 보유 시간이 트랜잭션 길이에 비례 | 트랜잭션 안에서 락 외 작업(Order INSERT)을 분리 | 트랜잭션 경계 재설계 비용 |
| DB connection 점유 | 잠금 주체를 Redis로 이동 | Redis 단일 실패 지점, 클럭 스큐 |
| 핫 row 직렬화 | Lua atomic decrement로 read-check-write 압축 | 스크립트 디버깅 난도, fence token 부재 |

이 세 한계는 다음 글에서 Redis 분산 락과 Lua atomic decrement로 닫습니다. 잠금을 in-memory KV로 한 번 더 옮기는 길입니다.
