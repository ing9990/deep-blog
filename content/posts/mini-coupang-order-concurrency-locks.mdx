이 글에서는 동시 주문이 몰릴 때 <E>모놀리스 서버에서 재고를 안전하게 차감하는 방법</E>을 단계별로 비교합니다. 한정된 재고 100개를 동시 주문자 200명(Thread)가 동시에 주문하는 테스트 코드를 기반으로, 도메인 메서드만 두는 출발점부터 JVM 안에서 옵션 SKU 단위로 직렬화하는 `synchronized`, DB 행 락으로 직렬화 범위를 확장하는 비관적 락까지 따라갑니다.

- 상품의 재고는 초기 100개라고 가정합니다.
- 200명의 사용자가 같은 옵션에 동시에 주문하는 시나리오 테스트입니다.
- 정합성을 지키면 성공 100건, 재고 부족 100건, 최종 재고 0이 되어야 합니다.

## 요구사항과 제약

### 기능 요구

- 회원이 옵션 ID와 수량(=1)으로 단건 주문을 생성한다
- 재고는 옵션(SKU 단위)으로 관리되며 주문 성공 시 차감
- 재고 부족 시 `INSUFFICIENT_AMOUNT` 에러로 거절
- 동시성과 무관하게 정합성: 주문 성공 수가 초기 재고를 넘지 않고, 남은 재고가 음수가 되지 않는다

## 1. 락 없음 (출발점)

### 개요

JVM 동기화도, DB 행 락도, 분산 락도 없습니다. 도메인 메서드 `OptionStock.decrease`가 자기 조건(요청 수량이 현재 quantity보다 큰가)만 검사하고 차감을 진행합니다. 단일 스레드에서는 잘 동작하지만, 동시에 들어온 트랜잭션이 같은 옵션 행을 보면 조회와 쓰기 사이의 race로 정합성이 깨지는 출발점입니다.

### 구현

```java title="OptionStock.java"
public void decrease(long delta) {
    validatePositiveDelta(delta, "차감");
    if (delta > this.quantity) {                                          // [!code highlight]
        throw new BusinessException(ErrorCode.INSUFFICIENT_STOCK,
            "재고가 부족합니다: 보유 " + this.quantity + ", 요청 " + delta);
    }
    this.quantity = this.quantity - delta;                                // [!code highlight]
}
```

```java title="OrderServiceNoLock.java"
@Transactional
public PlaceOrderResult placeOrder(Long accountId, PlaceOrderCommand command) {
    // member, option 조회 (생략)
    OptionStock stock = optionStockRepository.findByOptionId(command.optionId()) // [!code highlight]
        .orElseThrow(() -> new BusinessException(ErrorCode.STOCK_NOT_FOUND));
    stock.decrease(command.quantity());                                          // [!code highlight]
    // Order 조립 + INSERT (생략)

```

JPA dirty checking이 만드는 `UPDATE`는 `SET quantity = 99` 같은 계산된 값이지, `SET quantity = quantity - 1`의 DB-side 차감이 아니라는 점이 핵심입니다.

### 테스트 코드 및 결과

동시성 테스트는 세 단계 모두 같은 200 스레드 / 재고 100 시나리오를 사용합니다.

```java title="PlaceOrder<Stage>ConcurrencyTest.java"

@DisplayName("재고 100에 같은 SKU로 200 스레드가 동시 주문하면 100건만 성공해야 한다")
void place_200concurrent_sameSku_stock100_only100succeed() throws Exception {
    ExecutorService executor = Executors.newFixedThreadPool(THREADS);
    CountDownLatch barrier = new CountDownLatch(1);
    CountDownLatch done = new CountDownLatch(THREADS);
    AtomicInteger success = new AtomicInteger();
    AtomicInteger insufficient = new AtomicInteger();
    AtomicInteger other = new AtomicInteger();

    for (int i = 0; i < THREADS; i++) {
        executor.submit(() -> {
            try {
                barrier.await();
                orderService.placeOrder(prepared.memberAccountId(),
                    new PlaceOrderCommand(prepared.optionId(), 1L));
                success.incrementAndGet();
            } catch (BusinessException e) {                                  // [!code highlight]
                if (e.errorCode() == ErrorCode.INSUFFICIENT_AMOUNT) {        // [!code highlight]
                    insufficient.incrementAndGet();                          // [!code highlight]
                } else {
                    other.incrementAndGet();
                }
            } catch (Exception e) {
                other.incrementAndGet();
            } finally {
                done.countDown();
            }
        });
    }
    barrier.countDown();
    done.await(60, TimeUnit.SECONDS);
    // ... assert 결과: success / insufficient / 최종 재고
}
```

`BusinessException + ErrorCode.INSUFFICIENT_AMOUNT`만 재고 부족 거절로 카운트하고 그 외 예외는 `other` 버킷으로 분리해, 의도하지 않은 거절(예: `OPTION_NOT_FOUND`)이 주문 성공 누락으로 위장되는 것을 막습니다.

### 한계

단일 스레드 환경에서는 정합성이 유지되지만, 200 트랜잭션이 거의 동시에 진입하면 모두 같은 `quantity = 100`을 본 뒤 각자 차감을 시도해 56건이 lost update로 사라집니다. 도메인 메서드 안에는 조회와 쓰기 사이에 다른 스레드의 쓰기가 끼어드는 것을 막을 수단이 없기 때문입니다.

이 문제는 조회·검사·차감을 한 임계 영역으로 묶는 `synchronized`로 해결할 수 있습니다.

## 2. `synchronized`

### 개요

1단계에서 lost update가 일어난 이유는 조회와 차감 사이에 다른 스레드가 같은 행의 오래된 값을 잡았기 때문입니다. JVM 안에서 가장 단순한 해법은 옵션 SKU 단위로 락을 잡고, 그 안에서 조회·검사·차감·커밋까지 한 큐에 처리하는 것입니다. `ConcurrentHashMap<Long, ReentrantLock>`에 옵션 ID를 키로 락을 보관해 서로 다른 옵션은 병렬로 처리되고, 같은 옵션의 동시 주문만 하나씩 직렬화됩니다. 락 해제는 자기 자신이 잡은 락만 `finally`에서 푸는 try-finally 패턴으로 묶어 `IllegalMonitorStateException` 미스매치를 차단합니다.

<Diagram caption="2단계 아키텍처: 옵션 SKU 별로 ReentrantLock 풀을 두어 같은 옵션만 직렬화. 같은 옵션의 동시 주문은 락 큐에서 차례대로 처리된다">{`flowchart LR

        OS["doPlaceOrder()<br/>SELECT → 검사 → UPDATE"]
    end
    DB[("MySQL: option_stocks 행")]
    Out["성공 100 / 거절 100<br/>최종 quantity 0"]

    Client --> Map

### 구현

```java title="OrderServiceSynchronized.java"
@Service
public class OrderServiceSynchronized {

    private final ConcurrentMap<Long, ReentrantLock> locks = new ConcurrentHashMap<>(); // [!code highlight]
    // 4 repositories

    @Transactional
    public PlaceOrderResult placeOrder(Long accountId, PlaceOrderCommand command) {
        ReentrantLock lock = locks.computeIfAbsent(                                     // [!code highlight]
            command.optionId(), key -> new ReentrantLock());                            // [!code highlight]
        lock.lock();                                                                    // [!code highlight]
        try {
            return doPlaceOrder(accountId, command);
        } finally {
            lock.unlock();                                                              // [!code highlight]
        }
    }

    // doPlaceOrder: 1단계와 동일한 stock 조회 → decrease → 주문 INSERT
}
```

옵션 ID를 키로 락이 분기되므로 1단계의 글로벌 직렬화와 달리 인기 옵션 1개에 트래픽이 집중돼도 다른 옵션의 처리량은 영향받지 않습니다. 단일 인스턴스에서 같은 옵션의 동시 주문은 모두 같은 `ReentrantLock` 큐를 통과하므로, 옵션 행에 대한 경합 자체가 사라져 `@Transactional` 한 줄로 정합성이 유지됩니다.

### 한계

옵션 SKU 단위 락으로 단일 JVM 정합성은 회복했지만, 이 해결책은 락 풀이 한 프로세스 메모리 안에만 존재한다는 전제에 묶여 있습니다. WAS가 두 대 이상이면 각 JVM의 `ConcurrentHashMap`은 서로 다른 인스턴스이고, 같은 옵션 ID에 대해서도 두 JVM이 각자 자기 락을 잡은 채 병렬로 진입합니다. 같은 옵션 행에 동시 차감이 들어오면 1단계의 lost update가 그대로 돌아옵니다.

## 3. 비관적 락

### 개요

잠금을 JVM 메모리에서 DB 행으로 옮깁니다. 같은 행을 가리키는 모든 세션은 어느 인스턴스에서 들어오든 같은 X 락 큐에 줄을 서므로, 2단계의 단일 JVM 한정 한계가 사라집니다.

JPA에서 행 X 락을 명시적으로 얻으려면 `SELECT ... FOR UPDATE`에 대응하는 `@Lock(LockModeType.PESSIMISTIC_WRITE)` 어노테이션을 조회 메서드에 붙입니다. 이 메서드를 트랜잭션 안에서 호출하는 순간 X 락이 잡히고, **트랜잭션이 commit/rollback될 때까지 락이 유지됩니다**. 그동안 다른 트랜잭션은 같은 행을 잡으려 시도하면 블록되므로 1단계 `SELECT → 검사 → UPDATE` 사이에 끼어드는 race가 원천적으로 사라집니다.

조회 메서드는 **두 종류로 분리**합니다. 일반 페이지 노출처럼 락이 필요 없는 읽기 경로는 평문 `findByOptionId`를 쓰고, 주문 트랜잭션처럼 쓰기 의도가 있는 경로는 `findByOptionIdForOrder`로 명시적으로 락을 잡고 들어옵니다. 메서드 이름이 호출자의 의도(쓰기 경로)를 강제하는 게이트 역할을 합니다.

<Diagram caption="3단계 아키텍처: 트랜잭션 진입 시 SELECT FOR UPDATE로 X-lock을 잡고, 메모리에서 검사·차감 후 commit. 락 보호 구간은 SELECT부터 commit까지">{`flowchart LR
    subgraph WASA["WAS-A (JVM 1)"]

### 구현

```java title="OptionStockRepository.java"
public interface OptionStockRepository extends JpaRepository<OptionStock, Long> {

    // 일반 조회용. 락 없음. 상품 상세 등 읽기 전용 트래픽에서 사용한다.
    // MVCC 엔진이라 다른 트랜잭션의 X-lock과 무관하게 스냅샷을 읽으므로 절대 막히지 않는다.
    Optional<OptionStock> findByOptionId(Long optionId);

    // 주문 트랜잭션 전용. SELECT ... FOR UPDATE 로 X-lock을 잡는다.            // [!code highlight]
    // 같은 트랜잭션이 commit/rollback 될 때까지 다른 트랜잭션은 이 행을         // [!code highlight]
    // 수정하거나 다시 FOR UPDATE 로 잡으려 시도하면 블록된다.                   // [!code highlight]
    // 메서드 이름의 ForOrder 가 "쓰기 경로에서만 호출하라"는 신호를 박는다.
    @Lock(LockModeType.PESSIMISTIC_WRITE)                                       // [!code highlight]
    @Query("SELECT s FROM OptionStock s WHERE s.optionId = :optionId")
    Optional<OptionStock> findByOptionIdForOrder(@Param("optionId") Long optionId); // [!code highlight]
}
```

```java title="OrderService.java"
@Service
@RequiredArgsConstructor
public class OrderService {

    private final OptionStockRepository optionStockRepository;

    @Transactional
    public PlaceOrderResult placeOrder(Long accountId, PlaceOrderCommand command) {
        // member, option 조회 (생략)

        // 비관적 락을 잡고 stock 행을 읽는다. 이 시점부터 commit 까지 X-lock 유지.
        // 같은 옵션을 노리는 T2/T3 는 이 SELECT FOR UPDATE 에서 블록된다.
        OptionStock stock = optionStockRepository                                  // [!code highlight]
            .findByOptionIdForOrder(command.optionId())                            // [!code highlight]
            .orElseThrow(() -> new BusinessException(ErrorCode.STOCK_NOT_FOUND));

        // 락이 걸린 동안 메모리에서 검사·차감.
        // 다른 트랜잭션은 같은 행을 잡지 못하므로 lost update 가 발생할 수 없다.
        try {
            stock.decrease(command.quantity());
        } catch (BusinessException e) {
            if (e.errorCode() == ErrorCode.INSUFFICIENT_STOCK) {
                throw new BusinessException(ErrorCode.INSUFFICIENT_AMOUNT, e);
            }
            throw e;
        }

        // Order 조립 + INSERT (생략)
        // commit 직후 dirty checking 이 UPDATE 를 발행하고, 곧이어 X-lock 이 자동 해제된다.
    }
}
```

`findByOptionIdForOrder` 가 트랜잭션 밖에서 호출되거나 셀프 호출로 `@Transactional` 프록시가 우회되면 락이 안 잡혀도 예외 없이 통과합니다. 이 점 때문에 다음 절의 200 스레드 동시성 테스트는 단순 회귀 테스트가 아니라 **락 메커니즘이 실제로 동작하는지 검증하는 장치**로도 의미가 있습니다.

### 테스트 코드 및 결과

앞 두 단계와 동일한 200 스레드 / 재고 100 시나리오입니다 (`PlaceOrderPessimisticConcurrencyTest`). `OrderService` 가 빈으로 등록되므로 `@Autowired` 로 받아 그대로 사용합니다.

![3단계 비관적 락 200 스레드 측정 결과](/images/posts/mini-coupang-order-concurrency-locks/c-pessimistic-200-thread-result.png)

| 항목 | 기대 | 실측 (2단계 대비) |
|---|---|---|
| 주문 성공 | 100 | **100** (동일) |
| 재고 부족 거절 | 100 | **100** (동일) |
| 남은 재고 | 0 | **0** (동일) |
| 저장된 주문 | 100 | 100 |

단일 JVM과 단일 H2 인스턴스 환경에서는 2단계와 같은 숫자가 나옵니다. 의미 있는 차이는 적용 조건에 있습니다. 2단계는 단일 JVM 안에서만 직렬화하지만 3단계는 동일 행을 가리키는 모든 트랜잭션을 DB 레벨에서 직렬화합니다. 단일 H2 환경에서는 두 결과가 일치하는 것이 정상이며, scale-out 시뮬레이션 없이 정량적 우위를 보이려고 하면 측정값이 거짓이 됩니다.

### 한계

3단계까지의 시나리오는 결제 같은 외부 호출이 없거나, 있어도 트랜잭션과 분리되어 있다고 가정했습니다. 실제 주문 흐름에서는 결제 게이트웨이 호출이 한 트랜잭션 안에 끼어들기 쉽고, 비관적 락은 그 호출이 끝날 때까지 행 X 락을 풀지 않습니다.

| 비용 | 무엇이 묶이나 | 영향 |
|---|---|---|
| 락 보유 시간 = 트랜잭션 길이 | 재고 차감 외에 결제, Order `INSERT` 까지 한 트랜잭션 | 결제가 약 10초 걸리면 락도 그 시간만큼 유지 |
| DB 커넥션 점유 | 락 보유 동안 커넥션 함께 점유 | HikariCP 풀(기본 10)과 충돌, 빠른 커넥션 고갈 |
| 핫 row 직렬화 | 인기 옵션 1개에 트래픽 집중 | 처리량이 1행 × 1 커넥션 × 결제 응답 시간으로 묶임 |

이 문제는 모놀리스 서버 안에서는 더 이상 줄이기 어렵습니다. 재고 선점을 트랜잭션 밖으로 빼고 결제 실패에 보상 트랜잭션을 붙이는 분산 잠금 전략은 별도 글에서 다룹니다.

## 결론

### 정합성 결과

| 단계 | 잠금 주체 | 주문 성공 | 재고 부족 거절 | 남은 재고 |
|---|---|---|---|---|
| 1단계 락 없음 | 없음 | 200 | 0 | 56 |
| 2단계 `synchronized` | JVM 모니터 | 100 | 100 | 0 |
| 3단계 비관적 락 | DB 행 락 | 100 | 100 | 0 |

1단계는 lost update로 56건이 사라졌고, 2~3단계는 같은 옵션 행에 대한 동시 차감을 하나씩 직렬화해 정합성을 회복했습니다.

### 모놀리스 환경 적합성

| 단계 | 단일 JVM | 단일 DB 인스턴스 | 다중 인스턴스 |
|---|---|---|---|
| 1단계 락 없음 | 깨짐 | 깨짐 | 깨짐 |
| 2단계 `synchronized` | OK | OK | 깨짐 (락 풀이 JVM 안에 갇힘) |
| 3단계 비관적 락 | OK | OK | OK (DB 레벨 직렬화) |

<Callout type="info" title="잠금 위치는 정합성 범위와 같이 움직인다">
1단계는 도메인 메서드 안의 메모리 검사만, 2단계는 JVM 모니터, 3단계는 DB 행 락으로 잠금 위치를 한 칸씩 끌어올렸습니다. 잠금 위치가 위로 올라갈수록 같은 행에 동시에 닿을 수 있는 경로가 그만큼 줄어들고, 정합성이 깨지지 않는 범위도 그만큼 넓어집니다. 모놀리스 서버에서 적용할 수 있는 락의 형태는 여기까지이고, 그다음 단계는 트랜잭션 길이와 잠금 보유 시간을 분리하는 분산 잠금 전략에서 다룹니다.
</Callout>

### 남은 한계

| 한계 | 무엇이 부족한가 | 다음 단계 |
|---|---|---|
| 결제 같은 외부 호출이 트랜잭션 안에 들어옴 | 락 보유 시간 = 트랜잭션 길이 = 외부 호출 응답 시간 | 재고 선점을 트랜잭션 밖으로 분리 |
| 인기 옵션 1개에 트래픽 집중 | 핫 row 직렬화 = 처리량 상한 | 원자 선점 + 보상 트랜잭션으로 잠금 모델 자체를 변경 |
| 다중 인스턴스 환경 | 2단계 무력화, 3단계는 결제 응답 시간만큼 행 락 점유 | 분산 잠금 또는 Redis 원자 차감 |

세 가지 모두 모놀리스 안의 락만으로는 풀리지 않습니다. 분산 환경에서 락 보유 시간을 줄이고 외부 호출 실패에 보상 트랜잭션을 붙이는 전략은 별도 글에서 다룹니다.
