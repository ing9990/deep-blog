이 글에서는 동시 주문이 몰리는 서버에서 재고를 안전하게 차감하는 방법을 단계별로 비교합니다. 단일 스레드 통합 테스트는 통과하지만, 재고 100인 옵션에 200 스레드가 한꺼번에 주문하면 200건이 모두 성공으로 기록되고 재고가 56에서 멈춥니다. 락 없는 상태에서 출발해 `synchronized`, 비관적 락, Lua 원자 선점 + Saga 보상까지 정합성 전략을 단계적으로 바꾸며 같은 200 스레드 시나리오에서 성공 건수, 재고 부족 응답, 결제 실패 보상이 어떻게 달라지는지 확인합니다.

- 상품의 재고는 초기 100개라고 가정합니다.
- 200명의 사용자가 같은 옵션에 동시에 주문하는 시나리오 테스트입니다.
- 정합성을 지키면 성공 100건, 재고 부족 100건, 최종 재고 0이 되어야 합니다.

## 요구사항과 제약

### 기능 요구

- 회원이 옵션 ID와 수량(=1)으로 단건 주문을 생성한다
- 재고는 옵션(SKU 단위)으로 관리되며 주문 성공 시 차감
- 재고 부족 시 `INSUFFICIENT_AMOUNT` 에러로 거절
- 동시성과 무관하게 정합성: 주문 성공 수가 초기 재고를 넘지 않고, 남은 재고가 음수가 되지 않는다

## 1. 락 없음 (출발점)

### 개요

JVM 동기화도, DB 행 락도, 분산 락도 없습니다. 도메인 메서드 `OptionStock.decrease`가 자기 조건(요청 수량이 현재 quantity보다 큰가)만 검사하고 차감을 진행합니다. 단일 스레드에서는 잘 동작하지만, 동시에 들어온 트랜잭션이 같은 옵션 행을 보면 조회와 쓰기 사이의 race로 정합성이 깨지는 출발점입니다.

### 구현

```java title="OptionStock.java"
public void decrease(long delta) {
    validatePositiveDelta(delta, "차감");
    if (delta > this.quantity) {                                          // [!code highlight]
        throw new BusinessException(ErrorCode.INSUFFICIENT_STOCK,
            "재고가 부족합니다: 보유 " + this.quantity + ", 요청 " + delta);
    }
    this.quantity = this.quantity - delta;                                // [!code highlight]
}
```

```java title="OrderServiceNoLock.java"
@Transactional
public PlaceOrderResult placeOrder(Long accountId, PlaceOrderCommand command) {
    // member, option 조회 (생략)
    OptionStock stock = optionStockRepository.findByOptionId(command.optionId()) // [!code highlight]
        .orElseThrow(() -> new BusinessException(ErrorCode.STOCK_NOT_FOUND));
    stock.decrease(command.quantity());                                          // [!code highlight]
    // Order 조립 + INSERT (생략)
}
```

JPA dirty checking이 만드는 UPDATE는 `SET quantity = 99` 같은 계산된 값이지, `SET quantity = quantity - 1`의 DB-side 차감이 아니라는 점이 핵심입니다.

### 테스트 코드 및 결과

동시성 테스트는 세 단계 모두 같은 200 스레드 / 재고 100 시나리오를 사용합니다.

```java title="PlaceOrder<Stage>ConcurrencyTest.java"
@Test
@DisplayName("재고 100에 같은 SKU로 200 스레드가 동시 주문하면 100건만 성공해야 한다")
void place_200concurrent_sameSku_stock100_only100succeed() throws Exception {
    ExecutorService executor = Executors.newFixedThreadPool(THREADS);
    CountDownLatch barrier = new CountDownLatch(1);
    CountDownLatch done = new CountDownLatch(THREADS);
    AtomicInteger success = new AtomicInteger();
    AtomicInteger insufficient = new AtomicInteger();
    AtomicInteger other = new AtomicInteger();

    for (int i = 0; i < THREADS; i++) {
        executor.submit(() -> {
            try {
                barrier.await();
                orderService.placeOrder(prepared.memberAccountId(),
                    new PlaceOrderCommand(prepared.optionId(), 1L));
                success.incrementAndGet();
            } catch (BusinessException e) {                                  // [!code highlight]
                if (e.errorCode() == ErrorCode.INSUFFICIENT_AMOUNT) {        // [!code highlight]
                    insufficient.incrementAndGet();                          // [!code highlight]
                } else {
                    other.incrementAndGet();
                }
            } catch (Exception e) {
                other.incrementAndGet();
            } finally {
                done.countDown();
            }
        });
    }
    barrier.countDown();
    done.await(60, TimeUnit.SECONDS);
    // ... assert 결과: success / insufficient / 최종 재고
}
```

`BusinessException + ErrorCode.INSUFFICIENT_AMOUNT`만 재고 부족 거절로 카운트하고 그 외 예외는 `other` 버킷으로 분리해, 의도하지 않은 거절(예: `OPTION_NOT_FOUND`)이 주문 성공 누락으로 위장되는 것을 막습니다.

### 다음 단계: synchronized 도입

가장 직접적인 해법은 `synchronized`로 조회·검사·차감을 한 임계 영역에 묶는 것입니다. 단일 인스턴스에서는 성공 100건, 재고 부족 100건, 최종 재고 0으로 정합성이 회복됩니다.

## 2. synchronized

### 개요

1단계에서 lost update가 일어난 이유는 조회와 차감 사이에 다른 스레드가 같은 행의 오래된 값을 잡았기 때문입니다. JVM 안에서 가장 단순한 해법은 `synchronized`로 그 구간을 한 줄로 세우는 것입니다. `OrderService` 안에 `private final Object lock = new Object();`를 두고 `placeOrder`가 항상 그 모니터를 잡고 진입합니다.

### 구현

```java title="OrderServiceSynchronized.java"
@Service
@RequiredArgsConstructor
public class OrderServiceSynchronized {

    private final Object lock = new Object();                                          // [!code highlight]
    // 4 repositories

    @Transactional
    public PlaceOrderResult placeOrder(Long accountId, PlaceOrderCommand command) {
        synchronized (lock) {                                                          // [!code highlight]
            return doPlaceOrder(accountId, command);
        }
    }

    // doPlaceOrder: 1단계와 동일한 stock 조회 → decrease → 주문 INSERT
}
```

`lock`은 인스턴스 필드라 `OrderServiceSynchronized` 빈 단 하나가 모든 주문을 직렬화합니다 (옵션과 무관하게). 잠금 객체가 한 프로세스 메모리 안에만 존재한다는 한계는 다음 단계인 비관적 락이 DB 행으로 푸는 길로 이어집니다.

### 다음 단계: 비관적 락

`synchronized`로 단일 인스턴스 정합성은 회복했지만, 이 해결책은 한 프로세스 메모리에 묶인 락 객체가 전제입니다. WAS가 두 대 이상이거나 `ConcurrentHashMap<Long, Object>`로 옵션 ID 단위 락 풀을 끼워 넣어도 결론은 같습니다. 두 JVM의 모니터는 서로 다른 객체이므로 같은 옵션 행에 동시 차감이 들어오면 1단계의 lost update가 그대로 돌아옵니다.

## 3. 비관적 락

### 개요

잠금을 JVM 메모리에서 DB 행으로 옮깁니다. 같은 행을 가리키는 모든 세션은 어느 인스턴스에서 들어오든 같은 X 락 큐에 줄을 서므로, 2단계의 단일 JVM 한정 한계가 사라집니다.

JPA에서 행 X 락을 얻는 방법은 두 가지입니다. 명시적인 `SELECT ... FOR UPDATE`(`@Lock(PESSIMISTIC_WRITE)`)와 `@Modifying` UPDATE 한 줄. 둘 다 동일한 행 단위 직렬화를 만듭니다. 3단계는 후자를 씁니다. 조회·검사·차감을 한 SQL 안에 원자화할 수 있고, JPA dirty checking 이 발행하는 두 번째 UPDATE 도 끼지 않습니다.

### 구현

```java title="OptionStockRepository.java"
public interface OptionStockRepository extends JpaRepository<OptionStock, Long> {

    Optional<OptionStock> findByOptionId(Long optionId);

    @Modifying                                                                       // [!code highlight]
    @Query("""
        UPDATE OptionStock optionStock
        SET optionStock.quantity = optionStock.quantity - :qty
        WHERE optionStock.optionId = :optionId
                and optionStock.quantity >= :qty
        """
    )
    int decreaseQuantityIfEnough(@Param("optionId") Long optionId, @Param("qty") long qty); // [!code highlight]
}
```

WHERE 절의 `optionStock.quantity >= :qty` 가 재고 부족 검사를 SET 절과 한 번에 수행합니다. 반환값 affected 가 1이면 차감 성공, 0이면 재고 부족입니다.

```java title="OrderService.java"
@Service
@RequiredArgsConstructor
public class OrderService {

    @Transactional
    public PlaceOrderResult placeOrder(Long accountId, PlaceOrderCommand command) {
        // member, option 조회 (생략)
        int updated = optionStockRepository.decreaseQuantityIfEnough(                // [!code highlight]
            command.optionId(), command.quantity());                                 // [!code highlight]
        if (updated == 0) {                                                          // [!code highlight]
            throw new BusinessException(ErrorCode.INSUFFICIENT_AMOUNT);              // [!code highlight]
        }
        // Order 조립 + INSERT (생략)
    }
}
```

```sql title="발행된 쿼리 (Hibernate)"

    option_stocks

    quantity=quantity-?
```

단일 JVM과 단일 H2 인스턴스 환경에서는 2단계와 같은 숫자가 나옵니다. 의미 있는 차이는 적용 조건에 있습니다. 2단계는 단일 JVM 안에서만 직렬화하지만 3단계는 동일 행을 가리키는 모든 트랜잭션을 DB 레벨에서 직렬화합니다. 단일 H2 환경에서는 두 결과가 일치하는 것이 정상이며, scale-out 시뮬레이션 없이 정량적 우위를 보이려고 하면 측정값이 거짓이 됩니다.

### 다음 단계: 결제가 트랜잭션 안에 들어오면

3단계까지의 시나리오는 결제 같은 외부 호출이 없거나, 있어도 트랜잭션과 분리되어 있다고 가정했습니다. 실제 주문 흐름에서는 결제 게이트웨이 호출이 한 트랜잭션 안에 끼어들기 쉽고, 비관적 락은 그 호출이 끝날 때까지 행 X 락을 풀지 않습니다.

| 비용 | 무엇이 묶이나 | 영향 |
|---|---|---|
| 락 보유 시간 = 트랜잭션 길이 | 재고 차감 외에 결제, Order INSERT 까지 한 트랜잭션 | 결제가 약 10초 걸리면 락도 그 시간만큼 유지 |
| DB 커넥션 점유 | 락 보유 동안 커넥션 함께 점유 | HikariCP 풀(기본 10)과 충돌, 빠른 커넥션 고갈 |
| 핫 row 직렬화 | 인기 옵션 1개에 트래픽 집중 | 처리량이 1행 × 1 커넥션 × 결제 응답 시간으로 묶임 |

다음 단계는 잠금 주체를 옮기는 게 아니라 정합성 전략 자체를 바꿉니다. Redis Lua 스크립트로 재고를 트랜잭션 밖에서 원자적으로 선점하고, 결제는 트랜잭션 없이 외부 서비스로 보낸 뒤, 실패 시 Saga 보상으로 Redis 재고를 원복합니다.

## 4. Lua 선점 + Saga 보상

### 개요

비관적 락은 정합성을 지키지만 락 보유 시간이 트랜잭션 길이와 같습니다. 결제 같은 외부 호출이 한 트랜잭션 안에 들어오면 그 응답 시간만큼 행 X 락과 DB 커넥션을 함께 점유하므로, 처리량이 결제 응답 시간 단위로 묶입니다. 이 글의 시뮬레이션은 결제 호출을 ~10초로 가정하므로 그 결합이 두드러집니다.

4단계는 정합성 책임을 락 하나가 아니라 세 갈래로 분리합니다.

- 재고 선점은 Redis Lua 스크립트가 GET, 검사, DECRBY를 한 번에 원자적으로 실행해 트랜잭션 밖에서 끝냅니다.
- 결제는 트랜잭션 없이 외부 payment-service에 호출합니다.
- 결제가 성공하면 주문확정 이벤트가 발행되고, 컨슈머가 MySQL `option_stocks`를 영구 차감합니다. 결제가 실패하면 Saga 보상으로 Redis 재고를 원복(release)합니다.

이 모양에서는 Redis 원자 차감이 동시 정합성을, MySQL UPDATE의 WHERE 조건이 마지막 안전망을, Saga 보상이 결제 실패 복구를 맡습니다.

### Redis Lua 스크립트

`ProductStockRedisRepository`가 Lua를 두 개 보관합니다. GET, 검사, DECRBY가 같은 스크립트 안에서 실행되므로 다른 클라이언트가 그 사이에 끼어들 수 없습니다.

```java title="ProductStockRedisRepository.java"
private static final String RESERVE_SCRIPT = """                                     // [!code highlight]
    local current = redis.call('GET', KEYS[1])
    if not current then return -1 end
    local qty = tonumber(ARGV[1])
    if tonumber(current) < qty then return -2 end
    return redis.call('DECRBY', KEYS[1], qty)
    """;

private static final String RELEASE_SCRIPT = """                                     // [!code highlight]
    return redis.call('INCRBY', KEYS[1], ARGV[1])
    """;
```

두 스크립트는 Redisson `RScript`에 `READ_WRITE` 모드로 발행됩니다. `reserveStock`은 -1(키 부재), -2(재고 부족), 0 이상(차감 후 남은 수량) 세 값 중 하나를 돌려주고, `OrderService`가 이를 `STOCK_NOT_FOUND` / `INSUFFICIENT_AMOUNT` / 정상 진행으로 매핑합니다. `releaseStock`은 결제 실패 시 보상용 INCRBY만 수행합니다.

### 결제 서비스 분리

분산 환경을 흉내내기 위해 결제는 별도 Spring Boot 애플리케이션(payment-service, 8081 포트)으로 분리하고 backend는 OpenFeign으로 호출합니다. 도메인이 외부 시스템에 직접 의존하지 않도록 hexagonal port/adapter 구조를 둡니다.

- `PaymentPort` (도메인 인터페이스): `charge(PaymentChargeCommand) → PaymentChargeOutcome`
- `PaymentFeignAdapter` (인프라 어댑터): `PaymentFeignClient`를 호출하고 응답을 도메인 DTO로 변환

payment-service는 결제 시뮬레이션을 위해 ~10초 `Thread.sleep` 후 응답하고, `simulateFailure=true` 요청은 즉시 실패로 응답합니다.

### OrderService 4-phase

read TX와 write TX를 분리하고, 그 사이에 Redis 선점과 결제 호출을 트랜잭션 밖에 둡니다. JPA LAZY 프록시는 트랜잭션 안에서만 안전하므로 read TX 결과는 primitive와 String만 담은 record로 운반합니다.

```java title="OrderService.java"
public PlaceOrderResult placeOrder(Long accountId, PlaceOrderCommand command) {
    // Phase 1: read TX (회원/옵션/상품 조회 + 가격 추출)
    OrderInputs inputs = transactionTemplate.execute(status -> {                     // [!code highlight]
        Member member = memberRepository.findByAccountId(accountId)
            .orElseThrow(() -> new BusinessException(ErrorCode.NOT_A_MEMBER));
        ProductOption option = productOptionRepository.findByIdWithProduct(command.optionId())
            .orElseThrow(() -> new BusinessException(ErrorCode.OPTION_NOT_FOUND));
        Product product = option.getProduct();
        return new OrderInputs(member.getId(), option.getId(), option.getSku(),
            option.getOptionName(), option.getAdditionalPrice(),
            product.getId(), product.getName(), product.getBasePrice());
    });
    long unitPrice = inputs.basePrice() + inputs.additionalPrice();
    long totalAmount = unitPrice * command.quantity();

    // Phase 2: Redis Lua 원자 선점
    long reserved = stockRedisRepository.reserveStock(command.optionId(), command.quantity()); // [!code highlight]
    if (reserved == -1) throw new BusinessException(ErrorCode.STOCK_NOT_FOUND);
    if (reserved == -2) throw new BusinessException(ErrorCode.INSUFFICIENT_AMOUNT);

    // Phase 3: 결제 (외부 호출, 트랜잭션 밖)
    PaymentChargeOutcome outcome = paymentPort.charge(
        new PaymentChargeCommand(UUID.randomUUID().toString(), totalAmount, command.simulateFailure()));
    if (!outcome.paid()) {
        stockRedisRepository.releaseStock(command.optionId(), command.quantity());   // [!code highlight]
        throw new BusinessException(ErrorCode.PAYMENT_FAILED);
    }

    // Phase 4: write TX (Order INSERT + OrderConfirmed 발행 → MySQL 차감)
    return transactionTemplate.execute(status -> persistOrder(inputs, unitPrice, command));
}
```

read TX가 끝나면 Hibernate session 밖의 LAZY 프록시는 더 이상 안전하지 않으므로, Phase 2~4로 가져갈 값은 엔티티가 아닌 `OrderInputs` record(primitive와 String) 형태여야 합니다. write TX 안에서 `Member`를 다시 `findById`로 로드해 영속 상태에서 Order를 조립합니다.

### 주문확정 이벤트

write TX 안에서 `OrderConfirmed` 이벤트가 발행되고, 동기 `@EventListener`가 받아 `ProductService.decreaseStockOnOrderConfirmed`를 호출합니다. 이 메서드는 `@Transactional(propagation = MANDATORY)`로 외부 write TX에 합류해, 주문 INSERT와 재고 영구 차감이 한 커밋으로 끝납니다.

```java title="ProductService.java"
@Transactional(propagation = Propagation.MANDATORY)
public void decreaseStockOnOrderConfirmed(OrderConfirmed event) {
    int updated = optionStockRepository.decreaseQuantityIfEnough(                    // [!code highlight]
        event.optionId(), event.quantity());
    if (updated == 0) {
        log.error("Redis-MySQL drift: orderId={}, optionId={}, quantity={}",
            event.orderId(), event.optionId(), event.quantity());
    }
}
```

`decreaseQuantityIfEnough`의 WHERE `quantity >= :qty`가 마지막 안전망입니다. Redis 재고 유실 등으로 두 저장소가 어긋나 affected=0이 되는 경우는 로그로 노출하고, 환불·재고 복구 같은 사후 보상 흐름은 별도 글에서 다룹니다.

리스너를 `@TransactionalEventListener(AFTER_COMMIT)`이 아니라 평범한 `@EventListener`로 둔 이유는 두 가지입니다. 첫째, 주문 INSERT가 커밋된 뒤에 재고 차감만 실패해 두 결과가 어긋나는 상황을 만들지 않기 위해서입니다. 둘째, Spring 6.2의 `RestrictedTransactionalEventListenerFactory`가 같은 메서드의 `@TransactionalEventListener`와 `@Transactional` 결합을 거부하므로, 동기 합류가 가장 단순합니다. 진짜 비동기 분리(Outbox + Kafka + 멱등 컨슈머)는 다음 글에서 다루며, 4단계는 이벤트 기반 책임 분리의 형태만 보여줍니다.

### 테스트 코드 및 결과

200 스레드 중 10건에 `simulateFailure=true`를 주입해 5% 결제 실패 시나리오를 만듭니다. Redis는 Testcontainers로 띄우고, `PaymentPort`는 `@TestConfiguration`이 등록한 stub이 받습니다(요청에 simulateFailure=true가 없으면 항상 성공).

```java title="PlaceOrderLuaSagaConcurrencyTest.java"
@TestConfiguration
static class LuaSagaTestConfig {
    @Bean(destroyMethod = "shutdown")
    RedissonClient redissonClient() { /* Testcontainers Redis 연결 */ }

    @Bean @Primary
    PaymentPort paymentPort() {
        return cmd -> cmd.simulateFailure()
            ? PaymentChargeOutcome.failure("simulated")
            : PaymentChargeOutcome.success(cmd.orderRef());
    }
}

// 200 스레드, 10건은 simulateFailure=true 로 제출
for (int i = 0; i < THREADS; i++) {
    boolean shouldFail = i < FAILURE_INJECTED_THREADS; // 10
    executor.submit(() -> {
        try {
            barrier.await();
            orderService.placeOrder(memberId,
                new PlaceOrderCommand(optionId, 1L, shouldFail));
            success.incrementAndGet();
        } catch (BusinessException e) {
            switch (e.errorCode()) {
                case INSUFFICIENT_AMOUNT -> insufficient.incrementAndGet();
                case PAYMENT_FAILED      -> paymentFailed.incrementAndGet();
                default                  -> other.incrementAndGet();
            }
        } finally { done.countDown(); }
    });
}
```

| 항목 | 기대 | 실측 |
|---|---|---|
| 주문 성공 | 정합성 깨지지 않음 | **100** |
| 재고 부족 거절 | 결제 성공분과 보상분에 따라 가변 | **90** |
| 결제 실패 보상 | ≤ 10 | **10** |
| 다른 예외 | 0 | **0** |
| 최종 Redis 재고 | 0 | **0** |
| 최종 MySQL 재고 | 0 | **0** |
| 저장된 주문 | 100 | 100 |

확인되는 것은 세 가지입니다.

- 200건 모두 성공/재고 부족/결제 실패 중 한 갈래로 분류되어 누락 없이 처리됐습니다(100 + 90 + 10 = 200).
- 결제 실패 10건이 Redis 재고를 원복했고, 이 슬롯이 동시에 도착한 다른 reserve 호출로 회수되어 최종 Redis 재고가 0으로 수렴했습니다.
- 주문 INSERT가 커밋된 뒤 컨슈머가 MySQL `option_stocks`를 영구 차감해, Awaitility polling으로 검증한 최종 MySQL 재고가 0이 됩니다.

## 결론

### 정합성 결과

| 단계 | 잠금 주체 | 주문 성공 | 재고 부족 거절 | 결제 실패 보상 | 남은 재고 |
|---|---|---|---|---|---|
| 1단계 락 없음 | 없음 | 200 | 0 | n/a | 56 |
| 2단계 synchronized | JVM 모니터 | 100 | 100 | n/a | 0 |
| 3단계 비관적 락 | DB 행 락 | 100 | 100 | n/a | 0 |
| 4단계 Lua 선점 + Saga | Redis 원자 + DB 행 | 100 | 90 | 10 | 0 |

1~3단계는 결제 외부 호출 모델이 없으므로 "결제 실패 보상" 칸을 n/a로 두었습니다. 4단계는 결제 실패 10건을 Saga 보상으로 복구해 정합성을 유지합니다.

### 분산 환경 적합성

| 단계 | 단일 JVM | 단일 DB 인스턴스 | 결제 외부 호출과의 격리 | 실서버 적용 |
|---|---|---|---|---|
| 1단계 락 없음 | 깨짐 | 깨짐 | 트랜잭션 안 | 불가 |
| 2단계 synchronized | OK | 깨짐 | 트랜잭션 안 | 단일 인스턴스만 |
| 3단계 비관적 락 | OK | OK | 트랜잭션 안 | 결제 시간만큼 행 락 점유 |
| 4단계 Lua 선점 + Saga | OK | OK | 트랜잭션 밖 | 핫 row × 결제 시간 결합이 풀림 |

<Callout type="error" title="잠금 위치 이동에서 원자 선점 + 보상으로">
1~3단계는 정합성을 잠금 위치(JVM 모니터 → DB 행)로 표현했습니다. 4단계는 잠금 자체를 다른 모양으로 바꿉니다. Redis가 짧은 critical section의 원자성을, MySQL UPDATE WHERE 조건이 마지막 안전망을, Saga 보상이 결제 실패 복구를 맡습니다. 결제 같은 느린 외부 호출이 트랜잭션 안에 들어오는 순간 잠금 모델은 처리량을 결제 응답 시간으로 묶기 시작하므로, 그 지점에서 정합성을 락이 아니라 "원자 선점 + 보상"으로 표현하는 선택지가 의미 있어집니다.
</Callout>

### 남은 한계

| 한계 | 무엇이 부족한가 | 다음 단계 |
|---|---|---|
| in-process `@EventListener` | 주문 INSERT와 MySQL 차감이 한 커밋이라 결합도 높음 | Outbox + Kafka + 멱등 컨슈머로 비동기 분리 |
| Saga 보상 = release만 | 결제 부분 성공, 환불, 재고 복구 흐름 미구현 | Saga 오케스트레이터 + 환불 어댑터 |
| Redis 단일 노드 | 단일 실패 지점, 클럭 스큐, fence token 부재 | Redis 클러스터 또는 합의 기반 잠금 |
| 측정 환경 | 단일 H2 + 단일 Redis + 단일 backend | 멀티 인스턴스 시뮬레이션, 부하 곡선 비교 |

이 네 가지는 별도 글에서 다룹니다. 비동기 이벤트 분리(Outbox + Kafka)와 Saga 오케스트레이션을 각각 풀어낼 예정입니다.
