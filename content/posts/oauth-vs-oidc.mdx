OAuth와 OIDC는 비슷하게 생겨서 자주 같은 말로 쓰이지만, 사실 둘은 서로 다른 문제를 풀기 위해 만들어진 표준입니다. 이 글에서는 OAuth가 풀려고 한 문제, OIDC가 그 위에 얹어 추가로 풀어준 문제, 그리고 토큰 3종이 어떤 역할을 나눠 가지는지를 정리합니다.

## 등장 배경

### 인증과 인가의 분리

먼저 <E>인증(Authentication)</E> 과 <E>인가(Authorization)</E> 라는 두 단어를 분리해 두겠습니다. 이 둘이 섞이면 OAuth와 OIDC가 왜 따로 있는지를 영원히 이해할 수 없습니다.

- **인증**: "당신이 누구인지" 증명하는 일. 아이디·비밀번호, 지문, 이메일 인증이 모두 인증
- **인가**: "당신이 무엇을 할 수 있는지"의 권한 부여. 로그인된 사용자에게 <E>이 파일 읽기 가능</E>, <E>결제 가능</E> 같은 행동권을 주는 일

자기 서비스 안에서만 동작한다면 사실 둘이 깔끔하게 분리될 필요가 없었습니다. 쇼핑몰 하나가 자체 회원 DB를 두고 세션 쿠키로 로그인 상태를 유지하면, 누구인지 확인하자마자 무엇을 할 수 있는지가 자동으로 따라옵니다. 한 시스템 내부의 일이니까요.

문제는 <E>다른 서비스의 데이터에 접근해야 할 때</E> 부터 시작됐습니다. 가령 어떤 일정 관리 앱이 사용자의 Google Calendar를 읽고 싶다면, 사용자는 Google 비밀번호를 그 앱에 직접 알려줘야 했습니다. 이 방식의 단점은 분명합니다.

- 앱이 비밀번호를 저장하면 그 앱이 털릴 때 Google 계정 전체가 함께 털림
- 앱에 "캘린더만 읽기"가 아니라 "Gmail까지" 권한을 사실상 다 주는 셈
- 사용자가 비밀번호를 바꾸면 모든 연결된 앱에 다시 입력해야 함
- 권한 회수가 비밀번호 변경 외에는 사실상 불가

페이스북에 사진을 올리려고 인스타그램 비밀번호를 페이스북에 알려준다고 생각해 보면, 한 서비스가 다른 서비스 데이터에 접근할 때 비밀번호 공유는 무리한 방식이라는 게 명확합니다. <E>사용자가 비밀번호를 넘기지 않고도 "이 앱에 내 캘린더만 30일 동안 읽도록 허용" 같은 제한된 권한을 위임할 표준 방법이 필요했습니다.</E> 이게 OAuth가 풀려고 한 문제입니다.

### OAuth의 등장

**OAuth 2.0** (Open Authorization)은 정확히 이 "권한 위임" 문제를 푸는 표준입니다. 핵심 아이디어는 <E>비밀번호 대신 토큰을 사용한다</E> 입니다.

흐름을 사람으로 비유하면 이렇습니다. 일정 관리 앱이 "구글 캘린더 읽기 권한 좀 주세요" 라고 직접 묻는 게 아니라, 사용자를 잠깐 Google 로그인 화면으로 보냅니다. 사용자는 거기서 직접 Google에 로그인하고 "이 앱에 캘린더 읽기만 허용" 버튼을 누른 뒤 다시 앱으로 돌아옵니다. 이때 앱은 Google에게서 "이 사용자의 캘린더에 한정된 행동을 할 수 있는 출입증"을 받습니다. 비밀번호는 끝까지 Google과 사용자 사이에만 머무릅니다.

OAuth가 정의하는 4명의 등장인물:

- **Resource Owner**: 데이터의 주인. 보통 사용자
- **Client**: 데이터에 접근하고 싶어 하는 외부 앱 (위 예시의 일정 관리 앱)
- **Authorization Server**: 권한을 발급해 주는 서버 (Google의 OAuth 서버)
- **Resource Server**: 보호된 데이터를 가진 서버 (Google Calendar API 서버)

전체 흐름을 가장 표준적인 방식인 **Authorization Code Flow** 기준으로 그리면 다음과 같습니다.

<Diagram caption="OAuth Authorization Code Flow: 사용자가 Authorization Server에서 직접 동의한 뒤 Client가 code를 토큰으로 교환">{`sequenceDiagram
    participant U as 사용자
    participant C as Client (앱)
    participant AS as Authorization Server
    participant RS as Resource Server

    U->>C: "Google 캘린더 연결" 클릭
    C->>U: AS로 redirect (client_id, redirect_uri, scope)
    U->>AS: 로그인 + 권한 동의
    AS->>U: redirect_uri로 redirect (code 포함)
    U->>C: code 전달
    C->>AS: code + client_secret으로 토큰 요청
    AS->>C: Access Token 발급
    C->>RS: Access Token으로 API 호출
    RS->>C: 캘린더 데이터 응답
`}</Diagram>

여기서 등장한 핵심 용어들:

- **Client ID / Client Secret**: Authorization Server에 미리 등록한 앱의 신분. ID는 공개되어도 되지만 Secret은 서버에만 둠
- **Redirect URI**: 사용자를 인증 완료 후 돌려보낼 앱의 주소 (예: `https://myapp.com/oauth/callback`). 사전에 미리 등록되지 않은 URI로는 redirect되지 않음. 이게 없으면 공격자가 임의 사이트로 `code`를 가로챌 수 있음
- **Scope**: 요청하는 권한의 범위. `calendar.read`, `drive.readonly` 같이 세분화. 사용자 동의 화면에 그대로 표시됨
- **Authorization Code**: 짧게(보통 10분 이내) 유효한 임시 코드. URL로 노출되니까 그 자체로는 데이터 접근 불가. 반드시 Client Secret과 함께 토큰으로 교환해야 함
- **Access Token**: 실제 API 호출에 쓰는 출입증. 보통 1시간 안팎으로 만료
- **Refresh Token**: Access Token이 만료되면 새 토큰을 받을 때 쓰는 장기 토큰

여기서 가장 중요한 사실은 <E>OAuth는 "이 토큰의 소유자가 누구인지"를 정의하지 않는다는 점</E> 입니다. Access Token은 그냥 "이 토큰을 가진 누군가가 캘린더 읽기 권한이 있다"만 증명합니다. 토큰 자체에 "이 사람은 홍길동, 이메일은 hong@example.com" 같은 정보는 없어요. OAuth의 목적이 어디까지나 **권한 위임**이지 **신원 확인**이 아니기 때문입니다.

### OIDC가 왜 필요했나

문제는 사람들이 OAuth를 <E>소셜 로그인</E> 용도로 쓰기 시작하면서 발생했습니다. "Google 계정으로 로그인" 버튼을 누르면 OAuth 흐름이 돌고, 받은 Access Token으로 Google의 사용자 정보 API를 호출해 이메일·이름을 가져온 뒤, 그걸로 로그인 처리를 하는 식이죠.

이 방식의 문제는 두 가지입니다.

**첫째, 표준이 없어서 서비스마다 제각각이었습니다.** Google은 `/userinfo`, Facebook은 `/me`, 다른 서비스는 또 다른 경로. 응답 JSON 필드도 모두 달라서 앱은 서비스마다 별도 어댑터를 짜야 했습니다.

**둘째, Access Token은 인증 증명으로는 부적절합니다.** Access Token은 Resource Server에 보낼 출입증이지 "이 사용자가 누구인지를 증명하는 문서"가 아닙니다. 가령 어떤 악의적인 앱 A가 Google Calendar 권한을 받아낸 뒤 그 Access Token을 다른 서비스 B에 전달하면, B는 "이 토큰이 유효하니 사용자가 본인 맞네"라고 잘못 결론내릴 수 있습니다. 토큰에는 "이게 누구를 위해 발급됐는지"의 정보(audience)가 명확히 박혀 있지 않으니까요. 이걸 **Confused Deputy Problem** 이라고 부릅니다.

요약하면 <E>인증 표준이 별도로 필요했습니다.</E> OAuth의 위임 흐름은 그대로 재사용하되, 사용자가 누구인지 증명하는 부분을 표준화한 것이 필요했습니다.

### OIDC의 등장

**OIDC** (OpenID Connect)는 OAuth 2.0 위에 얹은 **인증 레이어**입니다. OAuth를 대체하는 게 아니라 OAuth를 그대로 사용하면서, 인증에 필요한 정보를 표준화된 방식으로 추가합니다.

핵심 아이디어 두 가지:

1. **ID Token이라는 새 토큰을 추가한다.** 이 토큰은 사용자의 신원 정보를 담은 JWT (JSON Web Token)로, 자체적으로 검증 가능합니다.
2. **표준 엔드포인트와 표준 응답 형식을 강제한다.** `/userinfo`, `/.well-known/openid-configuration` 같이 OIDC를 지원하는 모든 서비스가 같은 모양으로 동작합니다.

흐름은 OAuth Authorization Code Flow와 거의 같지만, `scope`에 `openid`가 들어가고 응답에 ID Token이 추가됩니다.

<Diagram caption="OIDC Authentication Flow: OAuth 흐름 위에 ID Token 발급과 클라이언트 측 자체 검증이 추가됨">{`sequenceDiagram
    participant U as 사용자
    participant C as Client (RP)
    participant OP as OpenID Provider
    participant RS as UserInfo Endpoint

    U->>C: "Google로 로그인" 클릭
    C->>U: OP로 redirect (scope=openid profile email)
    U->>OP: 로그인 + 동의
    OP->>U: redirect_uri로 redirect (code)
    U->>C: code 전달
    C->>OP: code 교환 요청
    OP->>C: Access Token + ID Token
    C->>C: ID Token 서명 검증 (JWKS)
    C->>RS: (선택) Access Token으로 추가 정보 요청
    RS->>C: 프로필 정보
`}</Diagram>

OAuth 위에 추가된 핵심 용어들:

- **OpenID Provider (OP)**: OAuth의 Authorization Server에 OIDC 기능을 더한 서버. Google, Kakao, Auth0 등
- **Relying Party (RP)**: OAuth의 Client에 해당. 사용자 신원을 OP에 의존(rely)하는 앱
- **ID Token**: 사용자 신원을 담은 JWT. Header·Payload·Signature 세 부분으로 구성. Payload에 `sub`(사용자 고유 ID), `iss`(발급자), `aud`(이 토큰이 누구를 위해 발급됐는지), `exp`(만료 시각), `iat`(발급 시각) 등이 표준 필드로 들어감. 클라이언트는 이 토큰의 서명을 검증해 정말 이 OP가 발급한 게 맞는지 직접 확인할 수 있음
- **Scope `openid`**: 이 값이 scope에 포함되어야만 OIDC 흐름. 빠지면 그냥 OAuth로 동작
- **Scope `profile`, `email`**: 표준화된 scope. ID Token에 어떤 추가 클레임을 넣을지 지정
- **Claims**: ID Token payload 안의 키-값 쌍들. `name`, `email`, `picture` 등. OIDC가 표준 클레임 이름을 정해 놓아서 서비스가 달라도 같은 이름으로 받음
- **UserInfo Endpoint**: Access Token으로 호출하면 사용자 프로필을 표준 JSON으로 돌려주는 표준 경로
- **Discovery**: `https://<provider>/.well-known/openid-configuration` 으로 GET 하면 그 OP의 모든 엔드포인트 URL과 지원 기능을 JSON으로 받음. 클라이언트가 사전에 하드코딩 없이도 자동 설정 가능
- **JWKS (JSON Web Key Set)**: Discovery 응답에 들어 있는 공개키 목록. ID Token 서명 검증에 사용. OP는 비밀키로 서명, RP는 JWKS의 공개키로 검증

핵심을 한 줄로 다시 정리하면, <E>OAuth는 "이 출입증으로 캘린더 읽어도 됨"만 증명하고, OIDC는 거기에 "그리고 이 출입증의 주인은 sub=12345인 홍길동임"이라는 신원 증명서를 한 장 더 끼워 준 것</E> 입니다.

## 내부 동작

<Callout type="warning" title="이 글의 핵심 포인트">
  Authorization Code Flow가 코드를 한 번 거치는 이유, PKCE가 왜 필요한지, JWT가 어떻게 자체 검증되는지 세 가지가 핵심입니다.
  3종 토큰의 역할 분리는 이 세 가지를 이해하면 자연스럽게 따라옵니다.
</Callout>

### 왜 코드를 거치는가

가장 자연스러운 설계는 "사용자가 동의하면 그 자리에서 Access Token을 바로 던져 주는 것"입니다. 실제로 OAuth 1세대에는 이런 방식이 있었습니다(**Implicit Flow**). 흐름이 짧아서 매력적이지만 치명적인 약점이 있습니다.

Implicit Flow는 토큰을 **URL fragment** (`#access_token=xxx`)에 실어서 브라우저로 돌려보냅니다. 이 토큰이 거치는 경로는 다음과 같습니다.

- 브라우저 주소창 (히스토리에 남음)
- 브라우저 확장 프로그램 (확장이 URL을 읽을 수 있음)
- Referer 헤더 (외부 리소스 요청 시 새는 경로)
- 서버 액세스 로그

**Authorization Code Flow는 두 단계로 쪼개서 이 노출을 차단합니다.**

```text
1단계: 브라우저로 돌아오는 건 "code"만 (단명, 1회용, 데이터 접근 불가)
2단계: 백엔드가 "code + client_secret"으로 Authorization Server와 토큰 교환
       (이 통신은 사용자 브라우저를 거치지 않는 서버↔서버 직통)
```

```http title="POST /oauth/token 요청"
POST /oauth/token HTTP/1.1
Host: oauth.googleapis.com
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&code=4/0AY0e-g5xK...
&redirect_uri=https://myapp.com/callback
&client_id=1234.apps.googleusercontent.com
&client_secret=GOCSPX-AbCdEfGhIjKl
```

응답:

```json title="토큰 응답"
{
  "access_token": "ya29.a0AfH6...",
  "expires_in": 3600,
  "refresh_token": "1//0gB5...",
  "token_type": "Bearer",
  "id_token": "eyJhbGciOiJSUzI1NiIs..."
}
```

여기서 두 가지 안전 장치가 동시에 작동합니다.

- `client_secret`은 백엔드만 알고 있는 비밀이라 브라우저에서 흘러나갈 수 없음
- `code`는 한 번 교환하면 즉시 무효화되고 유효 시간도 짧음 (보통 10분 이내)

그러니까 누군가가 브라우저 히스토리나 로그에서 `code`를 훔쳐도, `client_secret`이 없으면 토큰으로 바꿀 수 없고, 진짜 클라이언트가 먼저 교환했다면 이미 폐기된 코드라 쓸 수 없습니다.

OAuth 2.1 초안은 결국 Implicit Flow를 **공식 폐기**했습니다. 모든 시나리오에서 Authorization Code Flow를 쓰게 통일됐습니다.

### PKCE의 역할

위 흐름에는 한 가지 전제가 있습니다. <E>Client Secret을 안전하게 보관할 백엔드가 있다는 것.</E> 그런데 모바일 앱이나 브라우저 SPA (Single Page App)는 이 전제가 깨집니다. 코드가 사용자 기기에 그대로 다운로드되니까요. 앱 바이너리를 디컴파일하면 `client_secret`이 그대로 보입니다. 이런 클라이언트를 **Public Client** 라고 부릅니다.

Public Client에서 Authorization Code만 가지고 토큰을 교환할 수 있다고 하면, 공격자가 다음 시나리오로 토큰을 훔칠 수 있습니다.

```text
1. 공격자 앱이 정상 앱과 같은 redirect_uri 스킴 등록 (모바일 앱 한정 공격)
2. 사용자가 정상 흐름 진행, Authorization Server가 code를 redirect_uri로 보냄
3. OS가 같은 스킴을 가진 앱 둘 중 공격자 앱을 띄움
4. 공격자가 가로챈 code로 토큰 교환 → 토큰 탈취
```

**PKCE** (Proof Key for Code Exchange, "픽시"라고 읽음)는 이 공격을 막기 위한 확장입니다. 핵심 아이디어는 <E>동일한 클라이언트가 보낸 code임을 증명할 비밀을 매 흐름마다 즉석에서 만들어 쓴다</E> 입니다.

```text
[흐름 시작 직전, 클라이언트가 직접 생성]
  code_verifier  = 랜덤한 43~128자 문자열
  code_challenge = SHA256(code_verifier) → base64url

[1단계: Authorize 요청]
  GET /authorize?...&code_challenge=<위 값>&code_challenge_method=S256

[Authorization Server 저장]
  발급한 code와 code_challenge를 같이 저장

[2단계: Token 교환]
  POST /token
  grant_type=authorization_code
  code=...
  code_verifier=<원본 문자열>

[Authorization Server 검증]
  SHA256(code_verifier)가 저장된 code_challenge와 같은지 확인
  다르면 거부
```

`code_verifier`는 클라이언트 메모리에만 머무르고 네트워크로 한 번도 평문 전송되지 않습니다. 공격자가 `code`를 가로채도 같이 보내야 할 `code_verifier`를 알 수 없으니 토큰 교환이 실패합니다.

현재는 PKCE가 모든 클라이언트(Public이든 Confidential이든)에 권장됩니다. OAuth 2.1에서는 사실상 필수로 격상됐습니다.

<Callout type="error" title="핵심 통찰: ID Token은 자체 검증 가능한 신분증이다">
  OIDC의 본질은 단순합니다. OAuth는 "출입증"만 발급하고, OIDC는 거기에 클라이언트가 OP에 다시 묻지 않고도 검증할 수 있는 "신분증(JWT)"을 한 장 더 끼워 줍니다.
  이 자체 검증 가능성이 OIDC가 표준 인증 레이어가 될 수 있었던 이유입니다.
</Callout>

### JWT 자체 검증

**JWT** (JSON Web Token)는 ID Token이 사용하는 형식이며 Access Token에도 자주 쓰입니다. 점(`.`) 두 개로 구분된 세 부분으로 이루어집니다.

```text
<Header>.<Payload>.<Signature>
```

| 부분 | 내용 |
|---|---|
| Header | 서명 알고리즘 (`alg`), 키 ID (`kid`) |
| Payload | Claims (`sub`, `iss`, `aud`, `exp` 등) |
| Signature | Header + Payload의 base64url 인코딩 결과에 대한 서명 |

각 부분은 base64url로 인코딩된 JSON입니다. 디코딩하면 다음과 같이 보입니다.

```json title="Header"
{
  "alg": "RS256",
  "kid": "123"
}
```

```json title="Payload (Claims)"
{
  "iss": "https://accounts.google.com",
  "sub": "456",
  "aud": "myapp",
  "exp": 1735689600,
  "iat": 1735686000
}
```

```text title="Signature"
RSA-SHA256(base64url(Header) + "." + base64url(Payload), 비밀키)
```

여기서 <E>자체 검증된다</E> 의 의미가 명확해집니다. 클라이언트는 ID Token을 받자마자 다음을 **혼자서** 확인할 수 있습니다.

1. **서명 검증**: `Header`의 `kid`로 OP의 JWKS에서 해당 공개키를 찾아, 그 공개키로 `Header.Payload`의 RSA 서명을 검증. 위조됐다면 검증 실패
2. **`iss` (issuer)**: 우리가 신뢰하는 OP가 발급한 게 맞는지
3. **`aud` (audience)**: 이 토큰이 우리 앱(`client_id`)을 위해 발급된 것이 맞는지. 다른 앱용 토큰을 우리한테 들고 와도 거부됨. Confused Deputy를 막는 핵심
4. **`exp` (expiration)**: 만료되지 않았는지
5. **`nonce` (있다면)**: 우리가 보낸 nonce와 같은지 (재사용 공격 방지)

이 검증을 통과하면 클라이언트는 OP에 다시 묻지 않고도 "이 토큰의 주인이 `sub=456`"이라고 신뢰할 수 있습니다. JWKS의 공개키만 주기적으로 캐싱해 두면 매 요청마다 OP를 호출할 필요가 없어 빠릅니다.

비교를 위해 자주 쓰는 또 다른 방식인 **Opaque Token** (불투명 토큰)을 잠깐 보면, 이건 그냥 의미 없는 무작위 문자열이라 받는 쪽이 매번 발급한 서버에 "이 토큰 유효해?" 물어봐야 합니다 (Token Introspection). 자체 검증이 안 되는 대신 **즉시 폐기**가 가능하다는 장점이 있습니다 (JWT는 만료 시각까지는 폐기가 어려움).

### 토큰 3종 비교

여기까지 등장한 토큰 3종을 한 표에 정리하면 헷갈림이 줄어듭니다.

| 항목 | Access Token | ID Token | Refresh Token |
|---|---|---|---|
| 출처 | OAuth | OIDC | OAuth |
| 답하는 질문 | "이거 해도 돼?" (인가) | "넌 누구야?" (인증) | "토큰 새로 줘" |
| 받는 사람 (audience) | Resource Server | Client (RP) 자신 | Authorization Server |
| 형식 | Opaque 또는 JWT | 항상 JWT | 보통 Opaque |
| 검증 방식 | RS가 검증 (introspection 또는 JWT 서명) | Client가 자체 검증 | AS가 검증 |
| 수명 | 짧음 (분~시간) | 짧음 (분~시간) | 긺 (일~년) |
| 어디 보내나 | API 요청의 `Authorization: Bearer ...` | 절대 API에 보내지 않음 | Token 엔드포인트에만 |
| 잘못 쓰는 패턴 | 사용자 식별에 사용 | API 인증에 사용 | 클라이언트 외부에 노출 |

이 표의 마지막 줄이 실무에서 가장 자주 깨지는 지점입니다. 두 가지 패턴을 짚으면 다음과 같습니다.

- **ID Token을 API 인증에 보내는 실수**: ID Token은 클라이언트 자기 자신용입니다. Resource Server는 `aud`가 다르므로 거부해야 합니다. 실제로는 RS가 검증을 느슨하게 하면 통과되는 경우가 있어, 보안 리뷰에서 자주 지적되는 항목입니다.
- **Access Token에서 사용자 정보를 꺼내 쓰는 실수**: Google 같은 대형 OP는 Access Token이 Opaque (JWT 아님)일 수 있습니다. 그래서 토큰을 디코딩해서 사용자 ID를 꺼내려고 하면 실패합니다. 사용자 식별은 ID Token으로, API 권한은 Access Token으로, 역할이 분리되어 있다는 점을 받아들여야 합니다.

## 트레이드오프

OAuth와 OIDC를 다 알았다고 해서 매번 둘 중 하나를 무조건 도입하는 게 답은 아닙니다. 자체 세션이 가장 합리적인 경우도 많고, 둘을 잘못 매칭하면 보안과 운영 부담이 오히려 늘어납니다.

### 결정 트리

질문 두 개로 대부분의 경우가 갈립니다.

```text
질문 1: 사용자의 데이터를 다른 서비스에서 가져와야 하는가?
        (예: Google Calendar 읽기, GitHub 리포 목록 가져오기)

  ├─ Yes → OAuth 또는 OIDC 사용 (외부 서비스가 표준 강제)
  │         질문 2로 진행
  │
  └─ No  → 자체 세션이 1순위.
            "왜 OAuth/OIDC가 굳이 필요한가" 다시 점검.

질문 2: 그 외부 서비스의 사용자가 누구인지를 우리가 알아야 하는가?
        (소셜 로그인 = Yes, 단순 데이터 접근 = No)

  ├─ Yes → OIDC (ID Token으로 신원, Access Token으로 데이터 접근)
  │
  └─ No  → OAuth만 충분 (Access Token만 받고 끝)
```

이 트리만으로 90% 이상 결정됩니다.

### 시나리오별 선택

| 상황 | 적합한 선택 | 이유 |
|---|---|---|
| 우리 서비스 자체 회원가입·로그인 (단일 도메인) | 자체 세션 | 외부 표준 도입은 과잉. 세션 쿠키 + CSRF 방어로 충분 |
| "Google로 로그인" 같은 소셜 로그인 | OIDC | 사용자 신원 표준화 필요. ID Token으로 검증 |
| 우리 앱이 사용자의 Google Drive 파일을 다루기 | OAuth | 권한 위임만 필요. 신원 확인은 부수적 |
| GitHub로 로그인 + 리포 목록도 보여주기 | OIDC + OAuth scope | OIDC로 신원 확인, 같은 흐름에서 `repo` scope로 데이터 접근권도 함께 |
| 사내 여러 시스템 간 SSO | OIDC | 표준화된 신원 + 통합 로그아웃 등 SSO 기능 |
| 마이크로서비스 간 내부 호출 | OAuth Client Credentials | 사용자 없음. 서비스가 Client이자 Resource Owner |
| 모바일 앱이 우리 자체 백엔드에 로그인 | 자체 세션 또는 자체 발급 JWT | 외부 OP 없이 자체 발급. OAuth는 과잉 |
| B2B 파트너가 우리 API를 호출 | OAuth Client Credentials | 파트너별 `client_id` + scope로 권한 분리 |

가장 자주 잘못 매칭되는 케이스 두 개를 짚으면 다음과 같습니다.

- **단일 도메인 자체 로그인에 JWT (stateless) 도입**: 세션이 충분한데 토큰 폐기 어려움·갱신 복잡성·XSS 시 영구 탈취 위험을 떠안음
- **내부 서비스 호출에 사용자 OAuth 토큰 전달**: 서비스 호출의 신원이 사용자가 되어야 할지 서비스가 되어야 할지가 섞임. 일반적으로 사용자 토큰은 끝단까지 전달하지 말고, 내부 hop은 서비스 자격 증명을 따로 둠

### 자체 세션과 OIDC

"우리 사이트에 회원가입·로그인이 있다"는 단순한 요건에서 OIDC를 도입할 이유는 사실 거의 없습니다. 그런데도 도입을 고민하게 되는 이유는 보통 <E>나중에 SSO 확장할 수도 있으니까</E> 같은 가정 때문입니다. 이 가정은 비용이 큽니다.

| 항목 | 자체 세션 | OIDC (자체 OP 운영) |
|---|---|---|
| 구현 복잡도 | 세션 쿠키 + CSRF 방어 | OP 서버 운영 + JWKS 키 관리 + Discovery 문서 |
| 토큰 폐기 | 세션 즉시 무효화 | ID Token은 만료까지 유효 (블랙리스트 별도) |
| 갱신 흐름 | 자동 (쿠키 갱신) | Refresh Token 흐름 별도 구현 |
| 멀티 디바이스 로그아웃 | 세션 테이블에서 삭제 | 토큰 폐기 메커니즘 별도 |
| 외부 통합 가능성 | 추가 작업 필요 | 처음부터 표준 준수 |

자체 운영하는 OP는 **인증 인프라 자체가 새로운 운영 책임**입니다. 키 회전, 키 누출 대응, 표준 변경 추적, 라이브러리 업데이트가 모두 새로 생깁니다. 이 비용을 감당할 만한 명확한 이유 (여러 도메인 SSO, 외부 클라이언트에 우리가 OP 역할)가 없다면 자체 세션이 단순합니다.

기준 한 줄: <E>OIDC를 쓰는 다른 시스템이 우리 인증을 신뢰해야 하는가</E> 가 Yes면 OIDC, 그게 아니면 자체 세션.

### 잊기 쉬운 비용

OAuth든 OIDC든 도입했을 때 따라오는 운영 부담을 자주 잊습니다. 미리 인지하면 결정의 균형이 맞습니다.

- **토큰 저장 위치 결정**: 브라우저는 `localStorage` (XSS에 취약) vs `httpOnly` 쿠키 (CSRF 대응 필요) 둘 다 트레이드오프
- **만료 처리 UX**: Access Token이 갑자기 만료될 때 사용자 흐름이 끊기지 않게 무중단 갱신 구현 필요
- **Refresh Token 회전 (rotation)**: 리프레시 토큰 자체가 탈취되면 무한 갱신 가능. 사용 시마다 새 Refresh Token 발급 + 재사용 감지 필요
- **로그아웃의 진짜 의미**: OIDC에서 로그아웃은 우리 앱 세션 종료 + OP 세션 종료(End Session Endpoint) + ID Token 폐기를 모두 고려해야 일관됨
- **Scope 설계**: 너무 넓으면 동의 거부율 증가, 너무 좁으면 필요할 때마다 재인증
- **클럭 스큐 (clock skew)**: 서버와 클라이언트 시계가 어긋나면 `exp` 검증이 잘못 실패함. 보통 1~5분 허용 폭을 둠

## 마무리

OAuth와 OIDC는 자주 함께 등장하지만 푸는 문제가 다릅니다. OAuth는 비밀번호를 넘기지 않고 다른 서비스의 데이터에 접근할 권한을 위임하는 표준이고, OIDC는 그 위에 "이 토큰의 주인이 누구인지"를 증명하는 자체 검증 가능한 신분증(ID Token)을 추가한 인증 표준입니다.

선택의 기준은 단순합니다. 외부 서비스 데이터가 필요 없으면 자체 세션이 1순위, 외부 서비스 데이터만 쓰면 OAuth, 거기에 사용자 신원까지 알아야 하면 OIDC. 토큰 3종 (Access·ID·Refresh)이 각각 받는 사람과 답하는 질문이 다르다는 점만 잊지 않으면 대부분의 혼란이 자연스럽게 풀립니다.
