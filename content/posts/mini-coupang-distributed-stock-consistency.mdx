어떤 인기 많은 상품의 재고가 100개 있을 때 동시에 150명이 주문 요청을 한다면 <E>정확히 100개의 주문만 만들어져야 하며 50명은 실패</E>해야 합니다. 또한 결제를 실패한 인원이 있다면 <E>안전하게 재고를 롤백</E>할 수 있어야 합니다. 이 글은 대규모 트래픽과 동시성이 높은 환경에서 주문 서비스의 재고를 <E>원자적으로 선점하고 안전하게 해제</E>하기 위해 미니쿠팡에서 했던 고민과 소스코드를 공유하려고 합니다. 결제는 평균 10초 걸린다고 가정합니다 (실제 결제 서비스 로직이 없어 stub에서 `Thread.sleep(5–15초 사이 랜덤)`으로 대체).

- 옵션의 초기 재고는 100개라고 가정합니다.
- 같은 옵션에 동시에 도착하는 주문 요청 수가 재고 수를 초과한다고 가정합니다 (예: 재고 100, 동시 주문 150).
- 정합성 조건: 성공한 주문 수가 초기 재고를 넘지 않고, 결제가 실패한 주문은 재고를 원복합니다.

## 요구사항과 제약

### 기능 요구

- 회원이 옵션 ID와 수량으로 단건 주문을 생성한다.
- 주문 처리는 옵션 조회, 재고 선점, 결제, 주문 영속화 순으로 진행한다.
- 결제 성공 시 MySQL 재고를 영구 차감하고 알림을 발행한다.
- 결제 실패 시 선점한 재고를 원복하고 주문은 영속화하지 않는다.

### 평시 SLO (가설)

| 메트릭 | 목표 | 출처 |
|---|---|---|
| `POST /api/orders` p95 | ≤ 16s | 가설. 결제 stub `Thread.sleep(5–15초 랜덤, 평균 10초)` + 오케스트레이션 1초 안팎 |
| 재고 conservation 위반 | 0건 | 통합 테스트 (`PlaceOrderTest`, `PlaceOrderPaymentFailedTest`) |

### 트래픽 시나리오 가정

| 상황 | 트래픽 패턴 |
|---|---|
| 평시 | 옵션별 분산. 같은 옵션 동시 주문 1~5명 수준 |

## 아키텍처 결정

미니쿠팡의 주문은 다섯 개의 서비스를 거치며 정합성 책임을 나눠 가집니다. 주문 서비스는 오케스트레이션을 맡고, 상품 서비스가 재고의 단일 소유자입니다. 결제 서비스는 외부 시스템처럼 분리되어 있고 (현재는 stub), 회원 서비스는 인증을, 알림 서비스는 후처리를 맡습니다.

이 구조에는 네 가지 결정이 있습니다.

1. **재고는 상품 서비스가 단독으로 소유한다.** 주문 서비스는 재고 행을 직접 만지지 않고 Feign 호출로 상품 서비스에 위임합니다. 두 서비스가 같은 행을 만지면 사고 책임이 모호해지고, 락 전략을 두 곳에 걸쳐 맞춰야 합니다. <E>재고의 단일 소유자</E>라는 원칙이 이후 모든 결정의 출발점입니다.
2. **결제 호출은 DB 트랜잭션 밖에서 한다.** 결제가 평균 10초 걸리는데, 트랜잭션 안에 두면 그 시간만큼 행 락과 DB 커넥션이 묶입니다.
3. **재고 차감은 Redis Lua, 영구 차감은 Kafka로.** 동시성은 Redis 단일 스레드가, 수렴은 Kafka가 책임집니다. 둘 다 트랜잭션 밖이라 락이 필요 없습니다.
4. **결제 실패는 보상 이벤트로 흘려보낸다.** 주문 서비스가 실패 시점에 `order.payment-failed`를 발행하면 상품 서비스가 받아 Redis 재고를 풉니다. 책임은 한 곳에 모입니다.

## 재고 차감을 락이 아니라 Redis Lua로

### 왜 락이 아닌가

비관적 락이나 낙관적 락으로도 동시성은 막을 수 있습니다. 그런데 미니쿠팡 흐름에서는 결제 호출이 트랜잭션 안에 들어오는 순간, <E>락 보유 시간이 결제 응답 시간과 똑같아</E>집니다. 같은 옵션을 150명이 동시에 주문하면 첫 사람이 결제하는 평균 10초 동안 나머지 149명은 행 락을 기다리며 대기합니다. 처리량이 결제 응답 시간으로 묶이고, 이 사이 DB 커넥션 풀까지 빠르게 고갈됩니다.

차감 시점을 결제보다 앞으로 당기고, 차감 동작 자체를 락 없이 원자적으로 처리할 수 있다면 이 결합이 풀립니다. Redis는 단일 스레드로 명령을 처리하고, EVAL로 묶인 여러 명령은 그 사이에 다른 클라이언트가 끼어들 수 없습니다.

### 어떻게 구현했나

`ProductStockRedisRepository`가 두 개의 Lua 스크립트를 보관합니다. `reserveStock`은 GET, 검사, DECRBY를 한 명령에 묶고, `releaseStock`은 보상용 INCRBY만 수행합니다.

```java title="ProductStockRedisRepository.java"
private static final DefaultRedisScript<Long> RESERVE_STOCK_SCRIPT = new DefaultRedisScript<>("""
        local current = redis.call('GET', KEYS[1])
        if current == false then return -1 end
        if tonumber(current) < tonumber(ARGV[1]) then return -2 end
        return redis.call('DECRBY', KEYS[1], ARGV[1])
        """, Long.class);                                                              // [!code highlight]

private static final DefaultRedisScript<Long> RELEASE_STOCK_SCRIPT = new DefaultRedisScript<>("""
        local current = redis.call('GET', KEYS[1])
        if current == false then return -1 end
        return redis.call('INCRBY', KEYS[1], ARGV[1])
        """, Long.class);

public long reserveStock(long optionId, long quantity) {
    return redisTemplate.execute(
        RESERVE_STOCK_SCRIPT, List.of(buildKey(optionId)), String.valueOf(quantity));
}
```

반환값 세 가지로 호출 측이 분기합니다. `-1`은 키 없음 (`STOCK_NOT_FOUND`), `-2`는 재고 부족 (`INSUFFICIENT_AMOUNT`), `0` 이상은 차감 후 남은 수량입니다.

### 무엇을 해결했나

같은 옵션에 150명이 동시에 들어와도 Redis 단일 스레드 큐에서 150개의 EVAL이 순서대로 실행됩니다. 100번째까지는 DECRBY가 성공하고 101번째부터 `-2`가 반환됩니다. <E>락 없이 lost update 0건</E>이고, 한 사용자의 차감이 다음 사용자의 차감을 막지 않습니다 (대기 시간은 Redis EVAL 한 번, 0.5ms 안팎).

## 결제 호출은 트랜잭션 밖

### 왜 트랜잭션 밖인가

`@Transactional`이 결제 호출을 감싸고 있으면 결제가 끝나야 커밋이 되고, 그 사이 DB 커넥션과 행 락이 함께 점유됩니다. HikariCP 기본 풀 크기 10에서 100명이 들어오면 10명이 결제하는 동안 90명이 커넥션을 기다리고, 그동안 다른 API의 응답도 같이 멈춥니다.

재고 차감을 Redis로 옮긴 뒤에는 트랜잭션을 결제 전후로 잘라낼 수 있습니다. 옵션 조회는 짧은 읽기 한 번, 주문 영속화는 결제 성공 시점에만 한 번. 그 사이 결제 호출은 어느 트랜잭션에도 속하지 않습니다.

### 어떻게 구현했나

`OrderFacade.placeOrder`가 단계를 직접 조립합니다. 옵션 스냅샷 조회, Redis 재고 선점, 결제 호출이 모두 트랜잭션 밖에서 일어나고, `OrderService.persistOrder`만 `@Transactional`이 붙어 있습니다.

```java title="OrderFacade.java"
public PlaceOrderResult placeOrder(PlaceOrderCommand command) {
    OptionSnapshot snapshot = productOptionPort.findOption(command.optionId());     // [!code highlight]
    ensurePurchasable(snapshot);

    StockReserveOutcome reserved = stockReservePort.reserve(                        // [!code highlight]
        new StockReserveRequest(command.optionId(), command.quantity()));
    if (!reserved.reserved()) throw mapReserveFailure(reserved.reason());

    long totalAmount = snapshot.unitPrice() * command.quantity();
    String orderRef = UUID.randomUUID().toString();
    PaymentChargeOutcome outcome = paymentChargePort.charge(                        // [!code highlight]
        new PaymentChargeRequest(orderRef, totalAmount, command.simulateFailure()));

    if (!outcome.paid()) {
        orderPaymentFailedPublisher.publish(new OrderPaymentFailedEvent(
            command.memberId(), command.optionId(), command.quantity(), outcome.reason()));
        throw new BusinessException(ErrorCode.PAYMENT_FAILED);
    }

    return orderService.persistOrder(                                               // [!code highlight]
        command.memberId(), snapshot, command.quantity(), outcome.paymentId());
}
```

### 무엇을 해결했나

결제가 10초 걸리든 30초 걸리든 그 시간 동안 어떤 행 락도, 어떤 DB 커넥션도 점유되지 않습니다. 결제 응답이 늦어지는 것은 <E>그 한 사용자의 응답 시간이 늘어나는 효과로 그칠 뿐, 다른 주문의 처리량에 영향을 주지 않습니다</E>. 같은 옵션에 150명이 동시에 들어와도 150명 분의 Redis 차감은 거의 동시에 끝나고 (재고 100개분만 성공, 50명은 즉시 `INSUFFICIENT_AMOUNT` 응답), 성공한 100명의 결제만 각자 자기 시간을 보냅니다.

## 영구 차감과 보상은 Kafka 비동기

### 왜 비동기인가

결제 성공 시 MySQL 재고를 영구 차감하고, 결제 실패 시 Redis 재고를 원복해야 합니다. 두 작업 다 상품 서비스가 책임집니다. 주문 서비스가 직접 상품 서비스의 MySQL 행을 UPDATE 하거나 Redis를 INCRBY 해버리면, 재고의 단일 소유자라는 원칙이 무너집니다.

또 알림 서비스도 같은 이벤트가 필요합니다. 주문 확정 알림은 결제 성공 시, 결제 실패 알림은 결제 실패 시 보내야 합니다. 같은 사실을 두 컨슈머가 받아야 하므로 점-대-점 호출보다 토픽이 적합합니다.

### 어떻게 구현했나

주문 서비스는 영속화 트랜잭션 안에서 `ApplicationEventPublisher`로 도메인 이벤트를 던지고, `@TransactionalEventListener(AFTER_COMMIT)`이 받아서 Kafka로 발행합니다. 트랜잭션이 롤백되면 메시지도 나가지 않으므로 phantom 차감을 막습니다.

```java title="OrderConfirmedEventHandler.java"
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)                  // [!code highlight]
public void handle(OrderConfirmedEvent event) {
    Long orderId = event.getPayload().orderId();
    kafkaProducer.sendMessage(
        EventTopic.ORDER_CONFIRMED.getName(),
        String.valueOf(orderId),
        jsonConverter.toJson(event),
        () -> log.error("order.confirmed publish failed. orderId={}", orderId));
}
```

상품 서비스는 두 토픽을 같은 컨슈머에서 받아 헤더로 라우팅합니다.

```java title="OrderEventConsumer.java"
@RetryableTopic(backoff = @Backoff(delay = 1000, multiplier = 2.0), ...)
@KafkaListener(topics = {
    "#{T(...EventTopic).ORDER_CONFIRMED.getName()}",
    "#{T(...EventTopic).ORDER_PAYMENT_FAILED.getName()}"
})
public void consume(String message, @Header(RECEIVED_TOPIC) String topic) {
    long eventId = 0L;
    try {
        EventMessage eventMessage = jsonConverter.fromJson(message, EventMessage.class);
        eventId = eventMessage.eventId();
        if (EventTopic.ORDER_CONFIRMED.getName().equals(topic)) {
            processor.processOrderConfirmed(eventId, ...);                          // [!code highlight]
        } else if (EventTopic.ORDER_PAYMENT_FAILED.getName().equals(topic)) {
            processor.processPaymentFailed(eventId, ...);                           // [!code highlight]
        }
    } catch (DataIntegrityViolationException e) {
        log.info("Duplicate event skipped. eventId={}, topic={}", eventId, topic);
    }
}
```

### 무엇을 해결했나

주문 서비스의 응답은 Kafka 발행을 기다리지 않습니다. AFTER_COMMIT은 발행 실패와 무관하게 메서드 외부에서 비동기로 처리되므로, 사용자가 받는 응답은 주문 영속화가 끝난 시점에 결정됩니다. 알림 서비스의 처리 속도가 늦어져도 주문 응답은 영향받지 않고, 알림이 일시적으로 끊겨도 재고 정합성과 무관하게 흘러갑니다. Outbox 패턴이 도입되지 않았으므로 commit과 발행 사이에 프로세스가 죽으면 메시지가 누락될 수 있는데, 이 부분은 마지막 섹션에서 다시 짚습니다.

## 멱등성과 마지막 안전망

### 왜 멱등성이 필요한가

Kafka는 at-least-once 전달입니다. 같은 메시지가 두 번 들어올 수 있고, 컨슈머가 처리 중 죽으면 재시작 후 같은 offset에서 다시 받습니다. `order.confirmed`가 두 번 들어왔는데 그때마다 MySQL UPDATE를 한다면 재고가 두 번 차감됩니다. 같은 메시지가 같은 결과로 수렴해야 하는 이유입니다.

### 어떻게 구현했나

`processed_events` 테이블에 `(event_id, event_type)` UNIQUE 제약을 걸고, 컨슈머가 본 처리 직전에 INSERT 합니다. 같은 이벤트가 두 번 오면 두 번째 INSERT가 `DataIntegrityViolationException`으로 실패하고, 컨슈머가 catch 하여 처리를 스킵합니다.

```java title="OrderEventProcessor.java"
@Transactional
public void processOrderConfirmed(long eventId, OrderConfirmedPayload payload) {
    processedEventRepository.save(ProcessedEvent.of(eventId, "ORDER_CONFIRMED"));    // [!code highlight]
    int updated = optionStockRepository.decreaseQuantityIfEnough(                    // [!code highlight]
        payload.optionId(), payload.quantity());
    if (updated == 0) {
        log.error("MySQL 재고 영구 차감 실패. orderId={}, optionId={}, quantity={}",
            payload.orderId(), payload.optionId(), payload.quantity());
    }
}
```

`decreaseQuantityIfEnough`는 `UPDATE option_stock SET quantity = quantity - :qty WHERE option_id = :id AND quantity >= :qty` 형태입니다. WHERE 조건이 <E>마지막 안전망</E>입니다. Redis 차감과 MySQL 영구 차감 사이에 어떤 사고가 끼어들어도, MySQL 행에 남은 수량보다 차감 요청이 크면 UPDATE는 0행을 만들고 로그만 남기고 끝납니다.

<Callout type="error" title="핵심 통찰: 락이 아니라 책임 분리로 정합성을 만든다">
재고 정합성의 책임을 한 곳에 모으지 않고 세 갈래로 나눴습니다. 동시성은 Redis 단일 스레드의 EVAL이, 영구 차감은 멱등 컨슈머가, 결제 실패 복구는 Saga 보상 이벤트가 책임집니다. 어떤 단계도 락을 길게 잡지 않고, 외부 호출이 처리량을 묶지 않습니다.
</Callout>

### 무엇을 해결했나

컨슈머가 재시작되거나 Kafka가 재전송해도 차감이 한 번만 일어납니다. WHERE 조건은 가능성이 거의 없는 Redis-MySQL 격차 상황까지 흡수합니다. 두 장치가 겹쳐 있어 단일 장애 지점이 아닌 한 정합성이 깨지지 않습니다.

## 결제 실패 보상

### 왜 보상이 필요한가

Redis 차감은 결제 호출 전에 일어납니다. 결제가 실패하면 MySQL은 아무 변화가 없지만 Redis 재고는 이미 줄어 있습니다. 그대로 두면 다음 사용자가 잘못된 잔여 재고를 보게 됩니다.

### 어떻게 구현했나

주문 서비스는 결제 실패 시 주문을 영속화하지 않고 `order.payment-failed`만 발행합니다. 상품 서비스가 받아서 `releaseStock`을 호출하면 INCRBY로 원복합니다.

```java title="OrderEventProcessor.java"
@Transactional
public void processPaymentFailed(long eventId, OrderPaymentFailedPayload payload) {
    processedEventRepository.save(ProcessedEvent.of(eventId, "ORDER_PAYMENT_FAILED"));
    long remaining = productStockRedisRepository.releaseStock(                       // [!code highlight]
        payload.optionId(), payload.quantity());
    if (remaining == -1) {
        log.error("Redis 재고 복구 실패: 키 없음. optionId={}, quantity={}, reason={}",
            payload.optionId(), payload.quantity(), payload.reason());
    }
}
```

### 무엇을 해결했나

결제 실패는 <E>정합성을 깨지 않고 흡수</E>됩니다. Redis는 다음 사용자가 보기 전에 원복되고, MySQL은 애초에 변경되지 않았으므로 두 저장소가 같은 상태로 남습니다. 보상 이벤트가 도착할 때까지 짧은 lag (수십 ms 부터 수 초) 동안에는 다른 사용자에게 일시적 `INSUFFICIENT_AMOUNT`가 보일 수 있고, 이는 UX 재시도로 흡수됩니다.

## 측정과 검증

통합 테스트 모듈이 다섯 서비스 + Kafka + Redis + MySQL을 모두 띄운 상태에서 네 가지 시나리오를 돌립니다. `IntegrationTest` 베이스에서 BDD 형식으로 작성되어 있고, 결과는 Redis·MySQL·`orders` 테이블 세 곳을 모두 검증합니다.

| 시나리오 | 동시 사용자 | 기대 결과 | 실측 |
|---|---|---|---|
| 재고 100, 50명 주문 | 50 | 성공 50, Redis 50, MySQL 50 | **일치** |
| 재고 100, 100명 주문 | 100 | 성공 100, Redis 0, MySQL 0 | **일치** |
| 재고 100, 101명 주문 | 101 | 성공 100, 부족 1, Redis 0, MySQL 0 | **일치** |
| 재고 100, 1명 결제 실패 | 1 | 주문 0, Redis 100 (보상), MySQL 100 | **일치** |

```java title="PlaceOrderTest.java"
@Test
@DisplayName("재고 100, 101명 주문 → 100건 성공 + 1건 재고 부족, 재고 0")
void place101_100Success_1Insufficient_stock0() throws Exception {
    OrderScenario.Prepared prepared = scenario.prepare(101);
    OrderResult result = fireConcurrent(prepared, 101);

    assertThat(result.success()).as("성공 주문 수").isEqualTo(100);                  // [!code highlight]
    assertThat(result.insufficient()).as("재고 부족 1건").isEqualTo(1);              // [!code highlight]

    assertThat(scenario.redisStock(prepared.optionId())).isEqualTo(0L);
    awaitMysqlOptionStock(prepared.optionId(), 0L);
    assertThat(scenario.ordersCount()).isEqualTo(100L);
}
```

검증된 것은 세 가지입니다.

- 같은 옵션에 동시 101명이 들어와도 락 없이 <E>정확히 100건만 성공</E>합니다.
- MySQL 재고가 Kafka consumer를 거쳐 <E>Redis와 같은 값으로 수렴</E>합니다.
- 결제 실패 시 주문은 영속화되지 않고 <E>Redis만 보상 이벤트로 원복</E>됩니다.

별도 k6 부하 측정은 아직 수행하지 않았습니다. 통합 테스트가 정합성 조건을 닫아주는 단계까지가 이 글의 범위입니다.

## 남은 한계와 다음 단계

이 구현으로 닫지 못한 한계 세 가지입니다.

| 한계 | 무엇이 부족한가 | 다음 단계 |
|---|---|---|
| Outbox 미도입 | 주문 영속화 commit과 Kafka 발행 사이에 프로세스가 죽으면 `order.confirmed`가 누락될 수 있음. MySQL은 차감되지 않은 채로 남고 사용자만 주문 성공 응답을 받음 | Outbox 테이블 + relay로 최소 한 번 보장 |
| Redis 단일 노드 | 동시성의 1차 책임이 Redis 한 인스턴스에 있어 Redis 장애 시 전체 차감이 멈춤. 클럭 스큐, 메모리 압박 등도 단일 실패 지점 | Redis 클러스터 또는 Sentinel + replica |
| 부하 측정 미수행 | 통합 테스트는 정합성만 검증. p95, 처리량, 커넥션 풀 한계는 아직 데이터로 닫지 못함 | k6 부하 시나리오 + Grafana 대시보드 |

다음 글에서는 Outbox + Kafka + 멱등 컨슈머의 조합으로 발행 누락을 닫고, k6 부하 측정으로 처리량 한계를 정량으로 보여줄 계획입니다.
