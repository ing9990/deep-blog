이 글은 Kafka 클러스터를 띄울 때 Broker 가 받는 환경 변수, Producer 가 `send` 하기 전에 설정하는 옵션, Consumer 가 그룹에 참여하며 설정하는 옵션을 한 자리에 정리합니다. 각 항목은 무엇이고, 어떤 값을 받을 수 있고, 그 값이 어떻게 동작에 반영되는지를 짧게 따라갑니다.

## Broker 설정

Broker 는 컨테이너 환경에서 `KAFKA_` 접두사로 시작하는 환경 변수로 설정합니다. 같은 키를 `server.properties` 안에 직접 쓸 때는 소문자 점 표기(`node.id`, `process.roles` ...)를 씁니다. Kafka 2.8+ 부터는 KRaft 모드가 ZooKeeper 를 대체했고, 3.3+ 부터는 운영에서도 권장됩니다.

### KRaft 클러스터 식별

#### `KAFKA_NODE_ID`

브로커(또는 컨트롤러) 노드의 정수 식별자. 클러스터 안에서 유일해야 하며 같은 노드가 재시작해도 ID 가 유지되어야 합니다. 단일 노드면 `1`, 3노드 클러스터면 보통 `1`, `2`, `3` 으로 부여합니다.

#### `KAFKA_PROCESS_ROLES`

이 프로세스가 어떤 역할을 맡는지 KRaft 에 알려주는 값. 콤마로 여러 역할을 묶을 수 있습니다.

| 값 | 동작 |
|---|---|
| `broker` | 토픽 데이터(파티션, 로그)를 저장·서빙. 메타데이터는 컨트롤러에서 받음 |
| `controller` | 클러스터 메타데이터(토픽·파티션 목록, 리더 선출)만 관리. 토픽 데이터는 다루지 않음 |
| `broker,controller` | 한 프로세스가 둘 다 수행. 개발용 단일 노드에서 흔히 사용 |

#### `KAFKA_CONTROLLER_QUORUM_VOTERS`

KRaft 컨트롤러 쿼럼에 참여하는 모든 노드를 `<id>@<host>:<port>` 형식으로 나열합니다. 콤마로 구분하며 모든 `controller` 노드의 정보가 들어가야 합니다. 예: `1@kafka1:9093,2@kafka2:9093,3@kafka3:9093`. 단일 노드면 자기 자신만 적습니다.

#### `CLUSTER_ID`

클러스터 전체를 식별하는 22자 base64 문자열. 첫 기동 시 이 값으로 메타데이터 로그가 포맷되며, 재기동 시 다른 값으로 바꾸면 메타데이터가 일치하지 않아 부팅이 거부됩니다. 운영에서는 `kafka-storage random-uuid` 명령으로 한 번 생성한 뒤 그 값을 고정합니다.

### Listener 구성

Listener 는 브로커가 연 TCP 포트와 그 포트의 용도(클라이언트용 / 브로커 간 통신용 / 컨트롤러 통신용)를 정의합니다. 보통 클라이언트용·내부용·컨트롤러용으로 나누어 세 개 이상을 띄웁니다.

#### `KAFKA_LISTENERS`

브로커가 실제로 바인딩하는 주소·포트. `<name>://<host>:<port>` 를 콤마로 나열합니다. `0.0.0.0` 은 모든 네트워크 인터페이스에서 수신한다는 뜻입니다. 예: `PLAINTEXT://0.0.0.0:9092,CONTROLLER://0.0.0.0:9093,EXTERNAL://0.0.0.0:29092`.

#### `KAFKA_ADVERTISED_LISTENERS`

클라이언트에게 알려줄 접속 주소. 클라이언트는 처음 `bootstrap.servers` 로 임의 브로커에 연결한 뒤, 응답으로 받은 `ADVERTISED_LISTENERS` 의 주소로 다시 접속합니다. 도커 네트워크 안의 다른 컨테이너와 호스트에서 직접 띄운 클라이언트가 모두 같은 브로커에 붙어야 한다면 두 주소(`kafka:9092`, `localhost:29092`)를 listener 두 개로 분리해 광고합니다.

#### `KAFKA_LISTENER_SECURITY_PROTOCOL_MAP`

listener 이름과 보안 프로토콜을 매핑합니다.

| 프로토콜 | 동작 |
|---|---|
| `PLAINTEXT` | 평문 TCP. dev 전용 |
| `SSL` | TLS 암호화. 클라이언트 인증서 검증은 옵션 |
| `SASL_PLAINTEXT` | SASL 인증 + 평문 |
| `SASL_SSL` | SASL 인증 + TLS 암호화. 운영 표준 |

운영에서는 `EXTERNAL:SASL_SSL,INTERNAL:PLAINTEXT` 처럼 외부 트래픽에만 TLS+SASL 을 거는 구성이 흔합니다.

#### `KAFKA_INTER_BROKER_LISTENER_NAME`

브로커끼리 데이터를 주고받을 때 사용할 listener 이름. 브로커 간 트래픽을 외부와 분리해 내부 전용 listener 로 흘릴 수 있습니다.

#### `KAFKA_CONTROLLER_LISTENER_NAMES`

KRaft 컨트롤러 트래픽 전용 listener 이름. `KAFKA_PROCESS_ROLES` 에 `controller` 가 포함되면 필수입니다.

### 토픽 기본값

#### `KAFKA_NUM_PARTITIONS`

`auto.create.topics.enable=true` 상태에서 클라이언트가 존재하지 않는 토픽에 `send` 하면 토픽이 자동 생성됩니다. 그때 부여되는 기본 파티션 수.

#### `KAFKA_DEFAULT_REPLICATION_FACTOR`

같은 자동 생성 시점에 부여되는 기본 replication factor. 단일 노드 dev 에서는 `1`, 운영에서는 `3` 이 표준입니다.

#### `KAFKA_AUTO_CREATE_TOPICS_ENABLE`

존재하지 않는 토픽으로 `send` 또는 `poll` 호출이 들어왔을 때 동작.

| 값 | 동작 |
|---|---|
| `true` | 위 두 기본값으로 토픽이 자동 생성됨 |
| `false` | 정의되지 않은 토픽 접근 시 `UNKNOWN_TOPIC_OR_PARTITION` 오류. 토픽은 명시적으로 미리 생성해야 함 |

### 내부 토픽과 정합성

#### `KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR`

컨슈머 그룹의 오프셋이 저장되는 내부 토픽 `__consumer_offsets` 의 replication factor. 이 토픽이 유실되면 모든 컨슈머가 중복·누락 처리에 노출되므로 운영에서는 `3` 이 표준입니다.

#### `KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR`

트랜잭션 상태를 저장하는 내부 토픽 `__transaction_state` 의 replication factor. Producer 트랜잭션 사용 시 의미 있는 값이며, dev 단일 노드에서는 `1`.

#### `KAFKA_TRANSACTION_STATE_LOG_MIN_ISR`

같은 토픽의 `min.insync.replicas`. 트랜잭션 코디네이터가 상태 변경을 commit 하려면 이 수만큼의 replica 가 ISR 에 있어야 합니다.

#### `min.insync.replicas`

브로커 또는 토픽 수준 설정으로, `acks=all` 과 짝을 이룹니다. Producer 가 보낸 메시지가 ack 를 받으려면 ISR 에 들어 있는 replica 수가 이 값 이상이어야 합니다.

| 설정 | 동작 |
|---|---|
| `min.insync.replicas=1` | ISR 에 replica 1개만 있으면 ack |
| `min.insync.replicas=2` (RF=3 권장 조합) | 2개 이상 동기화된 상태에서만 쓰기 허용 |
| `min.insync.replicas` 미달 시 | Producer 가 `NotEnoughReplicasException` 을 받음 |

## Producer 설정

Producer 는 Kafka Java 클라이언트의 `ProducerConfig` 키로 설정하며, Spring Kafka 에서는 `spring.kafka.producer.*` 또는 `spring.kafka.producer.properties.*` 로 주입합니다.

### 연결과 직렬화

#### `bootstrap.servers`

Producer 가 처음 클러스터에 접속할 때 시도하는 브로커 목록. 콤마로 여러 개 나열할 수 있고, 한 노드가 죽어 있어도 다른 노드에서 메타데이터를 받아 옵니다. 이후 실제 `send` 는 `ADVERTISED_LISTENERS` 가 알려준 주소로 이루어집니다.

#### `key.serializer` / `value.serializer`

Producer 가 record 의 key 와 value 를 바이트 배열로 변환할 때 사용할 클래스 FQCN.

| 시리얼라이저 | 입력 타입 |
|---|---|
| `StringSerializer` | `String` (UTF-8) |
| `IntegerSerializer` / `LongSerializer` | `Integer` / `Long` |
| `ByteArraySerializer` | `byte[]` |
| `JsonSerializer` (Spring Kafka) | 임의 객체 → JSON |
| `KafkaAvroSerializer` (Confluent) | Avro 객체, schema registry 연동 |

### 보장 수준

#### `acks`

Producer 가 `send` 한 record 가 <E>성공</E>으로 간주되려면 브로커가 어디까지 확인해야 하는지를 결정합니다.

| 값 | 동작 |
|---|---|
| `0` | 브로커 응답을 기다리지 않고 즉시 성공으로 처리. 네트워크 패킷이 사라져도 알 수 없음 |
| `1` | 리더 replica 에만 쓰면 성공. 리더가 디스크에 기록한 직후 죽으면 데이터 유실 가능 |
| `all` (= `-1`) | ISR 에 있는 모든 replica 에 복제된 뒤 성공. `min.insync.replicas` 와 짝을 이루어 무손실 보장 |

결제·주문 같은 정합성이 중요한 이벤트에서는 `all` 이 권장됩니다.

#### `retries`

일시적 실패(`NotEnoughReplicasException`, `LeaderNotAvailableException` 등)를 만났을 때 클라이언트가 자동 재전송할 횟수.

| 값 | 동작 |
|---|---|
| `0` | 재시도 없음. 첫 실패가 곧 최종 실패 |
| `1` ~ `Integer.MAX_VALUE` | 그 횟수만큼 자동 재전송 |
| 기본값 (Kafka 3.0+) | `Integer.MAX_VALUE`. 실제 한계는 `delivery.timeout.ms` 가 결정 |

재시도는 `retry.backoff.ms` 만큼 대기 후 재시도하며, 누적 시간이 `delivery.timeout.ms`(기본 120000ms) 를 넘으면 그대로 실패 처리됩니다.

#### `enable.idempotence`

Producer 가 같은 메시지를 두 번 발송하더라도 브로커가 한 번만 기록하게 만드는 토글.

| 값 | 동작 |
|---|---|
| `false` | 재시도 시 중복 메시지가 생길 수 있음. at-least-once |
| `true` (Kafka 3.0+ 기본) | Producer 별 PID 와 sequence number 로 브로커가 중복을 거부. 단일 파티션 단위 exactly-once 효과 |

`true` 를 설정하면 클라이언트가 자동으로 `acks=all`, `retries>0`, `max.in.flight.requests.per.connection<=5` 를 강제합니다. 이 조건을 위반하면 시작 시점에 오류로 거부됩니다.

#### `max.in.flight.requests.per.connection`

한 connection 위에서 ack 를 아직 받지 못한 채 동시에 in-flight 상태로 둘 수 있는 `send` 요청 수의 상한.

| 값 | 동작 |
|---|---|
| `1` | 한 번에 한 요청만. 재시도가 발생해도 메시지 순서가 절대 뒤바뀌지 않음 |
| `2` ~ `5` | 동시 발송으로 처리량 향상. `enable.idempotence=true` 와 함께 쓰면 순서 보장도 유지 |
| `6` 이상 | `enable.idempotence=true` 와 함께 쓸 수 없음. 재시도 시 메시지 순서가 뒤바뀔 수 있음 |

### 배치와 압축

#### `linger.ms`

Producer 가 `send` 호출 즉시 보내지 않고, 같은 파티션으로 가는 record 를 모아 한 batch 로 묶기까지 기다리는 시간(밀리초).

| 값 | 동작 |
|---|---|
| `0` (기본) | record 가 큐에 들어오는 즉시 발송. 지연 최소, batch 효율 최저 |
| `5` ~ `100` | 그 시간만큼 모아서 한 번에 발송. 처리량 향상, 지연 증가 |

#### `batch.size`

파티션 단위 batch 의 바이트 상한. 기본 `16384` (16KB). batch 가 이 크기를 채우면 `linger.ms` 와 무관하게 즉시 발송됩니다. record 한 건이 이 크기를 넘으면 batch 없이 단건으로 보냅니다.

#### `compression.type`

batch 단위로 적용할 압축 알고리즘.

| 값 | 동작 |
|---|---|
| `none` (기본) | 압축 없음 |
| `gzip` | 압축률 높음, CPU 비용 큼 |
| `snappy` | 균형형, CPU 비용 낮음 |
| `lz4` | 압축 속도 빠름 |
| `zstd` | Kafka 2.1+ 부터 지원. 높은 압축률과 빠른 속도 |

압축은 Producer 에서 한 번 수행되어 브로커는 압축된 그대로 저장하고, Consumer 가 내려받을 때 다시 풉니다.

## Consumer 설정

Consumer 는 Kafka Java 클라이언트의 `ConsumerConfig` 키로 설정하며, Spring Kafka 에서는 `spring.kafka.consumer.*` 로 주입합니다.

### 연결과 그룹 정체

#### `bootstrap.servers`

Producer 와 동일한 의미. 처음 메타데이터를 받기 위한 진입점.

#### `group.id`

Consumer Group 식별자. 같은 `group.id` 를 공유하는 Consumer 들끼리 파티션을 분배합니다.

| 시나리오 | 동작 |
|---|---|
| group A 의 Consumer 1대 | 토픽의 모든 파티션을 혼자 소비 |
| group A 의 Consumer N대 (파티션 ≥ N) | 파티션을 N 등분해 분배. rebalance 발생 시 재분배 |
| group A, group B (서로 다른 `group.id`) | 같은 토픽을 각자 독립적으로 소비. 같은 record 가 두 그룹에 모두 전달됨 |

같은 서비스의 인스턴스가 여러 대 떠도 같은 `group.id` 를 공유하면, 한 메시지는 인스턴스 중 한 곳에서만 처리됩니다.

#### `key.deserializer` / `value.deserializer`

Producer 측 serializer 와 짝. 같은 클래스의 deserializer 를 사용해야 합니다 (`StringSerializer` ↔ `StringDeserializer`).

### 오프셋 시작점

#### `auto.offset.reset`

저장된 오프셋이 없는 상태(새 group 으로 가입했거나, 저장된 오프셋이 retention 으로 사라진 경우) Consumer 가 어디부터 읽기 시작할지 결정합니다.

| 값 | 동작 |
|---|---|
| `earliest` | 토픽에 남아있는 가장 오래된 오프셋부터 읽기 시작 |
| `latest` (기본) | 새 메시지(현재 시점 이후) 만 읽기. 이전 데이터는 건너뜀 |
| `none` | 오프셋이 없으면 `NoOffsetForPartitionException` 으로 시작 거부 |

이 옵션은 새로 가입할 때만 적용됩니다. 한 번이라도 오프셋이 commit 된 group 은 그 오프셋부터 이어 읽습니다.

### 오프셋 commit

#### `enable.auto.commit`

`poll()` 후 오프셋을 자동 commit 할지 여부.

| 값 | 동작 |
|---|---|
| `true` (기본) | `auto.commit.interval.ms` 주기로 백그라운드에서 자동 commit |
| `false` | 애플리케이션이 직접 commit. Spring Kafka 의 `AckMode` 가 이 영역을 제어 |

#### `auto.commit.interval.ms`

`enable.auto.commit=true` 일 때 자동 commit 주기. 기본 `5000` ms.

### 폴링 루프와 heartbeat

#### `max.poll.records`

한 번의 `poll()` 호출이 반환할 최대 record 수. 기본 `500`.

| 값 | 동작 |
|---|---|
| 작게 (예: `10`) | 한 처리 사이클이 짧아지고, rebalance 시 진행 손실이 작음 |
| 크게 (예: `2000`) | 처리량은 늘지만, 한 사이클에 다 처리하지 못하면 `max.poll.interval.ms` 위반 위험 |

#### `max.poll.interval.ms`

연속된 `poll()` 호출 사이의 최대 허용 간격. 기본 `300000` ms (5분). 이 시간 안에 다음 `poll()` 이 호출되지 않으면 그룹 코디네이터가 해당 컨슈머를 죽은 것으로 간주하고 rebalance 를 일으킵니다.

#### `session.timeout.ms`

heartbeat 가 끊긴 채 컨슈머가 살아있다고 판단되는 최대 시간. 기본 `45000` ms (Kafka 3.0+). 이 시간 안에 heartbeat 가 도착하지 않으면 group 에서 추방됩니다.

#### `heartbeat.interval.ms`

컨슈머가 그룹 코디네이터에게 heartbeat 를 보내는 주기. 기본 `3000` ms. `session.timeout.ms` 의 1/3 이하가 권장값입니다.

세 옵션의 관계는 다음과 같습니다.

- `heartbeat.interval.ms` 는 <E>살아 있다</E> 신호를 보내는 주기.
- `session.timeout.ms` 는 그 신호가 끊겼을 때 죽은 것으로 판단할 시간.
- `max.poll.interval.ms` 는 신호와 별개로, 사용자 코드가 너무 오래 처리만 하고 있을 때 죽은 것으로 판단할 시간.

heartbeat 는 백그라운드 스레드가 자동으로 보내므로 `session.timeout.ms` 위반은 보통 네트워크 단절이나 GC pause 때문이고, `max.poll.interval.ms` 위반은 처리 코드 자체가 느려서 발생합니다.

## 마무리

Broker 의 환경 변수, Producer 의 보장 수준, Consumer 의 그룹·오프셋·폴링 옵션을 한 자리에 두면 새 클러스터를 띄우거나 새 서비스를 붙일 때 기본값과 옵션별 동작을 빠르게 확인할 수 있습니다. 같은 키 이름이 환경 변수(`KAFKA_NODE_ID`)와 properties 파일(`node.id`) 사이에서 표기만 바뀌므로, 표기 규칙을 한 번 익혀 두면 문서를 오갈 때도 헤매지 않습니다.
