RAG는 LLM을 재학습하지 않고도 "가중치 안에 없는 지식"으로 답하게 만드는 패턴입니다. 여기서 핵심은 모델을 바꾸는 게 아니라, 답을 만들 때 참고할 자료를 매 요청마다 프롬프트에 주입하는 것입니다. 이 글에서는 이 단순한 아이디어가 어떻게 의미 검색을 벡터 공간의 기하학으로 환원하고, 어떤 트레이드오프를 만드는지 살펴봅니다.

<Note title="이 글의 학습 목표">
  - LLM이 가중치 안에 없는 지식을 답하는 원리를 이해한다
  - 의미 검색이 벡터 공간의 기하학으로 환원되는 방식을 구분할 수 있다
  - RAG와 Fine-tuning, Long-context 중 어느 것을 택할지 선택하는 기준을 얻는다
</Note>

## RAG란

**RAG(Retrieval-Augmented Generation)** 는 LLM이 답을 생성하기 전에 외부 지식 베이스에서 관련 문서를 검색(retrieval)해, 그 문서들을 프롬프트에 끼워 넣어(augmentation) 생성(generation)하게 하는 패턴입니다. 2020년 Meta AI 논문에서 제안된 뒤, 지금은 "LLM + 외부 데이터" 응용의 사실상 표준이 되었습니다.

핵심은 **LLM의 가중치를 전혀 건드리지 않는다**는 점입니다. 파라미터는 그대로 두고, 답을 만들 때 참고하는 자료만 매 요청마다 바꿔 공급합니다. LLM을 시험 보는 학생에 비유하면, RAG는 학생을 다시 훈련시키는 게 아니라 시험장에 관련 교재를 들고 들어가게 해주는 오픈북 시험에 가깝습니다.

구조적으로 RAG는 두 단계 파이프라인입니다.

1. **Indexing (오프라인)**: 문서를 잘게 쪼개(chunking) 각 조각을 숫자 벡터(embedding)로 변환해 벡터 DB에 저장
2. **Querying (온라인, 요청마다)**: 사용자 질문을 같은 방식으로 벡터화한 뒤, 벡터 DB에서 유사한 chunk를 top-k개 조회해 프롬프트에 붙여 LLM에 전달

기초 용어를 먼저 정리해둡니다.

| 용어 | 정의 |
|---|---|
| Embedding | 텍스트를 고정 차원의 실수 벡터(보통 768/1536/3072)로 변환하는 함수. 의미 유사 = 벡터 공간에서 방향 유사. |
| Vector DB | 벡터 간 유사도 기반 근사 최근접 이웃(ANN) 검색에 특화된 DB. `pgvector`, Pinecone, Weaviate, Qdrant, Milvus. |
| Chunk | 원본 문서를 쪼갠 단위. 보통 수백에서 천 토큰 수준. |
| Top-k retrieval | 질의 벡터와 가장 가까운 k개 chunk만 가져오기. 보통 3에서 10. |

## 왜 필요한가

RAG를 이해하려면 "LLM만 있으면 어떤 문제가 생기는가"를 먼저 봐야 합니다. 순수 LLM은 가중치 안에 들어있는 지식만 쓸 수 있고, 이 한 가지 제약에서 세 가지 문제가 파생됩니다.

### 1. Knowledge Cutoff

LLM은 학습이 끝난 시점(cutoff) 이후의 세상을 모릅니다. 2024년 1월까지 학습된 모델에게 "지난주 발표된 Next.js 16 신규 기능"을 물으면, 그 모델은 Next.js 16의 존재 자체를 모릅니다. 재학습에는 수억에서 수십억 원의 GPU 비용과 몇 주의 시간이 듭니다. 매일 바뀌는 사내 위키나 뉴스, 주가를 이 방식으로 따라갈 수는 없습니다.

### 2. Private / Domain Knowledge 부재

LLM은 공개 인터넷 데이터로 학습됩니다. 회사 내부 위키, 사내 코드베이스, 법무팀이 보관 중인 계약서 PDF, 특정 병원의 환자 기록 같은 비공개 데이터는 당연히 모릅니다. "우리 회사 휴가 규정이 뭐야?"라는 질문에 LLM은 일반론만 답할 뿐 실제 규정을 알 수 없습니다.

### 3. Hallucination

LLM은 "모른다"고 말하기보다 그럴듯한 거짓말을 지어내는 경향이 있습니다. 존재하지 않는 논문을 인용하고, 없는 API 함수를 호출하고, 날조된 법 조항을 답합니다. 이는 LLM이 확률적으로 다음 토큰을 예측하는 구조에서 파생되는 현상이지, 단순 버그가 아닙니다.

### RAG가 세 문제에 주는 해법

세 문제의 뿌리는 같습니다. **LLM은 자기 가중치 안에 든 지식만 쓸 수 있다**. RAG는 이 전제를 깨고 매 요청마다 외부 데이터를 프롬프트에 주입해 답변 근거를 바꿉니다.

- Knowledge cutoff → 벡터 DB의 문서를 업데이트만 하면 LLM 재학습 없이 최신 정보 반영
- Private 지식 부재 → 사내 문서를 인덱싱해두면 그대로 "우리 회사 지식" 질의 가능
- Hallucination → 프롬프트에 참고 문서를 명시해 "근거 문서 외 추측 금지" 지시를 곁들이면 환각이 크게 줄어듦 (완전 제거는 아님)

<Callout type="warning" title="RAG는 Fine-tuning의 일종이 아니다">
  RAG는 모델 가중치를 전혀 건드리지 않는 inference-time 기법입니다. Fine-tuning과는 **대안 관계**이며, 두 기법이 해결하는 문제가 다릅니다. 이 차이를 흐리면 설계 초기부터 잘못된 방향으로 갑니다.
</Callout>

## 동작 원리

<Callout type="warning" title="RAG의 내부 동작을 이해하는 핵심">
  RAG의 전체 구조는 세 가지 제약 위에 서 있습니다. Chunking이 만드는 "문맥 보존과 의미 해상도의 트레이드오프", 벡터 공간이 의미를 방향으로 부호화한다는 **기하학적 환원**, 그리고 ANN 검색이 요구하는 "recall · latency · memory"의 삼각 트레이드오프. 이 세 축을 잡고 나면 구조 전체가 자연스럽게 따라옵니다.
</Callout>

### Indexing 파이프라인

오프라인에서 한 번 수행하는 준비 단계입니다. 문서가 들어오면 Loading, Chunking, Embedding, Upsert 네 단계를 거칩니다.

<RagPipeline />

이 중 **Chunking**이 이 섹션의 핵심 결정 지점입니다. "문서를 통째로 임베딩하면 안 되나?"라는 질문이 자연스러운데, 두 가지 제약이 이를 막습니다.

첫째, 임베딩 모델의 토큰 한계. OpenAI `text-embedding-3-small`의 입력 한도는 8192 토큰입니다. 긴 문서는 그냥 안 들어갑니다.

둘째, 의미 해상도. 한 chunk가 너무 크면 여러 주제가 섞여 벡터가 "모호한 평균값"이 됩니다. "API 인증" 질문을 던졌을 때, 인증과 결제와 배포가 뒤섞인 10000자 chunk는 순수 "인증" chunk보다 유사도가 낮게 잡힙니다. 벡터는 의미의 평균으로 수렴하기 때문입니다.

그래서 chunk 크기는 작을수록 유리한 게 아니라 **트레이드오프**입니다.

| Chunk 크기 | 장점 | 단점 |
|---|---|---|
| 작음 (100 토큰 이하) | 의미 해상도 높음, 특정 질문에 집중 매칭 | 문맥 단절. "이 API는 JWT를 쓴다"만 남고 "어떤 상황에서"가 사라짐 |
| 중간 (500에서 1000 토큰) | 문맥 보존 + 의미 해상도의 균형. 실무 기본값 | 범용 기본값, 주제별 미세 조정 필요 |
| 큼 (2000 토큰 이상) | 한 chunk에 맥락이 풍부하게 들어감 | 여러 주제 혼합으로 벡터가 모호한 평균값이 됨 |

더 정교한 전략도 있습니다.

- **Recursive character splitting**: 단락(`\n\n`) → 문장(`.`) → 단어 → 문자 순으로 우선순위를 두고 경계를 찾음. LangChain의 `RecursiveCharacterTextSplitter`가 이 방식.
- **Semantic chunking**: 문장 단위 임베딩을 먼저 만들고, 인접 문장 간 유사도가 급락하는 지점을 chunk 경계로 삼음. 주제가 실제로 바뀌는 지점에서 자르자는 발상.
- **Document-structure chunking**: Markdown의 `##`, HTML의 `<section>`, 코드의 함수 경계 같은 의미 단위 구조를 활용.

### 임베딩의 원리

"텍스트를 벡터로 바꾼다"는 한 줄이 **왜 의미 검색을 가능하게 하는가**. 여기가 RAG가 단순 키워드 검색(BM25, Elasticsearch)과 갈라지는 지점입니다.

Embedding 모델은 입력 텍스트를 $\mathbb{R}^d$($d$차원 실수 공간)의 한 점으로 매핑하는 함수 $f: \text{text} \to \mathbb{R}^d$입니다. 보통 $d$는 768, 1536, 3072 같은 값입니다. 중요한 건 이 함수가 임의로 매핑하지 않고, 의미가 비슷한 텍스트는 가까운 점으로, 다른 텍스트는 먼 점으로 학습돼 있다는 것입니다.

<EmbeddingSpace />

위 그림은 실제 1536차원 공간을 2차원으로 축소한 개념도입니다. 같은 주제(동물, 데이터베이스, 결제)에 속한 문장들이 서로 가깝게 뭉치고, 다른 주제끼리는 멀리 떨어지는 것이 핵심입니다. "같은 방향을 가리킨다"를 수치화한 게 **cosine similarity**, 두 벡터 사이 각도의 코사인 값($-1$에서 $1$)입니다. 벡터의 크기(magnitude)는 무시하고 방향만 본다는 게 포인트입니다. 텍스트의 길이나 빈도가 아니라 "어디를 가리키느냐"가 의미를 표현합니다.

<Callout type="error" title="핵심 통찰: 의미 검색은 벡터 공간의 최근접 이웃 탐색이다">
  Embedding 모델은 수억 쌍의 "유사/비유사 텍스트"로 contrastive learning을 거쳐, "의미 유사 = 방향 유사"가 되도록 공간 자체를 조직합니다. 그 덕에 "의미 검색"이라는 추상 작업이 **벡터 공간에서 가장 가까운 점 찾기**라는 잘 정의된 수학 문제로 환원됩니다. 이 환원이 RAG의 엔진입니다.
</Callout>

이 환원이 가능한 건 contrastive learning 덕분입니다. 대규모 텍스트 쌍을 모아 모델에게 "같은 의미 쌍은 벡터를 가깝게, 무관한 쌍은 멀게"를 학습시키면, 모델은 의미 유사라는 추상 개념을 공간 구조로 흡수합니다. Word2vec 시절 고전이 된 관찰이 그 증거입니다.

$$v(\text{king}) - v(\text{man}) + v(\text{woman}) \approx v(\text{queen})$$

"왕에서 남성성을 빼고 여성성을 더하면 여왕"이 벡터 산수로 성립합니다. 의미의 축(성별, 왕족 여부 등)이 공간의 특정 방향에 분산된 형태로 부호화되어 있다는 뜻입니다. 문장과 문서 임베딩도 같은 원리로 확장됩니다.

여기서 자주 나오는 질문 하나. "그럼 cosine similarity 대신 유클리드 거리를 쓰면 안 되나?" 결론부터 말하면 **고차원 공간의 기하학적 특성 때문에** cosine이 선호됩니다. 고차원에서는 모든 점이 서로 비슷한 거리에 놓이는 curse of dimensionality 현상이 있어 유클리드 거리는 변별력이 떨어집니다. 반면 방향은 학습 과정에서 의미와 잘 정렬되도록 조정되고, 크기는 텍스트 길이 같은 부수 정보를 타므로 배제하는 편이 안정적입니다. 많은 임베딩 모델이 출력 벡터를 L2 정규화(크기 1로 맞추기)해 아예 단위 구 위에 놓는 이유입니다. 이러면 cosine similarity와 dot product가 수학적으로 동일해지고, 벡터 DB는 단순 행렬 곱셈으로 훨씬 빠르게 계산할 수 있습니다.

### Querying 파이프라인

이제 사용자 질문이 들어왔을 때 온라인으로 일어나는 일입니다. 위 `RagPipeline` 그림의 하단 흐름이 이 단계입니다.

우선 질문 텍스트를 **인덱싱에 썼던 것과 같은 임베딩 모델**로 벡터화합니다. 같은 모델이어야 한다는 점이 중요합니다. 모델이 다르면 같은 의미도 서로 다른 공간에 매핑돼 거리 비교 자체가 무의미해집니다.

그다음 벡터 DB에서 "질문 벡터 $q$와 가장 가까운 chunk 벡터 top-k개"를 찾아야 합니다. 가장 단순한 방법은 **exact search**, 저장된 모든 $N$개 벡터와 $q$의 유사도를 계산해 상위 $k$개를 고르는 것입니다. 시간 복잡도는 $O(N \cdot d)$입니다.

$N$이 10만이면 괜찮지만, 1억이라면? 1536차원 float32 벡터 1억 개는 약 600 GB, 질의 한 번에 1억 번의 내적이 필요합니다. 100ms 안에 답하려면 불가능합니다. 그래서 실무에서는 **근사 최근접 이웃(ANN, Approximate Nearest Neighbor)** 을 씁니다. "정확히 가장 가까운 점"을 포기하는 대신 "거의 가까운 점을 매우 빠르게" 찾는 알고리즘입니다. Recall이 98% 정도면 99에서 100%를 고집할 이유가 별로 없습니다. 어차피 LLM이 여러 chunk를 참고해 답을 보완하기 때문입니다.

대표 알고리즘을 감각적으로 소개하면 다음과 같습니다.

| 알고리즘 | 핵심 아이디어 | 특징 |
|---|---|---|
| HNSW | 벡터들을 다층 그래프로 연결. 위층은 듬성듬성, 아래층은 촘촘. 위에서 대충 방향 잡고 내려오며 정밀화 | 질의 시간 거의 $O(\log N)$. `pgvector`, Qdrant, Weaviate 기본 |
| IVF | 벡터 공간을 $K$개 클러스터로 분할. 질의 벡터가 속한 클러스터만 검사 | 클러스터 경계 근처 점을 놓칠 수 있음. FAISS 기본 옵션 |
| PQ | 벡터를 조각으로 쪼개 코드북으로 양자화. 저장 공간을 수십 배 압축 | 정확도 하락, 메모리 부족 대규모에 유리. 보통 IVF와 조합(`IVF-PQ`) |

HNSW는 도시 지도를 고속도로 → 국도 → 골목길 순으로 좁혀 내려가는 탐색에 가깝습니다. 대략적인 방향을 먼저 잡고 점점 정밀해지는 발상입니다.

공통 핵심은 **recall · latency · memory의 삼각 트레이드오프**입니다. 세 축 중 둘을 선택하면 나머지 하나는 포기해야 합니다. 프로덕션에서는 보통 HNSW로 시작해 "recall 95% 이상 + p95 50ms 이하"를 목표로 `ef_search`, `M` 같은 파라미터를 튜닝합니다.

Top-k 조회로 끝내지 않고 **Re-ranking**으로 재정렬하는 2단 파이프라인도 흔합니다. Embedding 모델은 두 텍스트를 따로따로 벡터화한 뒤 거리로 비교합니다(`bi-encoder`, 빠름). Re-ranker는 (질문, chunk) 쌍을 함께 입력받아 관련성을 채점합니다(`cross-encoder`, 정확하지만 느림). 그래서 "빠른 bi-encoder로 top-50을 뽑고 → 느린 cross-encoder로 top-5로 재정렬 → LLM에 넘김"처럼 조합합니다. Cohere Rerank, BGE-reranker 등이 이 용도입니다.

마지막으로 검색된 chunk들을 어떻게 프롬프트에 끼워 넣느냐가 답변 품질에 크게 영향을 줍니다.

```text title="rag-prompt-template.txt"
너는 사내 문서 기반 Q&A 어시스턴트다. 아래 [참고 문서]에만 근거해서
답해라. 문서에 없는 내용은 "주어진 문서에서 확인할 수 없습니다"라고
답하고, 추측하지 마라. 답변 끝에 근거 문서 번호를 [1], [2] 형식으로
표기해라.

[참고 문서]
[1] <chunk 1 텍스트>
[2] <chunk 2 텍스트>
[3] <chunk 3 텍스트>

[질문]
<사용자 질문>
```

핵심 지시가 셋 있습니다.

1. **근거 제한**: "문서에만 근거해서" 라는 지시로 hallucination을 억제
2. **모름 수용**: "없으면 없다고" 로 강제로 답하지 않게
3. **인용 요구**: "[N] 형식으로" 로 사용자 검증 가능성 확보

이 중 하나라도 빠지면 LLM은 가중치 안의 지식까지 섞어 답하거나, 문서에 없는 내용을 지어냅니다. RAG의 hallucination 감소 효과는 이 프롬프트 수준의 계약에 의존합니다.

한 가지 미묘한 이슈가 있습니다. **Lost in the Middle**입니다. LLM은 프롬프트에 긴 문맥이 들어가면 앞쪽과 맨 뒤쪽은 잘 기억하지만 중간에 있는 내용을 상대적으로 놓치는 경향이 있습니다. 그래서 top-k chunk를 배열할 때 가장 관련성 높은 chunk를 맨 앞이나 맨 뒤에 배치하는 전략을 씁니다. 중간에 묻으면 사실상 못 본 것과 같은 효과가 납니다.

## 어디서 마주치는가

RAG의 경쟁 후보는 크게 둘입니다. **Fine-tuning** (모델을 재학습해 지식을 주입)과 **Long-context** (점점 커지는 context window에 문서를 통째로 넣기). 세 기법의 지식 주입 방식부터 비교해야 합니다.

| 방식 | 지식이 어디에 있는가 | 업데이트 비용 | 추론 비용 | 신선도 |
|---|---|---|---|---|
| Fine-tuning | 모델 가중치 안 | 매우 높음 (GPU · 시간) | 낮음 | 학습 시점 고정 |
| RAG | 외부 벡터 DB | 낮음 (upsert만) | 중간 (검색 + LLM) | 실시간 업데이트 가능 |
| Long-context | 매 요청 프롬프트 | 없음 (문서 준비만) | 높음 (긴 토큰 소비) | 실시간 |

### Fine-tuning이 유리한 조건

스타일, 어조, 출력 형식을 학습시킬 때입니다. "우리 회사 고객 응대 톤", "특정 JSON 스키마로만 답하기" 같은 건 RAG로 주입하기 어렵습니다. 프롬프트로 지시할 수는 있지만 일관성이 떨어집니다. 또 도메인 특화 용어와 문법을 모델이 체화해야 할 때도 적합합니다. 의료 코딩(ICD-10), 법률 판결문 문체, 금융 리스크 레포트 등이 예입니다.

핵심은 Fine-tuning이 "**지식**을 넣는 수단"으로는 비효율이라는 점입니다. 한 번 학습하면 바꾸기 어렵고, 학습 데이터에 없던 엣지 케이스는 여전히 hallucinate합니다. Fine-tuning이 진가를 발휘하는 건 지식보다 **행동 양식(behavior)** 을 주입할 때입니다.

### RAG가 유리한 조건

지식이 자주 변할 때(사내 위키, 제품 문서, 뉴스, 가격표), 지식의 출처 추적이 중요할 때(법률, 의료, 감사 대응), 지식의 분량이 매우 클 때(수만에서 수백만 문서), 사용자별이나 권한별 데이터 격리가 필요할 때 유리합니다. 마지막 조건은 벡터 DB 메타데이터 필터로 "사용자 A는 자기 조직 문서만"을 만들 수 있는데, Fine-tuning은 이런 분리가 구조적으로 어렵습니다.

### Long-context가 유리한 조건

최근 Claude Sonnet 4.6(200K에서 1M 토큰), Gemini 2.5(1M에서 2M 토큰)처럼 context window가 급격히 커지면서 "RAG 무용론"이 나왔습니다. 실제로 다음 조건에서는 RAG보다 Long-context가 단순하고 품질도 좋습니다.

- 총 문서량이 context window 안에 들어갈 때 (수십에서 수백 페이지). chunking과 retrieval의 정보 손실을 감수할 이유가 없음
- 문서 간 교차 참조나 종합 추론이 필요할 때. RAG는 top-k로 관련 조각만 가져오니 전체 종합 추론에 구조적으로 약함
- 신선한 1회성 문서를 질의할 때. 방금 받은 계약서 PDF 하나를 여러 번 물어볼 때 굳이 인덱싱 파이프라인을 세우는 건 오버킬

그러나 Long-context가 RAG를 완전히 대체하지 못하는 이유도 명확합니다. 1M 토큰 입력은 한 번 호출에 비싼 API 과금이 붙고, 매번 긴 입력을 다시 읽어야 해서 latency가 큽니다. 그리고 앞서 언급한 Lost in the Middle 때문에 실제로 사용되는 건 앞뒤뿐일 수 있습니다. 무엇보다 100만 문서를 1M 토큰 안에 밀어 넣을 수는 없어서 임계 규모 이상에서는 선택지가 RAG뿐입니다.

실무에서는 "규모와 빈도의 트레이드오프"로 정리됩니다.

| 상황 | 선택 |
|---|---|
| 소규모 + 저빈도 호출 | Long-context |
| 대규모 또는 고빈도 호출 | RAG |
| 특정 조직의 문체 · 형식 체화 필요 | Fine-tuning (단독 또는 RAG와 병행) |

세 기법은 양자택일이 아닙니다. 실무 스택은 보통 Fine-tuning(스타일) + RAG(지식) 조합이나, 벡터 검색으로 관련 섹션을 넓게(예: top-50) 가져온 뒤 그 섹션 전체를 Long-context LLM에 넘겨 종합 추론을 맡기는 Hybrid RAG 형태로 씁니다.

### RAG를 쓰지 말아야 할 때

반대로 RAG가 부적합한 상황도 명확합니다.

- **단일 짧은 문서 Q&A**: 10페이지 PDF 하나 보고 답하는 거면 chunking과 벡터 DB 셋업이 과잉. 문서를 통째 프롬프트에 붙이는 게 나음
- **지식 주입이 아니라 행동 변경이 목적**: "우리 서비스에 맞는 어조로 답하기"는 RAG로 안 됨. Fine-tuning이 정답
- **수학 · 논리 추론 능력 향상**: RAG는 참고 자료를 주는 것이지 LLM의 추론 능력을 키우지 않음
- **답의 근거가 문서에 없는 질문**: "이 현상을 물리학적으로 설명해줘" 같은 추론 중심 질문은 외부 문서보다 LLM의 일반 지식이 나음. 억지로 RAG를 태우면 관련 없는 chunk가 섞여 답변이 오히려 나빠짐

## 트레이드오프

앞의 섹션들이 RAG의 구조적 이해였다면, 여기는 실제로 만들 때 반드시 마주치는 함정 모음입니다. 거의 대부분의 RAG 도입 실패는 아래 항목에서 옵니다.

### 1. Chunk 경계에 답이 걸림

질문의 답이 두 chunk에 걸쳐 있으면 어느 쪽도 단독으로는 완전한 답을 담지 못해 retrieval이 실패합니다.

<Tabs>
  <Tab label="경계에 걸린 예시">
    ```text
    [chunk 1 끝]   ... 결제 API의 기본 timeout은
    [chunk 2 시작] 30초이며, 설정 파일에서 변경 가능하다. ...
    ```
    두 chunk 모두 "결제 timeout = 30초"를 완결하지 않는다. 벡터 검색이 실패하기 쉽다.
  </Tab>
  <Tab label="완화된 형태">
    ```text
    [chunk 1 끝]   ... 결제 API의 기본 timeout은 30초이며, 설정 파일에서
    [chunk 2 시작] 결제 API의 기본 timeout은 30초이며, 설정 파일에서 변경 가능하다. ...
    ```
    overlap을 50에서 200 토큰 정도 두면 경계 인접 문맥이 양쪽 chunk에 모두 들어간다.
  </Tab>
</Tabs>

완화책은 overlap 충분히 주기, recursive splitter로 문장 경계 지키기, 검색 후 인접 chunk 병합("window expansion") 같은 전략입니다. 근본적으로 완전히 없앨 수는 없고, 줄일 수 있을 뿐입니다.

### 2. Embedding 모델 교체 = 전체 재인덱싱

임베딩 모델이 바뀌면 벡터 공간이 바뀝니다. `text-embedding-ada-002`로 인덱싱한 DB를 `text-embedding-3-small`로 질의하면 거리 비교가 무의미해집니다. 그래서 임베딩 모델을 교체하려면 모든 문서를 처음부터 다시 임베딩해야 합니다. 100만 chunk면 API 비용과 시간이 상당합니다. 초기에 모델 선택을 가볍게 보지 말아야 하는 이유입니다.

### 3. 메타데이터 필터 누락

"2024년 이후 문서만", "사용자 본인 팀 문서만" 같은 hard 조건이 필요한데 벡터 유사도만 쓰면 조용히 잘못된 답이 나옵니다. 벡터 검색은 유사한 걸 가져올 뿐 조건 만족을 보장하지 않습니다. 벡터 DB의 메타데이터 필터(`Pinecone` filter, `pgvector` WHERE)와 반드시 병행해야 합니다.

### 4. 키워드 미스 (Semantic ≠ Lexical)

Embedding은 의미는 잘 잡지만, 정확한 고유명사나 에러 코드, UUID 같은 키워드 매칭에는 의외로 약합니다. "에러 코드 `ERR_2045`"를 찾고 싶은데 벡터 검색이 비슷한 의미의 다른 에러 코드를 가져오는 일이 흔합니다. 해법은 **Hybrid search**입니다. BM25(어휘 기반) 점수와 벡터 점수를 가중 평균(RRF, Reciprocal Rank Fusion이 표준)합니다. Elastic, Weaviate, Qdrant가 내장 지원합니다.

### 5. Top-k 과다

"많이 가져올수록 좋은 답이 나오겠지"라는 순진한 가정은 위험합니다. 실제로는 top-k를 20이나 50으로 키우면 관련성 낮은 chunk가 섞여 LLM을 혼란시킵니다. "문서에 답이 없다"고 답해야 할 질문에 엉뚱한 chunk를 근거로 틀린 답을 지어내는 경우가 늘어납니다. 실무 기본값은 **3에서 5** 사이에서 시작해 평가 지표를 보고 조정합니다.

### 6. 평가 체계 없이 튜닝

"chunk 크기를 500에서 800으로 바꿨더니 답이 좋아진 것 같다"는 체감 판단은 거의 틀립니다. RAG는 튜닝 포인트가 너무 많습니다(chunk 크기, overlap, 임베딩 모델, top-k, re-ranker, 프롬프트). 평가 데이터셋 없이 바꾸면 개선인지 퇴보인지 알 수 없습니다.

최소한의 평가 세트는 둘입니다. **Retrieval 품질**은 질문-정답 문서 쌍을 수십에서 수백 개 확보해 "정답 문서가 top-k 안에 들어왔는가"(recall@k)를 측정합니다. **답변 품질**은 LLM-as-judge로 답변의 사실성과 완결성을 0에서 5점으로 채점합니다. RAGAS, TruLens 같은 라이브러리가 이 용도로 쓰입니다.

### 7. PII 유출

벡터 DB에 주민번호, 카드번호, 의료 기록이 그대로 들어가면, 검색된 chunk가 프롬프트를 거쳐 LLM 응답에 노출될 수 있습니다. OpenAI 같은 외부 LLM을 쓰면 그 데이터가 외부로 빠져나가는 것입니다. 인덱싱 전에 PII 마스킹을 걸거나, 민감 필드를 제외하거나, 온프레미스 LLM을 쓰는 게 필요합니다. RAG 특유의 문제라기보다 "데이터를 쉽게 꺼내 쓰는" 구조가 만드는 새로운 노출면입니다.

## 마무리

RAG의 핵심은 간단합니다. LLM의 가중치는 그대로 두고, 답을 만들 때 참고할 자료만 매 요청마다 바꿔 공급하는 것. 이 단순한 아이디어가 "의미 검색"이라는 추상 작업을 벡터 공간의 최근접 이웃 탐색이라는 수학 문제로 환원하면서 엔진이 됩니다. 그 환원 덕에 chunking의 트레이드오프, ANN의 삼각 제약, 프롬프트 수준의 계약이라는 세 축이 따라옵니다.

앞으로 LLM의 context window가 더 커지고 임베딩 모델이 더 정교해질수록 RAG의 세부 디자인은 계속 달라질 것입니다. 하지만 "가중치와 독립된 지식 주입"이라는 뼈대는 바뀌지 않습니다. 사내 데이터에 답하는 시스템을 설계한다면, Fine-tuning과 Long-context 중 어느 쪽 조건에 해당하는지 먼저 점검하고, RAG를 택했다면 chunking과 프롬프트 계약에 가장 많은 시간을 쓰는 게 투자 대비 효용이 가장 큽니다.
