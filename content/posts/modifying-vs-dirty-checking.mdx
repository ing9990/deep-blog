Spring Data JPA에서 데이터를 수정하는 코드는 외형이 거의 같아 보입니다. 그러나 `@Modifying` JPQL과 도메인 객체 변경(Dirty Checking)은 내부에서 완전히 다른 컴포넌트를 거칩니다. 이 글은 두 방법이 영속성 컨텍스트와 어떻게 다르게 상호작용하는지를 정리하면서, 1차 캐시 stale·lifecycle 우회·lost update 같은 실전 함정이 모두 같은 차이에서 비롯된다는 것을 보여줍니다.

<Note title="이 글의 학습 목표">
  - 두 업데이트 경로가 영속성 컨텍스트의 1차 캐시·스냅샷과 어떻게 다르게 상호작용하는지 이해한다
  - `@Modifying` 후 1차 캐시 stale·lifecycle 미동작·cascading 부재가 같은 뿌리에서 온다는 것을 구분할 수 있다
  - 단건/벌크·동시성·lifecycle 세 측면에서 어느 쪽을 선택할지의 기준을 얻는다
</Note>

## 두 업데이트 방식

Spring Data JPA에서 데이터베이스 레코드를 수정하는 두 가지 방법이 있습니다.

**방식 1. `@Modifying + @Query`를 사용한 UPDATE**

```kotlin title="ProductRepository.kt"
interface ProductRepository : JpaRepository<Product, Long> {
    @Modifying
    @Query("update Product p set p.quantity = p.quantity - 1 where p.id = :id")
    fun decreaseQuantity(@Param("id") id: Long): Int
}
```

JPQL 또는 native SQL 형태의 UPDATE, DELETE 문을 그대로 작성하고, Spring Data JPA가 이를 `Query#executeUpdate()`로 실행합니다. 결과는 영향받은 행 수(`int`). 엔티티 객체는 한 번도 메모리에 로드되지 않고, 한 번의 쿼리로 DB가 직접 컬럼을 갱신합니다.

**방식 2. 도메인 객체 변경을 통한 Dirty Checking**

```kotlin title="ProductService.kt"
@Transactional
fun decrease(productId: Long) {
    val product = productRepository.findById(productId)
        .orElseThrow { BusinessException(PRODUCT_NOT_FOUND) }
    product.decreaseQuantity(1)
    // save() 호출 없음. 트랜잭션 종료 시점에 자동 UPDATE
}
```

엔티티를 영속성 컨텍스트(Persistence Context)에 로드한 뒤, 자바 객체의 필드를 변경합니다. `save()`나 `update()`를 명시적으로 호출하지 않습니다. 트랜잭션 커밋 직전 flush 시점에 Hibernate가 <E>로드 시 스냅샷</E>과 <E>현재 상태</E>를 비교해 변경된 필드만 자동으로 UPDATE 문을 만들어 보냅니다. 이 메커니즘이 <E>Dirty Checking</E>(변경 감지)입니다.

두 방식의 외형 차이를 한 표에 모으면 다음과 같습니다.

| 구분 | `@Modifying` JPQL | 도메인 업데이트 (Dirty Checking) |
|---|---|---|
| 엔티티 로드 | 없음 | SELECT 후 영속화 |
| UPDATE 발행 시점 | 메서드 호출 즉시 | 트랜잭션 flush 시점 |
| 1차 캐시 | 우회 | 통과 (스냅샷 보관) |
| 반환값 | 영향받은 행 수(`int`) | 없음 |
| 비즈니스 로직 호출 | 불가 (DB 산술만) | 가능 (도메인 메서드 안에서 불변식 검증) |
| Lifecycle 콜백 | 미동작 | 동작 |

같은 결과를 만드는 두 경로지만, 이 표의 한 칸 한 칸이 뒤에서 다룰 실전 문제와 트레이드오프로 직결됩니다.

## 왜 두 방법이 모두 있는가

JPA가 표준화될 때부터 ORM은 본질적인 긴장 하나를 안고 있었습니다. <E>객체로 다루고 싶다</E>와 <E>DB는 집합 연산이 빠르다</E>의 충돌입니다. 두 업데이트 방법은 각각 이 긴장의 한쪽을 우선합니다.

도메인 업데이트가 디폴트인 이유부터 봅니다. JPA의 설계 의도는 <E>Java 객체를 다루듯 영속 데이터를 다루게 한다</E>입니다. 개발자가 SQL을 의식하지 않고 객체에 메시지를 보내는 코드(`product.decreaseQuantity(1)`)만 작성해도 ORM이 알아서 SQL을 합성해 줍니다. 가능한 이유는 영속성 컨텍스트가 **로드 시점의 스냅샷**을 보관하다가 flush 시점에 차이만 골라 UPDATE를 만들기 때문입니다.

이 방식의 진짜 가치는 비즈니스 로직이 도메인에 머문다는 점입니다. 재고를 깎을 때 <E>수량이 음수가 되면 안 된다</E>는 불변식은 `Product.decreaseQuantity()` 메서드 안에 있습니다. 호출자는 그 불변식을 우회할 수 없고, 메서드를 통하지 않으면 상태가 바뀌지 않습니다. 도메인 모델이 살아 있는 코드는 거의 항상 이 경로를 탑니다.

그런데 도메인 업데이트는 본질적으로 단건 처리에 최적화된 경로입니다. <E>5만 개 상품의 가격을 일괄 10% 인상</E>을 도메인 업데이트로 풀려면 5만 번의 SELECT, 5만 번의 객체 변경, 5만 번의 UPDATE가 필요합니다. 영속성 컨텍스트는 그 5만 개의 스냅샷을 모두 들고 있어야 하므로 메모리 압박도 함께 옵니다.

DB는 원래 이런 작업을 한 줄로 처리할 수 있습니다.

```sql
UPDATE product SET price = price * 1.1
```

`@Modifying`은 이 한 줄을 그대로 쓰게 해주는 옵션입니다. ORM의 객체 추상화를 잠깐 내려놓고, 집합 연산을 그대로 DB로 보냅니다. 메모리에 5만 개의 객체를 올리지 않고, 라운드트립도 한 번이고, DB는 자기가 가장 잘하는 일을 합니다.

둘 중 하나만 두면 어떻게 될까요. 도메인 업데이트만 있으면 벌크 작업이 비효율적이고, 조회한 뒤 값을 바꿔 다시 저장하는 흐름이라 동시성 충돌 시 lost update 위험이 그대로 남습니다. `@Modifying`만 있으면 도메인 불변식이 사라지고, 영속성 컨텍스트와 동기화가 깨지는 순간이 생기며, lifecycle 콜백(`@PreUpdate`, Auditing)이 호출되지 않습니다. JPA는 두 방식을 다 두고 개발자에게 선택권을 넘긴 것입니다. 기본은 객체로 다루고, 필요할 때만 SQL의 힘을 직접 빌려라는 정책입니다.

## 내부 동작

<Callout type="warning" title="이 글의 핵심 포인트">
  두 방법은 같은 SQL을 만들어 내는 것 같지만 거치는 컴포넌트와 시점이 다릅니다. 그 차이가 뒤에 나올 모든 실전 함정의 원인입니다.
</Callout>

### 영속성 컨텍스트와 스냅샷

먼저 도메인 업데이트의 토대인 **영속성 컨텍스트(Persistence Context)** 부터 짚습니다. 트랜잭션이 시작되면 Hibernate는 트랜잭션 단위로 살아 있는 메모리 공간을 하나 엽니다. 이 공간에 들어온 엔티티는 다음 두 가지를 동시에 가집니다.

- **1차 캐시 엔트리**: `(엔티티 클래스, ID)`를 키로 하는 Map. 같은 트랜잭션 안에서 동일 ID를 다시 조회하면 SQL 없이 이 Map에서 바로 반환됩니다.
- **스냅샷(Snapshot)**: `findById`로 SELECT 한 직후, 그 시점의 모든 영속 필드 값을 별도 배열로 복제해 보관합니다. 이게 변경 감지의 비교 대상입니다.

```kotlin
val product = productRepository.findById(1L).orElseThrow()
// 1차 캐시: { (Product, 1L) -> product 객체 }
// 스냅샷:   [name="볼펜", price=1000, quantity=10]   (로드 시점 복제본)
```

스냅샷은 개발자가 직접 볼 수 없습니다. Hibernate 내부의 `EntityEntry`라는 메타데이터 객체가 들고 있고, 영속성 컨텍스트가 닫힐 때까지 살아 있습니다.

### Dirty Checking의 flush 흐름

이제 객체의 필드를 바꿔 봅니다.

```kotlin
product.decreaseQuantity(1)   // 메모리상 quantity: 10 -> 9
```

이 시점에는 SQL이 발행되지 않습니다. 객체 안의 필드만 9로 바뀌었을 뿐, 스냅샷은 여전히 `[..., quantity=10]`을 들고 있습니다. 둘 사이의 차이가 곧 <E>dirty</E>이고, Hibernate는 이를 감지할 시점만 기다립니다.

flush가 발동하는 시점은 셋입니다.

1. 트랜잭션 커밋 직전 (가장 흔함)
2. 같은 트랜잭션 안에서 다른 JPQL 쿼리가 실행되기 전 (auto-flush)
3. 명시적 `entityManager.flush()` 호출

flush가 시작되면 Hibernate는 영속성 컨텍스트의 모든 영속 엔티티에 대해 스냅샷과 현재 상태를 필드 단위로 비교합니다. 다른 필드가 하나라도 있으면 그 엔티티에 대해 UPDATE 문을 만들고, 변경된 필드만(또는 설정에 따라 전체 필드를) SET 절에 포함시킵니다.

```sql
-- flush 시점에 자동 합성
UPDATE product SET quantity = 9 WHERE id = 1;
```

UPDATE가 성공하면 스냅샷은 새 값으로 갱신됩니다(`quantity=9`). 같은 트랜잭션에서 다시 같은 객체를 조회해도 1차 캐시에서 일관된 상태가 나옵니다.

### @Modifying의 executeUpdate 흐름

`@Modifying`이 붙은 메서드를 호출하면 Spring Data JPA는 JPQL을 파싱해 SQL로 번역한 뒤, JDBC `PreparedStatement#executeUpdate()`를 직접 실행합니다. 이 경로에서는 영속성 컨텍스트가 참여하지 않습니다.

```kotlin
productRepository.decreaseQuantity(1L)
// JPQL -> SQL 번역
// executeUpdate() -> DB가 즉시 UPDATE 실행
// 영향 행 수 반환
```

DB의 행은 즉시 갱신되지만, 영속성 컨텍스트의 1차 캐시와 스냅샷은 그 변경을 모릅니다. 만약 같은 트랜잭션 안에서 직전에 `findById(1L)`로 같은 행을 로드해 두었다면, 1차 캐시는 여전히 옛 값(`quantity=10`)을 들고 있고, 다음 조회도 그 옛 값을 반환합니다.

```kotlin
val before = productRepository.findById(1L).get()  // quantity=10 (DB와 동일)
productRepository.decreaseQuantity(1L)             // DB: quantity=9
val after = productRepository.findById(1L).get()   // 1차 캐시 hit -> quantity=10 (stale!)
```

이 stale 상태가 `@Modifying`의 가장 유명한 함정이며, 다음 절의 출발점입니다.

### 두 흐름을 한눈에

<Callout type="error" title="핵심 통찰: 두 방법의 차이는 영속성 컨텍스트를 통과하는지로 정리된다">
  도메인 업데이트는 메모리(1차 캐시 + 스냅샷)가 진실의 원본이고 flush 시점에 DB로 동기화됩니다. `@Modifying`은 DB가 진실의 원본이고 메모리는 그 변경을 자동으로 알지 못합니다. 이 차이 하나가 stale 캐시·lifecycle 우회·lost update를 모두 설명합니다.
</Callout>

```text title="두 경로 비교"
도메인 업데이트                            @Modifying
─────────────                              ─────────────
findById(1)
  ↓ SELECT
1차 캐시 ← Product(quantity=10)
스냅샷    ← [..., quantity=10]
  ↓
product.decreaseQuantity(1)
  ↓ (객체 필드만 9로)
  ↓
[트랜잭션 커밋 직전]
  ↓
스냅샷[10] vs 현재[9] → 차이 감지
  ↓
UPDATE product SET quantity=9 WHERE id=1
  ↓
스냅샷 ← [..., quantity=9]                decreaseQuantity(1)
                                            ↓ JPQL → SQL
                                          executeUpdate()
                                            ↓
                                          UPDATE product SET ... WHERE id=1
                                            ↓
                                          (1차 캐시·스냅샷 변화 없음)
```

이 비대칭이 왜 `clearAutomatically`나 `flushAutomatically` 같은 옵션이 존재하는지, 왜 도메인 업데이트가 동시성 충돌에 약한지를 모두 설명해 줍니다.

## 실전 문제

두 방식이 실제 코드베이스에 들어왔을 때 어떤 함정에 빠지는지 네 가지로 추립니다.

### 1차 캐시 stale

같은 트랜잭션 안에서 `findById`로 로드한 직후 `@Modifying`으로 같은 행을 갱신하면, DB는 새 값인데 1차 캐시는 옛 값을 그대로 들고 있습니다.

```kotlin
@Transactional
fun process(id: Long) {
    val before = repo.findById(id).get()  // quantity=10 로드, 1차 캐시 적재
    repo.decreaseQuantityBulk(id)         // @Modifying -> DB: 9
    val after = repo.findById(id).get()   // 1차 캐시 hit -> 여전히 10 (stale!)
    // before.quantity == after.quantity == 10
}
```

Spring Data JPA는 이 함정을 알고 있어 두 가지 옵션을 제공합니다.

```kotlin title="ProductRepository.kt"
@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query("update Product p set p.quantity = p.quantity - 1 where p.id = :id")
fun decreaseQuantity(@Param("id") id: Long): Int
```

- `flushAutomatically = true`: UPDATE 실행 **전에** 영속성 컨텍스트를 flush. 메모리에 쌓여 있던 변경이 DB에 먼저 반영되어 누락을 방지합니다.
- `clearAutomatically = true`: UPDATE 실행 **후에** 영속성 컨텍스트를 clear. 1차 캐시 전체가 비워져, 이후 조회는 반드시 DB를 다시 갑니다.

`clearAutomatically`는 트랜잭션 안의 모든 영속 엔티티가 detach 된다는 부작용이 있습니다. 같은 트랜잭션에서 다른 엔티티를 들고 있었다면 그것도 끊깁니다. 보통 `@Modifying`이 들어간 메서드는 트랜잭션의 마지막 단계로 배치하거나, 별도 트랜잭션으로 분리하는 패턴이 자주 나옵니다.

### Lost Update

도메인 업데이트의 흐름(조회 → 변경 → 저장)은 동시 요청에 약합니다.

```kotlin
@Transactional
fun decrease(id: Long) {
    val product = repo.findById(id).get()   // [Tx-A] quantity=10 읽음
    product.decreaseQuantity(1)             // [Tx-A] 메모리 9
    // [Tx-B]도 동시에 같은 흐름: 10 읽고 9 만듦
    // [Tx-A] 커밋: UPDATE ... SET quantity = 9
    // [Tx-B] 커밋: UPDATE ... SET quantity = 9   <- 1 깎였어야 할 것이 0 깎임
}
```

두 트랜잭션 모두 <E>10을 읽고 9로 쓴다</E>를 수행하므로 한 번의 차감이 사라집니다. Dirty Checking은 SQL을 `SET quantity = 9`처럼 절대값으로 보내기 때문에 이 충돌을 감지하지 못합니다.

반면 `@Modifying`을 `SET quantity = quantity - 1`처럼 상대 연산으로 쓰면 DB가 행 락을 잡고 산술을 수행하므로 동시 요청 둘이 들어와도 누락이 없습니다. 동시성을 정확하게 다루려면 도메인 업데이트는 비관적 락(`@Lock(PESSIMISTIC_WRITE)`) 또는 낙관적 락(`@Version`)을 함께 써야 하고, 그래서 재고 차감 같은 코드에서는 종종 `@Modifying` 또는 비관적 락 + 도메인 업데이트의 조합이 채택됩니다.

### Lifecycle 콜백·Auditing 우회

`@Modifying`은 영속성 컨텍스트를 거치지 않으므로 엔티티 lifecycle에 묶인 모든 자동화가 호출되지 않습니다.

- `@PreUpdate`, `@PostUpdate`
- `@LastModifiedDate`, `@LastModifiedBy` (Spring Data JPA Auditing)
- 이벤트 리스너, `AuditingEntityListener`

`updated_at` 컬럼이 갱신되지 않아 <E>분명히 수정했는데 수정 시각이 그대로</E>인 증상이 생깁니다. 해결은 두 가지입니다. JPQL 안에 `set updated_at = current_timestamp`를 직접 적거나, 그 컬럼이 중요한 도메인이면 처음부터 `@Modifying`을 쓰지 않는 것입니다.

<RelatedPost slug="jpa-auditing" type="deep-dive" />

이 함정의 깊은 배경은 위 글에서 다룹니다. 핵심만 가져오면 <E>Auditing은 Hibernate lifecycle 콜백에 올라타기 때문에, lifecycle을 거치지 않는 벌크 UPDATE는 자동 갱신이 안 된다</E>입니다.

### Cascading·연관관계 부재

도메인 업데이트는 `cascade = CascadeType.ALL` 같은 설정으로 연관 엔티티의 변경이 자동 전파됩니다. `@Modifying`은 DB UPDATE 한 줄이므로 연관 테이블에는 어떤 영향도 미치지 않습니다.

```kotlin
// 도메인 업데이트
order.cancel()  // OrderItem들의 status도 cascade로 같이 바뀜

// @Modifying
"update Order o set o.status = 'CANCELLED' where o.id = :id"
// order_item 테이블은 그대로
```

`@Modifying`을 쓰는 순간 연관 데이터 정합성은 전적으로 개발자의 책임이 됩니다. 보통 같은 메서드 안에서 자식 테이블에 대한 별도 UPDATE/DELETE 쿼리를 함께 발행하거나, 조건이 맞으면 native SQL의 JOIN UPDATE로 한 번에 처리합니다.

## 트레이드오프

이 절은 앞 절의 결과를 판단 기준으로 압축합니다. 둘 중 하나를 항상 쓰면 된다는 답은 없습니다. 작업의 성격에 따라 선택이 다릅니다.

### 결정 기준 표

| 측면 | 도메인 업데이트 (Dirty Checking) | `@Modifying` JPQL |
|---|---|---|
| 처리 단위 | 단건/소량 | 벌크/일괄 |
| 비즈니스 로직 위치 | 도메인 메서드 안 | 쿼리 문자열 안 (또는 분산) |
| 동시성 충돌 | 락 없으면 lost update | 상대 연산으로 자연 회피 |
| Lifecycle/Auditing | 자동 동작 | 우회됨 |
| Cascading | 자동 전파 | 수동 |
| 메모리 비용 | 엔티티 + 스냅샷 | 0 (객체 미로드) |
| 라운드트립 | SELECT + UPDATE | UPDATE 한 번 |

이 표만 봐도 <E>기본은 도메인 업데이트, 예외적으로 @Modifying</E> 정책이 왜 합리적인지 보입니다. 도메인 업데이트는 단건 + 비즈니스 로직 + lifecycle을 모두 커버하고, 그 외 영역(벌크·동시성·메모리)에서만 `@Modifying`이 우위입니다.

### 실전 매핑

- **재고 차감, 포인트 차감**: 동시성이 핵심이라 도메인 업데이트만으로는 부족합니다. 비관적 락 + 도메인 업데이트, 또는 `@Modifying`의 `SET q = q - 1` 형태 중 선택.
- **상태 전이** (주문 PAID 에서 SHIPPED): 단건 + 불변식 검증이 필요해 도메인 업데이트가 자연스럽습니다. `Order.markShipped()` 안에 <E>결제 완료 상태에서만 출고 가능</E> 같은 가드를 둘 수 있습니다.
- **배치 일괄 갱신** (만료된 쿠폰 일괄 비활성화): `@Modifying` 한 줄 + `updated_at` 같은 감사 필드는 직접 set.
- **소프트 삭제** (`deleted_at` 채우기): 단건이면 도메인 업데이트, 일괄이면 `@Modifying`.

### @Modifying의 숨은 비용

- **테스트 작성 비용**: 도메인 업데이트는 도메인 메서드 단위 테스트가 SQL 없이 끝납니다. `@Modifying`은 실제 DB(또는 Testcontainers)가 있어야 동작 검증이 됩니다.
- **리팩터링 마찰**: 컬럼명·필드명을 바꾸면 도메인 업데이트는 컴파일러가 잡아주지만, JPQL 문자열은 런타임에야 깨집니다. Spring Boot 시작 시 검증을 켜는 옵션이 있지만 모든 경우를 잡진 못합니다.
- **가독성**: 같은 도메인 동작이 도메인 메서드와 쿼리 문자열로 흩어지면 <E>이 변경이 어디서 일어나는지</E> 추적이 어려워집니다. 팀 컨벤션으로 <E>벌크는 @Modifying만 사용, 단건은 절대 사용 안 함</E>처럼 경계를 분명히 두는 것이 도움이 됩니다.

### 한 줄 정책

> 객체로 다룰 수 있으면 객체로 다루고, 그 추상화의 비용이 명확히 보일 때만 `@Modifying`으로 내려간다.

이 정책은 JPA의 설계 의도와도 정확히 일치합니다. ORM은 SQL 작성을 막는 도구가 아니라, 객체로 다룰 수 있는 대부분의 경우에 SQL 작성을 면제해 주는 도구입니다. 면제 대상이 아닌 경우(벌크·동시성·성능)에는 그 사실을 인정하고 SQL 쪽으로 이동하는 게 맞습니다.

## 마무리

`@Modifying`과 도메인 업데이트는 같은 결과를 만드는 두 방법처럼 보이지만, 한쪽은 영속성 컨텍스트를 통과하고 한쪽은 우회한다는 차이 하나가 모든 함정을 결정합니다. 1차 캐시 stale, lifecycle 우회, lost update, cascading 부재는 모두 이 차이에서 나오는 결과입니다. 평소에는 도메인 객체의 메서드를 호출해 변경하고, 객체 추상화의 비용이 명확히 측정되는 지점에서만 `@Modifying`을 쓰는 정책이 JPA의 설계 의도와도 일치합니다.
