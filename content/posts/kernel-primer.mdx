커널이라는 단어는 자주 듣지만, 그것이 정확히 "어디서 어떻게 돌고 있는지"는 흐릿한 경우가 많습니다. 이 글은 커널이 왜 하드웨어 가까이 있어야 하는지, CPU 특권 레벨이 어떻게 격리를 강제하는지, 그리고 시스템 콜이 유저와 커널을 연결하는 유일한 통로로 어떻게 작동하는지를 메커니즘 감각으로 따라갑니다.

<Note title="이 글의 학습 목표">
  - 커널이 왜 필요하고 어떤 4가지 책임을 지는지 이해한다
  - CPU 특권 레벨(Ring)과 유저/커널 모드 분리의 인과를 파악한다
  - 시스템 콜이 Ring 3에서 Ring 0으로 건너가는 유일한 합법 통로임을 구분할 수 있다
</Note>

## 커널이란

커널(Kernel)은 OS의 심장이자, 하드웨어와 애플리케이션 사이를 중재하는 최하위 소프트웨어 계층입니다. 우리가 흔히 "운영체제"라 부르는 Linux, Windows, macOS는 실제로는 커널 + 셸 + 시스템 유틸리티 + GUI의 묶음이고, 그 중 **하드웨어와 직접 대화하는 유일한 층**이 커널입니다.

커널의 책임은 네 가지로 정리됩니다.

| 책임 | 하는 일 |
|---|---|
| 프로세스 관리 | 어떤 프로그램이 언제 CPU를 쓸지 결정 (스케줄러) |
| 메모리 관리 | 물리 메모리를 프로세스별로 쪼개고 보호 (가상 메모리, 페이지 테이블) |
| 파일 시스템 | 디스크의 비트 뭉치를 "파일"이라는 추상으로 제공 |
| 디바이스 I/O | 네트워크 카드, 디스크, 키보드 등을 드라이버로 통제 |

비유로는 **아파트 관리사무소**를 떠올리면 직관적입니다. 입주자(프로세스)들이 전기, 수도, 엘리베이터(하드웨어)를 직접 건드리지 못하게 하고, 필요할 때 관리사무소(커널)에 요청해야만 이용할 수 있게 합니다. 왜 이렇게 귀찮게 막아두어야 하는지는 다음 섹션의 주제입니다.

경계를 하나 짚어두면, 일반 프로그램은 CPU의 제한된 권한(유저 모드)에서만 돌고, 커널은 모든 권한을 가진 모드(커널 모드)에서 돕니다. `ls`, `bash`, `systemd`는 유저 공간 프로그램이지 커널이 아니며, `uname -r`로 찍히는 `6.8.0-generic` 같은 버전이 실제 커널 버전입니다.

## 왜 필요한가

한 문장으로 답하자면, 여러 프로그램이 하나의 하드웨어를 안전하게 공유해야 하고, 그 공유 관리자는 하드웨어 가까이에 있어야 하기 때문입니다.

커널이 없는 세상을 잠시 상상해봅시다. 1970년대 이전의 초기 컴퓨터가 실제로 그랬습니다. 한 번에 한 프로그램만 돌았고, 그 프로그램이 메모리, CPU, 디스크를 전부 점유했습니다. 두 프로그램을 동시에 돌리려 하면 네 가지 문제가 터집니다.

| 문제 | 구체적으로 무엇이 깨지는가 |
|---|---|
| 메모리 충돌 | 프로그램 A가 주소 `0x1000`에 쓰는 사이 B가 같은 주소를 덮어쓰면 A의 데이터가 사라짐 |
| 자원 독점 | B가 무한 루프에 빠지면 A는 영원히 CPU를 쓰지 못함. 강제 회수 수단이 없음 |
| 보안 부재 | 격리가 없으므로 A가 "이건 내 파일이야"라고 우기면 B의 파일을 읽을 수 있음 |
| 하드웨어 파편화 | 디스크 컨트롤러가 제조사마다 다르면 각 앱이 드라이버 코드를 직접 가짐. 버그 하나가 하드웨어 물리 손상까지 이어질 수 있음 |

커널이 해결하는 방식은 단순합니다. "하드웨어에 직접 접근할 수 있는 건 나뿐"이라는 규칙을 **CPU 하드웨어 수준**에서 강제합니다. 모든 프로그램은 하드웨어가 필요하면 커널에게 **부탁**하고, 커널이 대신 수행합니다. 이 "부탁"의 구체적 형식이 시스템 콜이며, 그 메커니즘이 다음 섹션의 중심입니다.

## 동작 원리

<Callout type="warning" title="이 구조를 이해하는 핵심">

</Callout>

<Callout type="error" title="핵심 통찰: 커널 격리는 소프트웨어 약속이 아니라 실리콘 회로가 강제한다">
  앱이 특권 명령어를 쓰지 못하는 이유는 커널이 체크해서가 아닙니다. CPU 내부의 로직이 Ring 3에서 특권 명령어를 만나면 회로적으로 거부하고 예외를 발생시킵니다. 격리는 하드웨어 위에 선 약속이 아니라, 하드웨어 자체에 새겨진 제약입니다.
</Callout>

### CPU 특권 레벨

x86 CPU는 코드가 실행될 때마다 "지금 몇 번 링(ring)에서 돌고 있는지"를 2비트 레지스터인 `CPL`(Current Privilege Level)에 기록합니다. 링은 0, 1, 2, 3 네 단계가 있고 **숫자가 작을수록 권한이 큽니다**. 실무에서는 사실상 두 개만 씁니다.

| Ring | 이름 | 허용 범위 |
|---|---|---|
| 0 | 커널 모드 | 모든 명령어. 특권 명령어(`LIDT`, `HLT`, `IN/OUT`, `MOV CR3`) 포함 |
| 3 | 유저 모드 | 일반 연산만. 특권 명령어 시도 시 General Protection Fault 예외 발생 |

"특권 명령어"가 왜 특별한지 감을 잡아봅시다. 페이지 테이블 레지스터(`CR3`)를 바꾸면 현재 프로세스가 어떤 메모리를 보는지가 즉각 달라집니다. 인터럽트 벡터(`IDT`)를 등록하면 모든 인터럽트가 내 코드로 넘어옵니다. I/O 포트(`IN/OUT`)는 디스크 컨트롤러와 직접 대화하는 명령입니다. 이걸 유저 앱이 실행할 수 있다면 격리는 즉시 무너집니다. 앱이 다른 프로세스의 페이지 테이블을 제 것처럼 고쳐 메모리를 훔쳐 읽을 수 있게 되니까요.

그래서 CPU 설계자들은 이 명령어들을 "Ring 0에서만 실행 가능"으로 **실리콘 레벨에서 막았습니다**. 소프트웨어 체크가 아니라 CPU 회로가 기계적으로 거부합니다. "여러 앱이 격리되어야 한다 → 소프트웨어로만 격리하면 우회 가능 → CPU가 하드웨어에서 강제해야 한다 → 특권 레벨이 생긴다"는 인과 사슬이 지금의 구조로 이어진 것입니다.

### 유저 모드와 커널 모드

같은 CPU, 같은 메모리이지만 "지금 어떤 모드냐"에 따라 동일한 명령어가 다르게 취급됩니다. 프로세스가 실행되는 동안 CPU는 **두 모드를 끊임없이 왕복**합니다. `read()` 한 번만 불러도 다음 흐름이 펼쳐집니다.

1. 유저 모드에서 `read()` 호출 준비
2. 모드 전환 → 커널 모드 진입
3. 커널이 디스크에서 데이터 읽음
4. 모드 전환 → 유저 모드 복귀
5. 유저 코드 계속 실행

여기서 중요한 구분이 하나 있습니다. **이것은 컨텍스트 스위칭이 아닙니다**. 같은 프로세스 안에서 모드만 바뀌는 것이지, 다른 프로세스로 가는 것이 아닙니다. 프로세스 전환은 페이지 테이블까지 갈아끼우는 무거운 작업이고, 모드 전환은 CPU 레지스터 일부만 교체하는 훨씬 가벼운 작업입니다. 가볍다고는 해도 파이프라인 flush와 캐시 오염이 있어 수십 나노초 수준의 비용이 발생합니다. 시스템 콜이 많은 워크로드가 곧 "모드 전환 비용이 누적되는 워크로드"가 되는 이유입니다.

### 시스템 콜의 정체

유저 프로그램이 파일을 읽고, 네트워크로 보내고, 새 프로세스를 만들려면 Ring 0의 기능이 필요합니다. 그런데 Ring 3에서 Ring 0으로 "그냥 점프"할 수는 없습니다. 그게 가능하면 격리가 무너지니까요. 대신 커널은 **딱 하나의 진입점**만 열어둡니다. 이것이 시스템 콜입니다.

x86-64 Linux에서 `read()` 한 번의 실제 흐름을 따라가 봅시다. 아래 시각화에서 단계마다 CPU 레지스터가 어떻게 바뀌는지, 그리고 어느 순간 모드 전환이 일어나는지를 확인할 수 있습니다.

<SyscallFlow />

핵심은 "유저가 커널 어느 주소로든 뛰어들 수 없다"는 점입니다. `syscall` 명령은 항상 커널이 부팅 시 등록해둔 **고정된 엔트리 포인트**(`MSR_LSTAR`에 저장된 주소)로만 진입합니다. 거기서 `RAX`에 실린 번호를 보고 정해진 핸들러로 분기합니다. 대사관 입국 심사처럼, 들어오는 문은 하나고 그 안에서 어느 창구로 갈지가 결정됩니다.

아래는 위 시각화에 대응하는 실제 호출 패턴을 간략히 어셈블리 수준에서 본 모습입니다.

```nasm title="read-syscall.s"
; glibc read() wrapper, x86-64 Linux
mov  rax, 0          ; syscall number: sys_read
mov  rdi, [fd]       ; arg1: file descriptor
mov  rsi, [buf]      ; arg2: user buffer
mov  rdx, [n]        ; arg3: byte count
syscall              ; Ring 3 → Ring 0, jump to MSR_LSTAR
; --- 커널에서 sys_read 실행 후 여기로 복귀 ---
; RAX 에 실제 읽은 바이트 수 (또는 -errno)
```

지금까지의 흐름을 인과 사슬로 묶으면 이렇게 됩니다. CPU가 하드웨어로 모드를 나눠야 격리가 강제된다. 그래서 앱과 커널은 같은 CPU에서 번갈아 돈다. 모드를 건너뛰는 유일한 합법 통로가 필요하다. 그것이 시스템 콜이라는 "등록된 진입점"이다.

## 어디서 마주치는가

커널을 "어떻게 구성할 것인가"에는 역사적으로 두 갈래가 있습니다. 모놀리식(Monolithic)과 마이크로커널(Microkernel)입니다. 이 선택은 "커널이 얼마나 많은 기능을 Ring 0 안에 넣을 것인가"의 문제로 요약됩니다.

### 모놀리식 커널

프로세스 스케줄러, 메모리 관리, 파일 시스템, 네트워크 스택, 디바이스 드라이버가 전부 하나의 큰 커널 안에 들어 있는 방식입니다. Linux, Windows NT, macOS의 XNU가 모두 이쪽 진영입니다.

작동 감각을 보려면 네트워크 패킷이 들어와서 파일에 저장되는 흐름을 따라가 봅시다.

1. 네트워크 카드 인터럽트 → 네트워크 드라이버 (커널 내부)
2. TCP/IP 스택 처리 (커널 내부)
3. 소켓 버퍼에 전달 (커널 내부)
4. 유저 앱이 `read()` → 버퍼 복사
5. 앱이 `write()` → 파일 시스템 (커널 내부) → 디스크 드라이버 (커널 내부)

한 패킷이 처리되는 동안 모드 전환은 2번뿐입니다 (`read` 진입과 `write` 진입). 네트워크에서 파일 시스템, 디스크까지의 이동은 전부 커널 내부 함수 호출이라 Ring 전환이 일어나지 않습니다. 함수 호출은 몇 사이클이면 끝나기 때문에 **빠릅니다**.

대신 모든 드라이버와 서브시스템이 Ring 0 안에 같이 살기 때문에, 한 드라이버의 버그가 커널 전체를 무너뜨릴 수 있습니다. Windows 블루스크린의 단골 원인이 서드파티 드라이버인 이유가 이것입니다. 그래픽 드라이버 한 줄의 null pointer dereference가 OS 전체를 죽입니다.

### 마이크로커널

Ring 0에는 **최소한의 것만** 넣는 방식입니다. 보통 스케줄러, 기본 IPC(Inter-Process Communication), 메모리 관리 정도만 커널 안에 있고, 파일 시스템, 네트워크 스택, 드라이버는 전부 **유저 공간의 별도 프로세스(서버)** 로 분리합니다. QNX, seL4, Minix가 이쪽입니다.

같은 네트워크 수신 흐름을 마이크로커널에서 보면 장면이 달라집니다.

1. 네트워크 카드 인터럽트 → 커널의 기본 핸들러
2. 커널이 IPC 메시지로 네트워크 서버(유저 공간 프로세스)에 전달
3. 네트워크 서버가 TCP/IP 처리 후 IPC로 파일 시스템 서버에 전달
4. 파일 시스템 서버가 IPC로 디스크 드라이버 서버에 전달
5. 디스크 드라이버 서버가 실제 디스크 I/O 수행

각 서버는 유저 공간의 독립 프로세스라서 단계마다 **Ring 전환과 IPC 메시지 복사**가 발생합니다. 모놀리식에서 함수 호출이었던 것이 여기서는 프로세스 간 메시지 왕복입니다. 느립니다.

대가의 반대편에는 격리와 내결함성이 있습니다. 네트워크 드라이버가 죽어도 커널은 살아 있습니다. OS가 드라이버 서버를 재시작하면 복구됩니다. 그래서 자동차 ECU, 항공기 제어, 원자력 제어처럼 "죽으면 사람이 다치는" 시스템에 쓰입니다. QNX가 차량 인포테인먼트와 원자로 제어 계통에 쓰이는 이유가 이쪽 특성 때문입니다.

### 수렴의 이유

1992년 Torvalds와 Tanenbaum의 USENET 논쟁에서 Tanenbaum은 "모놀리식은 한물갔다"고 주장했습니다. 30년이 지난 지금 데스크톱, 서버, 모바일의 압도적 다수는 모놀리식입니다. 왜 이쪽으로 수렴했을까요?

1990년대 하드웨어에서 마이크로커널의 IPC 오버헤드는 체감 가능한 느림이었습니다. 느린 OS는 시장에서 쉽게 도태됩니다. 반면 드라이버 안정성은 "자주 터지긴 해도 재부팅하면 되는" 허용 가능한 고통이었습니다. 성능이 먼저 팔렸고, 안정성은 나중에 해결하면 되는 문제로 취급된 것입니다.

그렇다고 Linux가 모놀리식의 단점을 방치한 것은 아닙니다. 시간이 지나며 마이크로커널의 아이디어를 일부 흡수했습니다. **FUSE**(Filesystem in Userspace)는 파일 시스템을 유저 공간에 두는 장치입니다. **eBPF**는 커널 안에서 샌드박스 실행되는 유저 로직으로 격리 이득을 노립니다. 커널 모듈 서명과 Lockdown 모드도 모놀리식의 약점을 완화하는 방향입니다.

결국 적용 기준은 이렇게 요약됩니다.

| 선택지 | 적합한 자리 | 이유 |
|---|---|---|
| 모놀리식 | 범용 데스크톱, 서버, 모바일 | 성능이 최우선이고 재부팅이 허용됨 |
| 마이크로커널 | 자동차, 항공, 의료, 원자력 | 한 드라이버가 죽어도 전체는 살아야 함 |

## 마무리

커널은 "하드웨어를 안전하게 공유하기 위해 하드웨어 가까이에 둔 관리자"입니다. 이 단순한 목적이 CPU 특권 레벨이라는 하드웨어 제약과 만나 유저/커널 모드 분리를 낳았고, 그 경계를 넘는 유일한 합법 통로로 시스템 콜이 수렴했습니다. 모놀리식과 마이크로커널의 갈래도 결국 "이 경계를 몇 겹 두고 어디에 둘 것인가"의 문제입니다.

이 글을 덮고 가져가야 할 한 문장을 고르자면, **커널 격리는 소프트웨어 약속이 아니라 CPU 회로가 강제하는 규칙**이라는 것입니다. 이 감각 위에서만 시스템 콜의 비용도, 블루스크린의 범위도, 마이크로커널이 원자로에 쓰이는 이유도 자연스럽게 이어집니다.
