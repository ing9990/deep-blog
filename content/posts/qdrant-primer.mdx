Qdrant는 벡터 검색 엔진 중에서도 <E>띄우고 붙이기</E>가 가장 쉬운 축입니다. Docker 한 줄로 서버가 뜨고, Python client 몇 줄이면 collection을 만들고 검색까지 이어집니다. 이 글은 그 흐름을 처음부터 끝까지 따라가며, 입문 단계에 가장 자주 걸리는 몇 가지 함정을 함께 짚습니다.

## Qdrant란

Qdrant는 Rust로 쓰인 오픈소스 벡터 검색 엔진입니다. 고차원 실수 벡터(예: OpenAI `text-embedding-3-small`의 1536차원)를 저장하고, 쿼리 벡터와 가장 가까운 이웃(ANN, Approximate Nearest Neighbor)을 빠르게 찾아주는 전용 DB입니다. 벡터 DB가 왜 필요한지, HNSW 같은 ANN 인덱스가 내부적으로 어떻게 동작하는지는 별도 글에서 이미 다뤘으니, 이 글에서는 Qdrant 자체의 특징과 사용법에만 집중합니다.

<RelatedPost slug="vector-database-primer" type="prerequisite" />

Qdrant를 다른 벡터 DB와 구분하는 세 가지 특징이 있습니다. 첫째, **Standalone 서비스**입니다. pgvector처럼 기존 RDB의 확장이 아니라 독립된 서버로 실행됩니다. HTTP/gRPC API로 접근하고, 의존성이 PostgreSQL에 없어 이식성이 높습니다. 둘째, **Payload가 1급 시민**입니다. 각 벡터에 JSON 문서 같은 payload를 붙여 저장하고, 검색할 때 payload 조건으로 필터링할 수 있습니다. 셋째, **Rust 구현**이라 싱글 바이너리로 배포되고, JVM 튜닝 같은 런타임 오버헤드가 없습니다.

본문에 앞서 용어 몇 개를 정리합니다.

- **Collection**: 같은 차원과 같은 거리 메트릭을 공유하는 벡터들의 묶음. RDB의 테이블에 해당한다.
- **Point**: Qdrant에 저장되는 한 단위. `id + vector + payload`로 구성된다.
- **Vector**: 실수 배열. 차원은 Collection 생성 시 고정된다.
- **Payload**: Point에 딸린 임의 JSON. 검색 필터와 결과 표시에 사용된다.

## 왜 Qdrant인가

벡터 DB 자체가 왜 필요한지는 위 사전 글이 답합니다. 이 절에서는 한 단계 더 좁혀서, 벡터 DB 중에서도 왜 특히 Qdrant를 선택지로 두는지만 보겠습니다. 실무에서 수렴하는 이유는 세 가지입니다.

첫 번째는 **시맨틱 검색과 metadata 필터를 함께 써야 하는 경우**입니다. RAG나 이커머스 추천에서 <E>의미가 비슷한 것</E>만 단독으로 필요한 경우는 드뭅니다. 대부분은 <E>카테고리가 X, 언어가 ko, 가격이 Y 미만인 것 중에서 의미가 비슷한 것</E>처럼 **벡터 유사도와 metadata 조건이 결합된 질의**입니다. pgvector에서도 이게 가능하지만, 필터가 강할 때 ANN 인덱스를 온전히 활용하기가 까다롭습니다. Qdrant는 payload 필터를 HNSW 그래프 탐색 단계에 결합(filtered HNSW)하도록 설계되어, 필터 조건이 있어도 성능이 급격히 무너지지 않습니다. 뒤에서 이 점을 자세히 보겠습니다.

두 번째는 **운영 단순성**입니다. Docker 한 줄로 서버가 뜨고, REST나 gRPC API로 바로 붙일 수 있습니다. 전담 운영자 없이도 도입 가능한 편입니다. 셀프 호스팅이 부담스러우면 관리형(Qdrant Cloud)도 있어서 선택지가 넓습니다.

세 번째는 **파이썬 RAG 생태계와의 궁합**입니다. LangChain, LlamaIndex, Haystack 같은 주요 RAG 프레임워크가 Qdrant를 1급으로 지원하고, OpenAI나 Cohere, HuggingFace 임베딩 모델과의 연동 예제가 풍부합니다. 처음 RAG를 붙일 때 <E>모델 → 저장 → 검색</E>의 전 과정을 최소 코드로 이을 수 있습니다.

## 기본 사용 흐름

이 섹션이 글의 중심입니다. 설치부터 payload 필터까지 5단계로 나눠 따라갑니다. Python client(`qdrant-client`)를 기준으로 설명하되, REST나 gRPC로 직접 붙여도 동일한 흐름입니다.

<Callout type="warning" title="이 섹션의 핵심 포인트">
  Qdrant 사용은 5단계로 이어집니다. 서버 실행 → Collection 생성 → Upsert → Search → Payload 필터. 이 중 **Collection 생성 시 고정되는 차원과 거리 메트릭**, 그리고 **필터 필드에 만들어야 하는 payload 인덱스**가 입문 단계에서 가장 흔하게 놓치는 두 결정입니다.
</Callout>

### 서버 실행

Qdrant의 장점 중 하나가 <E>띄우기 쉬움</E>입니다. 공식 Docker 이미지로 한 줄에 끝납니다.

```bash title="run-qdrant.sh"
docker run -p 6333:6333 -p 6334:6334 \
    -v $(pwd)/qdrant_storage:/qdrant/storage \
    qdrant/qdrant
```

포트가 2개 열리는 이유가 있습니다. **6333은 REST API**, **6334는 gRPC API**입니다. 같은 기능을 두 프로토콜로 제공하는데, Python client는 기본으로 REST를 쓰고, 대량 upsert나 고빈도 검색 구간에선 gRPC가 유리합니다. 바이너리 직렬화라 payload 오버헤드가 작기 때문입니다. 둘 다 매핑해두고 client 옵션으로 전환하면 됩니다.

볼륨 마운트 `-v $(pwd)/qdrant_storage:/qdrant/storage`는 **데이터 영속화**입니다. 이 줄을 빠뜨리면 컨테이너 재시작 시 collection이 날아갑니다. 입문 시점에 가장 흔한 실수라 뒤 `입문 함정` 섹션에서 다시 언급합니다.

Python client 설치와 연결은 다음과 같습니다.

```python title="connect.py"
# pip install qdrant-client
from qdrant_client import QdrantClient

client = QdrantClient(host="localhost", port=6333)
print(client.get_collections())  # 처음엔 빈 리스트
```

로컬 테스트라면 `QdrantClient(":memory:")` 같은 **인메모리 모드**도 있습니다. 실제 서버 없이 동작하지만 디스크 세그먼트 병합 같은 일부 내부 동작이 생략되므로, CI에서 통과한 코드가 운영에서 다르게 보일 가능성이 있다는 점만 기억하면 됩니다. 관리형 서비스(Qdrant Cloud)를 쓸 때는 `url`과 `api_key`만 바꾸면 됩니다.

```python
client = QdrantClient(
    url="https://xxx.aws.cloud.qdrant.io",
    api_key="...",
)
```

### Collection 만들기

벡터를 저장하려면 먼저 **Collection**을 만들어야 하고, 이 시점에 두 가지가 **고정**됩니다. 한 번 정하면 변경이 불가능해서, 나중에 바꾸려면 새 collection을 만들고 데이터를 옮겨야 합니다.

첫 번째는 **벡터 차원**(`size`)입니다. 앞으로 이 collection에 들어갈 모든 벡터의 차원이며, 보통은 사용할 임베딩 모델이 결정합니다.

| 모델 | 차원 |
|---|---|
| OpenAI `text-embedding-3-small` | 1536 |
| OpenAI `text-embedding-3-large` | 3072 |
| Cohere `embed-multilingual-v3` | 1024 |
| HuggingFace `all-MiniLM-L6-v2` | 384 |

중간에 모델을 바꾸면 차원이 달라져서 기존 벡터가 무의미해집니다. 이건 Qdrant만의 문제가 아니라 벡터 DB 공통인데, 입문 시점에 설계 실수로 가장 많이 겪는 지점입니다.

두 번째는 **거리 메트릭**(`distance`)입니다. 두 벡터가 얼마나 비슷한지 어떻게 계산할지 결정합니다. 선택지는 세 가지입니다.

| 메트릭 | 언제 쓰나 | 비고 |
|---|---|---|
| `Cosine` | 텍스트 임베딩의 기본값. 벡터 방향(각도)만 본다 | 내부적으로 벡터를 정규화해서 저장 |
| `Dot` | 정규화된 벡터 또는 scoring 모델에서 내적 자체가 의미 있을 때 | 벡터 크기가 결과에 영향 |
| `Euclid` | 물리 좌표, 이미지 feature 일부 등 실제 거리가 의미 있을 때 | 고차원에선 잘 안 씀 |

입문 단계에서 텍스트 임베딩을 다룬다면 **`Cosine` 하나만 기억하면 거의 충분**합니다. 모델이 권장하는 메트릭이 따로 있으면 그걸 따르면 됩니다. OpenAI는 cosine을 권장합니다. 실제 코드는 이렇게 생겼습니다.

```python title="create_collection.py"
from qdrant_client.models import VectorParams, Distance

client.create_collection(
    collection_name="articles",
    vectors_config=VectorParams(
        size=1536,          # OpenAI text-embedding-3-small
        distance=Distance.COSINE,
    ),
)
```

HNSW 파라미터(`M`, `ef_construct`)나 디스크 저장(`on_disk=True`) 같은 세부 옵션도 있지만 기본값이 합리적이라 입문 단계에선 건드릴 필요가 없습니다. 프로덕션에서 대규모 벡터를 다루게 되면 그때 튜닝하면 됩니다.

### Upsert

Collection이 생겼으니 데이터를 넣을 차례입니다. Qdrant에서 한 건의 데이터는 **Point**라고 부르고 세 부분으로 이뤄집니다.

- `id`: 정수 또는 UUID. 임의의 문자열 ID는 허용되지 않으며, 문자열을 쓰려면 UUID 형식이어야 한다.
- `vector`: Collection의 `size`와 일치하는 float 리스트.
- `payload`: 임의의 JSON dict. 필수는 아니지만 거의 항상 같이 넣는다.

연산 이름이 <E>Upsert</E>인 이유는 **같은 id가 있으면 덮어쓰고, 없으면 새로 삽입**하기 때문입니다. 입문 시점에 이 동작이 직관적이라 편합니다. 가장 기본적인 호출은 다음과 같습니다.

```python title="upsert_basic.py"
from qdrant_client.models import PointStruct

client.upsert(
    collection_name="articles",
    points=[
        PointStruct(
            id=1,
            vector=[0.12, -0.34, 0.07],  # ...실제로는 1536개
            payload={
                "title": "Qdrant 입문",
                "category": "infrastructure",
                "lang": "ko",
                "tags": ["vector-db", "rag"],
            },
        ),
        PointStruct(id=2, vector=[0.08, 0.11, -0.22], payload={"title": "..."}),
    ],
)
```

실제 파이프라인에서는 벡터를 직접 쓸 일이 없고, 임베딩 모델로 문서에서 벡터를 뽑아 넣는 흐름이 됩니다. OpenAI 기준의 전형적인 코드는 다음과 같습니다.

```python title="upsert_with_openai.py"
from openai import OpenAI
from qdrant_client.models import PointStruct

openai = OpenAI()

docs = [
    {"id": 1, "text": "Qdrant는 Rust로 쓰인 벡터 검색 엔진입니다.", "category": "infra"},
    {"id": 2, "text": "pgvector는 PostgreSQL의 확장입니다.", "category": "infra"},
]

resp = openai.embeddings.create(
    model="text-embedding-3-small",
    input=[d["text"] for d in docs],
)

points = [
    PointStruct(
        id=d["id"],
        vector=resp.data[i].embedding,
        payload={"text": d["text"], "category": d["category"]},
    )
    for i, d in enumerate(docs)
]

client.upsert(collection_name="articles", points=points)
```

입문자가 놓치기 쉬운 지점이 두 가지 있습니다. 하나는 **배치 크기**입니다. 수만 건을 단일 요청으로 보내면 서버 타임아웃 또는 메모리 압박이 생깁니다. 보통 100~500건 단위 배치로 쪼개고 반복합니다. 아주 대량이면 `client.upload_collection()` 같은 파일 업로드 API를 씁니다. 다른 하나는 **인덱싱 지연**입니다. 기본 upsert는 요청이 즉시 반환되지만, 직후 바로 검색하면 아직 인덱싱되지 않은 상태일 수 있습니다. 테스트 코드에서는 `client.upsert(..., wait=True)`로 완료 대기를 걸면 확실합니다.

### 검색

이제 가장 중요한 부분입니다. **쿼리 벡터를 주면 collection에서 가장 비슷한 N개**를 돌려받는 동작입니다. 최신 `qdrant-client`에서 권장하는 API는 `query_points`입니다. 구버전의 `search`도 지금 동작하지만 레거시 경로입니다.

```python title="search_basic.py"
query_vec = openai.embeddings.create(
    model="text-embedding-3-small",
    input="벡터 DB 입문",
).data[0].embedding

result = client.query_points(
    collection_name="articles",
    query=query_vec,
    limit=5,               # top_k
    with_payload=True,     # 결과에 payload 포함
)

for point in result.points:
    print(point.id, point.score, point.payload["title"])
```

반환되는 각 point는 `id`, `score`, `payload`, 그리고 옵션으로 `vector`를 가집니다. `score`의 의미는 collection 생성 시 고른 **거리 메트릭에 따라 반대**입니다.

- `Cosine` 또는 `Dot`: **클수록 비슷함** (최대 1에 가까움)
- `Euclid`: **작을수록 비슷함** (0에 가까움)

이걸 모르고 <E>score가 0.8이면 유사도 80%?</E>로 오해하는 경우가 많은데, 코사인 기반 0.8은 꽤 비슷한 편이고, 유클리드 기반 0.8은 오히려 거리가 꽤 있는 편입니다. 메트릭을 확인하지 않고 score만 절대비교하지 않도록 주의합니다.

자주 쓰는 옵션 세 가지는 다음과 같습니다.

```python
client.query_points(
    collection_name="articles",
    query=query_vec,
    limit=10,
    with_payload=True,       # payload 포함 여부 (기본 False)
    with_vectors=False,      # vector 포함 여부 (기본 False, 보통 False 유지)
    score_threshold=0.7,     # 이 점수 이하는 버림 (cosine 기준)
)
```

`with_vectors=False`를 유지하는 이유는 벡터 자체가 전송량 대부분을 차지하기 때문입니다. 1536차원이면 한 point당 float 1536개로 약 6KB, 검색 결과 50개면 300KB가 그냥 벡터로 나갑니다. 결과 화면에서 벡터를 다시 쓸 일이 없으면 꺼두는 게 기본값입니다. `score_threshold`는 RAG에서 특히 유용합니다. 관련 없는 문서가 LLM 컨텍스트에 섞이면 답변 품질이 떨어지기 때문에, 0.7~0.8 같은 임계값으로 미리 거르는 패턴이 흔합니다.

### Payload 필터

Qdrant를 고르는 이유의 절반이 payload 필터라고 앞서 언급했습니다. 여기가 그 이유를 실제로 보여주는 부분입니다.

RAG에서 <E>이 사용자에게만 공개된 문서 중에서 질문과 비슷한 것 5개</E>를 찾는다고 해봅시다. 순수 벡터 검색만 한 뒤 후처리로 권한을 거르면 위험합니다. 상위 5개가 전부 권한 없는 문서면 결과가 비어버립니다. 정답은 <E>권한 있는 문서 안에서 비슷한 5개를 뽑는 것</E>입니다. Qdrant에서는 `query_points`에 **Filter**를 같이 넘겨서 해결합니다.

```python title="search_with_filter.py"
from qdrant_client.models import Filter, FieldCondition, MatchValue

result = client.query_points(
    collection_name="articles",
    query=query_vec,
    limit=5,
    with_payload=True,
    query_filter=Filter(
        must=[
            FieldCondition(key="category", match=MatchValue(value="infrastructure")),
            FieldCondition(key="lang", match=MatchValue(value="ko")),
        ],
    ),
)
```

Filter는 SQL WHERE와 비슷하지만 **세 가지 부울 조합**으로 구성됩니다.

- `must`: 전부 만족해야 함 (AND)
- `should`: 하나라도 만족하면 가산점 (OR, 필수는 아님)
- `must_not`: 하나라도 만족하면 제외 (NOT)

조건 종류도 다양합니다. 완전일치, IN, 범위, 배열 길이, 지리 좌표, null 체크 등이 지원됩니다.

```python
from qdrant_client.models import MatchValue, MatchAny, Range

# 완전일치 (문자열, 숫자, 불리언)
FieldCondition(key="category", match=MatchValue(value="infrastructure"))

# 여러 값 중 하나 (IN)
FieldCondition(key="tags", match=MatchAny(any=["rag", "vector-db"]))

# 숫자 범위
FieldCondition(key="price", range=Range(gte=1000, lt=50000))
```

<Callout type="error" title="핵심 통찰: 필터 필드에는 반드시 Payload Index">
  Collection을 막 만들었을 때 payload 필드에는 인덱스가 없습니다. 이 상태에서 필터를 쓰면 Qdrant는 후처리 방식으로 동작하거나, 필터가 강할 때 ANN 성능이 크게 떨어집니다. Qdrant가 pgvector 대비 내세우는 **filtered HNSW** 경로는 payload 인덱스가 있을 때만 활성화됩니다.
</Callout>

고정적으로 필터에 쓰는 필드는 **명시적으로 payload index를 만들어야** 합니다.

```python title="create_payload_index.py"
from qdrant_client.models import PayloadSchemaType

client.create_payload_index(
    collection_name="articles",
    field_name="category",
    field_schema=PayloadSchemaType.KEYWORD,  # 문자열 완전일치용
)

client.create_payload_index(
    collection_name="articles",
    field_name="price",
    field_schema=PayloadSchemaType.INTEGER,  # 범위 쿼리용
)
```

인덱스가 있으면 Qdrant는 filtered HNSW 경로를 써서 필터 조건을 그래프 탐색 단계에 결합합니다. 이게 Qdrant가 자랑하는 지점입니다. 필터가 까다로워도 ANN 성능이 안 무너집니다. 입문 시점에 기억할 것은 하나입니다. **필터에 쓰는 payload 필드는 반드시 payload index를 만든다.**

## 입문 함정

지금까지의 흐름을 따라오면서 이미 곳곳에서 <E>이건 놓치기 쉽다</E>를 언급했습니다. 이 섹션은 그것들을 한 곳에 모은 참조 박스입니다. 입문 후 실제로 짜증나는 순서대로 정리합니다.

**1. 볼륨 마운트 누락으로 데이터 소실**. `docker run ... qdrant/qdrant`만 치고 테스트하다가 컨테이너를 재시작하는 순간 collection과 벡터가 증발합니다. 로컬에선 `-v $(pwd)/qdrant_storage:/qdrant/storage`를, 프로덕션 쿠버네티스에선 StatefulSet과 PVC를 반드시 붙입니다.

**2. 임베딩 모델 교체 시 collection 재생성 필요**. Collection의 차원과 거리 메트릭은 생성 후 변경이 불가능합니다. 모델을 `text-embedding-3-small`(1536차원)에서 `large`(3072차원)로 바꾸려면 새 collection을 만들고 전체 재임베딩 및 재삽입이 필요합니다. <E>모델 바꾸면 collection 다시 만든다</E>를 운영 체크리스트에 넣어두는 게 안전합니다.

**3. score 메트릭 혼동**. `Cosine`/`Dot`는 클수록 비슷, `Euclid`는 작을수록 비슷. 여러 collection을 다루면 메트릭이 섞이는 순간 score 비교가 무의미해집니다. 한 프로젝트에서는 메트릭을 통일(대부분 cosine)하고, score 임계값은 코드 상수가 아니라 메트릭과 묶어서 관리합니다.

**4. 필터 거는 payload 필드에 인덱스 없음**. 앞에서 강조한 그 문제입니다. 필터에 쓰는 필드에 `create_payload_index`를 빠뜨리면 데이터가 커질수록 검색 지연이 비선형적으로 늘어납니다. Qdrant를 선택한 이유 중 하나(filtered HNSW)가 꺼진 상태입니다.

**5. Upsert 직후 검색에서 결과 누락**. 기본 upsert는 즉시 반환되고 인덱싱은 조금 뒤 완료됩니다. 테스트 코드나 초기 데이터 로드 후 검증에서는 `wait=True`를 넣습니다. 프로덕션에서는 보통 무시해도 되지만 <E>데이터 로드 → 검증 → 서비스 오픈</E> 흐름에서 주의해야 합니다.

**6. 대량 upsert 타임아웃**. 수만에서 수십만 건을 한 번에 넣으려고 하면 서버가 힘들어합니다. 배치 100~500 단위가 현실적이고, 아주 대량은 `upload_collection()`이나 snapshot import 경로를 씁니다.

## 트레이드오프

마지막으로, 벡터 DB를 고를 때 Qdrant 대신 다른 선택지가 나을 수 있는 조건들을 짧게 정리합니다. <E>언제 Qdrant가 맞고, 언제 다른 게 나을지</E>의 감각만 남기는 게 목표입니다.

| 옵션 | 장점 | 단점 |
|---|---|---|
| Qdrant | filtered HNSW 강함, 운영 단순, Rust 싱글 바이너리 | 별도 서버를 운영해야 함 |
| pgvector | 기존 PostgreSQL 그대로, 트랜잭션/조인 활용 가능 | 필터 강할 때 ANN 성능 저하, RDB와 자원 경쟁 |
| Milvus | 수억 이상 분산 확장, 기능 풍부 | 구성 요소 많음(etcd, Pulsar 등), 운영 복잡 |
| Elasticsearch | 이미 ES 기반이면 합치기 쉬움 | 벡터 전용 대비 성능/기능 제한, 리소스 무거움 |
| Pinecone | 관리형, 인프라 고민 제로 | 외부 SaaS, 비용과 데이터 상주 제약 |

조건별 선택 가이드는 다음과 같습니다. **이미 PostgreSQL이 중심이고 데이터 규모가 수백만 미만, 필터도 단순**하면 **pgvector**로 시작하는 게 운영 부담이 가장 작습니다. **벡터 검색과 metadata 필터가 핵심 워크로드이고 수천만 규모, 독립 운영이 가능**하면 **Qdrant**입니다. 이 글이 타겟한 지점입니다. **수억 이상 벡터에 여러 팀이 공유하고 전담 운영 인력이 있다**면 **Milvus**를 고려하되 운영 복잡도는 감수해야 합니다. **이미 ES 기반 검색 파이프라인이 있고 벡터를 보조 신호로 섞고 싶다**면 **Elasticsearch dense_vector**입니다. **인프라 운영 자체를 하기 싫고 예산이 있다**면 **Pinecone** 또는 **Qdrant Cloud**가 선택지입니다.

## 마무리

Qdrant 입문의 핵심은 다섯 단계의 흐름과 두 가지 결정으로 요약됩니다. 흐름은 **서버 실행 → Collection 생성 → Upsert → Search → Payload 필터**. 결정은 **Collection 생성 시 차원과 거리 메트릭을 어떻게 고정할지**, 그리고 **필터에 쓸 payload 필드에 인덱스를 만들었는가**입니다. 이 두 가지만 놓치지 않으면 Qdrant의 강점인 filtered HNSW를 그대로 살릴 수 있고, 입문 단계의 대부분의 함정을 피할 수 있습니다.

이 글을 덮고 나면 로컬 서버에 작은 collection을 하나 만들고, 문서 몇 개를 임베딩해 넣은 뒤, payload 필터를 걸어 검색해보는 것을 권합니다. 다섯 단계를 한 번 손으로 지나가 보는 것이 읽기만 하는 것보다 훨씬 빠른 학습 경로입니다.
