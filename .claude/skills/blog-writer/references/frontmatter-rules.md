# Frontmatter Rules

Stage 3 진입 직후 스킬은 frontmatter 초안을 자동 생성하고 사용자에게 표 형태로 제시해 1회 승인을 받는다. 수정 요청이 있으면 해당 필드만 교체한 뒤 재제시한다.

---

## 자동 생성 필드

아래 6개 필드는 모두 스킬이 자동 생성하고, 사용자 1회 승인을 받은 뒤 확정한다.

- `title` — 주제 + 부제
- `slug` — URL 경로 식별자
- `date` — 오늘 날짜
- `tags` — 분류 태그 (2~5개)
- `keywords` — 자동 링크 대상 키워드
- `summary` — 인덱스 카드 요약문

---

## 각 필드 로직

### title

Stage 1 첫 턴 주제와 부제를 결합한다. 부제는 Stage 2 노트의 "한 줄 주제"에서 추출한다. 형식: `"<주제>: <부제>"`

예시:
- 입력: "캐시 스탬피드" → `"캐시 스탬피드: 캐시가 DB를 폭격할 때"`
- 입력: "분산 락" → `"분산 락: Redlock 논쟁과 실용적 대안"`
- 입력: "JPA N+1 문제" → `"JPA N+1 문제: 3가지 해결 전략의 트레이드오프"`

부제는 독자의 관심을 끄는 방향으로 작성한다. "~의 동작 원리" 같은 중립적 부제보다 "~이 왜 위험한가", "~의 진짜 트레이드오프" 같이 긴장감이 있는 표현을 선호한다.

### slug

소문자 + 하이픈만 사용한다 (CLAUDE.md §4.1 규칙). 한글 주제는 영문 대표어로 변환한다.

예시:
- "캐시 스탬피드" → `cache-stampede`
- "데이터베이스 인덱스의 동작 원리" → `how-database-index-works` (또는 `database-index`로 단순화 후보 제시)
- "JPA 영속성 컨텍스트" → `jpa-persistence-context`

변환이 모호하면 사용자에게 2~3개 후보를 제시한 뒤 선택을 요청한다. 자동으로 결정하지 않는다.

### date

오늘 날짜를 `YYYY-MM-DD` 형식으로 사용한다. 시스템 날짜를 `date +%Y-%m-%d` 또는 동등한 방법으로 획득한다.

### tags

**필수 제약:**
- 2~5개 (CLAUDE.md §4.2)
- 카테고리 상위 태그 1개 이상 필수: `Backend`, `Database`, `Infrastructure`, `CS`, `DevOps`, `Architecture` 중 선택

**자동 생성 흐름:**
1. 기존 태그 목록 스캔: `content/posts/**/*.mdx` frontmatter에서 모든 태그 수집
2. 주제에 어울리는 기존 태그 우선 선택
3. 기존 태그로 부족하면 신규 태그 제안 (아래 §신규 태그 경고 참조)

**대소문자 엄격 일치**: `Database`와 `database`는 다른 태그로 취급된다. 기존 목록과 정확히 매칭해야 한다. 스캔 결과와 정확히 동일한 문자열을 재사용한다.

### keywords

`keywords` 배열에는 영문 대표어 + 한글 + 동의어 1개를 포함한다.

예시: `["Cache Stampede", "캐시 스탬피드", "Thundering Herd"]`

**충돌 체크 필수**: `lib/generated/keyword-map.ts`를 로드한 뒤 기존 키워드와 대소문자를 정규화해 비교한다. 충돌 발견 시 아래 §키워드 충돌 해결 절차를 따른다.

이 글이 "권위를 갖는" 키워드만 등록한다. 단순 언급 수준의 키워드는 등록하지 않는다.

### summary

노트 "Why" 섹션 첫 문단을 기반으로 작성한다.

**관점 규칙**: "무엇을 설명합니다" 형태는 금지. "~을 이해할 수 있습니다" 또는 "~을 구분할 수 있습니다" 관점으로 작성한다.

**길이 제약**: 10~300자 (Velite 스키마 제약). 1~2 문장 권장. 너무 짧으면 인덱스 카드가 빈약하고, 너무 길면 카드에서 잘린다.

예시: "캐시 스탬피드는 구현 버그가 아니라 설계 가정의 깨짐입니다. 트레이드오프 관점에서 완화 전략을 비교하고, 왜 완벽한 해결책이 없는지 살펴봅니다."

## draft:true 충돌 방지 전략

**문제**: 키워드 맵은 같은 키워드가 두 글에 등록되면 빌드 실패한다. 새 글을 바로 `draft: false`로 저장하면 충돌 시점이 늦어지고, 이미 절반쯤 작성된 뒤 실패한다.

**해결 절차**:

1. frontmatter 초안 확정 → `draft: true`로 `content/posts/<slug>.mdx` 저장
2. `pnpm generate-keyword-map` 실행 — draft 글은 맵에 편입되지 않으므로 충돌 없음
3. 사용자 승인 + 검증 루프(`velite` → `type-check` → `build`) 성공
4. `draft: false`로 전환
5. `pnpm generate-keyword-map` 재실행 — 이 시점에 키워드가 정식 등록됨. 충돌 있으면 여기서 발견되고 사용자 결정 요청

이 전략은 키워드 충돌 dry-run 로직을 재구현할 필요를 없앤다. 공식 빌드 파이프라인을 그대로 활용한다.

## 사용자 승인 흐름

스킬이 frontmatter 초안을 완성하면 아래 형식으로 제시한다:

```
Frontmatter 초안을 준비했습니다. 검토해주세요:

  title:    <제목>
  slug:     <slug>
  date:     <YYYY-MM-DD>
  tags:     <태그 리스트>
            └─ 기존 태그 N개 중 K개 재사용, M개 신규
  keywords: <키워드 리스트>
            └─ 기존 키워드 맵과 충돌 체크: 충돌 없음 ✓ / 충돌 M건 ⚠️
  summary:  <요약 문장>
            (N자)

수정할 항목이 있나요? ("OK", "summary만 다시", "태그 변경: ..." 등으로 응답)
```

사용자 응답 패턴:
- `"OK"` — 전체 승인, Stage 3 본문 작성으로 진행
- `"summary만 다시"` — summary만 재생성, 나머지 유지
- `"태그 변경: [Database, CS]"` — 지정된 태그 목록으로 교체 후 재제시
- `"slug를 jpa-n-plus-one으로"` — 해당 필드만 교체 후 재제시

재제시 시에는 변경된 필드에 `(변경됨)` 표시를 붙여 어디가 바뀌었는지 명확히 한다.

## 신규 태그 경고

기존 태그로 표현 불가능한 신규 태그를 만들어야 할 때는 반드시 경고를 노출한다:

```
⚠️ 신규 태그 N개를 만들려 합니다: [태그1, 태그2]
   기존 태그 M개 중 K개 재사용, N개 신규.
   진행할까요? (또는 기존 태그로 대체 요청)
```

신규 태그는 정당화 가능한 경우에만 추가한다. 기존 태그로 충분히 표현 가능하면 재사용을 우선한다.

## 키워드 충돌 해결

충돌 감지 시 아래 형식으로 사용자에게 옵션을 제시한다:

```
⚠️ 키워드 충돌 감지:
   "<키워드>" 이(가) 이미 `<기존-slug>` 글에 등록되어 있습니다.

해결 옵션:
  (1) 더 구체화: "<키워드>" → "<키워드 — 더 구체적 형태>" (예: "Cache" → "Cache Stampede")
  (2) 기존 글에서 키워드 이전: <기존-slug>에서 "<키워드>" 제거하고 이 글로 이전
  (3) 이 키워드 제외: frontmatter에서 "<키워드>"를 빼고 다른 키워드만 사용

어떤 옵션을 선택하시겠어요?
```

사용자가 옵션 (2)를 선택하면 기존 MDX 파일의 frontmatter를 수정한다. 수정 전에 "기존 글을 수정합니다 — 계속할까요?"를 한 번 더 확인한다.
