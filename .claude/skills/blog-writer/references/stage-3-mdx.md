# Stage 3: MDX Generation

Stage 2에서 최종화된 노트(`.claude/drafts/<slug>-notes.md`)를 입력으로 실제 MDX 파일을 작성한다. 이 노트는 Stage 1 §0.6에서 생성되고 §4 Q&A 루프 동안 live로 쌓인 뒤 Stage 2에서 검토·보완된 결과물이므로, Stage 3는 노트를 **Read로 다시 읽어** 최신 상태를 사용한다 (컨텍스트 기억에 의존하지 않음). 본문 구조는 노트의 7-섹션을 타입별 매핑에 따라 H2 섹션으로 변환하며, 자동 콜아웃 3종과 교차 참조 컴포넌트를 정해진 위치에 배치한다.

## 본문 구조 매핑

노트의 5-섹션을 MDX H2 섹션으로 매핑한다. **타입에 따라 섹션 4의 매핑이 달라지므로**, Stage 2 노트 헤더의 `타입` 필드를 먼저 확인한 뒤 해당 타입의 매핑을 그대로 따른다.

### Type A 매핑 (CS 지식)

| 노트 섹션 | MDX 헤딩 예시 |
|---|---|
| 1. What | `## <주제>란` |
| 2. Why | `## 왜 중요한가` |
| 3. How | `## 동작 원리` |
| 4. When | `## 어디서 마주치는가` |
| 5. Tradeoffs | `## 트레이드오프` |

### Type B 매핑 (기술·도구)

| 노트 섹션 | MDX 헤딩 예시 |
|---|---|
| 1. What | `## <주제>란` |
| 2. Why | `## 왜 필요한가` |
| 3. How | `## 내부 동작` |
| 4. Problems | `## 실전 문제` |
| 5. Tradeoffs | `## 트레이드오프` |

### 공통 규칙

**헤딩은 TOC(ON THIS PAGE)에 그대로 노출된다.** 짧고 스캔하기 쉬운 한국어 제목을 쓴다. 아래 규칙을 반드시 지킨다.

1. **영문 섹션 태그 금지** — `(What)`, `(Why)`, `(How)`, `(When)`, `(Tradeoffs)`, `(Problems)` 등 영문 괄호를 헤딩에 붙이지 않는다. 이 태그들은 노트(Stage 2)의 내부 구분용이며 발행 헤딩에는 사용하지 않는다.
2. **H2는 10자 이내, H3는 15자 이내**를 목표로 한다 (띄어쓰기 포함). TOC에서 줄바꿈 없이 한 줄에 들어오는 길이가 기준이다.
3. **문장형 헤딩 금지** — 헤딩은 명사구 또는 짧은 의문형으로 쓴다. `"나누는" 모든 곳에서 카디널리티가 작동한다` 같은 서술형 문장은 본문 첫 줄에 쓰고, 헤딩은 `나누기의 원리` 수준으로 축약한다.
4. 위 매핑 테이블은 예시이며, 주제에 맞는 자연스러운 한국어 제목으로 자유롭게 조정한다. 핵심은 **짧고 직관적**인 것이다.

Section 5는 노트에 해당 내용이 실질적으로 기술되어 있을 때만 생성한다. 내용이 없는 섹션은 억지로 채우지 않는다.

**H2 시각적 구분**: 렌더링 시 모든 H2 상단에 `border-top` 구분선 + 넉넉한 여백(`margin-top: 3em`, `padding-top: 1.5em`)이 자동 적용된다. 섹션 전환마다 시각적 호흡이 생기므로, 작성자가 수동으로 `---` 구분선을 삽입할 필요가 없다. MDX 본문에 `---`(thematic break)를 넣으면 이중 구분선이 되므로 사용하지 않는다.

**두 타입 모두**: Section 3 (How)이 글 전체 분량의 큰 부분을 차지해야 한다 — 이 섹션이 짧으면 미완성이다.

## Hook Paragraph 작성법

- **위치**: frontmatter 직후, 학습 목표 콜아웃 직전
- **분량**: 2~3 문장. 너무 길면 독자 피로를 유발한다.
- **목적**: 독자의 관심을 끌고 본문 진입 동기를 부여한다.
- **관점**: "이 글을 읽으면 무엇을 얻는가" — 사실 나열이 아니라 독자 가치 중심으로 작성한다.
- **작성 소스**: Stage 2 노트의 Why 섹션 + 한 줄 주제에서 뽑는다.

Hook paragraph 예시 (캐시 스탬피드 주제):

```mdx
캐시 스탬피드는 구현 버그가 아닙니다. 캐시 키가 동시에 만료될 때 수십 개의 요청이 DB로 몰리는 현상은, "캐시가 있으면 DB를 보호한다"는 가정 자체가 깨지는 순간에 발생합니다. 이 글에서는 왜 완벽한 해결책이 없는지, 그리고 각 완화 전략이 어떤 가정을 요구하는지 살펴봅니다.
```

## 자동 삽입 콜아웃 3종

스킬은 매 글에 다음 3개 콜아웃을 자동 삽입한다. 이 3개는 독자의 이해를 구조적으로 돕는 장치이며, 사용자가 명시적으로 "빼달라"고 할 때만 제거한다. 이 3종 외에도 **보조 콜아웃**(흔한 오해/반론 warning, 전제 지식 info 등)을 필요한 위치에 추가할 수 있다. 보조 콜아웃 상세는 `style-guide.md`의 "자주 쓰는 패턴" 참고.

### 1. info — 학습 목표 (글 서두)

- **위치**: Hook paragraph 직후, 첫 번째 H2(`## 왜 이 주제를 알아야 하는가`) 직전
- **용도**: 독자가 첫 30초 안에 "이 글이 내게 가치 있는가"를 판단할 수 있도록 한다.
- **내용**: 3가지 학습 목표 bullet list. Stage 2 노트의 "Why" 섹션에서 추출한다.

정확한 템플릿:

```mdx
<Callout type="info" title="이 글의 학습 목표">
  1. <학습 목표 1 — "~을 이해한다" 형태>
  2. <학습 목표 2 — "~을 구분할 수 있다" 형태>
  3. <학습 목표 3 — "~을 선택하는 기준을 얻는다" 형태>
</Callout>
```

학습 목표 번호 앞에는 서식 없는 순서 숫자를 쓴다. 동사 형태는 3가지 패턴을 순서대로 적용한다: (1) "이해한다", (2) "구분할 수 있다", (3) "선택하는 기준을 얻는다". 주제에 따라 동사는 조정 가능하지만 마지막 목표는 항상 독자가 가져갈 판단 기준이어야 한다.

### 2. warning — 핵심 포인트 (타입별 분기)

- **위치**:
  - Type A: Section 3 (How) 상단, 메커니즘 설명 직전
  - Type B: Section 3 (How) 상단, 메커니즘 설명 직전
- **용도**: 이 섹션의 핵심을 한 문단으로 요약해 독자가 빠르게 핵심을 파악할 수 있게 한다. 독자가 이 섹션을 건너뛰었더라도 한 문단에서 핵심 교훈을 얻도록 설계된 장치다.

#### Type B 템플릿

```mdx
<Callout type="warning" title="이 글의 핵심 포인트">
  아래 N가지 전략은 각각 **서로 다른 상황**에서 유리합니다.
  자신의 시스템 환경과 요구사항을 먼저 파악해야 올바른 선택이 가능합니다.
</Callout>
```

N은 실제 전략/대안 개수로 치환한다. 문구는 주제에 맞게 조정 가능하다.

#### Type A 템플릿

```mdx
<Callout type="warning" title="이 구조를 이해하는 핵심">
  이 구조는 현재의 CS 제약(<하위 제약 구체 — 예:
  "디스크 seek 비용과 연속 읽기의 경제학", "메모리 계층의 지연 격차",
  "TCP 혼잡 제어의 AIMD" 등>) 하에서 이런 형태로 작동합니다.
  이 제약을 이해하면 구조 전체가 자연스럽게 따라옵니다.
</Callout>
```

`<하위 제약 구체>`는 해당 글의 Root Cause에서 실제로 드러낸 핵심 제약 1~3개로 치환한다. 문구는 주제에 맞게 조정 가능하다.

### 3. error — 핵심 통찰 (Root Cause 섹션, 타입별 강조점 차이)

- **위치**:
  - Type A: Section 3 (How) 내부, 핵심 메커니즘 직전
  - Type B: Section 3 (How) 내부, 핵심 메커니즘 직전
- **용도**: 글의 가장 중요한 "한 문장 깨달음"을 강조한다. `error` 타입은 시각적으로 가장 강한 신호이므로 한 글에 **한 번만** 쓴다.

공통 템플릿:

```mdx
<Callout type="error" title="핵심 통찰: <한 줄 요약>">
  <Root Cause 섹션의 가장 중요한 한 문장 — 타입에 따라 강조점이 다름>
</Callout>
```

#### Type B 강조점

**가정의 깨짐, 모델링의 gap, 구조적 취약점**을 드러낸다. 독자가 "아, 이 도구/패턴은 특정 가정 위에 서 있구나"라고 깨닫게 하는 것이 목적.

예: `핵심 통찰: 캐시 스탬피드는 캐시 계층의 구조적 취약점이다` — 본문에서 "독립 만료 가정이 실제 워크로드에서는 성립하지 않는다"를 2~3 문장으로 서술.

#### Type A 강조점

**CS 제약의 필연성, 제약 → 구조의 인과**를 드러낸다. 독자가 "아, 이 구조는 CS 하부 제약이 강제한 결과구나"라고 깨닫게 하는 것이 목적.

예: `핵심 통찰: B+Tree는 자료구조의 미학이 아니라 디스크 I/O 경제학의 산물이다` — 본문에서 "디스크 seek가 비싸고 연속 읽기가 싸다는 단일 제약이 페이지 단위 I/O를 강제했고, 이것이 B+Tree의 높은 fanout과 낮은 트리 높이를 필연적으로 만들었다"를 2~3 문장으로 서술.

두 타입 모두 **글 전체의 철학적 중심**을 한 문장으로 응축하는 장치다. 제목의 `<한 줄 요약>`은 글의 "Root Cause" 섹션에서 가장 중요한 한 문장으로 채운다.

## 섹션별 시각화 배치

어떤 시각화를 어디에 배치할지 결정하는 기준이다. 자세한 판단 로직은 `visualization-rules.md` 참조.

- **Section 3 (Alternatives & Tradeoffs)**: 비교표 (`| ... |`) 우선. 영역별 유불리가 다른 복잡한 트레이드오프 매트릭스는 **[A-2] 정적 React 컴포넌트**(센티먼트 인디케이터 — `CardinalityTradeoff` 패턴 참고)로 색상 코딩한다.
- **Section 4 (Root Cause)**: [A-2] 정적 React 컴포넌트 권장. 가정/모델의 시각화, 시스템 개념도, 타이밍 도식. `vizStateClasses()` 기반 색상 시맨틱으로 구조를 한눈에 전달한다.
- **Section 5 (How)**: [A-1] 인터랙티브 React 컴포넌트 권장. 동적 동작, 단계별 진행, 타임라인, 사용자가 조작하며 결과를 확인하는 인터랙티브 시각화.
- **Section 6 (Anti-use cases)**: 시각화 거의 사용하지 않는다. 텍스트로 "이런 상황에서는 쓰지 마라"를 명시하는 것이 더 명확하다.
- **Section 7 (Gotchas)**: 필요 시 코드 블록으로 안티패턴/올바른 패턴 대비. 시각화는 거의 없음.

### 가독성 밀도 강제 (Density Enforcement)

Stage 2 노트의 `가독성 밀도 체크` 표에 기록된 "중간 삽입 수단"과 "예시 전략"은 Stage 3에서 **반드시** 실행된다. 실행 규칙:

1. **헤딩 사이 밀도**: H2 아래 H3가 2개 이상 연속되면, 각 H3 사이에 노트의 중간 삽입 수단(시각화/비교표/코드블록) 1개 이상을 삽입한다. 헤딩만 나열된 구간을 만들지 않는다.
2. **긴 문단 분할**: 한 H2 또는 H3 아래 연속 텍스트가 600자(한국어 기준)를 넘길 것으로 보이면 중간에 시각화 · 코드블록 · 비교표 · 짧은 예시 블록(`<Callout type="info">` 또는 인용문) 중 하나를 삽입한다.
3. **예시 배치**: 노트의 "예시 전략"에 기록된 지점에만 예시를 삽입한다. 모든 개념마다 예시를 붙이지 않는다. 예시 이후에는 반드시 원 기술 용어로 돌아와 정확한 메커니즘을 기술한다 — 비유만으로 설명을 끝내지 않는다.
4. **깊이 보존**: 가독성을 위해 기술적 깊이를 희석하지 않는다. 예시와 시각화는 깊이를 유지한 상태에서 **진입 난이도만** 낮추는 역할이다.

## 코드 블록 작성 규칙

- Shiki 라인 하이라이트 `// [!code highlight]`를 적극 사용한다. 강조하고 싶은 한두 줄에만 붙인다. 전체 블록이 하이라이트면 아무것도 강조하지 않는 것과 같다.
- `title="파일명.ext"` 속성으로 파일명을 표기한다. 예: ` ```python title="xfetch.py" `. 파일명이 없어도 되는 경우(개념 코드, 의사 코드)는 생략 가능.
- 동일 알고리즘을 여러 언어로 비교할 때는 차이가 명확한 부분만 하이라이트하고, 중복 코드는 최소화한다.
- 언어 선택 우선순위: Python, Kotlin, TypeScript, Go, SQL, Rust — 백엔드/CS 친화적 언어 우선. 주제에 가장 자연스러운 언어를 선택한다.
- 인라인 코드(`` `code` ``)는 변수명, 함수명, 짧은 표현식에만 사용한다. 문장 전체를 코드 블록으로 감싸지 않는다. 시각적으로 teal 컬러 텍스트(`--code-inline-fg`) + 10% 틴트 배경으로 렌더되어, 본문(white) · 링크(blue) · 키워드 링크(indigo)와 자동 구분된다.
- 코드 블록 직전에 "이 코드가 무엇을 보여주는가"를 한 문장으로 설명한다. 코드 블록은 설명 없이 덩그러니 등장하지 않는다.
- 글 상세 페이지의 본문 폭은 ~984px이다. JetBrains Mono 14px 기준 약 95 character/줄까지 가로 스크롤 없이 표시된다. 이보다 긴 라인은 줄바꿈하거나 의도적으로 축약하라.

## 수식 작성 규칙 (KaTeX)

시간 복잡도, 수학 공식, 기호 등은 **반드시** 수식 문법으로 작성한다. 일반 텍스트로 `O(n log n)` 같은 표기를 쓰지 않는다.

**인라인 수식**: 문장 중간의 수식은 `$...$`로 감싼다.

```mdx
평균 시간 복잡도는 $O(n \log n)$이며, 최악의 경우 $O(n^2)$까지 증가합니다.
공간 복잡도는 $O(\log n)$이지만 재귀 깊이가 $n$에 가까워질 수 있습니다.
```

**블록 수식**: 독립된 수식은 `$$...$$`로 감싼다.

```mdx
퀵소트의 평균 재귀 관계식은 다음과 같다.

$$T(n) = 2T(n/2) + O(n) = O(n \log n)$$
```

**자주 쓰는 LaTeX 명령**:

| 용도 | LaTeX | 결과 |
|---|---|---|
| 로그 | `\log n`, `\log_2 n` | log n, log₂ n |
| 지수 | `n^2`, `2^{n}` | n², 2ⁿ |
| 첨자 | `x_i`, `a_{ij}` | xᵢ, aᵢⱼ |
| 분수 | `\frac{a}{b}` | a/b (조판) |
| 합 | `\sum_{i=1}^{n} i` | Σ |
| 곱 | `\prod_{i=1}^{n}` | ∏ |
| 극한 | `\lim_{n \to \infty}` | lim |
| 부등호 | `\leq`, `\geq`, `\neq` | ≤, ≥, ≠ |
| 무한대 | `\infty` | ∞ |
| 집합 | `\in`, `\subset`, `\mathbb{R}` | ∈, ⊂, ℝ |

**주의**:
- 코드 블록 내부의 `$`는 수식으로 해석되지 않는다 (파이프라인 순서상 rehype-pretty-code가 먼저 처리). SQL `$1`, Shell `$VAR` 등 안전.
- 백틱 안의 수식은 동작하지 않는다. 인라인 수식은 일반 텍스트 흐름에 포함시키고 `$` 기호로 감싸라.

## 테이블 작성 규칙

테이블은 일반 마크다운 문법 그대로 작성한다. 빌드 파이프라인이 자동으로 카드 스타일(둥근 외곽, 헤더 배경, hover 강조, 가로 스크롤)을 적용한다.

```mdx
| 케이스 | 시간 복잡도 | 설명 |
|---|---|---|
| 최선 | $O(n \log n)$ | 피벗이 배열을 균등 분할 |
| 평균 | $O(n \log n)$ | 랜덤 피벗 선택 |
| 최악 | $O(n^2)$ | 이미 정렬된 배열 + 끝 원소 피벗 |
```

**규칙**:
- 테이블 내부에 **수식 + 인라인 코드 + 링크**를 자유롭게 사용할 수 있다. 예: `` `ORDER BY` ``, `$O(1)$`, `[인덱스](/posts/...)`.
- 칼럼이 4개 이하일 때 가장 깔끔하다. 5개 이상이면 독자가 수평 스캔을 못 하므로 분할하거나 설명 표 대신 본문 단락으로 풀어서 작성.
- **비교 테이블은 트레이드오프 소통의 핵심 도구**다. "A가 B보다 좋다" 같은 서술보다 "조건 X에서는 A가 유리, 조건 Y에서는 B가 유리"를 테이블로 정리하라.
- 긴 내용은 셀 안에 넣지 말고 본문으로 이동. 셀은 한 줄, 길어도 두 줄 이내가 적절.
- 숫자 칼럼을 우측 정렬하고 싶으면 셀에 `className="num"`을 추가할 수 있지만, 일반 마크다운 문법으로는 직접 표현이 어렵다. 대부분의 경우 기본 좌측 정렬로 충분하다.

**예시 — 기술 선택 비교**:

```mdx
| 선택지 | 장점 | 단점 | 적합한 상황 |
|---|---|---|---|
| Redis | $O(1)$ 조회, TTL 지원 | 메모리 비용 | 캐시 수명 10초~1시간 |
| Memcached | 단순함, 저 메모리 | TTL만 지원, 내구성 없음 | 뜨거운 캐시 전용 |
| Postgres + 테이블 | 트랜잭션, 영속성 | 쿼리 레이턴시 | 감사/히스토리 필요 |
```

## RelatedPost 컴포넌트 배치

교차 참조 컴포넌트는 3가지 `type`으로 구분하며, 각각 배치 위치가 다르다.

- **`prerequisite`**: 섹션 시작 부분, 본문 진입 직전. "이 개념을 모르면 이해하기 어렵다"가 명확한 경우에만 삽입한다. 예: 분산 락 기반 완화 서브섹션 시작에 `<RelatedPost slug="distributed-lock" type="prerequisite" />` 배치.
- **`deep-dive`**: 본문 흐름 안에서 "더 자세한 건..." 언급 직후. "여기서는 간략히 다루고, 자세한 건 별도 글"을 명시하는 패턴에서 사용한다.
- **`parallel`**: 글 끝부분, 마무리 직전. "같이 읽으면 좋은 글"로 독자 네비게이션을 보강한다.

**중복 금지**: 한 글 안에 같은 slug의 `<RelatedPost />`는 한 번만 등장한다. type이 달라도 같은 slug는 한 번이다.

**감지 소스**: Stage 2 노트의 "교차 참조 (Related Posts)" 섹션에서 자동 추출한다. 노트에 없는 slug는 본문에 삽입하지 않는다.

## 마무리 / 참고 자료 섹션

모든 글은 다음 두 섹션으로 끝난다.

**마무리** (`## 마무리`):
- 1~2 문단 분량
- 핵심 메시지 재강조. 독자가 이 글에서 가져가야 할 핵심 이해를 명확히 전달한다.
- 단순 요약이 아니라 "독자가 이 글을 덮고 가장 기억해야 할 한 문장"을 전달한다.
- 마무리는 서론의 Hook paragraph와 수미쌍관을 이루도록 작성하면 좋다.

**참고 자료** (`## 참고 자료`):
- 외부 링크 목록 (bullet list)
- 형식: `- [제목](URL)`
- 우선순위: 논문 > 공식 문서 > 잘 쓰인 블로그 포스트
- 3~6개 권장. 너무 많으면 독자가 어디를 먼저 읽어야 할지 모른다.
