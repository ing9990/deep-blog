# Stage 3: MDX Generation

Stage 2 노트를 입력으로 실제 MDX 파일을 작성한다. 본문 구조는 노트의 7-섹션을 그대로 H2 섹션으로 매핑하며, 자동 콜아웃 3종과 교차 참조 컴포넌트를 정해진 위치에 배치한다.

---

## 본문 구조 매핑

노트의 7-섹션을 아래와 같이 MDX H2 섹션으로 1:1 매핑한다.

| 노트 섹션 | MDX 헤딩 |
|---|---|
| 1. Why | `## 왜 이 주제를 알아야 하는가 (Why)` |
| 2. Where | `## 어디서 마주치는가 (Where)` |
| 3. Alternatives & Tradeoffs | `## 대안 비교 — No Silver Bullet (Alternatives & Tradeoffs)` |
| 4. Root Cause | `## 왜 이 문제가 존재하는가 (Root Cause)` |
| 5. How | `## 어떻게 동작하는가 (How)` |
| 6. Anti-use cases | `## 언제 쓰지 말아야 하는가 (Anti-use cases)` |
| 7. Gotchas | `## 실무 함정 (Gotchas)` |

H2 제목은 한국어 + 영문을 병기한다 (예: `왜 이 문제가 존재하는가 (Root Cause)`). Section 5~7은 노트에 해당 내용이 실질적으로 기술되어 있을 때만 생성한다. 내용이 없는 섹션은 억지로 채우지 않는다.

## Hook Paragraph 작성법

- **위치**: frontmatter 직후, 학습 목표 콜아웃 직전
- **분량**: 2~3 문장. 너무 길면 독자 피로를 유발한다.
- **목적**: 독자의 관심을 끌고 본문 진입 동기를 부여한다.
- **관점**: "이 글을 읽으면 무엇을 얻는가" — 사실 나열이 아니라 독자 가치 중심으로 작성한다.
- **작성 소스**: Stage 2 노트의 Why 섹션 + 한 줄 주제에서 뽑는다.

Hook paragraph 예시 (캐시 스탬피드 주제):

```mdx
캐시 스탬피드는 구현 버그가 아닙니다. 캐시 키가 동시에 만료될 때 수십 개의 요청이 DB로 몰리는 현상은, "캐시가 있으면 DB를 보호한다"는 가정 자체가 깨지는 순간에 발생합니다. 이 글에서는 왜 완벽한 해결책이 없는지, 그리고 각 완화 전략이 어떤 가정을 요구하는지 살펴봅니다.
```

## 자동 삽입 콜아웃 3종

스킬은 매 글에 다음 3개 콜아웃을 자동 삽입한다. 이 3개는 블로그 정체성을 구조적으로 반복 주입하는 장치이며, 사용자가 명시적으로 "빼달라"고 할 때만 제거한다.

### 1. info — 학습 목표 (글 서두)

- **위치**: Hook paragraph 직후, 첫 번째 H2(`## 왜 이 주제를 알아야 하는가`) 직전
- **용도**: 독자가 첫 30초 안에 "이 글이 내게 가치 있는가"를 판단할 수 있도록 한다.
- **내용**: 3가지 학습 목표 bullet list. Stage 2 노트의 "Why" 섹션에서 추출한다.

정확한 템플릿:

```mdx
<Callout type="info" title="이 글의 학습 목표">
  1. <학습 목표 1 — "~을 이해한다" 형태>
  2. <학습 목표 2 — "~을 구분할 수 있다" 형태>
  3. <학습 목표 3 — "~을 선택하는 기준을 얻는다" 형태>
</Callout>
```

학습 목표 번호 앞에는 서식 없는 순서 숫자를 쓴다. 동사 형태는 3가지 패턴을 순서대로 적용한다: (1) "이해한다", (2) "구분할 수 있다", (3) "선택하는 기준을 얻는다". 주제에 따라 동사는 조정 가능하지만 마지막 목표는 항상 독자가 가져갈 판단 기준이어야 한다.

### 2. warning — No Silver Bullet (Alternatives 섹션)

- **위치**: Section 3 (Alternatives & Tradeoffs) 상단, 비교표 직전
- **용도**: 매 글마다 "정답은 없다, 가정을 정의해야 한다"는 철학을 반복 주입한다.

정확한 템플릿:

```mdx
<Callout type="warning" title="No Silver Bullet 원칙">
  아래 N가지 전략 중 "정답"은 없습니다. 각 전략은 **서로 다른 가정**에 기대며,
  당신의 시스템의 가정이 무엇인지 먼저 정의해야 올바른 선택이 가능합니다.
</Callout>
```

N은 실제 전략/대안 개수로 치환한다. 문구는 주제에 맞게 약간 조정 가능하지만 "정답은 없다 + 가정 정의 우선" 메시지는 고정 상수다. 이 콜아웃은 독자가 섹션을 건너뛰었더라도 이 한 문단에서 핵심 교훈을 얻도록 설계된 장치다.

### 3. error — 핵심 통찰 (Root Cause 섹션)

- **위치**: Section 4 (Root Cause) 시작 부근, 본문 파고들기 직전
- **용도**: 글의 가장 중요한 "한 문장 깨달음"을 강조한다. `error` 타입은 시각적으로 가장 강한 신호이므로 한 글에 한 번만 쓴다.

정확한 템플릿:

```mdx
<Callout type="error" title="핵심 통찰: <한 줄 요약>">
  <"왜 이 문제가 존재하는가"의 본질 — 가정의 깨짐, 모델링의 gap 등>
</Callout>
```

제목의 `<한 줄 요약>`은 글의 "Root Cause" 섹션에서 가장 중요한 한 문장으로 채운다. 예: `핵심 통찰: 캐시 스탬피드는 캐시 계층의 구조적 취약점이다`. 본문은 2~3 문장으로 그 취약점이 왜 발생하는지 구체적으로 서술한다.

## 섹션별 시각화 배치

어떤 시각화를 어디에 배치할지 결정하는 기준이다. 자세한 판단 로직은 `visualization-rules.md` 참조.

- **Section 3 (Alternatives & Tradeoffs)**: 비교표 (`| ... |`) 우선. 복잡한 트레이드오프 매트릭스는 정적 SVG로 보완.
- **Section 4 (Root Cause)**: SVG 다이어그램 권장. 가정/모델의 시각화, 시스템 개념도, 타이밍 도식. 정적 이미지만으로 충분히 설명 가능한 경우가 많다.
- **Section 5 (How)**: React 컴포넌트 권장. 동적 동작, 단계별 진행, 타임라인, 사용자가 조작하며 결과를 확인하는 인터랙티브 시각화.
- **Section 6 (Anti-use cases)**: 시각화 거의 사용하지 않는다. 텍스트로 "이런 상황에서는 쓰지 마라"를 명시하는 것이 더 명확하다.
- **Section 7 (Gotchas)**: 필요 시 코드 블록으로 안티패턴/올바른 패턴 대비. 시각화는 거의 없음.

## 코드 블록 작성 규칙

- Shiki 라인 하이라이트 `// [!code highlight]`를 적극 사용한다. 강조하고 싶은 한두 줄에만 붙인다. 전체 블록이 하이라이트면 아무것도 강조하지 않는 것과 같다.
- `title="파일명.ext"` 속성으로 파일명을 표기한다. 예: ` ```python title="xfetch.py" `. 파일명이 없어도 되는 경우(개념 코드, 의사 코드)는 생략 가능.
- 동일 알고리즘을 여러 언어로 비교할 때는 차이가 명확한 부분만 하이라이트하고, 중복 코드는 최소화한다.
- 언어 선택 우선순위: Python, Kotlin, TypeScript, Go, SQL, Rust — 백엔드/CS 친화적 언어 우선. 주제에 가장 자연스러운 언어를 선택한다.
- 인라인 코드(`` `code` ``)는 변수명, 함수명, 짧은 표현식에만 사용한다. 문장 전체를 코드 블록으로 감싸지 않는다.
- 코드 블록 직전에 "이 코드가 무엇을 보여주는가"를 한 문장으로 설명한다. 코드 블록은 설명 없이 덩그러니 등장하지 않는다.

## RelatedPost 컴포넌트 배치

교차 참조 컴포넌트는 3가지 `type`으로 구분하며, 각각 배치 위치가 다르다.

- **`prerequisite`**: 섹션 시작 부분, 본문 진입 직전. "이 개념을 모르면 이해하기 어렵다"가 명확한 경우에만 삽입한다. 예: 분산 락 기반 완화 서브섹션 시작에 `<RelatedPost slug="distributed-lock" type="prerequisite" />` 배치.
- **`deep-dive`**: 본문 흐름 안에서 "더 자세한 건..." 언급 직후. "여기서는 간략히 다루고, 자세한 건 별도 글"을 명시하는 패턴에서 사용한다.
- **`parallel`**: 글 끝부분, 마무리 직전. "같이 읽으면 좋은 글"로 독자 네비게이션을 보강한다.

**중복 금지**: 한 글 안에 같은 slug의 `<RelatedPost />`는 한 번만 등장한다. type이 달라도 같은 slug는 한 번이다.

**감지 소스**: Stage 2 노트의 "교차 참조 (Related Posts)" 섹션에서 자동 추출한다. 노트에 없는 slug는 본문에 삽입하지 않는다.

## 마무리 / 참고 자료 섹션

모든 글은 다음 두 섹션으로 끝난다.

**마무리** (`## 마무리`):
- 1~2 문단 분량
- 핵심 메시지 재강조. "정답은 없다, 가정을 정의하라" 류의 철학적 닫음이어야 한다.
- 단순 요약이 아니라 "독자가 이 글을 덮고 가장 기억해야 할 한 문장"을 전달한다.
- 마무리는 서론의 Hook paragraph와 수미쌍관을 이루도록 작성하면 좋다.

**참고 자료** (`## 참고 자료`):
- 외부 링크 목록 (bullet list)
- 형식: `- [제목](URL)`
- 우선순위: 논문 > 공식 문서 > 잘 쓰인 블로그 포스트
- 3~6개 권장. 너무 많으면 독자가 어디를 먼저 읽어야 할지 모른다.
