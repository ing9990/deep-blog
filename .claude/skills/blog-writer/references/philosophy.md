# Philosophy

이 파일은 blog-writer 스킬의 주제 적합성 판단과 글의 방향성에 대한 정규 레퍼런스다. 스킬이 트리거될 때마다 이 파일을 가장 먼저 읽어야 한다. 여기서 정의하는 철학이 모든 Stage의 의사결정 기준이 된다.

---

## 핵심 철학

**"기술 주제를 최대한 이해하기 쉽게 정리한 글"**

이 블로그는 독자가 기술 주제를 깊이 있게, 그러나 쉽게 이해할 수 있도록 돕는다. 이해를 위해 다음 세 가지를 중심으로 다룬다:

1. **내부적 작동** — 기술이 실제로 어떻게 동작하는지, 표면 아래의 메커니즘을 드러낸다.
2. **기술이 필요한 이유** — 왜 이 기술이 존재하는지, 어떤 문제를 해결하는지의 맥락을 제공한다.
3. **트레이드오프 비교** — 대안이 있는 경우, 각 선택지의 장단점과 적합한 상황을 비교한다.

"X를 쓰면 좋다"로 끝나는 글이 아니라, **"X가 왜 필요하고, 내부에서 어떻게 작동하며, 다른 선택지와 비교하면 어떤가"**를 독자가 이해할 수 있는 글을 만든다. 사용법/튜토리얼 주제도 이 세 가지 각도를 더해 깊이 있게 다룰 수 있다.

---

## 주제 타입 분류 (Type A vs Type B)

이 블로그의 주제는 두 가지 근본 유형으로 나뉘며, 각 유형은 **글의 구조적 중심축이 다르다**. Stage 1 진입 직후 스킬이 주제를 분류하고, 이후 모든 스테이지(Stage 2 노트, Stage 3 MDX)는 확정된 타입을 그대로 따른다.

### Type A — 기본기 (Fundamentals)

**정의**: CS의 본질 개념, 운영체제/데이터베이스/네트워크/컴파일러 등 분야의 근본 원리, 특정 벤더나 도구에 종속되지 않는 보편 기술.

**예시 주제**: 데이터베이스 인덱스, B+Tree, LSM Tree, JVM Garbage Collection, JIT 컴파일, 메모리 모델, TCP 혼잡 제어, HTTP/2 멀티플렉싱, 리눅스 프로세스/스레드, 컨텍스트 스위칭, 해시 테이블, 레드-블랙 트리, 페이지 테이블, CPU 캐시 계층.

**핵심 축**: **"왜 생겨났고 어떻게 작동하는가"** — OS, DB, 네트워크, 메모리 계층 같은 하부 CS 제약을 근거로 "왜 이 구조에 수렴했는가"를 풀어내는 deep-dive. 대안이 있을 경우 "역사적 대안들과 현재 방식으로의 수렴 이유" 형태의 서사로 나타난다.

**독자가 가져가는 것**: "이 기술이 어떤 제약 하에서 이런 모습에 도달했는지"에 대한 근본적 이해.

### Type B — 스킬 · 도구 (Tools & Frameworks)

**정의**: 특정 기술 스택의 라이브러리, 프레임워크, 플랫폼. 사용자가 선택권을 가지며 실제로 대안이 존재하는 주제.

**예시 주제**: QueryDSL vs JPA Criteria, Spring Boot 자동 설정 · IoC 컨테이너 내부, Kafka vs RabbitMQ vs Pulsar, Redis Cluster vs Sentinel, React Query vs SWR vs RTK Query, Nginx vs Envoy, gRPC vs REST.

**핵심 축**: **"내부 동작 + 왜 필요한가"** (deep-dive) → **"대안 비교 + 도입 트레이드오프"**. 먼저 내부 메커니즘과 이 기술이 필요한 이유를 설명한 뒤, 대안과의 트레이드오프로 마무리한다.

**독자가 가져가는 것**: "이 도구의 내부가 어떻게 작동하는지" + "왜 이 도구가 필요한지" + "다른 선택지들 대비 어떤 조건에서 유리/불리한지"의 판단 기준.

### 타입 판별 기준

Stage 1 진입 시 스킬이 주제 키워드로 자동 추정한 뒤, 사용자에게 1회 확인을 받는다. 자동 추정 힌트:

- 주제가 **벤더 중립적 CS 개념**(인덱스, GC, TCP, 해시 테이블, 페이지 테이블 등) → Type A
- 주제가 **특정 프레임워크/라이브러리/플랫폼 이름을 포함**(Spring, QueryDSL, Kafka, Redis Cluster, Nginx 등) → Type B
- 주제가 두 유형의 경계에 걸쳐 있거나 모호하면 사용자에게 직접 묻는다

**타입은 Stage 1 승인 시점에 확정되며 Stage 2 노트와 Stage 3 MDX로 전달된다. 타입이 잘못 확정되면 글의 구조가 처음부터 어긋나므로, 자동 추정에 의존하지 말고 반드시 사용자 확인을 거친다.**

### 타입별 글의 초점 차이

- **Type A에서**: "이것이 무엇이고, 왜 필요하며, 내부에서 어떻게 동작하고, 언제 써야 하는가"를 중심으로 설명한다. 핵심은 **정의 → 필요성 → 메커니즘 → 적용 기준**의 단계적 이해.
- **Type B에서**: "이것이 무엇이고, 왜 필요하며, 내부에서 어떻게 동작하고, 실전에서 어떤 문제를 만나는가"를 중심으로 설명한다. 핵심은 **정의 → 필요성 → 메커니즘 → 실전 문제 + 도입의 대가**.

## 섹션 골격 (Type별 변형)

주제 유형에 따라 섹션 골격이 분기한다. 두 변형 모두 1~4번이 필수이다.

### Type A — Fundamentals 골격

| 순서 | 섹션 | 필수 여부 | 핵심 질문 |
|---|---|---|---|
| 1 | What | 필수 | 이것은 무엇인가? |
| 2 | Why | 필수 | 왜 필요한가? (없을 때 vs 있을 때 내부 동작 비교) |
| 3 | How | 필수 | 어떻게 동작하는가? (내부 메커니즘, 구조) |
| 4 | When | 필수 | 언제 사용하고 언제 사용하지 말아야 하는가? |
| 5 | Tradeoffs | 권장 | 비용과 트레이드오프는? (쓰기 비용, 메모리 등) |

**Type A의 중심**: Section 3 (How)이 글의 **가장 큰 축**이다. CS 하부 제약이 구조를 강제하는 인과 관계를 여기서 풀어낸다.

### Type B — Tools & Frameworks 골격

| 순서 | 섹션 | 필수 여부 | 핵심 질문 |
|---|---|---|---|
| 1 | What | 필수 | 이것은 무엇인가? |
| 2 | Why | 필수 | 왜 필요한가? (도입 전 vs 후) |
| 3 | How | 필수 | 내부적으로 어떻게 동작하는가? (문법이 아닌 메커니즘) |
| 4 | Problems | 필수 | 사용 시 마주치는 실전 문제들은? |
| 5 | Tradeoffs | 권장 | 도입의 대가는? (사이드 이펙트, 복잡성, 운영 비용) |

**Type B의 중심**: Section 4 (Problems)가 글의 **가장 큰 축**이다. 단순 사용법을 넘어 실전 문제와 사이드 이펙트까지 다룬다.

### 공통 원칙

두 유형 모두 1~4번 중 하나라도 작성이 어렵다면 그 주제는 글감으로 약할 수 있다. 그 경우 사용자와 상의해 각도를 조정한다. 사용자가 6번 이상의 커스텀 항목을 추가하는 것도 허용한다.

## 거절 기준 (Topic Suitability)

아래 두 가지 유형의 주제는 블로그 방향과 맞지 않는다. 해당 주제를 사용자가 요청하면 전환 제안을 한다.

**참고**: 순수 사용법/튜토리얼은 더 이상 거절 대상이 아니다. "내부 작동 원리 + 왜 필요한가 + 트레이드오프" 각도를 더해 깊이 있게 다룰 수 있으며, 사용자가 원하면 그대로 진행한다.

### 거절 대상 1: 단편 팁 / 치트시트

**정의**: 사용 빈도 높은 명령어, 단축키, 설정값 모음.

**예시**:
- "VS Code 단축키 모음"
- "Git 자주 쓰는 명령어 10개"

**왜 맞지 않는가**: gist나 Notion 노트로 충분하다. 블로그 형식(제목 + 본문 + 교차 참조 + 시각화)이 단순 목록에는 오히려 비효율이다.

### 거절 대상 2: 개인 회고 / 경력 일기

**정의**: 경력 성장, 학습 여정, 이직 경험 등 개인 서사 중심의 글.

**예시**:
- "개발자 1년 차 회고"
- "이직 준비하면서 느낀 점"

**왜 맞지 않는가**: 포트폴리오 영역이다. `portfolio-writer` 스킬이 이 목적으로 별도 존재한다. 이 블로그는 기술 지식 공유 목적이다.

## 사용법 주제의 깊이 전환

사용자가 "JPA 사용법", "Docker 쓰는 법" 같은 주제를 요청하면, 거절하지 않고 다음과 같이 깊이를 더하는 각도를 제안한다:

**"JPA 사용법" 요청 시**:
```
주제를 확인했습니다. 이 블로그는 이해하기 쉬운 깊이 있는 글을 지향합니다.

JPA를 주제로, 다음과 같은 각도를 추가하면 더 좋은 글이 될 것 같습니다:
  1. JPA가 왜 필요한가 — JDBC 직접 사용 대비 어떤 문제를 해결하는지
  2. JPA 내부 동작 — 영속성 컨텍스트, 프록시, 지연 로딩의 메커니즘
  3. 트레이드오프 — ORM vs Native SQL, 언제 JPA가 맞고 안 맞는지

이 방향으로 진행할까요? 또는 다른 각도가 있으면 알려주세요.
```

**"Docker 쓰는 법" 요청 시**:
```
주제를 확인했습니다. 이 블로그는 이해하기 쉬운 깊이 있는 글을 지향합니다.

Docker를 주제로, 다음과 같은 각도를 추가하면 더 좋은 글이 될 것 같습니다:
  1. Docker가 왜 필요한가 — 컨테이너 격리가 해결하는 실제 문제
  2. Docker 내부 동작 — namespace, cgroup, union filesystem의 메커니즘
  3. 트레이드오프 — Docker vs VM vs LXC, 각각의 적합한 상황

이 방향으로 진행할까요? 또는 다른 각도가 있으면 알려주세요.
```

사용자가 제안을 수용하면 해당 각도로 Stage 1을 진행한다. 사용자가 원래 주제 그대로 가겠다고 하면 그 결정을 존중하고 진행한다.

---

## 거절의 강도

거절은 "부드러운 안내 + 사용자 결정 존중" 정책이다. 스킬은 주제 확인을 한 번 수행하고 각도 전환을 제안하되, 사용자가 명시적으로 원래 주제를 고수하면 스킬은 그 결정을 따른다. 이후 같은 안내를 반복하지 않는다.
