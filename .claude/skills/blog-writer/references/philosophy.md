# Philosophy

이 파일은 blog-writer 스킬의 주제 적합성 판단과 거절 기준에 대한 정규 레퍼런스다. 스킬이 트리거될 때마다 이 파일을 가장 먼저 읽어야 한다. 여기서 정의하는 철학이 모든 Stage의 의사결정 기준이 된다.

---

## No Silver Bullet 원칙

이 블로그는 "어떻게 사용하는가"가 아니라 "왜 이 선택을 해야 하는가, 그리고 그 선택의 대가는 무엇인가"를 다룬다. 모든 기술, 패턴, 아키텍처에는 해결하려는 문제와 감수하는 비용이 동시에 존재하며, 이 블로그는 그 두 가지를 항상 함께 드러낸다. "X를 쓰면 좋다"가 아니라 "X는 Y 가정 하에 Z 문제를 해결하지만 W 비용을 지불한다"가 글의 핵심 문장이다.

모든 기술적 결정에는 숨겨진 가정이 있다. 단순 큐가 메시지 순서를 보장한다는 가정, JVM GC가 일시정지를 낮게 유지한다는 가정, 관계형 DB가 트랜잭션을 완벽히 직렬화한다는 가정 — 이 가정들은 특정 조건 아래에서만 성립한다. 저자의 역할은 그 가정을 독자 앞에 명시적으로 꺼내 놓는 것이다. "이 상황에서는 맞다, 저 상황에서는 틀리다"를 구분할 수 있어야 진짜 이해다.

일반적인 기술 블로그는 "이 기술을 쓰면 이 문제가 해결된다"고 끝난다. 이 블로그는 그 문장 뒤에 반드시 "단, 이 가정이 깨지면 이렇게 된다"를 붙인다. 그 차이가 이 블로그를 공식 문서와 다른 가치를 가지게 만든다. 독자는 여기서 "언제 이 기술을 쓰지 말아야 하는가"까지 얻어가야 한다.

## 주제 타입 분류 (Type A vs Type B)

이 블로그의 주제는 두 가지 근본 유형으로 나뉘며, 각 유형은 **글의 구조적 중심축이 다르다**. No Silver Bullet 원칙은 두 유형 모두에 살아 있지만, 그 원칙을 전개하는 방식과 섹션 골격이 달라진다. Stage 1 진입 직후 스킬이 주제를 분류하고, 이후 모든 스테이지(Stage 2 노트, Stage 3 MDX)는 확정된 타입을 그대로 따른다.

### Type A — 기본기 (Fundamentals)

**정의**: CS의 본질 개념, 운영체제/데이터베이스/네트워크/컴파일러 등 분야의 근본 원리, 특정 벤더나 도구에 종속되지 않는 보편 기술.

**예시 주제**: 데이터베이스 인덱스, B+Tree, LSM Tree, JVM Garbage Collection, JIT 컴파일, 메모리 모델, TCP 혼잡 제어, HTTP/2 멀티플렉싱, 리눅스 프로세스/스레드, 컨텍스트 스위칭, 해시 테이블, 레드-블랙 트리, 페이지 테이블, CPU 캐시 계층.

**핵심 축**: **"왜 생겨났고 어떻게 작동하는가"** — OS, DB, 네트워크, 메모리 계층 같은 하부 CS 제약을 근거로 "왜 이 구조에 수렴했는가"를 풀어내는 deep-dive. 트레이드오프 비교는 부차적이며, 등장할 경우 "역사적 대안들과 현재 방식으로의 수렴 이유" 형태의 서사로 나타난다 — 비교 표가 아니라 진화사.

**독자가 가져가는 것**: "이 기술이 특정 CS 제약 하에서 필연적으로 이런 모습에 도달했다"는 근본적 이해. 선택의 기준이 아니라 **존재의 근거**.

### Type B — 스킬 · 도구 (Tools & Frameworks)

**정의**: 특정 기술 스택의 라이브러리, 프레임워크, 플랫폼. 사용자가 선택권을 가지며 실제로 대안이 존재하는 주제.

**예시 주제**: QueryDSL vs JPA Criteria, Spring Boot 자동 설정 · IoC 컨테이너 내부, Kafka vs RabbitMQ vs Pulsar, Redis Cluster vs Sentinel, React Query vs SWR vs RTK Query, Nginx vs Envoy, gRPC vs REST.

**핵심 축**: **"내부 동작 + CS 연계"** (deep-dive) → **"대안 비교 + 도입 트레이드오프"**. 먼저 내부 메커니즘을 CS 지식과 연결해 풀어낸 뒤, 대안과의 트레이드오프로 마무리한다. 순수 사용법은 여전히 거절 대상이다 (§거절 기준 참조).

**독자가 가져가는 것**: "이 도구의 내부가 어떻게 작동하는지" + "다른 선택지들 대비 어떤 조건에서 유리/불리한지"의 판단 기준.

### 타입 판별 기준

Stage 1 진입 시 스킬이 주제 키워드로 자동 추정한 뒤, 사용자에게 1회 확인을 받는다. 자동 추정 힌트:

- 주제가 **벤더 중립적 CS 개념**(인덱스, GC, TCP, 해시 테이블, 페이지 테이블 등) → Type A
- 주제가 **특정 프레임워크/라이브러리/플랫폼 이름을 포함**(Spring, QueryDSL, Kafka, Redis Cluster, Nginx 등) → Type B
- 주제가 두 유형의 경계에 걸쳐 있거나 모호하면 사용자에게 직접 묻는다

**타입은 Stage 1 승인 시점에 확정되며 Stage 2 노트와 Stage 3 MDX로 전달된다. 타입이 잘못 확정되면 글의 구조가 처음부터 어긋나므로, 자동 추정에 의존하지 말고 반드시 사용자 확인을 거친다.**

### No Silver Bullet의 두 얼굴

No Silver Bullet 원칙은 두 타입 모두에 적용되지만, 적용 형태가 다르다.

- **Type A에서**: "이 구조가 유일한 답은 아니지만, 현 CS 제약(디스크 seek 비용, 메모리 계층, 네트워크 지연 등) 하에선 필연적으로 수렴한다". 핵심은 **제약에 따른 수렴**.
- **Type B에서**: "이 도구가 유일한 답은 아니다. 시스템 가정이 다르면 다른 선택이 맞다". 핵심은 **가정에 따른 선택**.

양쪽 다 "정답은 없다"는 입장이지만, Type A는 **CS 제약의 필연성**이 서사의 기둥이고, Type B는 **시스템 가정의 다양성**이 서사의 기둥이다. 이 차이는 섹션 골격에 그대로 반영된다.

## 섹션 골격 (Type별 변형)

주제 유형에 따라 섹션 골격이 분기한다. 두 변형 모두 1~4번 중 필수 섹션이 존재하지만, **무엇이 필수인지**가 다르다.

### Type A — Fundamentals 골격

| 순서 | 섹션 | 필수 여부 | 핵심 질문 |
|---|---|---|---|
| 1 | Why | 필수 | 왜 이 주제를 알아야 하는가? |
| 2 | Where | 필수 | 어디서 마주치는가? |
| 3 | Root Cause (확장) | 필수 | 어떤 CS 제약이 이 구조를 강제하는가? |
| 4 | How | 필수 | 실제 동작 메커니즘은 무엇인가? |
| 5 | Historical Alternatives | 선택 | 과거 어떤 시도가 있었고 왜 수렴했는가? |
| 6 | Anti-use cases | 권장 | 언제 이 구조가 부적합한가? |
| 7 | Gotchas | 권장 | 실무 함정은? |

**Type A의 중심**: Section 3 (Root Cause)과 Section 4 (How)가 글의 **가장 큰 두 축**이다.

- Section 3은 **"CS 근거 추적"** — OS, DB, 네트워크, 메모리 계층 등 어떤 하부 제약이 이 구조를 강제하는지 파고든다. 예: "디스크 seek는 비싸고 연속 읽기는 싸다"가 페이지 단위 I/O와 B+Tree의 높은 fanout을 강제한다. 이 섹션이 글 전체의 지적 무게 중심.
- Section 4는 그 근거 위에서 **실제 메커니즘**을 풀어낸다. Section 3이 "왜 이런 구조여야 했나"라면, Section 4는 "그 구조가 실제로 어떻게 돌아가나"다. 두 섹션은 연속된 한 덩어리로 읽혀야 한다.
- Section 5 (Historical Alternatives)는 **선택** 섹션이며, 넣을 때는 "대안 비교표"가 아니라 **"역사적 진화"** 로 프레이밍한다 — "초기엔 X를 썼지만 Y 문제로 Z에 수렴했다"라는 서사 형태. 일반 Type B 스타일의 비교표(장점/단점/적합 상황)는 Type A에 넣지 않는다.

### Type B — Tools & Frameworks 골격

| 순서 | 섹션 | 필수 여부 | 핵심 질문 |
|---|---|---|---|
| 1 | Why | 필수 | 왜 이 주제를 알아야 하는가? |
| 2 | Where | 필수 | 어디서 마주치는가? |
| 3 | Alternatives & Tradeoffs | 필수 | 어떤 선택지가 있는가? |
| 4 | Root Cause | 필수 | 왜 이 문제가 존재하는가? |
| 5 | How | 권장 | 실제로 어떻게 동작하는가? |
| 6 | Anti-use cases | 권장 | 언제 쓰지 말 것인가? |
| 7 | Gotchas | 권장 | 실무 함정은? |

**Type B의 중심**: Section 3 (Alternatives & Tradeoffs)가 글의 가장 큰 축이다. 대안 도구들과의 비교표가 필수이며, 각 대안의 숨겨진 가정을 드러내는 문단이 뒤따른다. Section 4 (Root Cause)는 "왜 이 도구/패턴이 필요했는가"의 맥락을 CS 지식과 연결해 제공한다. Section 5 (How)에서 내부 동작을 다루되, 타 도구와의 비교 축이 끊기지 않도록 "이 부분에서 대안 X는 다르게 처리한다" 식으로 비교 맥락을 유지한다.

### 공통 원칙

두 유형 모두 1~4번 중 하나라도 작성이 어렵다면 그 주제는 이 블로그에 맞지 않을 가능성이 높다. "JPA 사용법"이 거절되는 이유도 여기에 있다 — Type B 기준으로 보면 Alternatives에 할 말이 없고(사용자가 JPA를 이미 쓰기로 결정한 상태), Type A 기준으로 보면 Root Cause/How가 JPA에 종속되어 CS 근거로 내려가지 못한다. 순수 사용법 주제는 두 기준 모두에서 미끄러진다.

## 거절 기준 (Topic Suitability Rejection)

아래 세 가지 유형의 주제는 블로그 철학과 맞지 않는다. 이 유형에 해당하는 주제를 사용자가 요청하면 즉시 거절하는 것이 아니라, 트레이드오프 관점으로 전환할 수 있는 각도를 먼저 제안한다. 세 유형 모두 "## 전환 제안 템플릿" 섹션의 방식을 따른다.

### 거절 대상 1: 순수 사용법 / 튜토리얼

**정의**: "X 사용법", "Y 설정 방법", "Z 시작하기" 패턴. 독자가 이미 X를 쓰기로 결정한 상태에서 따라 하는 글.

**예시**:
- "JPA 사용법"
- "Docker Compose 쓰는 법"
- "Spring Security 설정 방법"
- "GraphQL 시작하기"
- "Redis 캐시 도입하기"

**왜 거절하는가**: 트레이드오프 없는 설명서는 공식 문서로 충분하다. 블로그가 추가 가치를 제공하지 못하며, 저자가 배우는 경험도 얕아진다. "이 글을 읽으면 무엇을 이해하게 되는가"라는 질문에 "JPA를 쓸 수 있게 된다" 이상을 답할 수 없는 주제는 이 블로그의 목적에 맞지 않는다.

### 거절 대상 2: 단편 팁 / 치트시트

**정의**: 사용 빈도 높은 명령어, 단축키, 설정값 모음.

**예시**:
- "VS Code 단축키 모음"
- "Git 자주 쓰는 명령어 10개"

**왜 거절하는가**: gist나 Notion 노트로 충분하다. 블로그 형식(제목 + 본문 + 교차 참조 + 시각화)이 단순 목록에는 오히려 비효율이다.

### 거절 대상 3: 개인 회고 / 경력 일기

**정의**: 경력 성장, 학습 여정, 이직 경험 등 개인 서사 중심의 글.

**예시**:
- "개발자 1년 차 회고"
- "이직 준비하면서 느낀 점"

**왜 거절하는가**: 포트폴리오 영역이다. `portfolio-writer` 스킬이 이 목적으로 별도 존재한다. 이 블로그는 지식 공유 목적이지 개인 기록 목적이 아니다.

## 전환 제안 템플릿

거절 대상 주제를 받았을 때 아래 방식으로 응답한다. 직접 거절하지 말고, 트레이드오프 관점으로 접근 가능한 각도를 3개 내외로 제안한다. 사용자가 제안 중 하나를 선택하면 Stage 1으로 진행한다.

**"JPA 사용법" 요청 시**:
```
이 블로그는 "사용법" 중심의 글을 지양합니다.
철학은 "No silver bullet + 트레이드오프 비교"입니다.

JPA를 주제로 가되, 트레이드오프 관점에서 다룰 수 있는 각도:
  1. JPA N+1 문제와 3가지 해결 전략의 트레이드오프
  2. ORM vs Native SQL — 어느 레이어에서 비즈니스 로직을 표현해야 하는가
  3. JPA Dirty Checking의 비용 — 언제 수동 update를 써야 하는가
  4. JPA 영속성 컨텍스트가 해결하는 문제와 그 대가

이 중 하나로 진행하거나, 다른 각도가 있으면 알려주세요.
(또는 지금 주제를 "사용법"으로 진행하고 싶다면 그렇게 말씀해주세요.
 강하게 권하진 않지만 사용자 결정을 존중합니다.)
```

## 거절의 강도

거절은 "부드러운 경고 + 사용자 결정 존중" 정책이다. 스킬은 주제 검증을 딱 한 번 수행하고 전환을 제안하되, 사용자가 명시적으로 "그래도 사용법으로 진행"이라고 하면 스킬은 그 결정을 따른다. 철학은 기본값이지 강제가 아니다. 다만 해당 글은 블로그 평균 글의 품질에 못 미칠 가능성이 높음을 사용자가 인정하고 진행하는 것으로 간주하며, 스킬은 이후 같은 경고를 반복하지 않는다.
