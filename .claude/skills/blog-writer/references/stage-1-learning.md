# Stage 1: Interview & Live Note Logging

Stage 1은 사용자가 Claude에게 배우는 단계이자 **노트가 실시간으로 쌓이는 단계**다. Claude가 교사, 사용자가 학생 역할이며, 이 단계의 목적은 최종 MDX를 만드는 것이 아니라 사용자가 주제를 깊이 이해하는 것이다. **노트 파일은 Stage 1 시작 시점에 `.claude/drafts/<slug>-notes.md`에 생성되고, Q&A 진행 동안 계속 append/update된다** (Stage 2에서 새로 만들지 않는다). Stage 1의 품질이 Stage 2 최종화와 Stage 3 MDX의 품질을 결정한다.

**중요**: 노트는 **사용자에게 보여주지 않는 agent 전용 산물**이다. 매 턴 노트 업데이트를 보고하지 않으며, 주요 마일스톤만 대화 중 한 문장으로 언급한다 (§4 노트 실시간 업데이트 규칙 참조).

---

## 0. 진입 모드 (Entry Modes)

Stage 1에 들어오는 경로는 두 가지다. 진입 모드에 따라 §0.5 ~ §0.6 처리 여부가 달라지지만, §1 이후는 두 모드가 합류해 동일한 흐름을 탄다.

### Mode A — 직접 트리거 (Direct Trigger)

사용자가 "블로그 써줘", "X 포스트 만들어줘", "X 글 작성", "X 블로그" 등으로 명시적으로 스킬을 트리거한 경우. §0.5 프로액티브 offer 단계는 건너뛰고 바로 §1 주제 검증으로 진입한다. 노트 즉시 생성(§0.6)은 §1.5 타입 확정 직후에 실행된다.

### Mode B — 프로액티브 Offer (Proactive Offer)

사용자가 "블로그 써줘" 없이 기술 질문을 이어가던 중, Claude가 "이 주제 블로그로 정리해둘까요?"를 선제 제안한 경우. 사용자가 수락하면 §0.6 노트 즉시 생성 → 기존 대화 맥락을 노트에 append → §1~§3 (주제 검증 · 타입 분류 · 목차 제안)을 압축 버전으로 진행 → 자연스럽게 §4 Q&A 루프로 흡수.

**Mode B의 핵심**: 이미 나눈 대화를 버리지 않는다. 사용자가 offer 수락 시점까지 나눈 Q&A 교환은 그대로 "Q&A 루프 초반부"로 간주해 노트의 `진행 중 Q&A 로그`에 즉시 기록한다.

## 0.5 프로액티브 Offer 트리거 판정 (Mode B only)

Claude가 Mode B 오퍼를 발동할지 판정하는 기준. 잘못된 offer는 대화 노이즈를 만들고 사용자를 지치게 하므로 **보수적으로** 작동한다.

### Offer 대상 질문 (원리 · 설계 이해)

- "X가 뭔가요?", "X는 어떻게 동작하나요?", "왜 X여야 하나요?"
- "X는 Y와 뭐가 다르나요?", "X의 내부는 어떻게 생겼나요?"
- 특정 기술의 트레이드오프 · 역사 · 수학적 본질에 대한 궁금증
- 즉 사용자가 "쓰는 법"이 아니라 **"왜 이렇게 생겼는지"**를 묻는 경우

### Offer 제외 (비대상)

- **디버깅 / 에러 해결**: "이 에러 어떻게 고치나요?", "왜 `null`이 나와요?"
- **설치 / 설정**: "X 설치 방법", "Y를 어떻게 구성하나요?"
- **순수 사용법 질문**: "X를 어떻게 쓰나요?" — `philosophy.md` §거절 기준 대상
- **일회성 팩트 질문**: "X의 기본값이 뭐였죠?", "Y의 버전 몇부터 지원?"
- **철학 거절 주제**: `philosophy.md` §거절 기준 전체 — 순수 사용법, 단편 팁 / 치트시트, 개인 회고. 이런 주제는 offer 자체를 **발동하지 않는다**.

### Offer 빈도 — 주제당 1회

- 같은 주제에 대해 offer는 **한 세션 내 최대 1번**만 발동한다.
- 사용자가 한 번 거절했다면 같은 주제로 다시 offer하지 않는다.
- 여러 주제가 혼재된 대화에서는 각 주제별로 독립적으로 판정한다.

### Offer 시점 — 주제의 "리듬" 감지

질문 1개만으로 섣부르게 offer하지 않는다. 다음 두 조건 중 하나가 만족될 때 offer 후보로 등록한다.

1. 사용자가 같은 주제로 **2번째 이상 연속 질문**을 던진 시점 (주제에 대한 궁금증이 지속됨을 확인)
2. 또는 첫 질문이 이미 **깊은 설계 질문**("InnoDB는 왜 B+Tree를 선택했나요?", "TCP 혼잡 제어의 AIMD가 왜 필요한가요?") 인 경우

offer 후보로 등록되면 해당 턴의 답변 말미에 offer 메시지를 붙여 발송한다.

### Offer 메시지 템플릿

```
(답변 마무리 뒤에 자연스럽게 이어붙임)

---

이 주제 — **<주제명>** — 블로그 글감으로도 괜찮아 보입니다.
앞으로 대화를 블로그 초안 노트에 기록해두고, 나중에 "블로그로 써줘"
라고 하시면 노트를 바탕으로 바로 MDX를 작성할 수 있습니다.

기록을 시작할까요? (노트는 agent 전용이라 대화 흐름에는 영향이 없습니다)
```

사용자 응답 패턴:
- **수락** ("네" / "OK" / "좋아요" / "시작해" 계열) → §0.6 노트 즉시 생성으로 진입
- **거절** ("아니요" / "괜찮아요" / "나중에" 계열) → offer 취소, 같은 주제로 재 offer 금지, 대화 계속
- **불명확** → 한 번만 재확인. 재확인 후에도 불명확하면 거절로 간주하고 대화 계속.

## 0.6 노트 즉시 생성 프로토콜

Mode A: §1.5 타입 확정 직후 실행. Mode B: 사용자가 offer를 수락하는 순간 실행.

### 실행 단계

1. **slug 추정**: 주제에서 영문 kebab-case slug 생성 (예: "데이터베이스 인덱스" → `database-index-mechanics`). 불확실하면 임시 slug 사용, Stage 2 최종화 시점에 확정.
2. **디렉토리 확인**: `.claude/drafts/` 없으면 `mkdir -p .claude/drafts`로 자동 생성.
3. **노트 파일 생성**: `.claude/drafts/<slug>-notes.md`에 `references/stage-2-note.md`의 **헤더 + 빈 섹션 뼈대**를 쓴다. 본문 내용은 `<!-- [TBD] -->` 주석으로 대기 상태 표기.
4. **헤더 초기 값 기입**:
   - `작성일`: 오늘 날짜
   - `목표 slug`: 추정값
   - `타입`: 확정된 Type A/B (Mode B는 이 시점에 미정일 수 있음 → `TBD`로 쓰고 §1.5 이후 업데이트)
   - `한 줄 주제`: 주제명만 임시로 기입, 구체화는 Stage 2에서
5. **Mode B 특례 — 기존 대화 append**: 사용자가 offer를 수락하기까지 나눈 Q&A 교환을 노트의 `### 진행 중 Q&A 로그` 섹션에 **즉시 append**한다. 사용자 질문과 Claude 답변을 요약형으로 한 블록씩 기록. 이 덕에 Mode B는 "0부터 다시 시작"이 아니라 "이미 진행된 대화를 노트화"하는 형태가 된다.

### 사용자에게 보이는 메시지

노트 생성 자체는 한 문장으로 알린다.

- Mode A: "노트 파일을 `.claude/drafts/<slug>-notes.md`에 생성했습니다. 이후 Q&A 동안 계속 업데이트됩니다."
- Mode B: "노트 파일을 `.claude/drafts/<slug>-notes.md`에 생성하고, 지금까지 나눈 대화를 기록했습니다. 타입 분류부터 이어갑니다."

이후의 노트 업데이트는 §4 `노트 실시간 업데이트 규칙`에 따라 주요 마일스톤만 언급한다.

## 1. 주제 적합성 사전 검증

`philosophy.md`의 거절 기준을 적용한다. 순수 사용법/튜토리얼, 단편 팁/치트시트, 개인 회고 중 하나에 해당하면 `philosophy.md`의 전환 제안 템플릿을 사용해 트레이드오프 각도를 3개 제안한다. 사용자가 제안 중 하나를 선택하면 그 주제로 Stage 1을 진행하고, 사용자가 원래 주제를 고집하면 `philosophy.md`의 거절의 강도 정책을 따른다.

## 1.5 주제 타입 분류 (Type A vs Type B)

주제 적합성 통과 직후, 스킬은 `philosophy.md` §주제 타입 분류를 근거로 주제의 타입을 판별한다. 타입은 학습 목차와 이후 모든 스테이지(Stage 2 노트, Stage 3 MDX)의 구조를 결정하므로, 자동 추정에 의존하지 말고 반드시 사용자 확인을 거친다. 타입이 잘못 확정되면 글의 중심축이 어긋난 채 Stage 3까지 진행되어 복구 비용이 크다.

### 자동 추정 힌트

- 주제가 **벤더 중립적 CS 개념**(인덱스, GC, TCP, 해시 테이블, 페이지 테이블, 컨텍스트 스위칭 등) → Type A
- 주제가 **특정 프레임워크/라이브러리/플랫폼 이름 포함**(Spring, QueryDSL, Kafka, Redis Cluster, Nginx, React Query 등) → Type B
- 애매하거나 두 유형의 경계에 걸쳐 있으면 추정을 보류하고 사용자에게 직접 묻는다

### 사용자 확인 템플릿

```
주제를 분석한 결과 **Type <A | B>** 로 추정했습니다:

  주제: <주제>
  추정 타입: Type <A | B> — <"기본기" | "스킬·도구">
  근거: <키워드/주제 특성에 기반한 추정 이유>

Type A (기본기)와 Type B (스킬·도구)는 글의 구조적 중심축이 다릅니다:

  - Type A: Root Cause (CS 제약 추적) + How (메커니즘)가 글의 중심.
            트레이드오프 비교는 "역사적 진화" 서사로만 등장.
  - Type B: Alternatives & Tradeoffs (대안 비교)가 글의 중심.
            Root Cause / How는 CS 연계로 뒷받침.

이 추정이 맞으면 "OK" 또는 "A로 진행" / "B로 진행"이라고 말씀해주세요.
다른 타입이 맞다면 이유와 함께 알려주시면 변경합니다.
```

사용자가 "둘 다 해당하는 것 같은데"라고 모호한 응답을 주면, **글의 중심축이 CS 근거인지 대안 비교인지**를 기준으로 한 번 더 물어본다: "이 글을 덮은 뒤 독자가 가져가야 할 가장 중요한 한 가지가 'CS 제약에 따른 수렴의 이해'인가요, 아니면 '다른 도구와 비교해 이걸 고를 기준'인가요?"

### 타입 확정 후

확정된 타입은 다음 위치에 전달된다:
- Stage 1의 학습 목차 제안 (§2) — 타입별 템플릿 선택
- Stage 1 Q&A 루프 (§4) — 강조점 차이 적용
- Stage 2 노트 파일 헤더의 `type` 필드
- Stage 3 MDX 구조 매핑 및 자동 콜아웃 문구

## 2. 학습 목차 제안

§1.5에서 확정된 타입에 맞는 템플릿으로 학습 목차를 제안한다. 두 타입은 섹션 구성과 각 섹션의 비중이 다르므로, 잘못된 템플릿을 쓰면 글 전체가 어긋난다.

### Type A — Fundamentals 템플릿

```
주제: <주제>
타입: Type A (기본기)

이 타입은 "어떤 CS 제약이 이 구조를 강제했는가"를 중심 축으로 합니다.
다음 학습 목차를 제안합니다:

  1. Why — 왜 이 주제를 알아야 하는가 (필수)
  2. Where — 어디서 마주치는가 (필수)
  3. Root Cause — 어떤 CS 제약이 이 구조를 강제하는가 (필수, 확장)
  4. How — 실제 동작 메커니즘 (필수)
  5. Historical Alternatives — 과거 시도와 수렴 과정 (선택, 서사형)
  6. Anti-use cases — 언제 이 구조가 부적합한가 (권장)
  7. Gotchas — 실무 함정 (권장)

Type A에서는 3번 (Root Cause)과 4번 (How)이 글의 가장 큰 두 축입니다.
트레이드오프 비교표는 사용하지 않고, 필요하면 5번에 "역사적 진화" 서사로
풉니다 — "초기엔 X를 썼지만 Y 문제로 Z에 수렴했다" 같은 형태로.

수정하거나 추가할 항목이 있으면 알려주세요. 예:
  - "3번은 더 자세히 — OS 메모리 계층까지 내려가 주세요"
  - "5번 제외 (역사 서사는 필요 없음)"
  - "8번으로 '실측 벤치마크' 추가"

수정 없으면 "OK"라고 말씀해주세요. 1번부터 시작합니다.
```

### Type B — Tools & Frameworks 템플릿

```
주제: <주제>
타입: Type B (스킬·도구)

이 타입은 "내부 동작 + 대안 비교"를 중심 축으로 합니다.
다음 학습 목차를 제안합니다:

  1. Why — 왜 이 주제를 알아야 하는가 (필수)
  2. Where — 어디서 마주치는가 (필수)
  3. Alternatives & Tradeoffs — 대안과 트레이드오프 (필수)
  4. Root Cause — 왜 이 문제가 존재하는가 (필수)
  5. How — 실제 메커니즘 (권장)
  6. Anti-use cases — 언제 쓰지 말 것인가 (권장)
  7. Gotchas — 실무 함정 (권장)

Type B에서는 3번 (Alternatives)이 글의 가장 큰 축입니다. 비교표와 각 대안의
숨겨진 가정 문단이 필수이며, 5번 (How)에서는 내부 동작을 풀되 타 도구와의
비교 맥락을 유지합니다 — "이 부분에서 대안 X는 다르게 처리한다" 식으로.

수정하거나 추가할 항목이 있으면 알려주세요. 예:
  - "4번은 더 자세히"
  - "5번은 제외"
  - "8번으로 '역사적 배경' 추가"

수정 없으면 "OK"라고 말씀해주세요. 1번부터 시작합니다.
```

---

## 3. 사용자 수정/승인

1~4번은 이 블로그 철학상 필수 항목이다. 사용자가 1~4번 중 하나를 제거하려 하면, 한 번만 아래 재확인 메시지를 표시한다. 사용자가 재확인 후에도 제거를 원하면 따른다.

```
1~4번은 이 블로그 철학상 필수 항목입니다. 정말 제거할까요?
(제거하면 글이 트레이드오프 중심이라는 블로그 정체성에서 벗어납니다.)
```

5~7번은 사용자가 자유롭게 추가/제거/순서 변경할 수 있다. 사용자가 8번 이상의 커스텀 항목을 추가하는 것도 허용한다.

## 4. 항목별 Q&A 루프

각 항목에서 Claude가 먼저 선제적으로 설명하고, 사용자 질문을 받는다. 아래 패턴을 복합적으로 운용하되, §1.5에서 확정된 타입에 따라 강조점이 달라지고, **대화 중 노트가 live로 업데이트된다** — Stage 2에서 post-hoc으로 만드는 것이 아니라 Q&A 진행 동안 비유·콜아웃·시각화 후보와 원본 Q&A가 노트에 계속 쌓인다.

### 노트 실시간 업데이트 규칙

Q&A 루프 동안 Claude는 노트를 **지속적으로** 업데이트한다. 업데이트 발동 조건은 두 가지다.

**(a) 자연 체크포인트 — 섹션 전환 시점**

한 섹션(Why / Where / ...)이 마무리되고 다음으로 넘어가는 시점에 해당 섹션의 핵심 내용을 노트의 1 ~ 7번 본문 섹션에 요약해 append한다. 이 시점에 대화 한 턴 분량의 업데이트가 이뤄진다.

**(b) 즉각 기록 신호 — 발생 즉시 append**

다음 중 하나가 감지되면 체크포인트를 기다리지 않고 **즉시** 노트의 해당 라이브 로깅 필드에 append한다.

| 신호 | 감지 기준 | 기록 필드 |
|---|---|---|
| **이해 어려움** | 사용자가 같은 개념을 2번 이상 재질문, "잘 모르겠다" / "다시 설명" 등 표현, Claude가 같은 개념을 두 번째 각도로 풀어야 할 때 | `### 이해하기 어려워한 지점 (비유 후보)` — "[개념] — [사용자 반응] — [비유 아이디어]" |
| **새 키워드** | 사용자가 처음 보는 용어에 대해 질문 ("X가 뭔가요?"), 또는 Claude가 설명 중 새 전문 용어를 처음 도입 | `### 새로 등장한 키워드 (콜아웃 후보)` — "[키워드] — [정의 한 줄] — [왜 콜아웃 대상인가]" |
| **복잡한 흐름** | Claude가 3단계 이상의 순차 / 병렬 / 분기 흐름을 설명해야 하는 경우 (B+Tree 탐색, Page Split 과정, GC mark-sweep 등) | `### 복잡한 흐름 (시각화 후보)` — "[흐름 이름] — [단계 요약] — [SVG / React 중 적합 쪽]" |
| **원본 Q&A** | 매 Q&A 교환 | `### 진행 중 Q&A 로그` — append-only, 사용자 질문 + Claude 답변 요약 |

### 업데이트의 사용자 가시성 — 대부분 silent, 마일스톤만 언급

노트 업데이트 자체는 사용자에게 **대부분 보이지 않는다**. 매 턴 "노트 업데이트 완료" 같은 메시지는 **금지** (대화 노이즈).

예외적으로 아래 **주요 마일스톤**은 한 문장으로 언급한다.

- 첫 시각화 후보 기록 시: "이 흐름은 시각화 후보로 노트에 기록했습니다 — 나중에 SVG로 풀어낼 수 있겠습니다."
- 첫 비유 후보 기록 시: "이 개념은 비유가 필요해 보여 노트에 기록했습니다."
- 첫 콜아웃 키워드 기록 시: (선택적 — 너무 빈번하면 생략)
- 한 섹션이 마무리되고 노트에 본문 요약이 반영될 때: "Section N 내용은 노트에 반영했습니다. 다음으로 넘어갈까요?"
- 노트가 MDX 전환에 충분할 만큼 쌓였을 때: §6 MDX 전환 체크포인트 참조

사용자가 명시적으로 "노트 어떻게 돼가?" / "노트 보여줘"라고 물으면 그때 파일 경로를 알려주고 현재 상태를 요약 보고한다.

### 타입별 Q&A 강조점

Claude의 선제 설명과 사용자 질문 유도는 타입별로 다른 각도를 향한다.

- **Type A (Fundamentals)** — "왜 이런 구조에 수렴했는가"를 파고드는 질문을 유도한다. 예: "이 구조 없이 더 단순하게 만들 수 없나요?", "하부 OS/DB/네트워크 레벨에서 무엇이 이걸 강제하나요?", "역사적으로 대안은 없었나요?". Claude의 선제 설명은 CS 하부 제약(디스크 seek, 메모리 계층, 캐시 일관성, TLB 미스 비용 등)과 현재 구조 사이의 인과 관계를 먼저 드러낸다. 트레이드오프 비교 질문은 Type A의 중심이 아니므로, 등장하면 "역사적 진화" 각도로 재프레이밍해 답한다.
- **Type B (Tools & Frameworks)** — "다른 도구 대비 무엇이 다른지, 왜 이걸 골라야 하는지"를 파고드는 질문을 유도한다. 예: "대안 X와 비교하면 어느 축에서 이기나요?", "어떤 가정 하에서 이 선택이 맞나요?", "내부 동작에서 이 차별점이 어디서 나오나요?". Claude의 선제 설명은 내부 메커니즘을 CS 지식과 연결해 먼저 풀어낸 뒤, 대안과의 차별점을 드러낸다.

양쪽 모두 "단순 사용법 질문"("이거 어떻게 쓰나요?")이 들어오면 트레이드오프 또는 내부 동작 각도로 재프레이밍해서 답한다. 이 블로그의 글은 사용법 설명서가 아니다.

### Claude의 선제 설명 패턴

각 항목 시작 시 Claude가 먼저 3~5 문단으로 해당 항목을 설명한다. 사용자가 무엇을 질문해야 할지 모르는 상태를 방지하기 위한 설계다. 설명의 길이는 항목 복잡도에 비례하되, 핵심 개념과 가장 흔한 오해를 반드시 포함한다.

설명 후 고정 마무리 멘트를 항상 붙인다: "질문 있으시면 말씀해주세요. 없으면 '다음'이라고 하면 [N+1]번으로 넘어갑니다."

### 사용자 질문 처리

사용자 질문은 자유 형식이다. Claude가 답변한 후 "더 궁금한 게 있나요? 없으면 '다음'" 형태로 마무리한다. 사용자의 질문이 예상 범위를 벗어나도 성실히 답변하되, 해당 내용이 Related Posts 감지 조건을 만족하면 §5 Related Posts 감지 절차를 따른다.

**예시**:
```
User: GC 중단이 발생하면 캐시 스탬피드랑 어떤 관계가 있어요?

Claude: 좋은 질문입니다. GC stop-the-world 중단이 길어지면 다수의 요청이
        동시에 캐시 만료를 목격하게 됩니다. GC 동안 캐시 갱신을 못 했고
        재개 직후 요청이 몰리기 때문이죠.

        이 부분은 JVM GC 튜닝 글(jvm-gc-tuning)에서 자세히 다루지만,
        캐시 스탬피드 맥락에서 핵심만 요약하면: "GC 임계값을 낮추면
        중단 시간이 줄어 스탬피드 트리거 확률이 감소한다"입니다.

        더 궁금한 게 있나요? 없으면 '다음'으로 3번 Alternatives로 이동합니다.
```

### 난이도 추적

Stage 1 동안 Claude가 각 항목의 난이도 점수를 내부적으로 추적한다. 추적 지표:

| 지표 | 측정 방법 |
|---|---|
| 재질문 수 | 한 항목 안에서 사용자가 후속 질문한 횟수 |
| 오해 교정 횟수 | 사용자가 잘못 이해한 내용을 Claude가 정정한 횟수 |
| 자발적 부가 설명 | Claude가 첫 설명 후 자발적으로 추가 설명한 횟수 |

점수 해석:
- **0~1점**: 쉬움 — 글에서 간단 설명으로 충분
- **2~3점**: 보통 — 별도 섹션 + 일반 텍스트로 처리
- **4점 이상**: 어려움 — MDX에서 Callout 또는 인터랙티브 시각화 강조 대상

점수는 컨텍스트 내 메타 정보로 추적되며, Stage 2 노트 파일에 기록된다.

## 5. Related Posts 감지

Stage 1 시작 시 스킬이 `lib/generated/keyword-map.ts`를 Read 도구로 읽어 `SLUG_TO_ENTRY`와 `KEYWORD_MAP`을 파악한다. Q&A 루프 중 사용자 질문이 기존 글의 키워드와 매칭되면 해당 개념에 대한 깊은 설명을 생략하고, 한 줄 요약만 하고 Stage 3에서 `<RelatedPost />` 배치를 예약한다.

이 패턴은 중복 설명을 방지하고, 사용자가 블로그 전체를 연결된 지식 그래프로 탐색하도록 유도한다.

**예시 대화**:
```
User: (캐시 스탬피드 주제 Q&A 중) 분산 락은 어떻게 동작하는 거예요?
      Redis로 구현할 때 어떤 원리인지 궁금합니다.

Claude: [내부 감지: SLUG_TO_ENTRY에 "distributed-lock" 존재,
         keywords에 "분산 락", "Redlock" 포함]

        분산 락은 이 블로그에 이미 별도 글이 있습니다:
        "Distributed Lock — Redlock과 그 비판들".
        거기서 Redlock 알고리즘, Kleppmann의 Fencing Token 반박,
        그리고 ZooKeeper 기반 대안까지 깊이 다룹니다.

        여기 캐시 스탬피드 맥락에서 알아야 할 건 딱 한 가지입니다:
        "분산 락으로 스탬피드를 막을 때 락 자체의 정합성도 의심해야 한다."
        네트워크 파티션이나 GC 중단으로 락 홀더가 살아있는지 불확실해지면
        스탬피드 방지 보장이 깨진다.

        최종 MDX의 해당 지점에 아래를 배치할게요:
          <RelatedPost slug="distributed-lock" type="deep-dive" />

        다음으로 넘어갈까요?

User: 네, 다음으로 갈게요.

Claude: [내부 기록: Related Posts = [{slug: "distributed-lock",
         type: "deep-dive", 배치위치: "Alternatives 섹션 하단",
         근거: "분산 락 동작 원리 질문"}]]

        좋습니다. 4번 Root Cause로 넘어갑니다. ...
```

감지된 Related Posts는 Stage 2 노트 파일의 `### 교차 참조 (Related Posts)` 섹션에 자동 기록된다.

## 6. MDX 전환 체크포인트

Stage 1은 명확한 "종료 조건"이 없다. 노트는 §4 live 업데이트로 계속 쌓이고 있고, 대화는 이어질 수 있다. MDX 생성으로 넘어가는 것은 **명시적 전환**이며, 두 방향에서 발동 가능하다.

### (A) 사용자 발동 — 언제든지 허용

사용자가 "블로그로 써줘", "이제 MDX 생성해줘", "포스트 만들어줘", "글 작성해줘" 등으로 명시적 트리거하면 **즉시** Stage 2 (노트 최종화) 단계로 전환한다. 1 ~ 4번 필수 항목이 일부 비어 있어도 전환은 하되, Stage 2 최종화 과정에서 빈 섹션 보완을 위한 짧은 추가 질문 루프가 발생할 수 있다 (`stage-2-note.md` 참조).

### (B) Claude 발동 — 1회 제안

노트가 **1 ~ 4번 필수 섹션을 모두 커버할 만큼** 실질적으로 쌓였을 때 (Q&A 로그 및 본문 섹션에 Why / Where / Root Cause · Alternatives / How 에 해당하는 내용이 각각 실질적으로 존재), Claude가 **한 번만** 제안한다.

```
노트가 충분히 쌓였습니다 (Section 1 ~ 4 실질 내용 확보).
이제 MDX로 정리해볼까요? "네" 또는 "블로그 작성해줘"라고 하시면
Stage 2 최종화 → Stage 3 MDX 생성으로 넘어갑니다.

아니면 계속 이어서 질문하셔도 됩니다 — 노트는 계속 쌓입니다.
```

사용자가 거절하거나 무응답으로 질문을 이어가면 제안은 **재발동하지 않는다** (노이즈 방지). 단, 노트가 더 크게 성장하면 (예: 처음 제안 시점 대비 실질 내용이 50 % 이상 추가됨) 한 번 더 제안할 수 있다. 최대 2회까지.

### 자동 전환 금지

어떤 경우에도 Claude가 사용자 동의 없이 Stage 2 / 3으로 전환하지 **않는다**. "노트가 충분해 보이니 MDX로 넘어갑니다"라고 혼자 결정하는 것은 **금지**. 전환은 항상 명시적 사용자 승인이 선행되어야 한다.

### Stage 2 진입 시점의 책임 이양

사용자 승인으로 Stage 2에 진입한 순간, Stage 1의 §4 live 업데이트 루프는 중단되고 Stage 2 (노트 최종화)의 책임이 된다. 이후 추가 Q&A가 필요하면 Stage 2에서 짧은 보완 루프를 수행한다.

## 대화 예시 (전체 흐름)

아래는 "캐시 스탬피드" 주제로 Stage 1 전체 흐름을 시뮬레이션한 예시다.

```
User: 캐시 스탬피드 블로그 써줘.

Claude: 주제 확인했습니다. "캐시 스탬피드"는 트레이드오프와 근본 원인이
        명확한 주제라 이 블로그에 잘 맞습니다.

        [lib/generated/keyword-map.ts 읽는 중...]
        기존 글 목록을 파악했습니다.

        아래 학습 목차를 제안합니다:

          1. Why — 왜 이 주제를 알아야 하는가 (필수)
          2. Where — 어디서 마주치는가 (필수)
```
