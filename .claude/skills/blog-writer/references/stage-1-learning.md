# Stage 1: Learning Loop

Stage 1은 사용자가 Claude에게 배우는 단계다. Claude가 교사, 사용자가 학생 역할이며, 이 단계의 목적은 최종 MDX를 만드는 것이 아니라 사용자가 주제를 깊이 이해하는 것이다. Stage 1의 품질이 Stage 2 노트와 Stage 3 MDX의 품질을 결정한다.

---

## 흐름 5단계

```
[User trigger: "캐시 스탬피드 블로그 써줘"]
        |
        v
[1] 주제 적합성 사전 검증
    → 거절 대상이면 philosophy.md의 전환 제안 템플릿으로 분기
    → 적합하면 계속 진행
        |
        v
[2] 학습 목차 제안
    → 7-섹션 철학 골격 기반 초안 제시
        |
        v
[3] 사용자 수정/승인
    → "OK" 또는 항목 추가/제거/재구성
        |
        v
[4] 항목별 Q&A 루프
    → Claude 선제 설명 (3~5 문단)
    → 사용자 질문 자유 처리
    → 난이도 추적 + Related Posts 감지
    → "다음" 신호 시 다음 항목으로 전환
        |
        v
[5] 종료 체크포인트
    → 모든 항목 소진 확인
    → Stage 2 진입 의사 확인
```

---

## 1. 주제 적합성 사전 검증

`philosophy.md`의 거절 기준을 적용한다. 순수 사용법/튜토리얼, 단편 팁/치트시트, 개인 회고 중 하나에 해당하면 `philosophy.md`의 전환 제안 템플릿을 사용해 트레이드오프 각도를 3개 제안한다. 사용자가 제안 중 하나를 선택하면 그 주제로 Stage 1을 진행하고, 사용자가 원래 주제를 고집하면 `philosophy.md`의 거절의 강도 정책을 따른다.

---

## 2. 학습 목차 제안

주제 적합성 통과 후 아래 템플릿으로 학습 목차를 제안한다.

```
주제: <주제>

이 블로그의 철학(트레이드오프 우선 + No silver bullet)에 맞춰 다음 학습 목차를 제안합니다:

  1. Why — 왜 이 주제를 알아야 하는가 (필수)
  2. Where — 어디서 마주치는가 (필수)
  3. Alternatives & Tradeoffs — 대안과 트레이드오프 (필수)
  4. Root Cause — 왜 이 문제가 존재하는가 (필수)
  5. How — 실제 메커니즘 (권장)
  6. Anti-use cases — 언제 쓰지 말 것인가 (권장)
  7. Gotchas — 실무 함정 (권장)

수정하거나 추가할 항목이 있으면 알려주세요. 예:
  - "4번은 더 자세히"
  - "5번은 제외"
  - "8번으로 '역사적 배경' 추가"

수정 없으면 "OK"라고 말씀해주세요. 1번부터 시작합니다.
```

---

## 3. 사용자 수정/승인

1~4번은 이 블로그 철학상 필수 항목이다. 사용자가 1~4번 중 하나를 제거하려 하면, 한 번만 아래 재확인 메시지를 표시한다. 사용자가 재확인 후에도 제거를 원하면 따른다.

```
1~4번은 이 블로그 철학상 필수 항목입니다. 정말 제거할까요?
(제거하면 글이 트레이드오프 중심이라는 블로그 정체성에서 벗어납니다.)
```

5~7번은 사용자가 자유롭게 추가/제거/순서 변경할 수 있다. 사용자가 8번 이상의 커스텀 항목을 추가하는 것도 허용한다.

---

## 4. 항목별 Q&A 루프

각 항목에서 Claude가 먼저 선제적으로 설명하고, 사용자 질문을 받는다. 아래 세 가지 패턴을 복합적으로 운용한다.

### Claude의 선제 설명 패턴

각 항목 시작 시 Claude가 먼저 3~5 문단으로 해당 항목을 설명한다. 사용자가 무엇을 질문해야 할지 모르는 상태를 방지하기 위한 설계다. 설명의 길이는 항목 복잡도에 비례하되, 핵심 개념과 가장 흔한 오해를 반드시 포함한다.

설명 후 고정 마무리 멘트를 항상 붙인다: "질문 있으시면 말씀해주세요. 없으면 '다음'이라고 하면 [N+1]번으로 넘어갑니다."

### 사용자 질문 처리

사용자 질문은 자유 형식이다. Claude가 답변한 후 "더 궁금한 게 있나요? 없으면 '다음'" 형태로 마무리한다. 사용자의 질문이 예상 범위를 벗어나도 성실히 답변하되, 해당 내용이 Related Posts 감지 조건을 만족하면 §5 Related Posts 감지 절차를 따른다.

**예시**:
```
User: GC 중단이 발생하면 캐시 스탬피드랑 어떤 관계가 있어요?

Claude: 좋은 질문입니다. GC stop-the-world 중단이 길어지면 다수의 요청이
        동시에 캐시 만료를 목격하게 됩니다. GC 동안 캐시 갱신을 못 했고
        재개 직후 요청이 몰리기 때문이죠.

        이 부분은 JVM GC 튜닝 글(jvm-gc-tuning)에서 자세히 다루지만,
        캐시 스탬피드 맥락에서 핵심만 요약하면: "GC 임계값을 낮추면
        중단 시간이 줄어 스탬피드 트리거 확률이 감소한다"입니다.

        더 궁금한 게 있나요? 없으면 '다음'으로 3번 Alternatives로 이동합니다.
```

### 난이도 추적

Stage 1 동안 Claude가 각 항목의 난이도 점수를 내부적으로 추적한다. 추적 지표:

| 지표 | 측정 방법 |
|---|---|
| 재질문 수 | 한 항목 안에서 사용자가 후속 질문한 횟수 |
| 오해 교정 횟수 | 사용자가 잘못 이해한 내용을 Claude가 정정한 횟수 |
| 자발적 부가 설명 | Claude가 첫 설명 후 자발적으로 추가 설명한 횟수 |

점수 해석:
- **0~1점**: 쉬움 — 글에서 간단 설명으로 충분
- **2~3점**: 보통 — 별도 섹션 + 일반 텍스트로 처리
- **4점 이상**: 어려움 — MDX에서 Callout 또는 인터랙티브 시각화 강조 대상

점수는 컨텍스트 내 메타 정보로 추적되며, Stage 2 노트 파일에 기록된다.

## 5. Related Posts 감지

Stage 1 시작 시 스킬이 `lib/generated/keyword-map.ts`를 Read 도구로 읽어 `SLUG_TO_ENTRY`와 `KEYWORD_MAP`을 파악한다. Q&A 루프 중 사용자 질문이 기존 글의 키워드와 매칭되면 해당 개념에 대한 깊은 설명을 생략하고, 한 줄 요약만 하고 Stage 3에서 `<RelatedPost />` 배치를 예약한다.

이 패턴은 중복 설명을 방지하고, 사용자가 블로그 전체를 연결된 지식 그래프로 탐색하도록 유도한다.

**예시 대화**:
```
User: (캐시 스탬피드 주제 Q&A 중) 분산 락은 어떻게 동작하는 거예요?
      Redis로 구현할 때 어떤 원리인지 궁금합니다.

Claude: [내부 감지: SLUG_TO_ENTRY에 "distributed-lock" 존재,
         keywords에 "분산 락", "Redlock" 포함]

        분산 락은 이 블로그에 이미 별도 글이 있습니다:
        "Distributed Lock — Redlock과 그 비판들".
        거기서 Redlock 알고리즘, Kleppmann의 Fencing Token 반박,
        그리고 ZooKeeper 기반 대안까지 깊이 다룹니다.

        여기 캐시 스탬피드 맥락에서 알아야 할 건 딱 한 가지입니다:
        "분산 락으로 스탬피드를 막을 때 락 자체의 정합성도 의심해야 한다."
        네트워크 파티션이나 GC 중단으로 락 홀더가 살아있는지 불확실해지면
        스탬피드 방지 보장이 깨진다.

        최종 MDX의 해당 지점에 아래를 배치할게요:
          <RelatedPost slug="distributed-lock" type="deep-dive" />

        다음으로 넘어갈까요?

User: 네, 다음으로 갈게요.

Claude: [내부 기록: Related Posts = [{slug: "distributed-lock",
         type: "deep-dive", 배치위치: "Alternatives 섹션 하단",
         근거: "분산 락 동작 원리 질문"}]]

        좋습니다. 4번 Root Cause로 넘어갑니다. ...
```

감지된 Related Posts는 Stage 2 노트 파일의 `### 교차 참조 (Related Posts)` 섹션에 자동 기록된다.

---

## 6. 종료 조건

- **정상 종료**: 모든 목차 항목을 소진하고 사용자가 확인한 경우. "모든 항목을 다뤘습니다. Stage 2로 넘어가 학습 내용을 노트로 정리할까요?" 형태로 의사를 확인한다.

- **조기 종료 (사용자 요청)**: 사용자가 중간에 종료를 원하면, 아직 다루지 않은 항목 목록을 표시하고 진행 여부를 확인한다. 1~4번 필수 항목 중 미진행 항목이 있으면 "필수 항목 N번이 아직 남아 있습니다. 건너뛰면 블로그 철학에서 벗어납니다. 정말 종료할까요?" 형태로 재확인한다. 사용자가 승인하면 따른다.

- **강제 종료 (휴리스틱)**: "한 항목에서 재질문 5회 이상" 또는 "전체 Q&A 30회 이상" 도달 시 Claude가 "이 정도 내용이면 Stage 2로 넘어가도 충분할 것 같습니다. 학습 노트로 정리할까요?"라고 제안한다. 사용자 승인 시에만 전환한다. 사용자가 계속 원하면 Q&A를 이어간다.

## 대화 예시 (전체 흐름)

아래는 "캐시 스탬피드" 주제로 Stage 1 전체 흐름을 시뮬레이션한 예시다.

```
User: 캐시 스탬피드 블로그 써줘.

Claude: 주제 확인했습니다. "캐시 스탬피드"는 트레이드오프와 근본 원인이
        명확한 주제라 이 블로그에 잘 맞습니다.

        [lib/generated/keyword-map.ts 읽는 중...]
        기존 글 목록을 파악했습니다.

        아래 학습 목차를 제안합니다:

          1. Why — 왜 이 주제를 알아야 하는가 (필수)
          2. Where — 어디서 마주치는가 (필수)
          3. Alternatives & Tradeoffs — 대안과 트레이드오프 (필수)
          4. Root Cause — 왜 이 문제가 존재하는가 (필수)
          5. How — Probabilistic Early Expiration 메커니즘 (권장)
          6. Anti-use cases — 언제 분산 락이 오히려 독인가 (권장)
          7. Gotchas — 실무 함정 (권장)

        수정할 항목이 있으면 알려주세요. 없으면 "OK"라고 하시면 시작합니다.

User: 5번 "How"를 "Probabilistic Early Expiration 상세 메커니즘"으로 바꿔줘.
      나머지는 OK.

Claude: 수정했습니다.
          5. How — Probabilistic Early Expiration 상세 메커니즘 (권장)

        1번 Why부터 시작합니다.

        ─── 1. Why — 왜 이 주제를 알아야 하는가 ───

        캐시는 DB 부하를 줄이기 위한 가장 흔한 수단입니다. 그런데 캐시 만료
        (TTL)라는 단순한 기능이 특정 조건에서 DB를 오히려 더 위험하게 만들
        수 있습니다. 그게 캐시 스탬피드(Cache Stampede) 입니다.

        흔한 오해가 있습니다: "TTL을 길게 설정하면 된다." 실제로는 TTL이
        길수록 스탬피드 발생 시 영향 반경이 커집니다. 트래픽이 몰리는 시점
        에 TTL이 만료되면 수백~수천 요청이 동시에 DB로 쏟아집니다.

        이 주제를 모르면 트래픽 급증 이벤트(신규 서비스 오픈, 마케팅 캠페인
        등) 직후 DB 장애의 원인을 설명하지 못하게 됩니다. 실제로 여러 서비스
        에서 "이벤트 직후 DB CPU 100%"의 주범이 캐시 스탬피드였습니다.

        질문 있으시면 말씀해주세요. 없으면 '다음'이라고 하면 2번으로 넘어갑니다.

User: 스탬피드가 발생하는 조건이 뭔가요?

Claude: 세 가지 조건이 동시에 충족될 때 발생합니다:

        1. 동일 키에 대한 요청이 동시에 여러 개 들어올 것 (높은 동시성)
        2. 해당 키의 캐시가 만료되어 있을 것 (TTL 만료)
        3. 캐시 미스 후 DB 재조회 비용이 클 것 (느린 쿼리 또는 집계)

        조건 3이 중요한 이유: 재조회가 1ms면 100개 요청이 동시에 DB를 쳐도
        100ms 이내에 끝납니다. 100ms짜리 집계 쿼리면 100개 × 100ms = 10초
        의 DB 부하가 됩니다. 스탬피드의 피해는 재조회 비용에 비례합니다.

        더 궁금한 게 있나요? 없으면 '다음'으로 2번 Where로 이동합니다.

User: 다음.

Claude: [내부: Section 1 난이도 = 재질문 1회 → 점수 1 (쉬움)]

        ─── 2. Where — 어디서 마주치는가 ───

        캐시 스탬피드는 세 가지 상황에서 주로 등장합니다.

        첫 번째: 서비스 오픈 또는 대규모 이벤트 직후. 수만 명의 사용자가
        동시에 서비스에 진입하면서 콜드 캐시(모든 키가 만료된 상태)를 만납니다.
        2019년 넷플릭스 오리지널 공개 직후 추천 캐시 전체가 동시에 만료된
        사례가 잘 알려져 있습니다.

        두 번째: 정각/정시 배치 처리 후. 자정에 모든 캐시를 일괄 초기화하거나
        TTL을 동일하게 설정한 경우, 자정 직후 모든 키가 동시에 만료됩니다.
        이를 "Thundering Herd"라고도 부릅니다.

        세 번째: 배포 직후 캐시 워밍이 덜 된 상태. 블루/그린 배포에서 그린
        환경의 캐시가 비어 있는 상태로 트래픽을 받기 시작할 때 발생합니다.

        질문 있으시면 말씀해주세요. 없으면 '다음'이라고 하면 3번으로 넘어갑니다.

User: 다음으로 갑시다.

Claude: [내부: Section 2 난이도 = 재질문 0회 → 점수 0 (쉬움)]

        3번 Alternatives & Tradeoffs로 넘어갑니다. ...
```

---

이 예시는 목차 제안 → 수정 승인 → 첫 항목 선제 설명 → 사용자 질문 → 답변 → 다음 항목 전환까지의 전체 흐름을 보여준다. 실제 운용에서 Q&A 깊이와 길이는 사용자 참여도에 따라 유연하게 조정된다.
