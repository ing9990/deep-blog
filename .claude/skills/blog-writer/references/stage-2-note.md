# Stage 2: Note Finalization & MDX Plan

**노트 파일은 Stage 1 시작 시점에 이미 생성되어 있다** (`stage-1-learning.md` §0.6 노트 즉시 생성 프로토콜). Stage 2의 역할은 **새로 만드는 것이 아니라** Stage 1 §4 Q&A 루프 동안 live로 쌓인 노트를 **검토·최종화**하고, **MDX 구성 계획**을 추가하는 것이다. 빈 섹션이 있으면 짧은 보완 질문 루프로 채우고, 라이브 로깅 필드(비유 · 콜아웃 · 시각화 후보)를 Stage 3 MDX의 강조 수단으로 변환한다.

이 노트는 Stage 3 MDX 생성의 직접 입력이 되며, 학습 자산으로 영구 보존된다. **노트는 사용자에게 보여주지 않는 agent 전용 산물**이다 — 기본적으로 사용자 리뷰 체크포인트 없이 Stage 3로 진입하며, 사용자가 명시적으로 노트를 보고 싶어 할 때만 파일 경로를 안내한다.

---

## 파일 위치

노트 파일은 `.claude/drafts/<slug>-notes.md`에 위치한다. **이 파일은 Stage 1 §0.6에서 이미 생성되어 있으며**, Stage 1 §4 Q&A 루프 동안 live로 업데이트된 상태로 Stage 2에 도달한다. Stage 2는 이 파일을 Read 도구로 불러와 최신 상태를 확인하고 최종화 작업을 수행한다.

`.claude/drafts/`는 `.gitignore`에 포함되어 있어 로컬 전용이다. 스킬은 이 파일을 자동 삭제하지 않는다 — 학습 여정 자체가 자산이며, 사용자가 필요 없어지면 수동으로 정리한다.

## 각 섹션 작성 지침

각 섹션은 단순 요약이 아니라 Stage 3 MDX 생성의 직접 입력이 되어야 한다. 완성도가 높을수록 Stage 3 결과물의 품질이 높아진다.

### 1. Why

- 독자가 이 주제를 모를 때 발생하는 구체적인 문제를 기술한다 — 추상적 "중요합니다"는 금지
- 흔한 오해를 하나 이상 나열한다 (예: "TTL을 길게 설정하면 스탬피드를 피할 수 있다")
- 실무 영향을 구체화한다 — "무엇이 잘못될 수 있는가" (예: "이벤트 직후 DB CPU 100%")
- "이 글을 다 읽으면 이해하는 것" 3~5개 항목으로 마무리한다

### 2. Where

- 실제 시나리오 3개 이상을 작성한다
- 이름 있는 사례를 우선 사용한다 (회사명, 사건명, 논문명, 오픈소스 이슈)
- 각 시나리오는 1~2 문단으로 충분히 구체화한다 — "어떤 조건에서 발생했는가"까지 포함

### 3 / 4 / 5. 타입별 중심 섹션 (분기)

섹션 3/4/5는 **타입에 따라 의미와 순서가 다르다**. Stage 1에서 확정된 타입에 맞는 가이드만 따른다.

#### Type B 가이드

**Section 3 — Alternatives & Tradeoffs** (Type B의 정체성 핵심)

- **표 형식이 필수다**. 컬럼: 접근 / 핵심 아이디어 / 장점 / 단점 / 적합한 상황
- 표 아래에 "No silver bullet 강조 문단"을 반드시 작성한다. 각 접근의 숨겨진 가정을 한 줄씩 명시한다. 예: "뮤텍스 기반 락은 단일 노드를 가정한다", "PER 알고리즘은 재조회 비용이 안정적이라는 가정을 한다"
- Type B에서 가장 공들여 작성한다. 표만 있고 가정 문단이 없으면 미완성이다

**Section 4 — Root Cause**

- "동작 방식보다 깊은 왜"를 다룬다. How 섹션이 "어떻게 작동하는가"라면, Root Cause는 "왜 이 문제가 애초에 생겼는가"다
- 어떤 가정이 깔려 있는지, 왜 직관적 해결책이 실패하는지를 설명한다
- 가능하면 수학적 본질이나 모델링의 gap을 언급한다 (예: "독립 만료를 가정했지만 실제로는 동일 TTL로 설정된 키들이 동시에 만료된다 — Dirac delta 분포")

**Section 5 — How**

- 단계별 메커니즘을 작성한다
- 이해하기 어려운 단계에 ⚠️ 마크를 붙인다 — Stage 3에서 이 마크가 있는 단계는 Callout 또는 시각화 강조 대상이 된다
- 타 도구와의 비교 맥락을 잃지 않도록 한다 — "이 부분에서 대안 X는 다르게 처리한다" 식 참조

#### Type A 가이드

**Section 3 — Root Cause (확장)** (Type A의 중심축 1)

- Type A에서 가장 공들여 쓰는 섹션이며, 글 전체 분량의 큰 부분을 차지한다
- **"어떤 CS 제약이 이 구조를 강제하는가"** 를 파고든다 — OS (메모리 계층, 페이지 테이블, TLB), DB (디스크 I/O 경제학, 버퍼 풀), 네트워크 (RTT, 혼잡 제어), 컴파일러 (명령어 파이프라인, 캐시 라인) 등 어느 층위의 제약인지 명시
- 제약 → 구조 사이의 인과 사슬을 단계적으로 기술한다. "X가 비싸다 → 그래서 Y가 필요하다 → 그래서 Z가 수렴했다" 형태
- "이 제약이 사라지면 다른 구조가 가능한가"라는 반사실 질문에 답해, 제약과 구조의 결합을 명시적으로 드러낸다
- 수학적 본질을 쓸 수 있으면 쓴다 — log 함수, 확률 분포, 비용 모델 등
- **Type B와 달리 대안 비교표를 쓰지 않는다**. Type A에서의 "No silver bullet"은 제약에 따른 수렴이지 선택지 비교가 아니다

**Section 4 — How** (Type A의 중심축 2)

- Section 3과 **한 덩어리로 읽혀야 한다** — "그래서 이 제약 위에 이렇게 만들어졌다"의 연속
- Section 3의 CS 근거 위에서 실제 메커니즘을 단계적으로 전개한다
- 내부 구조, 데이터 흐름, 상태 변화를 구체적으로 보여준다. 어려운 단계에 ⚠️ 마크
- ASCII 다이어그램, 의사 코드, 실제 코드 스니펫을 적극 사용해 구조를 시각화한다

**Section 5 — Historical Alternatives** (선택)

- **선택 섹션**이다. 주제에 역사적 서사가 풍부하지 않으면 과감히 생략한다
- 작성 시: "비교표"가 아니라 **"진화사" 서사**로 쓴다. "초기엔 X를 썼지만 Y 문제로 Z에 수렴했다" 같은 시간 순 흐름
- 장점/단점 열거가 아닌, 왜 현재 구조가 과거의 문제를 해결했는지의 인과 설명

### 6. Anti-use cases

- 언제 이 기술/패턴을 쓰지 말아야 하는가를 구체화한다
- 대안이 더 적합한 상황 2~3개를 예시로 든다 — "낮은 트래픽 서비스에서는 분산 락 오버헤드가 스탬피드 피해보다 크다"

### 7. Gotchas

- 실무 함정 2~3개를 작성한다
- 자주 하는 실수, 잘못된 설정, 모니터링으로 잡기 어려운 함정을 포함한다

```
**A**: 핵심은 락의 "선점(preemption)" 개념입니다. 락은 만료 이후에 반응하지만,
      PER은 만료 전에 확률적으로 미리 갱신합니다. ...
```

## Stage 2 정리: MDX 구성 계획

이 섹션은 Stage 3 진입 직전 Claude가 작성하는 실행 계획이다. Stage 1 Q&A 로그를 분석해 아래 다섯 항목을 채운다.

### 가장 강조할 3가지

Stage 1에서 가장 중요하다고 판단된 3가지 키 포인트를 선정한다. 이 3가지는 Stage 3의 학습 목표 Callout에 그대로 삽입된다.

### 난이도 높았던 부분 (강조 대상)

난이도 점수 4 이상인 섹션을 나열하고, 각 섹션에 사용할 강조 수단을 결정한다.

| 섹션 | 난이도 | 강조 수단 |
|---|---|---|
| Section 3 - Alternatives | 5 | Callout(warning) + 비교 표 확장 |
| Section 4 - Root Cause | 4 | Callout(error) + 인터랙티브 시각화 (PER β 파라미터 playground) |

### 사용할 MDX 요소

Stage 3에서 사용할 MDX 요소를 미리 결정한다.

- **Callout 종류**: info (서두 학습 목표), warning (No silver bullet), error (핵심 통찰) — 3종 필수
- **코드블록 언어**: Java/Kotlin/Python 등 + 제목 (title="..."), 하이라이트 라인 ({N-M})
- **시각화 컴포넌트 후보**: 컴포넌트명 + 설명 + 기존 재사용 여부
- **SVG 후보**: 정적 다이어그램이 필요한 경우 + 설명

### 교차 참조 (Related Posts)

Stage 1에서 감지된 기존 글 목록을 표로 정리한다.

| slug | 배치 위치 | type | 근거 |
|---|---|---|---|
| distributed-lock | Alternatives 섹션 하단 | deep-dive | "분산 락 동작 원리" 질문 |
| redis-data-structures | Where 섹션 1번 시나리오 | parallel | Redis 캐시 구현 언급 |

type 정의:
- `prerequisite`: "이 개념을 모르면 이해 어려움" — 강조 박스, 본문 흐름 앞쪽
- `deep-dive`: "간단히만 언급, 자세한 건 다른 글" — 카드형, 자연스러운 흐름 중
- `parallel`: "같은 영역의 다른 각도" — 약한 강조, 글 하단

### 사용할 키워드 (frontmatter 초안)

Stage 3 Frontmatter 생성의 기초 자료. 기존 태그/키워드와 충돌 체크는 Stage 3에서 수행하지만, 여기서 초안을 만들어 둔다.

## 사용자 리뷰 체크포인트 (선택)

**노트는 agent 전용 산물**이므로 사용자에게 "노트 파일을 열어 확인해 주세요"라고 요청하는 것은 **기본 동작이 아니다**. Stage 2 최종화 완료 후 Stage 3 진입 전에는 단순히 "노트 최종화 완료. MDX 생성을 시작합니다"로 한 문장만 알리고 Stage 3로 진입한다.

아래 두 가지 경우에만 사용자에게 노트를 직접 노출한다.

**예외 1 — 사용자 명시적 요청**: 사용자가 "노트 보여줘", "노트 어디 있어?", "노트 내용 확인하고 싶다"라고 명시적으로 요청한 경우. 파일 경로(`.claude/drafts/<slug>-notes.md`)를 알려주고, 필요 시 Read 결과를 요약해 공유한다.

**예외 2 — 사용자가 노트를 직접 편집한 정황**: 사용자가 "노트 파일 X 부분을 고쳤다" / "노트에 Y를 추가했다"처럼 직접 편집을 언급하면, Stage 3 진입 시 스킬은 편집된 버전을 Read 도구로 **다시 읽어** 최신 상태를 입력으로 사용한다. 컨텍스트에 의존하지 않고 **파일을 source of truth**로 삼는다.

### 왜 리뷰 체크포인트가 기본이 아닌가

과거 버전의 블로그 라이터 스킬에서는 Stage 2 후 "노트 열어 확인해 주세요"를 강제했지만, 실제 운영에서 이는 다음 문제를 만들었다:

- 사용자는 노트 원본(Q&A 로그 포함 raw dump)을 읽고 싶지 않다 — MDX 결과물이 진짜 산출물
- "OK"를 받기 위한 턴이 불필요하게 대화를 늘린다
- 노트가 agent-facing artifact임을 명시적으로 드러내는 게 오히려 투명성 측면에서 정직함

따라서 Stage 3 결과물(MDX)로 최종 품질을 평가받고, 노트는 그 과정의 "백그라운드 작업 공간"으로 남긴다.
